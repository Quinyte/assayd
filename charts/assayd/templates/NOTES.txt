`gateway.enabled` is false, so no traffic passes through a gateway and NOTHING
below is enforced for any Agent this release runs:

  * no token budgets and no rate limits    - an agent can spend without bound
  * no authentication at the gateway       - callers are not identified
  * no tool filtering                      - an agent reaches every tool its
                                             MCP servers offer, not a declared
                                             subset
  * no NetworkPolicy, in any namespace     - nothing stops traffic reaching an
                                             agent Pod directly, so any control
                                             a gateway would apply is also
                                             bypassable

Every Agent carries `GovernanceSkipped=GatewayDisabled` in its conditions and
stays `Ready`: you were promised nothing here, so nothing is broken. That
condition and this message are the whole of the notice you get.

  kubectl get agent <name> -o jsonpath='{.status.conditions}'

Turning it on is not a flag flip today. This chart ships no agentgateway
subchart, so `gateway.enabled: true` requires that you install the Gateway API
and agentgateway CRDs yourself. Without them the OPERATOR REFUSES TO START, and
its last log line names the missing kind — deliberately, because an operator who
asked for governed traffic and did not get it must not be told everything is
fine. Design 03 §3.1 asks for `GatewayIncompatible=CRDsAbsent` on each Agent
instead, which is the friendlier half of the same fail-closed answer and is not
implemented; this note says what the code does, not what the design wants.

And turning it on authenticates each new Agent's route and governs nothing
else. It also needs `gateway.servingUrl`. See below.

Also not enforced yet, independent of the gateway: an Agent Card's signature is
not verified, its advertised skills are not cross-checked against the CR's
grants, and no registration deadline is counted. See `docs/designs/02-*.md` §5.

`gateway.enabled` is true, so the operator emits ONE resource per Agent:

  * an `HTTPRoute` in `assayd-run-<agent-namespace>`, attached to Gateway
    `{{ .Values.gateway.namespace | default .Values.namespace }}/{{ .Values.gateway.name }}` on listener `http`, matching the host
    `<agent>.<agent-namespace>.{{ .Values.gateway.hostnameSuffix | default "assayd.internal" }}` and forwarding to that
    revision's Service

and, for an Agent whose `spec.expose.a2a.auth` is `apikey` or absent, an
`AgentgatewayPolicy` named `<agent>-auth` beside it. The operator writes none
for an Agent never served that still carries a stored `spec.budget` (until it
is removed), for one whose `<agent>-auth` name holds a policy without its UID
(`ForeignTrafficPolicy`; an Agent already served under `apikey` keeps the
policy it has, which is then not re-asserted), or for a route this operator
published before it carried the compiler (`Adopt`, below). A `traffic` policy
of another name on the same route does not stop the write: it keeps a new
route unpublished, and an in-place lock unproved, under `ForeignTrafficPolicy`,
and an Agent already served keeps its policy. The policy carries API-key
authentication over the ConfigMaps labelled `assayd.dev/api-keys: "true"` in that run
namespace, admitting the group named for the Agent's namespace. A new Agent's
route is published only after an anonymous request through it gets 401, sent
to `gateway.servingUrl`, which is therefore required. `auth: none` is
published at once, unauthenticated, labelled `assayd.dev/auth: "none"`.
Editing a served `auth: none` Agent to `apikey` locks its route in place: the
policy is written onto the route that is serving, and the Agent records
`apikey` only after an anonymous request through it gets 401. The lock is
one-way: `apikey` -> `none` is refused, so only recreating the Agent undoes it.

That is authentication on one route, not governance. No `AgentgatewayBackend`
is emitted, and there are still no budgets, no rate limits and no tool
filtering. A route this operator published before it carried the compiler is
left unauthenticated, and its Agent says so with `GovernanceSkipped`, reason
`CompilerUpgradeUnsupported`, until its owner edits `spec.expose.a2a.auth` to
`apikey`, which locks it in place the same way. Each Agent's status says what
applies to it:

  kubectl get agent <name> -o jsonpath='{.status.auth}{"\n"}{.status.conditions}'

No NetworkPolicy is materialized in any namespace either, so an agent Pod
remains reachable directly and anything the gateway would apply is bypassable.

A policy of your own on that Gateway can hold every Agent (design 03 A75). While
an `AgentgatewayPolicy` in the Gateway's namespace targets it on listener `http`,
or on another listener on its port that can take the Agent's host, and sets
anything that could answer an anonymous request with 401 or a status of its
choosing (authentication, authorization, extAuth, extProc, directResponse,
transformation and more: design 03 §3.2's field table), or
`strategy.inheritance: Override`, or while the Gateway's
`spec.allowedListeners.namespaces.from` is anything but `None`, no new Agent is
published and no lock is recorded: `PolicyApplyIncomplete`, reason
`GatewayAuthPolicy`, and each held Agent pages until you remove or rescope it.
A served Agent keeps serving; one beside such a policy that sets anything but
authentication alone, with its phase unset or `PostRouting`, reports
`GatewayAuthPolicy` too, because it cannot be ruled out that the policy widens
or bypasses the route's own authentication; `PreRouting` authentication counts
as more than authentication alone. The operator reads the Gateway by name,
which this chart's `-gateway-labels` Role grants.

The Gateway object itself is yours to create — this chart ships no agentgateway
subchart. Its listener must admit the run namespaces, or every route is rejected
and every request 404s with no other signal:

  allowedRoutes: {namespaces: {from: Selector,
    selector: {matchLabels: {assayd.dev/run-namespace: "true"}}}}

The Gateway's namespace must exist before this chart is installed: the
operator's read of the gateway's NACK Events is a Role rendered into it, and
`helm install` fails if the namespace is missing.

Upgrading an install that already runs with `gateway.enabled: true` on a
cluster that does not serve the agentgateway CRDs: the operator now REFUSES TO
START there, because it requires `AgentgatewayPolicy` to be served as well as
`HTTPRoute` (design 03 §3.1). Install agentgateway's CRDs, or set
`gateway.enabled: false`.

The host above is a routing key matched against the `Host` header. Nothing here
creates DNS for it.

`gateway.servingUrl` is set to {{ .Values.gateway.servingUrl }}. Each new
Agent's route is published only after an anonymous request sent there gets
401. Nothing checks that it reaches the listener named `http`. If it reaches

In every run namespace, admission reserves two more writes (design 03 §6):
an AgentgatewayPolicy may be written only by the operator, and a ConfigMap
labelled `assayd.dev/api-keys` only by the operator and the identities in
`admission.apiKeyWriters` (by default, the `system:masters` group). The
operator writes each API-key Agent's `<agent>-auth`. It writes no key set: the
keys are yours to add, as `sha256:` hashes with a `group` naming the Agent's
namespace, and until one exists every caller of an API-key Agent gets 401.

Each entry in a key set is one key. Name the entry anything but the key
itself, and give it the value
  {"keyHash":"sha256:<hex>","metadata":{"group":"<agent-namespace>"}}
where <hex> is the lowercase hex SHA-256 of the key. Label the ConfigMap
`assayd.dev/api-keys: "true"` and write it in the Agent's run namespace:
`assayd-run-<agent-namespace>` for a short name, or find it with
  kubectl get ns -l assayd.dev/agent-namespace=<agent-namespace>
Callers send the key as `Authorization: Bearer <key>`. A worked example is in
https://github.com/Quinyte/assayd/blob/main/docs/install.md

`helm upgrade` never updates this chart's crds/. Before every upgrade, apply
the CRDs of the version you are upgrading to:
  helm pull oci://ghcr.io/quinyte/charts/assayd --version <version> --untar
  kubectl apply --server-side --force-conflicts -f assayd/crds/
Skip it, and an Agent CRD older than `status.auth` drops that field without an
error. With the gateway enabled, an Agent the operator tries to publish then
stops with `PolicyApplyIncomplete`, reason `AuthRecordNotKept`, and nothing is
written to the gateway for it until the CRDs are applied.
