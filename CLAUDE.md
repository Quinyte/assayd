# CLAUDE.md — assayd

assayd ("graphene" in early drafts) is a lightweight, Kubernetes-native agent platform.

**Phase: implementing P1, under the scope reset of ADR-0030.** The agent-operator, its CRD, the chart and CI exist and pass on k3d and kind.

**Do not read "approved" as "settled."** An earlier version of this line said all 27 designs were approved and critique-passed. That was false, and it was the first thing every contributor read. Design 02's own header says it "is not approved and must not be cited as such"; design 03's approves only its first slice, which the human approved on 2026-09-12 after thirteen critiques, and says the rest "is not approved, and must not be implemented", even though its whole body was consolidated on 2026-09-10 — a consolidated document is not an approved one. Design 16 also approves only its first slice, which the human approved on 2026-09-14 after twelve critiques, and the rest of design 16 is not approved and must not be implemented. Design 03's amendment A84, approved on 2026-09-23, is the only other approval the human has given. Every other design is not approved: until 2026-09-23 twenty-three Status lines, designs 04–15 and 17–27, opened "approved" on the strength of a critique PASS, and the human corrected them that day. Check the Status line of the design you are about to touch, and trust that over any summary — including this one. `docs/designs/README.md` carries the table; it summarises the Status lines and does not override them (ADR-0030 Amendment 1), and `make docs` fails when a Status line and its row disagree about approval.

**What is actually true of the system today**: an agent answers a request. `test/responder` is a real A2A responder, built and pushed by `hack/e2e.sh`, deployed by the operator from a registry digest, and asked a question through its revision Service — the thing no test here could do until 2026-09-06, when the e2e still ran `registry.k8s.io/pause` for everything. **Traffic now traverses a real gateway, on a route the OPERATOR emits.** `hack/e2e.sh` installs Gateway API v1.6.0 and agentgateway 1.5.0 on k3d and installs the chart with `gateway.enabled=true`; `TestAnAgentAnswersThroughTheGateway` creates an Agent, waits for the `HTTPRoute` the operator wrote to be published, and gets the agent's answer through the Gateway's own Service, with an API key. Nothing in that test authors a route any more. Deleting the route brings a new one back with a different UID, still carrying traffic; making the emitter a no-op, or rendering `--gateway-enabled=false` into the chart regardless of the value, kills both gateway e2es at the route wait. Getting there closed two gaps that were invisible from either side alone: the operator passed A5.9's admission policy and was then refused by RBAC that granted no `httproutes`, and the policy itself compared a route's `parentRef` against the *operator's* namespace rather than the *Gateway's*, so moving the Gateway made the reservation match nothing and silently admit any author (design 07 A6, A6.10).

**What remains untrue**: the chart ships no Gateway, so the e2e's Gateway is still created by the harness — and **the policy compiler is one slice deep**. With `gateway.enabled`, the operator now runs design 03's first-slice `Create` (design 03 A71, answering an independent review). A new Agent whose `-auth` compiles to API keys — which is every Agent with no `expose` block — gets `<agent>-auth` written onto a prepared route with no `backendRefs`, converged by §3.3.2's tuple, and the route is published only after an anonymous request through `--gateway-serving-url` gets `401`. `auth: none` is published at once with the marker label `assayd.dev/auth: "none"`. `oauth` and a stored `spec.budget` are `PolicyCompileFailed`, and a served Agent keeps its last good `-auth` (I1). That is ALL it enforces: no `AgentgatewayBackend` is emitted, so no budget, rate limit or tool allowlist is enforced anywhere. Since slice PR 5 (design 03 A72), a served `auth: none` Agent edited to `apikey` is locked in place by J2's `Lock`. `<agent>-auth` is written onto the route that is already serving, the route keeps its `backendRefs` throughout, and status records `apikey` only after an anonymous request through the route goes `200` → `401` and the `401` can be attributed to the policy — and **that attribution had a hole, which design 03 A77 closes**: when a promotion moved the route's `backendRef` in the crediting pass, the previous revision's own `401` was credited against the new revision's card digest, measured against `main` `3f37c25` for J2 and K2 and not reachable for the missing-policy `Lock`, which wrote no route (`docs/research/auth-lock-false-credit-2026-09.md`). **No `Lock` now takes a `ProbingAfter` answer until the Gateway reports `Accepted` and `ResolvedRefs` on the route at its current generation** — the pass that moves a route ends short of the request, still at `ProbingAfter`, and the next one probes. J2's and K2's one `ProbingBefore` request is not gated, and is not a hole: it sets `beforeObserved` only on a body whose digest equals the one `status.cards[]` records for the revision the route's single `backendRef` names, so a card from the backend the route has just left does not set it, except where two revisions serve byte-identical cards, which is the residue §3.3.3 already states (A62, A78) — **and the missing-policy `Lock` re-points its route at `status.activeRevision`**, at `ProbingAfter`, only while `status.cards[]` records a digest for that revision, so the wedge that Agent used to sit in ends when a carded revision is promoted. A route not carrying exactly one `backendRef` is unattributable. The gate is a control-plane fact, so it narrows the window rather than closing it: the proxy may still lag the controller's report, and the route is read through the manager's cache. Since design 03 A75 (ADR-0034 Amendment 5, the human's L1 and W1), no `Create` or `Lock` credits a `401` while a policy on the assayd Gateway could have answered it, or while the Gateway admits ListenerSets or cannot be read: the transaction holds at `ProbingAfter`, reason `GatewayAuthPolicy`, and pages. Re-creations of served Agents hold too, a cost the human accepted. A Gateway-level `Allow` rule was measured widening a route beside its `<agent>-auth`, so a served API-key Agent beside any counting Gateway-level policy but one that sets authentication alone reads `GovernanceSkipped=True` and `PolicyApplyIncomplete=True`, reason `GatewayAuthPolicy`, and is `Degraded`, because it cannot be ruled out that the policy widens or bypasses the route's authentication; its route is not withdrawn. The lock is one-way: `apikey` → `none` is refused. A route published before the compiler, or one whose status was lost, is refused as `Adopt` and stays unauthenticated under `GovernanceSkipped=CompilerUpgradeUnsupported`, until the Agent is deleted and created again, or K2 locks it the same way. K2 needs a stored `refusedMode` that is not `apikey` and a spec that compiles (`k2Consent`, `desire.compiles()`), and `refuseAdopt` records the mode the Agent asked for, so the default Agent — which asks for `apikey` — is not locked by editing it to `apikey`: its owner edits `auth` to `none`, waits until `status.auth.transaction.refusedMode` reads `none`, then edits it to `apikey`, with no `spec.budget` stored. An unfinished `Create`, or a J2 or K2 `Lock`, whose target no longer matches the spec is abandoned, and only the policy it wrote is deleted. A NACK Event changes status only when its `involvedObject` is the Gateway and its source is agentgateway's controller. A `traffic` policy the operator did not emit on an Agent's route is reported as `ForeignTrafficPolicy`. `TestAServedNoneAgentIsLockedInPlace` measures J2 on k3d against agentgateway 1.5.0. A `Create` refuses to write to the gateway on an install whose Agent CRD predates `status.auth`, because it could not keep its record: `helm upgrade` never updates `crds/`, and the e2e harness now applies them. A served API-key Agent that loses its route or its policy, even both at once, gets them back from `status.auth`: the route prepared and published only after a new `401`, and the policy trusted only after a `401` that can be attributed, under the same A75 gate. An API-key route with `backendRefs` is never created, only updated. One window remains: a policy deleted between a pass's check and its route update leaves the route published without it until the next pass, whose outcome depends on where it finds the transaction: a `Create` still short of `Served` finds the policy missing or changed and strips the route back to prepared before writing the policy again, and a transaction already `Served` re-creates the policy by the `Lock` with the route left open. One probe proves one gateway replica and no replica count is declared, so a served API-key Agent reads `GovernanceSkipped=False`, reason `AuthVerifiedOnOneReplica` (H2). **And a served Agent no longer reports `Ready=True` after the assayd Gateway stops accepting its route.** That defect was measured on k3d on 2026-09-14 by renaming the Gateway's listener: once no transaction was in flight nothing re-read route status, and the state never healed, because the route's `sectionName` is a constant the operator re-asserts. Design 03 A80 specified the re-derivation, the human decided its three calls on 2026-09-21, and **A81 implements it** (`internal/controller/authserved.go`). A pass of a served Agent with no transaction in the slot, or with a refused `Adopt` in it, judges two objects it has already read. An explicit `Accepted=False` or `ResolvedRefs=False` from the assayd Gateway **at the route's current generation** raises `PolicyApplyIncomplete=ServingRouteNotAccepted`, `Ready=False`, phase `Degraded`, leaves `GovernanceSkipped` where it was with a note, and **withdraws no traffic**. A served `<agent>-auth` that exists, carries the Agent's UID and renders to `appliedDigest`, whose tuple the Gateway reports broken at the policy's current generation, raises `PolicyApplyIncomplete` and `GovernanceSkipped=True`, both `AuthPolicyNotAttached` — the fail-open half, announced and not closed. **When both halves fire on one pass — which is what renaming the listener does, since it detaches the route AND leaves `<agent>-auth` attached to nothing — the ROUTE reason leads**: `PolicyApplyIncomplete`, `Ready` and `Degraded` read `ServingRouteNotAccepted`, because nothing reaches the agent on that pass and the policy half's claim cannot be true of it. A80 ordered them the other way on an assumption the two could not fire together, and A81 reverses it on the measurement (A81). **Anything that is not an explicit failure at the current generation is unknown: it raises nothing and clears nothing**, and a standing report is re-asserted from a two-flag claim store on `status.auth`, because every route write bumps the generation and the Gateway's report lags it, so the stronger rule would flip a served Agent to `Degraded` on every rollout and the obvious clearing rule would retract a true report there. **(A4-spec) was offered and not taken**, so the judgement reads no listeners and a Gateway that is readable but has stopped writing status is caught by nothing, for any mode. The operator does read `spec.listeners`, on every served pass with a mode — `capturingListeners`, for A75's W1, to decide which listener a Gateway-level policy can take traffic on — and **this judgement does not use it**; an earlier version of this paragraph said nothing reads them, which is rule 7 (A81). **The policy half is now measured, and the measurement is not what the row expected** (design 03 A82, `docs/research/a80-policy-half-conformance-2026-09.md`). §8.1 case 19 (f) still only writes the report agentgateway would write and measures the operator's reaction to it; the `make conformance-cluster` case that produces the state is built, on agentgateway 1.5.0, and it splits in two. A byte-unchanged `<agent>-auth` reported `Accepted=True` with reason `PartiallyValid`, because a labelled key `ConfigMap` an administrator wrote holds an entry the controller rejects, sits on a route the Gateway goes on accepting — and that route answers `401`. So the report is reachable, `AuthPolicyNotAttached` is not dead code, **and the fail-open consequence it announces is not true of the state that reaches it**. The bypass shape is real too — `Attached=False` on the synthetic `StatusSummary` ancestor answers `200` with the backend's own body on an accepted route — **and the operator both reports it and closes it**: §5's precondition is render against render, so an out-of-band edit to the policy does not take it out of the judgement: the state is entered, **repaired on the first pass after the edit** and **reported on whichever pass first reads the synthetic ancestor**, which may be before, with or after it, because that ancestor is not generation-gated. §8.1 case 19 (f) pins the co-location — one pass doing both — and the window is one watch round-trip, since the policy watch is label-selected with no predicate and the edit enqueues the Agent itself. **A80's premise is satisfied, not falsified** — the case is the fixture A80 said did not exist — and the measured `200` is a window between the edit and the next reconcile, pinned in envtest with two mutations against the operator. What bounds the shapes still unproduced is a mechanism, not a stimulus count: 1.5.0 writes the real Gateway ancestor for `targetRefs` that resolved and the synthetic one for those that did not, so for a one-`targetRef` `<agent>-auth` the only ways to break it are to remove the route — which puts a `Create` in the slot rather than firing the route half — or to edit the ref, which the first pass after the edit repairs. An identity that can write the policy can instead strip the UID label and repoint `targetRefs` in one patch, and then nothing raises and the route serves unauthenticated standing: §3.2's name-and-label rule working as designed, recorded as a separate follow-up. That same two-ancestor shape is a second rule-8 instance, because `policyReport` short-circuits on the synthetic ancestor and would report not-attached against a contemporaneous `Attached=True`. Nothing tried produced `Accepted=False` on a policy, nor `Attached=False` on the real Gateway ancestor. All three cases require the route to read `Accepted=True` at its current generation, so none can be satisfied by the conflated listener-rename state. **And the measurement found the operator's own report naming the wrong cause there**: the Gateway says `Attached=True`, "Attached to all targets", while the message opens "the assayd Gateway reports that it does not attach the `<agent>-auth` policy" under reason `AuthPolicyNotAttached`, and the Agent goes `Ready=False`, `Degraded` with its authentication intact — rule 8, recorded as OWED in §5 and A82 rather than fixed by it. One rejected entry does this to EVERY served API-key Agent in the run namespace, not one, because they share one key source. **A80's own (B) decision was re-opened by this**, and **the human answered on 2026-09-23 — (B1) + (B4) — which design 03 A83 implements.** The posture is unchanged: report only, withdraw nothing, both conditions under `AuthPolicyNotAttached`. The MESSAGE now branches on which of `policyReport`'s four broken answers fired: the synthetic `StatusSummary` ancestor and an explicit `Attached=False` keep the non-attachment lead; `Accepted=False` says the Gateway rejected the policy outright; `Accepted=True` with a non-`Valid` reason says the Gateway accepted it **but not the whole of it**, says in terms that the Gateway is NOT reporting it unattached AT THE POLICY'S CURRENT GENERATION — not “on this pass”, which overstates a reading the generation gate makes narrower, and `Attached` was measured lagging `Accepted` by a generation on 1.5.0 — and that the judgement issues no request so whether a credential is still required is not established either way, and sends the reader to the Gateway's own reason **and message**, with the key-`ConfigMap` attribution and its namespace-wide blast radius HEDGED, because 1.5.0 reports the same `PartiallyValid` for three measured causes and only that one is shared; and a HELD report, which re-derived no clause, says it is restating a claim it cannot narrow. **Whether it ALSO says what the Gateway has done since belongs to the NOTE, not the lead, and there are THREE held paths, not two**: a Gateway gone quiet at this object's generation and an errored `-auth` step both checked it and both say it, through `heldNote` and `erroredNote`; the third, where §5's precondition excluded the policy, did not, and gets `unjudgedNote` — leaving `heldNote` on it put “the Gateway has not reported since” into the same message as “nothing here will clear this claim”, one message and two claims with the second never checked. §5's precondition is stated only where the pass established it: a claim held over a pass that read NO policy — after a foreign takeover of the `-auth` name, or after an upgrade whose render digest is not the one `status.auth` records, which is permanent — says that instead, and says nothing here will clear it. Two clauses at once take the stronger claim's words, which moves no answer. **The REASON does not branch** — `AuthPolicyNotAttached` on every clause — because the claim store on `status.auth` is one boolean per half and carries no clause, so a per-clause reason could not be held across a pass that re-derives nothing; that residue is stated in §5. **It is a control-plane fix and the human accepted the bound**: it reads no request, so it would mis-hedge a future translation failure reporting `PartiallyValid` while disabling authentication. **(B2)'s re-probe — the only proposed mechanism that tells the two measured shapes apart — and (B3) were offered and not taken**, and D5(c)'s synthetic short-circuit is untouched and still open. Building it found FIVE unpinned branches, four of them A83's own and three of them found by the independent reviewer or by re-mutating after its fixes: the errored hold's POLICY half, A81's, reached by no row; `clauseRejected`'s `!routeOK` hedge, which no fixture writes `Accepted=False` to reach; `judged` at the held call site and again at the RAISING call site, whose literal could be flipped with the whole suite green; and the mirror arm of the note selector that fixed the first of those. Each is now pinned by a row that fails on it. **And the same measurement found a state nothing reports at all**: deleting the selected key `ConfigMap` takes every key in the namespace to `401` while policy, route and Agent all read healthy — a silent authentication outage, NFR-8, recorded in §5 and owed. **Nothing pages**, because design 10 is not built and no alert rule ships in this repository. Building it corrected two of A80's own statements: `refuseAdopt` had to carry the claim store across its wholesale assignment of `status.auth`, or the refused `Adopt` class hot-loops; and A80's one-line `authKept` remedy reaches only the passes that call `persistStatus`, which a served Agent in steady state never does. **And A81's own first implementation shipped a fatal bug its review caught**: a held report's message was appended to rather than rebuilt, so it grew a few hundred bytes a pass until the API server refused every status write for that Agent — the operator's whole status frozen during the incident the judgement exists to report, and reproduced independently by the review. A held message is now **rebuilt from the report's own text** with one note appended; the markers stay as what the tests read. §3.3.3 asks that a held report keep its `LastTransitionTime`, and its `ObservedGeneration` only where the held claim is the stored condition's own reason and nothing else writes that condition on the pass: a held `PolicyApplyIncomplete` takes the pass's generation when a route reason is raised or held beside it, or when its stored reason was the route's and the route has come back — every case measured (design 03 A84). The operator fetches, validates and digests the card the container serves (A68), but does **not** verify its signature, cross-check its skills against the CR's grants, or count the registration deadline — §5 carries those three individually. So the platform's central claim — that governance becomes real **at the gateway** — now has its *path* proven, one *concern* compiled and enforced, and the rest of its *governance* still unbuilt.

**The gateway is now provably the only way in — under a hand-authored rule, on k3d only.** `TestTheGatewayIsTheOnlyWayIn` applies design 07 A5.4's ingress half by hand, then measures ADR-0030's stop criterion for the slice: the gateway reaches the agent, an ordinary namespace does not, and the operator's card fetch still gets through. Three mutations kill it (drop either allow rule; apply no policy). It **skips, reporting the axis unverified, on any CNI that does not enforce NetworkPolicy** — kind's default does not, and a policy there is accepted and does nothing. The operator still materializes no NetworkPolicy and holds no `networkpolicies` RBAC (design 07 A6.6).

**And it refuses a principal — under the operator's own policy.** `TestTheGatewayRefusesADisallowedPrincipal` measures the `<agent>-auth` the OPERATOR emitted — API-key authentication over a ConfigMap of `sha256:` hashes, and one CEL authorization rule admitting the group named for the Agent's namespace — at the gateway rather than at the network: permitted principal `200` with the agent's own answer, **valid credential in the wrong group `403`**, no credential `401`. The shape was measured by hand first: inverting the rule inverted both outcomes, and removing `authorization` while keeping authentication left anonymous at `401` and moved the wrong-group caller to `200`, so the `401` and the `403` are different controls and not one. The hand-authored `assayd-e2e-authz` is gone: beside the emitted policy it would be a second `traffic` policy on one route, and two resolve at random. The key set carries the product's constant label, `assayd.dev/api-keys: "true"`, and is written by an administrator; nothing in assayd writes keys. In a run namespace, admission refuses a create, or an update that changes what is reserved, of a policy from anyone but the operator and `admission.extraOperators`, and of an API-key `ConfigMap` from anyone but those and `admission.apiKeyWriters` (by default `system:masters`). Deletes are RBAC's (design 07 A6.7, A6.10; design 03 A70, A71).

**And an MCP tool call goes through it.** `TestAnAgentCallsAnMCPToolThroughTheGateway` runs a real MCP exchange — `initialize`, `tools/list`, `tools/call` — against `test/mcpserver`, a two-tool Streamable HTTP server behind an `AgentgatewayBackend` on a second Gateway listener. Its route is written by the chart's `admission.toolRouteWriters` identity, which `assayd-gateway-routes` admits on any listener but the serving one, `http`, and only with hostnames no Agent's serving host can match. Until design 07 A6.15 the e2e impersonated the operator to write it, because no one else could, so no real user could publish a tool. A hand-authored `backend.mcp.authorization` allowlist (design 03's `toolAllowlist`) does more than refuse: it **removes the disallowed tool from `tools/list`**, so an agent never learns it exists, and a refused call returns `Unknown tool` rather than "forbidden" — good for non-disclosure, a trap for whoever debugs it. Flipping the rule inverts the listing and both calls. **And an agent completes an A2A task by making the MCP call itself.** `test/responder` implements `SendMessage` on the HTTP+JSON binding its card declares. `TestAnAgentCompletesATaskByCallingAToolThroughTheGateway` sends one `SendMessageRequest` through the operator's route, with an API key, and the agent completes it by calling an MCP tool through the gateway, at the `ASSAYD_GATEWAY_URL` the operator injected. Once the gateway's allowlist excludes the tool, the same task fails with the gateway's `Unknown tool`. So ADR-0030's "one **agent** completes one A2A task and one MCP tool call through the gateway" holds — **by fixtures**. It is ONE A2A method, A2A 1.0 only, on a test fixture, and the operator speaks no A2A. The tool call is unauthenticated, and nothing restricts an agent's egress to the gateway: the fixture simply has no other address (design 07 A6.12, A6.13). The next work is the rest of the narrow slice in ADR-0030, not the next design.

## Skills — use them, do not paraphrase them

Nine skills live in `.claude/skills/`. **A skill with a `paths:` key does not resolve until a matching file has been read in the session** — so `/implement-feature` returns "Unknown skill" on a cold start even in the right directory, and `/write-spec`, `/adr`, `/design-component` and `/audit-docs` behave the same way. That is a property of `paths`, not a broken session. `/verify-change`, `/review-code`, `/critique-design` and `/research-latest` carry no `paths` and always resolve.

| Skill | Use when |
|---|---|
| `implement-feature` | writing or changing any code under `api/ internal/ cmd/ test/ config/ charts/` |
| `review-code` | before merging a diff — forks its own context |
| `critique-design` | before approving a design or amending an approved one — forks its own context |
| `write-spec` | writing a design, an ADR, a CRD type, or any user-facing string |
| `research-latest` | any landscape, library or standard question — never answer from memory |
| `design-component` · `adr` · `audit-docs` | designing, recording a decision, checking doc consistency |
| `verify-change` | **after any amendment or fix** — the loop that closes it: gate → independent critique → cross-family critique → spike the unmeasured claim |
