## MAJOR 1 — `docs/research/auth-lock-false-credit-2026-09.md`: the recorded run contradicts the fixture it is recorded against, at the two rows that set up the credit

This note is what "measured" resolves to in `03:3`, `03:1424`, `03:1451`, `README:11`, ADR-0034 Amendment 6, `AGENTS.md:13` and `CLAUDE.md:11`. Its central table cannot describe one run.

The fixture is stated twice and consistently. The oracle is **policy-blind** and answers per revision: "Asked for the card path, it answers `200` with the taken revision's card while that revision serves it, and `401` when the taken revision refuses it" (line 16) — and the note is explicit that this is deliberate, because "one that always answers `401` once a policy exists cannot show the defect". The revisions are fixed: "r1 serves no card at its card path and has no digest in `status.cards[]`" (line 17). Line 27 restates it: "r1 answers `401` at the card path, **because it refuses it** — which is exactly why r1 has no recorded digest."

Under that fixture r1's answer is a constant `401`. But the table says r1 answered **`200`** twice: pass 1, "`ProbingBefore` sends one anonymous request, gets `200` from r1"; pass 2, "`ProbingAfter` probes, gets `200` from r1, credits nothing". Nothing about r1 or the taken revision changes between pass 2 and pass 3 — the harness column for pass 3 mints r2 and withholds the route's parent status, and the taken revision is still r1 by the note's own sub-row. So exactly one of these is true:

- r1 refuses, as lines 16, 17 and 27 say, and the two `200` cells are false: the run was `401 → 401`, `ProbingBefore` observed nothing because it got a `401` and not because the digest was missing, and pass 2's "credits nothing" happened for a different reason than the table gives; or
- r1 serves its card, as rows 24–25 say, in which case something other than r1 produced pass 3's `401` — and the note's thesis, that "**that revision's own `401`** is credited", is not what the run showed. It would also mean the oracle is policy-aware after all, which line 16 denies.

Either way "**Observed at the moment of the credit**" (line 30) is asserted across the inconsistency, and a reader cannot reconstruct which run happened. This matters more than an ordinary drafting slip because of what the note is for: `03:1451` argues that a provenance tag "is worth nothing if the finding cannot be opened", and the sixth critique's MINOR 7 offered two exits — commit the reproduction, or downgrade the word to "derived from `runLock`". A third thing was published instead, a prose account of a run, and it is now the warrant for a sentence in the two files every contributor reads first.

**I disagree with the forked pass, which graded this a BLOCKER, and I lower it to MAJOR.** A BLOCKER in this corpus has meant a rule that is wrong or unimplementable, or a false claim about shipped behaviour. Nothing here touches a rule, a condition, a message, a decision or a test: the defect the note reports is independently derivable from `runLock` — I derived it, the forked pass derived it, and three earlier reviewers did — the note itself says the code reading is "evidence and not proof", and the owed envtest cases 18 (f) and (g) are what will actually pin it. The shared clause's own reason for the missing-policy exemption is the structural one and is correct. The fix is to correct the table or to take one of the sixth critique's two exits. That is a MAJOR.

**Fix.** Resolve the `200`/`401` question first, because the answer decides what the note says. If r1 refuses throughout, rewrite rows 24–25 to the answers the run actually got and re-derive each row's "why" from them. If the intended fixture is a backend that serves its card while `status.cards[]` holds no digest for it — a coherent and more interesting shape, since the operator's fetch goes direct to the Service and can have failed — then say so at line 17, say what changed between pass 2 and pass 3, and stop attributing pass 3's `401` to r1's own refusal. Better still, take the sixth critique's first exit: write the envtest case in `test/envtest` (`AuthProbe` and `AuthDeadline` are already fields for exactly this) and rewrite the note against what it prints.

## MAJOR 2 — `03:776` and `03:1454`: "a NACK costs the hold's **reason** and never the page" is false on the release path the operator's own message names first

The sixth critique's fix was adopted close to verbatim, and the absolute in it was not re-derived. The sentence covers two windows — "at once while the Event stands, and from the deadline onwards whatever becomes of the Event, whose default life is an hour" — and concludes "never the page". The one-hour argument is right about **expiry** and silent about **deletion**, and `freshNack`'s own message tells the reader: "To release the hold, delete that Event, or wait for the API server to expire it".

Walk it. A J2 `Lock` at `ProbingAfter` under a standing A75 hold takes a NACK: `freshNack` rewinds to `Converging` and the tail raises `AuthLockUnverified` under `out.nack != ""` — reason lost, page kept, as the design says. An administrator now does what the message says and deletes the Event, inside the four minutes, with the tuple still unmet. Next pass: `authPolicyIntact` passes, `freshNack` returns `""`, the stage is `Converging` so the arm breaks on `routeConverged`/`policyConverged` **before** `gatewayAuthPolicies`; `held` is false because the A75 read was never reached; in the tail `deadlinePassed` is false and `out.nack` is empty, so neither arm fires; `out.withhold` stays nil; and `reconcileGateway` does not restore the carried seed, because `err` is nil. The Agent an A75 hold had made `Degraded` reads `Ready=True`, under a policy W1 says could widen or bypass its authentication, until the deadline.

So the NACK case costs the page too, on a trigger of its own — and the trigger is the operator's own advice. The paragraph's enumeration ("two cases reach it") is right; only case two's cost is wrong, and `03:1454`'s "The window is an Event that goes **before** the deadline, which is the other case's trigger" is wrong in the same place. This is rule 7's shape and rule 8's at once, in the paragraph that exists to be honest about exactly this hole.

**I initially graded this a MINOR and raise it, agreeing with the forked pass.** The paragraph disclaims the whole area ("Neither case is A77's, and A77 widens neither") and the fix is one clause, which argued for MINOR. What decides it the other way is consistency: rounds five and six each graded "an absolute written this round while closing a finding, false against the code" as a MAJOR, and this is the third instance of that exact shape, on a sentence about a page being silently dropped.

**Fix.** "…and from the deadline onwards whatever becomes of the Event. So a NACK costs the hold's **reason** while the Event stands; it costs the page as well if the Event goes before the deadline with the tuple still unmet — which is the first release this operator's own NACK message names." And drop "which is the other case's trigger" from `03:1454`.

## MAJOR 3 — the missing-policy `Lock`'s exemption is called structural and given a second reason that is not, and `03:1424` repeats it

Note line 37: "The missing-policy `Lock` does not reproduce, and **the reason is structural**. Its branch takes the route as found and writes nothing to it (`rt = cur`), so its `backendRef` cannot move mid-transaction; **and** it enters at `ApplyingPolicies`, so it must pass `Converging` — where `routeConverged` compares the route's current generation against the Gateway's reported one — before it can probe at all. Driven through the same promotion, it parks at `Converging` and sends **zero** probes."

The first reason is structural, correct, and sufficient — it is the one the shared `AGENTS.md`/`CLAUDE.md` clause uses, and it is why that clause is safe. The second is not structural and cannot be, for the reason the first gives: a branch that writes no route does not move `metadata.generation`, so `routeConverged` compares the generation the Gateway has already reported and **passes**. Passing `Converging` is also not by itself a reason to park there — the note's own J2 table has that run clear the tuple at pass 2 and probe in the same pass, and `runLock` `continue`s from `Converging` straight into `ProbingAfter` inside one pass. Whatever held that run at `Converging` was something the note does not name: a freshly re-created `<agent>-auth` reporting no ancestors yet would do it, and so would a route generation already ahead of the Gateway's report when the `Lock` was entered.

Read as structural it is worse than unexplained, it is false: if the missing-policy `Lock` could not leave `Converging`, A77's own re-point — which `03:775` places at `ProbingAfter` step 1 for exactly this `Lock` — would be unreachable, and case 18 (a), which asserts this `Lock` reaches `Served`, could not be built. `03:1424` carries the same clause into §11, where an implementer reads what was and was not measured: "could **not** drive the missing-policy `Lock` there, which parks at `Converging` and sends no probe."

**Fix.** Keep one reason and make it the structural one: "Its branch takes the route as found and writes nothing to it (`rt = cur`), so no backend moves under the probe and there is nothing for the attribution to misread." Report the parking separately as an observation of that run, with what held it, or drop it. Same correction at `03:1424`.
