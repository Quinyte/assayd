## 1. Purpose & scope

The flagship: semantic admission (FR-20). A new Agent/Model revision earns traffic by passing its EvalSuite against the candidate *through the production path*. In scope: the EvalSuite CRD, the **EvalRunner slot** (`evalrunner/v1`), the gate controller's interaction with design 02's rollout machine, the dataset builder, metric semantics, verdict rules, nightly trend runs. Out of scope: session substrate (17), drift consumption of trends (20), runner pack packaging (18).

### 1.1 The first slice — blue/green, one suite (approved by the human on 2026-09-14)

**This section is approved for implementation, by the human on 2026-09-14 (ADR-0024 Amendment 1). Nothing in it is implemented yet.** It answers ADR-0030's build step 4, "a narrow design-16 gate, blue/green before canaries". The human approved it after twelve critiques, answering Q1 to Q13 each as recommended ("Decisions of the human", below); §14's table at the end records each critique and the amendment that answers it. ADR-0024 Amendment 1 records the approval, and the statements of ADR-0024 that this slice changes, among them that rerun-shopping is "structurally impossible" and that an eval Job holds its own SVID. The rest of this design is specified, not approved, and must not be implemented. *(Added by A3, and revised by every amendment since. §14 logs each revision and the critique it answers, in the table at its end.)*

**The human decided Q1 to Q13 on 2026-09-14, each as recommended ("Decisions of the human", at the end of this section).** The slice below is drawn on those answers. Wherever another answer would have changed a rule, the rule names its question, and each question keeps its alternatives as the record.

**What the slice is.** An Agent names one EvalSuite in `spec.gates`. A revision minted by the Agent's current spec is evaluated before it takes any traffic. An eval controller in the operator's manager sends each of the suite's cases to the candidate revision's own Service as one A2A `SendMessage` task, and compares the answer with the case's expectation (Q1). If enough cases pass, the revision is promoted wholesale: `status.activeRevision` flips, and the serving route's one `backendRef` moves to it, as for any promotion today (design 07 A6.10). If not, the candidate is held, named by no route, while the active revision keeps serving. There are no canaries and no traffic split, so the slice never sets phase `Canary`.

**Why this is the smallest gate that is still real.** It keeps three properties:

- The candidate is the real revision workload: the digest-pinned image it would serve with, its immutable material, and its injected environment (design 02 §3.2).
- Each case is a real A2A 1.0 task, on the binding the candidate's own card declares, not a bespoke echo path.
- The verdict alone decides promotion, and it is bound to the full revision digest it was earned on, not the forty-bit name (A2).

What it gives up is in the "Out of the slice" table: no runner image, no Job, no judge, no dataset artifact, and no path through the gateway for the eval's own requests.

#### The EvalSuite, in the slice

The slice's schema is a strict subset of §3's, so the full schema can add fields later without migrating a stored suite (Q8). Minimal:

```yaml
apiVersion: assayd.dev/v1alpha1
kind: EvalSuite
metadata: {name: smoke, namespace: team-a}
spec:
  dataset:
    cases:
      - {id: arithmetic, message: "What is 2 + 2?", expect: {contains: "4"}}
```

Realistic, with the one Agent field the slice reads:

```yaml
apiVersion: assayd.dev/v1alpha1
kind: EvalSuite
metadata: {name: claims-regression, namespace: claims}
spec:
  dataset:
    cases:
      - id: deductible-lookup
        message: "What is the deductible on policy P-1042?"
        expect: {contains: "500"}
      - id: refuses-travel
        message: "Book me a flight to Lisbon."
        expect: {contains: "cannot help with travel"}
      - id: health
        message: "status"
        expect: {equals: "ok"}
  metrics:
    - {name: task_completion, threshold: "0.66"}
  caseTimeoutSeconds: 10
```

```yaml
# on the Agent claims/pa-reviewer, beside the rest of its spec
gates:
  - evalSuiteRef: claims-regression
```

The rules, each owed as CEL on the CRD, with a refusal that names the fix:

| Field | Rule |
|---|---|
| `dataset.cases` | 1 to 20 items. An empty list is refused at admission, because an eval with no cases would pass every revision. This moves §7's "a suite with zero cases fails closed" from a condition to admission |
| `cases[].id` | a DNS label, unique within the suite |
| `cases[].message` | 1 to 4096 characters, sent as the task's one text part |
| `cases[].expect` | exactly one of `contains` or `equals`, each 1 to **512** characters. Compared with the answer text, case-sensitive, with no normalization. **A case whose message already satisfies its own expectation is refused**, by `(!has(self.expect.contains) || !self.message.contains(self.expect.contains)) && (!has(self.expect.equals) || self.message != self.expect.equals)`: an agent that echoes its input would pass it, and `test/responder` is such an agent. A4, from the critique's m9. The rule catches only the literal echo. An agent that paraphrases its input can still pass a weak expectation. **The bounds are the ones measured to install** (A5, from the re-critique's N6, on envtest v1.36.2). cel-go estimates `contains` as the product of the two strings' sizes. At 4096 × 4096 over 20 cases, the API server refused the CRD itself: "estimated rule cost exceeds budget by factor of 5.4x". A message of 4096 with expectations of 512, 256 or 128 installed, and so did 1024 with 1024. The slice keeps the message at 4096 and caps each expectation at 512. The `has()` guards are required: without them, every well-formed case is refused with `no such key` |
| `metrics` | optional, at most one entry, and its `name` must be `task_completion`. Absent means `threshold: "1"`: every case must pass |
| `metrics[].threshold` | a decimal string greater than 0 and at most 1, with at most three decimal places. It is a string because controller-gen refuses float fields without `allowDangerousTypes`, and §3's `threshold: 0.85` is a float (below, "What design 16 says that the slice cannot keep"). A threshold of 0 would pass every revision, so it is refused |
| `caseTimeoutSeconds` | 1 to 10, default 10 (Q1) |
| every other §3 field: `runner`, `target`, `dataset.goldenSetRef`, `dataset.fromSessions`, `gate`, `budget`, and any other metric | absent from the slice's schema. kubectl's default server-side field validation refuses an unknown field. A client that does not ask for that validation has the field pruned in silence. That is the API server's behaviour for every CRD, not a rule this slice adds |

On the Agent, `spec.gates` holds at most one `GateRef` (Q4). `evalSuiteRef` resolves in the Agent's own namespace. The suite carries no `target` in the slice, so the Agent's reference is the only binding between the two (Q8).

The **suite digest** is the SHA-256 of the canonical JSON of the suite's `spec`, with defaults applied, object keys sorted, and cases sorted by `id`. A change to any case's message or expectation, to the threshold, or to the timeout changes it. Reordering cases does not. Because a reorder leaves the pair unchanged, a run's record is kept by `id`, never by position (step 10, A12).

#### Who runs the eval (Q1)

On Q1's recommended answer, a second controller in the agent-operator's manager runs the eval. It has its own work queue, and `MaxConcurrentReconciles: 2`, so at most two cases are in flight across the cluster. It is not a new pod, image or ServiceAccount. It exists because the Agent reconciler has one worker: the operator sets no `MaxConcurrentReconciles`, so controller-runtime's default of one applies, and a case run there would make every other Agent wait. That includes another tenant's design 03 `Lock`, whose passes must all fit inside `AuthTransactionDeadline`, 4 minutes (`internal/controller/authtxn.go`). A tenant whose image sleeps on `POST /message:send`, or who re-digests a suite against a held candidate, would then push other tenants' `Lock`s past that deadline, into `PolicyApplyIncomplete/AuthLockUnverified`, which pages (`reviews/16-a3-critique.md` M2). With a separate eval controller, a slow tenant delays only other tenants' evals. It never delays another Agent's reconcile, `Create` or `Lock`. The delay grows with the number k of tenants whose candidates are slow: two workers give a benign case a wait of about k/2 × `caseTimeoutSeconds`, and a run has no deadline, so a 20-case run can take about 20 × k/2 × 10 s. *(Corrected by A5, from the re-critique's n3. A4 stated the bound for one slow tenant only.)*

**On the Agent being evaluated, the eval and the Agent's own `-auth` transaction are serialised.** The eval controller claims no case while a `Create` or a `Lock` is recorded in `status.auth.transaction` on that Agent, at any of its stages, and while one is being abandoned. The exceptions are in the table below. Meanwhile the Agent reads `GatesPassed=False/EvalWaitingForAuth`. *(A5 to A11.)*

- **The stages.** For a `Create`: `PreparingRoute`, `ApplyingPolicies`, `Converging`, `ProbingAfter` and `Publishing`. For a `Lock`: `ProbingBefore`, `ApplyingPolicies`, `Converging` and `ProbingAfter`.
- **Why.** Every eval patch bumps the Agent's resourceVersion. The Agent reconciler writes status with a full `Update` at the resourceVersion it read: at the end of each pass (`writeStatus`), and ahead of each gateway write (`persistStatus`, `internal/controller/authtxn.go`). So a transaction's pass that overlapped an eval patch would fail with `Conflict`, lose the pass, and sometimes lose a probe's observation.
- **The rule is for recorded transactions, not for incidents.** It reads `status.auth.transaction`, and, for the one exempt `Lock` below, the hold on it. A served Agent with no transaction recorded is evaluated and promoted whatever incident stands beside it, as an ungated Agent's revisions are. Two such incidents are:
  - W1 (design 03 A75): a served API-key Agent beside a Gateway-level policy that could widen its route. `reportAboveServed` raises `PolicyApplyIncomplete=True/GatewayAuthPolicy`, and the Agent pages and is `Degraded`.
  - A served Agent beside a foreign traffic policy on its route, reported as `ForeignTrafficPolicy`.

  The rule exists to keep eval patches off a transaction's status writes. It does not freeze promotion during an incident. Q12 counts this among its costs. *(A11, from the eighth critique's m4.)*

What the rule does with each record in `status.auth.transaction`:

| Recorded | The eval | Why |
|---|---|---|
| a `Create`, at any stage | waits | its status writes must not conflict with eval patches |
| a missing-policy `Lock`: a re-creation, whose `targetMode` equals the recorded `mode` | waits, and can wedge ("The missing-policy wedge", below) | the same |
| a J2 or K2 `Lock` before `ProbingAfter` | waits | it is writing and converging the policy that closes the route |
| a J2 or K2 `Lock` at `ProbingAfter` that meets the exemption's five clauses (below) | claims | it can finish only through a promotion |
| a J2 or K2 `Lock` at `ProbingAfter` that does not meet them | waits | it can finish on its own passes, or a hold stands on it. A held `Lock` stays held after a promotion, so exempting it would earn nothing ("What it buys", below) |
| a J2 or K2 `Lock` being abandoned while it waits on a finalizer (`abandonWaiting`), whose record meets the five clauses | claims | abandonment has no deadline, completes once the finalizer lets go, and each of its passes is safe to re-run. A pass lost to an eval patch delays it by at most one 30 s re-check |
| a refused `Adopt`, `{kind: Adopt, stage: Refused}` (`refuseAdopt`) | claims | a standing record, not a transaction in flight. It stays until the Agent is recreated, or until its owner edits it to `apikey` (K2, design 03 §1.1). After its first pass it writes nothing, because `writeStatus` returns early on an equal status. The route stays as `Adopt` leaves it, unauthenticated, and each promoted revision serves on it, which is design 03's `Adopt` behaviour and unchanged here |

- **A transaction held indefinitely holds the eval indefinitely, for new claims.** There are two cases. A Gateway-level hold keeps a transaction at `ProbingAfter` (design 03 A75). A `Create` or `Lock` past its deadline "stays in its stage and keeps working" (design 03 §3.3.3). Both are already paged, through `PolicyApplyIncomplete`. On Q12 (a), the eval keeps waiting after the deadline. `EvalWaitingForAuth`'s message then names the transaction, its stage, and when the deadline passed. On Q12 (b), a transaction past its deadline releases the eval, whether or not a hold stands. *(Scoped to new claims and to Q12 (a) by A11, from the eighth critique's m1.)*
- **What wakes the eval controller while it waits.** Its `For(&Agent{})` watch does. The transaction ending, or a hold clearing, changes the Agent's status: the transaction record goes, a condition is withdrawn, or `AuthLockUnverified`'s message stops naming the hold. That write enqueues the Agent. And every pass that sends no case returns a requeue, so a waiting Agent is looked at again even when nothing writes. A pass waiting on a transaction, or on clause 5's hold, returns `RequeueAfter: AuthProbeInterval`, 5 s (`internal/controller/authtxn.go`), the rate design 03 probes at. A pass held by a paused candidate, or by a run-start refusal that read a card, returns `RequeueAfter: CardDriftInterval`, 5 minutes. Its inputs are the candidate's card and its availability, and each of those reaches the eval controller as an Agent event anyway, so 5 s would only re-fetch the card sixty times as often. That is the mistake `internal/controller/card.go` records as already made here: "a card is not a per-reconcile input". *(A13, from the tenth critique's m4. A12 gave every waiting pass 5 s, and costed only clause 5's reads.)* **A run-start fetch that failed is the exception: that pass returns `RequeueAfter: CardRetryInterval`, 15 s.** Nothing in Agent status changes when the eval controller's own fetch is refused or times out. The recorded digest is still valid, and the shared predicates already required it, so this branch has no Agent event to wake it and five minutes would be its whole retry. 15 s is design 02's own interval for a failed card fetch, chosen for this case (`cardFetchDue`, `internal/controller/card.go`). *(A15, from the eleventh critique's m4.)* **Every requeue the eval controller returns goes through one field**, whose zero value is the constant each branch names ("What the slice depends on"), so a test can shorten any of them without touching a constant. That is the three branches above and two more stated where they arise: a candidate held with a final verdict, which requeues at `CardDriftInterval` to notice a suite edit ("EvalSuites are read uncached"), and a pass whose read-back failed, which returns `CardDriftInterval` and sends nothing (step 11). The two owed rows that shorten the field sit on those last two. *(Scope stated by A17, from the twelfth critique's m2. A15 introduced the field under an enumeration of three branches, and both rows that shorten it are on the other two.)* A pass whose clause-5 read fails records the hold (below) and returns the error instead, so controller-runtime's per-item error backoff governs its retry. *(A11, from the eighth critique's noted items. Corrected by A12, from the ninth critique's m1: A11 cited a backstop requeue that no waiting pass returned.)*

#### The exemption: a J2 or K2 `Lock` that can finish only through a promotion

A `Lock` credits its `401` in only two cases: `beforeObserved` is set, or `status.cards[]` records a digest for **the revision the route's single `backendRef` names** (`cardAttributes`, `internal/controller/authtxn.go`). A route that does not carry exactly one `backendRef` names no revision and is unattributable, whatever `status.cards[]` records (design 03 A77, §3.3.3). Neither slice's emitter writes a second one. *(Corrected by A19. A7 wrote "a revision that one of the route's `backendRefs` names", which was `cardAttributes`' own reading until design 03 A77 narrowed it to the single ref.)* A J2 or K2 `Lock` re-asserts the route on `status.activeRevision` on every pass (`runLock`), so for these two kinds the route follows promotion. Suppose the serving revision has no recorded card, and nothing was observed before the `Lock`. While a candidate exists, the serving revision is not the desired one, and the Agent reconciler re-reads only the desired revision's card. So no card re-read can end this. The `Lock` reaches `Served` only after a promotion moves the route to a revision whose card is recorded, and on a gated Agent that promotion needs a verdict. So the eval must be allowed to earn it. The rule exempts the state in which all five of these hold. *(A7, narrowed by A8, A9 and A10.)*

- **What clause 5 costs.** Only a pass of the eval controller that has met clauses 1 to 4 pays. - **It does not bring back N4's contention.** Before `ProbingAfter` the `Lock` is writing and converging the policy that closes the route, and clause 2 keeps the eval off it. A run adds one for its start. - **What it buys.** A passed candidate is promoted only under the fourth promotion condition, which requires its card to be recorded. So the promoting pass ends short of the request, and the credit comes on a later pass. A pin, or removing the gate, also moves the route for these two kinds, and so also ends the wait.

#### The missing-policy wedge

The `Lock` of a missing policy is a re-creation: its target mode equals the recorded mode. **Since design 03 A77 it writes the route, conditionally.** At `ProbingAfter`, after the policy is read intact and after A75's Gateway read, it re-asserts `<agent>-serving` published on `status.activeRevision` — but **only while `status.cards[]` records a digest for that revision** (`cardedRevision`, `runLock`, `internal/controller/authtxn.go`). When that condition fails the route is taken as found, as it always was, and `reconcileServed`, which re-asserts a served Agent's route on the active revision, is still not reached while a `Lock` is recorded. So a promotion during that `Lock` moves the route when the promoted revision is carded **and a pass reaches `ProbingAfter`'s re-point**, and leaves it where it was otherwise. **What is left is the wedge**: the `Lock` cannot finish when the revision the route names has no recorded card **and `status.activeRevision` has none either**, because then there is nothing to re-point onto that could attribute, and no later pass changes that without a card (design 03 §3.3.3). It is not exempt, so the gate waits. *(A8, corrected by A9 and A10; narrowed by A19 for design 03 A77 and A78, which the human decided on 2026-09-15, ADR-0034 Amendment 6, and PR #48 implemented. A8 wrote "It never writes the route", which the re-point makes false.)*

That revision, called R here, is the one the route's **single** `backendRef` names, which is what `cardAttributes` reads; a route not carrying exactly one names no revision and is unattributable whatever `status.cards[]` holds (design 03 A77). R is not always `status.activeRevision` at the moment the `Lock` is entered: `reconcileServed` checks the policy before it re-ensures the route, so a missing-policy `Lock` can be entered in the very pass that promotes, and the switch has then set `status.activeRevision` to the promoted revision C while the route still names R. **That state no longer wedges when C is carded and a pass reaches the re-point.** The re-point moves the route onto C, and the `401` is then attributed on C's recorded digest. On a gated Agent C carries a card at that moment, because Q10's fourth promotion condition requires one. **A carded C is not enough on its own: a pass has to reach the re-point.** It sits at `ProbingAfter`, after the intact read, the fresh-NACK check and the foreign-policy check (`runLock`, design 03 §3.3.3), so a `Lock` short of `ProbingAfter` — one held at `ApplyingPolicies` by a foreign `traffic` policy at `<agent>-auth`, say — never re-points however carded C is, and design 03 A77 records that state as never taken over, never deleted, and unbounded (§8.1 case 18 (c)). **So the route and the active revision stay apart in three ways**: a pass that never reaches the re-point; a failed drift re-read that clears C's digest before one does, which `recordCardAttempt` can do while the `Lock` is still at `ApplyingPolicies` or `Converging`, and that is the ordinary case, since the `Lock` is entered on the pass the policy is found missing; and a promotion that never needed Q10's card at all — a pinned rollback Q5 admits, or a promotion after `spec.gates` was removed (Q9). *(Rewritten by A19. A9 ended this paragraph "If R has no recorded card, that `Lock` wedges even though C's card is recorded", which design 03 A77's re-point makes false in exactly that case.)*

A route that carries more than one `backendRef` is the sentence above rather than the fallback: it names no revision, and the message says so, with the administrator's delete as its only exit. That is where the operator emits that arm. A route that carries **none** reaches the same sentence only in the one stale pass, and the honest text there names no administrator: `routePublished` is false for such a route, so `runLock`'s re-creation branch hands it to `recreateRoute` in that same pass whenever `status.activeRevision` is set, which a served-under-`apikey` Agent always has. *(Split by A19. A11 put a route with no `backendRef` in the fallback, and before design 03 A77 a route with two was attributed on whichever ref had a card, so neither reached this bullet.)* A route read that fails with any other error is different. `currentServingRoute` returns the error, and `runLock` returns it (`internal/controller/httproute.go`, `authtxn.go`), so the `Lock` stays recorded, and the generic text shows for as long as that failure lasts. *(Scoped by A11, from the eighth critique's m6. Corrected by A12, from the ninth critique's m4.)*
- **The wedge is design 03's, not the gate's, and design 03 has narrowed it.** On an ungated Agent the same state wedges once a new revision is promoted **whose card is not recorded**; a promotion to a carded revision ends it **on the first pass that reaches the re-point** — which a foreign `traffic` policy on `<agent>-serving`, a fresh NACK, or a `Lock` short of `ProbingAfter` prevents — because the missing-policy `Lock` re-points its route at `status.activeRevision` while that revision is carded. With no new revision, the route's revision stays the desired one, and a card re-read can end it. What the gate adds is that a held candidate stops that re-read, **usually** cannot itself be promoted — except by the two paths this section already names, a verdict already `Passed` before the `Lock` began, or the outcome of the case in flight when it began where that case is the run's last — and so mostly closes the one exit the re-point opened: on a gated Agent the promotion that would fire it is the promotion the eval is waiting to earn. The amendment that made the re-point is **design 03 A77** — the human's decision of 2026-09-15 (ADR-0034 Amendment 6), through design 03's own critique, implemented by PR #48 with A78 beside it. It is safe for the same reason it is safe for J2: the policy targets the route, so moving the `backendRef` changes which revision answers, not what the route admits. **It is conditional twice over, so it narrows the wedge rather than removing it**: where neither the revision the route names nor `status.activeRevision` has a recorded card digest there is nothing to re-point onto that could attribute, and no later pass changes that without a card; and where no pass reaches the re-point, a carded `status.activeRevision` changes nothing either (design 03 §3.3.3). Q13 is the human accepting that state on 2026-09-14, against the wider wedge as it then stood; A19 records that it is narrower and reopens nothing. *(Rewritten by A19. A9 wrote this bullet while the amendment was hypothetical — "A design 03 amendment would remove the wedge … That amendment is outside this slice … Q13 asks the human whether to accept the wedge in this slice meanwhile" — and it has since landed, narrowing rather than removing, by the route Q13 (a) directed.)*

#### The case in flight when a transaction begins

The rule is checked at the live read before each claim, so it stops new claims, not a case already in flight. *(A6, A9 and A10.)*

- **Its record.** A case in flight when a transaction is entered records its outcome after the transaction began. That record bumps the resourceVersion, and the transaction's next pass loses its `Update` to `Conflict`, or stops at `requireFreshAgent` with `errStaleAgent` (`internal/controller/authtxn.go`). The cost is one pass, once, from at most one outcome.
- **The verdict.** That outcome may be the last case's, and then it carries the verdict, because the verdict is written in the same patch as the last case's record (step 7). No other verdict is written while a `Create` or `Lock` is recorded, because no case is claimed.
- **An `Interrupted` record.** Recording `Interrupted` for a claim found with no outcome (step 10) is an eval write, not a claim, and it also waits on the no-transaction predicate. So an orphaned last case cannot bring a verdict in while a transaction is recorded.
- **A promotion.** A promotion whose `Passed` verdict is already written is not stopped by a transaction or by a hold, because the promoting pass checks only the four promotion conditions.

#### The two controllers

The split between the two controllers:

- **The eval controller writes `status.eval` and nothing else.** It writes with a JSON merge patch under an optimistic lock (`client.MergeFromWithOptimisticLock`). Before every write it reads the Agent with the manager's uncached API reader, because the manager's cache can lag its own last patch. The lock guards a write, not the request the write is about, so a case is claimed before it is sent ("How a run works", step 10). *(Corrected by A5, from the re-critique's N1. A4 said the lock meant the controller never acted on a status it had not read. The act is the send, and the send came first.)*
- **The Agent reconciler never writes `status.eval`.** It reads the verdict, and it sets every `GatesPassed` reason. Its status write is a full `Status().Update` that carries the resourceVersion it read (`writeStatus`). So an Update racing an eval patch fails with `Conflict`, and the pass re-runs from a fresh read. It does not write back a stale `status.eval`. **Its own status does not change with eval progress.** `GatesPassed=False/EvalRunning` names the run's pair and its N cases, not how many are done; `status.eval.cases[]` shows that. So an eval patch makes the Agent reconciler run a pass whose status write is a no-op, because `writeStatus` returns early on an equal status. The two writers contend only when a run starts, is blocked, or ends. *(A5, from the re-critique's N1.)*
- **Both decide whether a case may be sent with the same predicates**, implemented once and called by both: the gate is declared; the EvalSuite CRD is installed; `status.candidateRevisionDigest` is set and differs from `status.activeRevisionDigest`; the candidate is available; no I1 hold stands (`authHoldsPromotion`); a card digest is recorded for the candidate's digest; **no `Create` or `Lock` is recorded in `status.auth.transaction`**, where neither a refused `Adopt` nor a J2 or K2 `Lock` that can finish only through a promotion counts (above); and **`status.observedGeneration` equals `metadata.generation`**. The last one stops the sends to a candidate that a spec edit is about to supersede, before the Agent reconciler has recorded the new one. An edit to a referenced env source's content mints a revision without changing the generation. Until the Agent reconciler's next pass records the new candidate, cases keep going to the old one. Each is a real request, and none can promote anything, because the verdict is bound to the old digest. *(A5, from the re-critique's N4 and n7.)* The generation clause belongs to the eval controller alone. The Agent reconciler is the observer that sets `observedGeneration` in the same pass, so it does not evaluate the clause, and no `GatesPassed` row depends on it. *(A6, from the third critique's m6.)* The exemption's clause 5 is the eval controller's alone in the same way. The Agent reconciler reads its result from `status.eval.blocked`, and makes no Gateway or policy reads of its own. *(A11, from the eighth critique's m2.)*
- **EvalSuites are read uncached, by both controllers**, with the manager's API reader: the eval controller on every eval pass, and the Agent reconciler on every pass of a gated Agent, where the third promotion condition needs the suite's digest as read in that pass, `EvalSuiteNotFound` and `EvalSuiteUnreadable` come from the same read, and the gate branch computes the pair from it before a run exists. No EvalSuite informer is started, so an absent CRD cannot fail manager start, and the owed RBAC stays `get` alone. A cached read in either controller would start a cluster-wide EvalSuite informer and would need `list` and `watch`, which the owed role does not grant, so it would be refused on every gated Agent. *(A15, from the eleventh critique's m7. A13 pinned the eval controller's reader and left the Agent reconciler's unstated.)* Design 02 §3.3 requires a CRD installed after start to take effect without a restart, and this keeps that true. A suite edit is noticed on the eval controller's next pass. While a candidate is held with a final verdict, the controller requeues every `CardDriftInterval`, 5 minutes. That interval is the bound on noticing a suite edit that re-opens a held candidate. An EvalSuite watch, started when discovery first sees the CRD, is out of the slice. *(A4, from the critique's m4.)*

On Q1's option (a), the same run happens inside the Agent reconciler instead. The split above then collapses into one writer, and Q1 lists that option's costs.

#### How a run works

1. **When a run starts.** The eval controller starts a run when the shared predicates above hold, when no run and no final verdict exists for the pair of revision digest and suite digest, and when that pair is not in `status.eval.failed[]` (step 7, Q3).

    **A run start replaces the whole record of the previous pair.** Everything in `status.eval` that a run produces belongs to the pair `status.eval` records. When the pair a run starts for differs from the recorded one, one patch — the run-start write — accounts for every field of the table below:

    - it records `suite`, `revision`, `revisionDigest`, `suiteDigest`, `endpointPath` and `cardDigest` for the new pair;
    - it sets `verdict` to `Running`;
    - it clears `score`, `at` and `cases[]`, which the previous pair's run produced;
    - it leaves `failed[]`, which is keyed by pair and carries finality (step 7), and `blocked` and `blockedFor`, which every pass computes for itself.

    **`score` is why the clear cannot stop at the outcomes.** `api/v1alpha1/agent_types.go` renders it verbatim in the `Eval` printer column, so it is the default `kubectl get agents` output, and the safeguard the CRD names for a stale one — "`Revision` names what was gated, so a stale score is recognisable as stale" — is exactly what this patch would remove, because it moves `revision` and `revisionDigest` to the new pair in the same write. Left standing, the previous suite's score would show beside the new candidate for the whole re-run, with `at` carrying the previous verdict's timestamp and nothing marking either stale; and it would stand indefinitely if the candidate then became unavailable, because a paused run has no deadline (step 8). *(A15, from the eleventh critique's MAJOR 1. A13 cleared `cases[]` and `verdict` only, under a heading that claimed the record.)* Without the clear of `cases[]`, a suite edit — which Q3 makes the only re-run path — would find an entry for every suite `id`, left by the previous suite. No case would be sent, step 7's predicate would already be satisfied, and the run would either recompute a verdict from the old outcomes or never write one. *(A13, from the tenth critique's MAJOR 2.)*

    **The clears are not read back on their own**, and the read-back list (step 11) does not carry them. A merge patch expresses a clear as a null, and a stale CRD that prunes the field returns the same absence as a clear that applied, so no installed-CRD state exists that a read-back of a cleared field could tell apart. They ride in the patch whose set fields *are* read back, and are covered by it: on a stale CRD `suiteDigest`, `endpointPath` and `cardDigest` do not come back, and the pass stops before any case is sent. *(A15, from the eleventh critique's m5. A13 claimed a guard that cannot fire.)*
2. **The endpoint path, chosen once per run.** At run start, the eval controller fetches the candidate's card from its Service. It uses the eval client (step 4: no redirect followed, and `Proxy: nil`, so no environment proxy is used), not the card fetch's `fetchOnce`. It accepts the card only if its digest equals the digest `status.cards[]` records for the candidate's full digest, and it records that digest as `status.eval.cardDigest`, beside the path it takes from the card. Otherwise no run starts on this pass: the eval controller writes `status.eval.blocked`, reason `EvalAwaitingCard`, and the next pass tries again. *(A5, from the re-critique's n4 and N3.)* **Two causes share that reason, and the message distinguishes them**, because they are not the same finding: a card that was fetched and whose digest does not match the recorded one, and a fetch that did not succeed at all — a refused connection, a timeout, a body that does not parse — where no digest was compared. Reporting a mismatch for a refused connection names a check that was never made, the distinction step 6 already draws between `Unreachable` and `Interrupted`. The failed-fetch message names the error class, and that pass retries at `CardRetryInterval` rather than `CardDriftInterval` ("What wakes the eval controller while it waits"). *(A15, from the eleventh critique's m4.)* `cardDigest` is a record of where the path came from. The fourth promotion condition still accepts any recorded card digest: a card that drifts after the run changes nothing the verdict covers, and requiring the same digest would hold a passed revision because its card was redescribed. From that card it takes the first `supportedInterfaces[]` entry whose `protocolBinding` is `HTTP+JSON` and whose `protocolVersion` is `1.0`. The join: take only `url.Parse(entry.url).Path`, trim one trailing `/`, and append `/message:send`. A path of `""` or `/` gives `/message:send`, and `/a2a/` gives `/a2a/message:send`. An entry whose URL carries a query or a fragment is refused, as is a URL that does not parse. So is a card with no such entry at all. Each of these refusals is written to `status.eval.blocked`, reason `EvalBindingUnsupported`. The chosen path is recorded in `status.eval.endpointPath` and used for every case of that run, so a restart resumes against the same path. `status.cards[]` records no interfaces, so without this record the path would have to be re-derived from a card that may have changed. *(A4, from the critique's M3.)*
3. **Where the request goes.** To the candidate revision's Service, by its ClusterIP and `spec.runtime.port`, as the card fetch does (`internal/controller/card.go`), at `endpointPath`. The host and port in the card's URL are ignored: a card is written by the agent, and the operator sends nothing to an address the agent chose.
4. **No redirect is followed.** The eval client's `CheckRedirect` returns `http.ErrUseLastResponse`, so any `3xx` is `ProtocolError`. Go's default client follows up to 10 redirects, and on `307` and `308` it re-sends a `POST` body. So a candidate answering `307 Location: <anywhere>` would make the operator re-post the suite's message from the operator's own network position, and read one bit back. `internal/controller/authprobe.go` already refuses redirects this way. **The card fetch has the same hole today, for `GET`:** `fetchOnce` uses `&http.Client{}` with no `CheckRedirect` (`internal/controller/card.go`). Its fix is owed to design 02 §3.4, in a separate change that is not part of this slice. *(A4, from the critique's M4.)*
5. **What is sent.** One `SendMessageRequest` per case, as `docs/research/a2a-v1.0-card-and-transport-2026-09.md` §2 pins it: the header `A2A-Version: 1.0`; a `message` with a fresh `messageId`, `role: ROLE_USER`, and one text part carrying `cases[].message`; no `contextId`, so every case opens a fresh context; and no `configuration`, so the call blocks until the task is terminal or interrupted. **That last one is the protocol's default, not this design's choice**, and it is load-bearing: were it the other way, every case would come back `TASK_STATE_SUBMITTED` and step 6 would score it `fail`/`TaskNotCompleted`, failing every honest revision. The default is `SendMessageConfiguration.return_immediately`, a `bool` whose proto3 default is false, whose normative comment in `specification/a2a.proto` at `v1.0.1` reads "If `false` (default), the operation MUST wait until the task reaches a terminal (`COMPLETED`, `FAILED`, `CANCELED`, `REJECTED`) or interrupted (`INPUT_REQUIRED`, `AUTH_REQUIRED`) state before returning". §2 of the research document records it. `test/responder` is not cited for it: it is this repository's own fixture, and a fixture cannot corroborate a protocol default — that is the circularity `internal/controller/card.go` records as how a v0.x card shape survived here undetected. *(A15, from the eleventh critique's m8. A13 attributed the default to a §2 that listed `configuration` as optional and said nothing about omitting it.)* No credential is sent. The candidate is on no route, and design 03 puts `-auth` on the route, so nothing between the operator and the candidate asks for one.
6. **What a case's outcome is.** The answer text is every text part of `task.artifacts[].parts[]`, or of `message.parts[]` when the response is a message, joined by one space, in order. The body is read up to 1 MiB. Only `{id, outcome, reason}` is recorded, never the answer text.

   | Answer | Outcome | Reason |
   |---|---|---|
   | `200`; `task.status.state` is `TASK_STATE_COMPLETED`, or the response is a message; the answer text satisfies `expect` | pass | — |
   | the same, and the answer text does not satisfy `expect` | fail | `Mismatch` |
   | `200`, and the task is in any other state | fail | `TaskNotCompleted` |
   | any `3xx` (step 4), any other status, a body over 1 MiB, or a body that is not a `SendMessageResponse` | fail | `ProtocolError` |
   | a refused connection, or no answer within `caseTimeoutSeconds` | fail | `Unreachable` |
   | a claim found with no outcome (step 10), or a send cut short by cancellation | fail | `Interrupted` (Q11) |

   A case the candidate answered badly, or not at all, fails. The cost is that one network blip fails a good revision (Q3).
7. **The verdict, and the record of failed pairs.** Once every suite `id` has exactly one entry in `cases[]` **with a recorded outcome**, `score` is passed ÷ total. *(A12; tightened by A13, from the tenth critique's m5: a `Sending` entry is a claim in flight, not an outcome.)* The verdict is written in the same patch as that case's record, so it adds no patch of its own (A9, from the sixth critique's m3). The run passes when `passed × 1000 ≥ t × total`, where `t` is the threshold in thousandths. That is integer arithmetic, so no rounding decides a boundary. On Q3's recommended answer, a `Failed` verdict also appends `{revisionDigest, suiteDigest}` to `status.eval.failed[]`. That list holds at most 10 entries, and the oldest is evicted, the same cap as `status.supersededCandidates`. A pair in `failed[]` never starts a run again, reason `EvalPairAlreadyFailed`. So reverting a failed revision B to A and re-applying B does not re-run B. The record is bounded, and a re-run is still possible in two ways: after ten other failed pairs have evicted this one, or after any visible edit of the suite, which gives a new pair. Q3 states this. *(A4, from the critique's M1.)*
8. **An unavailable candidate pauses the run.** The rollout step's not-ready branches come before the gate. So a candidate that stops being available mid-run is sent no further case. Its recorded outcomes stay, and the run resumes at the next case by `id` once it is available again. It reads `GatesPassed=False/EvalPaused`, naming k of N. Nothing times a paused run out: a crashlooping candidate stays held for good, and that is fail-closed. This departs from §9, which fails "the crash cases": the slice fails only cases that were sent. A run-level deadline is out of the slice. *(A4, from the critique's m1.)*
9. **Pacing.** The eval controller sends one case per pass. After each case it patches the outcome into `status.eval.cases[]`, and returns `RequeueAfter: 5s` as a backstop. The next pass is driven by that patch: the controller's `For(&Agent{})` has no generation predicate, so its own status write enqueues the Agent again. It does not return `Requeue: true`, because that goes through the rate limiter, whose per-item backoff grows exponentially and is not reset while the run continues. *(A4, from the critique's m2.)* How each case is sent at most once is step 10.
10. **The send protocol: read, claim, send, record.** *(A5, from the re-critique's N1. A4 said a recorded case was never sent again, but the send came before the locked write. So a routine race with the Agent reconciler dropped an outcome and re-sent its case, and cache lag re-sent a case already recorded.)*
    - **Read live.** Before claiming, the eval controller reads the Agent with the uncached API reader. A pass that trusted the cache could see a recorded case as unrecorded.
    - **Keyed by `id`, not position.** The next case is the first suite `id`, in `id` order, that has no entry in `cases[]`. Claims and records find their entry by `id`, and the verdict requires exactly one entry per suite `id`. A reordered suite keeps its digest and its pair, so a pick by position could re-send a case whose outcome is recorded and never send another. Entries belong to the pair `status.eval` records, and a run start for a different pair clears them (step 1). *(A12, from the ninth critique's MAJOR 2; the pair scoping by A13.)*
    - **Claim.** It writes the next case's entry, `{id, outcome: Sending, claim: <nonce>}`, by a merge patch under the optimistic lock, with a nonce that is fresh for this send, and reads the claim back (step 11). A request follows only a claim that succeeded and came back. A claim that fails with `Conflict` sends nothing, and the next pass starts again at the live read. So a lost race costs a pass, never a second request.
    - **Send, on a context that shutdown does not cancel.** One request, as steps 3 to 6 say. It is sent synchronously inside the pass, never in a goroutine, because controller-runtime's `Start` waits only for its workers and would not wait for a goroutine. The claim before the send, the send, and the record after it all run on `context.WithoutCancel` of the reconcile context. The claim is bounded by 5 s, the send by `caseTimeoutSeconds`, and the record by 5 s including its retries. Immediately before the claim, the pass checks the reconcile context: once `ctx.Err()` is set, it claims nothing and returns. So no case is claimed after shutdown begins, and a claim that starts always completes. Between the cancel and the controller's call to `Queue.ShutDown()`, a worker that returns from a pass can still dequeue a queued Agent and run its reconcile on the cancelled context. After `ShutDown`, the default priority queue hands out nothing. So the check guards two kinds of pass: one already running between its live read and its claim when the cancel lands, and one that starts in the window before `ShutDown` (A8, from the fifth critique's s3; widened by A9, from the sixth critique's m6). *(A7, from the fourth critique's r1. A6 left the claim on the reconcile context, where a cancellation during its patch could commit the claim and lose the response, and gave no mechanism for "no new case".)* Controller-runtime cancels the reconcile context when the manager shuts down, then waits up to `GracefulShutdownTimeout` for reconciles in flight. Nothing in `cmd/` or `internal/` sets that today, so it is the default, 30 s. The slice owes setting it explicitly, to 30 s, in `cmd/operator/main.go`, with a unit test that it is at least 25 s, because a bound that rests on an unset default is rule 7's case (A7, from the fourth critique's r2). The chart's `terminationGracePeriodSeconds` is also 30 (`charts/assayd/templates/operator.yaml`). A claim, a case and its record take at most 5 s + 10 s + 5 s = 20 s, inside both. So a graceful stop lets the case in flight finish and record what the candidate answered. That covers every `helm upgrade`, drain and rolling update. A chart test is owed that keeps `terminationGracePeriodSeconds` at 25 s or more. *(A6, from the third critique's P2. A5 named no context. The obvious one, the reconcile context, would have failed the case in flight on every rolling update of the operator.)*
    - **Record.** It writes the outcome in place of `Sending`. On `Conflict`, it re-reads live and re-applies the outcome, but only while the claim still stands: the same `revisionDigest`, `suiteDigest` and `claim` at that case's entry, found by `id`, **and `outcome` still `Sending`**. The last condition stops an old leader, still finishing its send during a handover, from overwriting an `Interrupted` that the new leader wrote after it may already have computed the verdict. *(A6, from the third critique's m3.)* The eval controller is the only writer of `status.eval`, so a newer status written by the Agent reconciler never invalidates the outcome. A claim that no longer stands, because a new generation superseded the run, is dropped with the run.
    - **A claim found with no outcome** means the eval controller stopped between claiming and recording without a graceful stop. That is SIGKILL, an OOM kill, a lost node, a lease lost to a partition, or a record that exhausted its 5 s bound. Nobody knows whether the candidate received the request. Q11 decides what happens. On its recommended answer, the case is never sent again: it is recorded as failed, reason `Interrupted`, and counts against the threshold like any failed case. A send cut short by cancellation, which only a hard stop can now do, is also `Interrupted`, never `Unreachable`. `Unreachable` names a refused connection or a timeout that was observed. *(A6, from the third critique's P2 and m3.)*
    - **An ambiguous claim fails closed.** A claim patch that the API server commits, but whose response is lost (a timeout, a 5xx, a reset), is not a `Conflict`. That pass sends nothing. The next pass finds the claim with no outcome and records `Interrupted`, for a case the candidate never received. It costs what a hard stop costs, and it never sends twice. Keeping ambiguous nonces in memory, to send them later within the same process, is out of the slice. *(A6, from the third critique's m3.)*
    - **The eval controller is leader-gated.** It runs only in the manager that holds the lease. That is controller-runtime's default for a controller, and nothing in `cmd/` or `internal/` overrides it. At most once does not depend on it: the optimistic lock admits one claim per case, whoever makes it. *(A6, from the third critique's m3.)*
    - **A re-sent case is not assumed to be idempotent for the candidate.** A2A gives each message a client-chosen `messageId`, and this design does not rely on any agent de-duplicating by it. Every send carries a fresh `messageId`. So a case sent twice would be two tasks, with two sets of tool calls and spend. That is why the protocol claims first.
11. **The record must be kept.** *(A5, from the re-critique's N2.)* The new `status.eval` fields are fields of the **Agent** CRD, and `helm upgrade` never updates `crds/`. An Agent CRD that predates them prunes them without an error. Every claim would then vanish, and case 1 would be sent every 5 s for as long as the candidate exists, with no condition saying so. Two guards stop that:
    - **The eval controller reads back what it writes.** It reads back the fields its run-start write sets — `verdict: Running`, `suite`, `revision`, `revisionDigest`, `suiteDigest`, `endpointPath` and `cardDigest` — every `blocked` and `blockedFor` write, and every claim, from the object the patch returns, as design 03's `persistStatus` reads back `status.auth` (`internal/controller/authtxn.go`). If a field did not come back, it sends nothing, writes nothing more, and returns `RequeueAfter: CardDriftInterval`. The run-start write carries nothing that changes from pass to pass: `score` and `at` are cleared by it rather than written by it, and a clear carries the same value every time. So on a stale CRD, a repeated run-start write carries the same values, the API server stores no change, and no event re-enqueues the Agent. The cost is at most one card fetch and one no-op patch per gated Agent per `CardDriftInterval`, plus one more per other event on the Agent, such as the Agent reconciler's own status writes, until the CRD is applied. On a stable Agent those events are the card drift re-reads (A8, from the fifth critique's s4). *(A7, from the fourth critique's r3. A6 said only that the controller sent nothing, and the obvious reading re-fetched the card and rewrote status on every pass.)* This read-back is the eval controller's only guard against a stale CRD. It does not also check the schema, so each guard is pinned by a test of its own (A6, from the third critique's m1).
    - **The Agent reconciler names the cause.** A pruned write cannot carry the new fields, `blocked` included, so the eval controller cannot report the pruning through `blocked`. The older `status.eval` fields and the conditions do survive, and a run-start write that left `revisionDigest` naming the candidate with no `verdict` would betray a stale CRD. The slice checks the schema instead, because that names the cause before any write. On every pass of an Agent that declares a gate, the Agent reconciler reads the `agents.assayd.dev` CustomResourceDefinition. It checks that version `v1alpha1`'s entry in `spec.versions[]` carries, under `schema.openAPIV3Schema`'s `status.eval`, each of `suiteDigest`, `endpointPath`, `cardDigest`, `blocked`, `blockedFor`, `verdict`, `cases` (with `claim` in its items) and `failed`. `blockedFor` is in the set because the gate branch's fail-closed reading rests on it: without the field, every read of it is "absent", and an exempt `Lock` would report `EvalWaitingForAuth` for ever while clause 5 found nothing every 5 s. *(A13, from the tenth critique's MAJOR 1.)*
      - **The reader.** The read registers `apiextensions.k8s.io/v1` types in the operator's scheme, which registers none today (`cmd/operator/main.go`). `k8s.io/apiextensions-apiserver` is already a direct dependency. It uses the manager's uncached API reader behind a TTL cache like `EvalSuiteDetector`'s. So the Agent CRD, about 74 KB, is fetched once per TTL rather than once per pass, and no cluster-wide CRD informer is started. The operator already holds `get` on `customresourcedefinitions`.
      - **A missing field.** It sets `GatesPassed=False/EvalRecordNotKept`, with the remedy design 03's `AuthRecordNotKept` gives: apply this release's `charts/assayd/crds/` with `kubectl`, because `helm upgrade` never updates it.
      - **A failed read.** The last answer in the TTL cache stands, as the detector's does. With no answer cached, it sets `GatesPassed=False/EvalRecordUnverifiable`, naming the error.
      - Either way the candidate holds, which is fail-closed. *(A6, from the third critique's m2. A5 said a pruned write could carry no reason at all, and the older fields do survive.)*
    - Applying the Agent CRD's new status fields on upgrade is owed to design 07, beside Q7.

#### Promotion

The rollout step keeps its order (`internal/controller/agent_controller.go`): the not-ready branches, then the I1 hold, then the gate, then promotion. The slice changes only what the gate branch asks. Today, with a gate declared and the EvalSuite CRD installed, that branch holds with no exit, reason `GateControllerUnimplemented`. In the slice the gate is satisfied only when all four of these are true, read in the same pass:

- `status.eval.verdict` is `Passed`;
- `status.eval.revisionDigest` equals the desired revision's full digest (A2);
- `status.eval.suiteDigest` equals the digest of the EvalSuite as read in this pass;
- `status.cards[]` records a non-empty card digest for the desired revision's full digest. *(A4, from the critique's M6.)*

A satisfied gate is not a branch of its own. The gate branch's condition is "the gate is not satisfied", so a satisfied gate falls through to the promotion branch in the same pass, as a gate-free Agent does today. That pass is the Agent reconciler's first pass after the eval controller writes the `Passed` verdict, which its status patch triggers. *(A4, from the critique's m2.)*

**The fourth condition is new enforcement (Q10).** Today a card failure never withholds traffic (design 02 §3.4, `agent_controller.go`). Under the slice, a gated candidate with no recorded card cannot be promoted. That is because the card precondition at run start does not hold until promotion. The card is re-read every `CardDriftInterval`, and a failed re-read clears the recorded digest (`recordCardAttempt`, `internal/controller/card.go`). A run of 20 cases can span one such re-read. The fourth condition is what makes the guarantee in "How it composes with what exists" true at the moment of promotion.

If any condition is false, the candidate holds. The branch keeps its guard, `status.activeRevisionDigest != desiredDigest`. So adding a gate, or editing the suite, never evaluates the revision already serving. `gates` is on design 02's policy surface, so adding one mints nothing, and the serving revision is evaluated only if a later spec mints it again.

**A failed verdict holds the candidate. It does not delete it (Q2).** The phase is `Held`, and no route names the candidate, until a new generation supersedes it (design 02 §3.3) or the suite's digest changes. Design 02 §3.3's rollout step 5, and §4 step 5 here, say "candidate deleted". The slice cannot keep that: the desired spec still names the revision, so the next pass would re-create it and evaluate it again (below, "What design 16 says that the slice cannot keep").

**Two edits skip the gate, and the slice states both.**

- **Removing `spec.gates` promotes a held candidate on the next pass**, under `GatesSkipped=True/NoGatesDeclared`. The candidate may be one whose verdict was `Failed`. `gates` is on the policy surface, so removing it mints nothing, and anyone with `agents/update` can do it. Q9 decides whether that stays so.
- **A pin, `spec.release.targetRevisionDigest`, selects any retained workload that carries the pinned digest.** It does not check that the revision ever served (`resolveReleasePin`, `internal/controller/release.go`). A failed candidate is retained, because garbage collection protects `status.candidateRevision`. So without a rule, a pin to the failed candidate's digest would serve the revision that just failed, under a reason that calls it a rollback. Q5 gives the rule. *(A4, from the critique's M7.)* The rule applies only while a gate is declared. On an Agent with no gate, pins behave exactly as today (A5, from the re-critique's N5).

#### How it composes with what exists

- **`candidateRevision` and `activeRevision`.** As above. The candidate is recorded in `status.candidateRevision` and `candidateRevisionDigest` while it is evaluated and while it is held. At most one is in flight, as today.
- **A new Agent, and design 03's `Create`.** `Create` is entered only once a revision serves: while `status.activeRevision` is empty, the operator enters no `-auth` transaction and collects the Agent's routes (`internal/controller/authtxn.go`). So a new gated Agent is evaluated first, promoted on a pass, and only then prepared, given its policy, probed and published. A new Agent whose first revision fails has no route at all. Its time to first answer is the run plus `Create`.
- **A gated promotion while a `Create` is in flight is harmless.** `Create`'s probe is anonymous, against a prepared route with no `backendRefs`, so its `401` never depends on which revision serves. `Publishing` names `status.activeRevision` as it stands at the moment of publishing. *(A4, from the critique's "Verified sound".)*
- **The I1 promotion hold.** It comes before the gate, and no case is sent while it stands. Such a candidate cannot be promoted while the hold stands. The edit that fixes its `-auth` mints a new revision anyway, because `expose` is on the behaviour surface. So a run would be spent on a revision that can never serve.
- **A promotion during a `Lock` (J2, K2, and a missing policy).** The gate adds no ordering. A `Lock` works on the serving route. A J2 or K2 `Lock` keeps that route on the active revision, and a missing-policy `Lock` re-points it at `status.activeRevision` at `ProbingAfter` while that revision has a recorded card digest, and leaves it where it found it while it has none (design 03 A77; below, A9 as narrowed by A19). A held candidate is named by no route, so neither `ProbingBefore` nor `ProbingAfter` can reach it. J2's edit mints a revision, because `expose.a2a.auth` is behaviour surface, and on a gated Agent that revision is evaluated before it can be promoted. The `Lock` does not wait for the verdict, with one exception. A J2 or K2 `Lock` whose serving revision has no recorded card, whose before-state was not observed, and on which no Gateway-level or foreign-traffic hold stands, can finish only through a promotion. So the rule exempts it and lets the eval earn that promotion ("Who runs the eval", A7). Otherwise the verdict waits for the `Lock`: no case is claimed while a `Create` or `Lock` is recorded on the Agent. So at most one outcome, of the case in flight when the `Lock` began, can make the `Lock`'s status writes conflict ("Who runs the eval", A5 and A6). A run already under way pauses at its next unsent case, and resumes once the transaction is gone. A promotion can still happen during a `Lock`, when a verdict was already `Passed` before the transaction began: for example, a missing-policy `Lock` that starts while a passed candidate awaits its promoting pass. What follows holds for a J2 or K2 `Lock`, which re-asserts the route on the promoted revision. A missing-policy `Lock` moves the route too, but only at `ProbingAfter` and only while `status.cards[]` records a digest for `status.activeRevision` (design 03 A77): it then re-points onto the promoted revision and attributes on that revision's card. While that digest is missing it keeps attributing on the revision the route still names, and the route follows the promotion only after the `Lock` reaches `Served` and `reconcileServed` re-asserts it (A8, from the fifth critique's S1, narrowed by A19). That `Lock` is often entered in the promoting pass itself, after the switch, because `reconcileServed` checks the policy before it would re-ensure the route. If **neither** the revision the route still names **nor** `status.activeRevision` has a recorded card, the `Lock` never reaches `Served`. It is then the wedge under "Who runs the eval", with the same exits (A9, from the sixth critique's M1, narrowed by A19). A pass that lands while a `Lock` is short of `Served` is a promotion during a `Lock`, which design 03 §3.3.3 already handles: the promotion clears `beforeObserved` and `beforeRevision`, and a later `401` is credited only on the card digest `status.cards[]` records for the new revision. The fourth promotion condition guarantees that digest is recorded in the pass that promotes. It can still be cleared by a failed drift re-read afterwards. The `Lock` then fails closed, into `AuthLockUnverified`, as design 03 §3.3.3 specifies for an unattributable `401`. *(Corrected by A4, from the critique's M6. A3 said the run-start precondition guaranteed it, and it does not.)*
- **A Gateway-level auth policy (design 03 A75), and the gateway itself.** Eval requests do not cross the gateway. The candidate's own egress does: its tool calls and LLM calls go to `ASSAYD_GATEWAY_URL`. So a Gateway-level policy, a policy on the MCP listener, or a gateway fault in flight can fail a case whose answer depends on a tool. Neither digest covers that state, and on Q3's recommended answer the resulting `Failed` verdict is final for the pair. That is defensible, because the candidate is evaluated under the egress policy it would serve under. But it means the verdict depends on cluster state outside its binding, and Q3 carries the cost. A new Agent that passes its gate and then meets a Gateway-level hold on `Create` is promoted and stays unpublished, reason `GatewayAuthPolicy`, as today. *(Corrected by A4, from the critique's M5. A3 said a Gateway-level policy changed no case's outcome.)*
- **`GatesSkipped` and `GatesPassed`.** As the table says. The discovery rule stays: a failed discovery reads as "installed", so a gated Agent holds rather than promoting ungated.
- **Supersession.** A new generation abandons the run. Outcomes recorded for the old digest are dropped with it, and the new candidate starts at its first case. The old candidate is appended to `status.supersededCandidates`, as today. A failed pair stays in `failed[]` (step 7).
- **A pinned rollback, and a removed gate.** Q5 and Q9, above under "Promotion". As this design reads today's code, a pinned rollback holds with no exit whenever a gate is declared and the EvalSuite CRD is installed: the gate branch has no pin input, and the I1 hold does (`authHoldsPromotion`). The critique confirmed that reading by reading, not by running.
- **Card drift on a held candidate.** No new run. A card change without a spec change mints no revision (design 02 §3.4), and the verdict covers the revision's behaviour. A drift re-read that fails clears the digest, and the fourth condition then holds promotion until a re-read succeeds.

#### What the verdict proves, and what it grants

- **It proves** that the candidate container, at the digest named, answered the suite's cases as recorded, from inside the cluster, at the time recorded, under the gateway state its own egress met at that time.
- **It does not prove the production path.** Eval requests do not cross the gateway, the route's `-auth`, or any policy on the route. §1's promise, that a revision passes its EvalSuite "through the production path", is not kept by the slice (Q1).
- **The candidate's own egress is real.** Every revision gets `ASSAYD_GATEWAY_URL` (design 02 §3.2). A tool call the candidate makes while answering a case goes through the gateway to a real tool, with real side effects, and any LLM spend is real. No receipt records it. A suite must be written as if every case runs in production, because its tool calls do.
- **Eval traffic is distinguishable, and the gate does not defend against a dishonest image author.** Nothing marks an eval request. It still differs from production traffic: it comes from the operator's Pod, with no credential, and not through the gateway. An image written to cheat can answer the eval one way and production another. The gate catches regressions by honest authors. *(A4, from the critique's m9.)*
- **EvalSuite write is unauthenticated invocation of the held candidate.** Anyone who can write an EvalSuite in the Agent's namespace can make the operator send the held candidate up to 20 messages of their choosing per suite edit. Those messages skip the API key and the group check that `<agent>-auth` requires of every caller through the route. They drive the candidate's real tools and LLM spend, with no budget, and each case reads one bit back. Under Q2's recommended answer a failed candidate is held indefinitely, so it is a standing target. The same writer can also pass a revision by weakening its suite. Q6 decides who may hold that grant. *(A4, from the critique's M8. A3 said the messages reach "that author's own agent", which nothing enforced.)*
- **The operator becomes a second way in, at the network layer.** Design 07 A5.4 admits the operator's Pods to agent Pods for the card fetch, and says the eval runner "arrives through the gateway and needs no rule of its own". The slice falsifies that premise. A NetworkPolicy works at L4, so the card-fetch allow rule now also carries arbitrary A2A tasks. Design 07 A5.4's amendment is owed (below).
- **The operator becomes an A2A client.** It sends only to a Service it owns, at an address it reads from the API server, never to an address from a card or a suite, and it follows no redirect (step 4). `test/responder` records that the A2A client is design 08's, as `assayd invoke`. The slice adds a second one, inside the operator, limited to one method (Q1).

#### What design 16 says that the slice cannot keep

- **"Candidate deleted" on a fail** (§4 step 5; design 02 §3.3, rollout step 5) cannot be implemented as written. The reconcile is level-triggered, and the desired spec still names the deleted revision, so the next pass re-creates the workload and runs the eval again. The slice holds the candidate instead (Q2).
- **D2's "rerun-shopping structurally impossible"** does not follow from binding digests. Binding makes a rerun attributable, not impossible: §6's own flake policy retries infra-failed cases, and nothing in this design stops a second run on the same digests. ADR-0006 names retry-until-pass as a bias amplifier, and says handling it is unbuilt. The slice does not make the claim true either. Its record of failed pairs refuses an automatic re-run and an edit-free re-run of the same pair, for the last 10 failed pairs. A re-run still follows any visible edit of the suite. *(Corrected by A4, from the critique's M1. A3 said the slice made the claim true.)*
- **"Through the production path"** (§1) and **"the gate controller never proxies eval traffic"** (§4 step 2) both assume the candidate header route and a per-run identity, and neither exists. On Q1's recommended answer, the operator is itself the source of eval traffic.
- **Two references join a suite and an Agent**: `EvalSuite.spec.target.agentRef` (§3), and the Agent's `spec.gates[].evalSuiteRef` (design 02). Nothing says what happens when they disagree (Q8).
- **`threshold: 0.85` is a float** (§3), and controller-gen refuses float fields unless `allowDangerousTypes` is set. The slice uses a decimal string.
- **§10's first sentence** still gives the eval Job "the candidate-route credential (gate-controller SVID)". That is the identity model r1's MAJOR withdrew, and r2 asked for the sentence to be struck before ADR-0024 (`reviews/16-review.md`, R2-a). It is still there. It is outside the slice, and is recorded here rather than edited.

- **Q1 — Who sends eval requests, and from where?**
  - (a) The Agent reconciler itself, to the candidate's Service, one case per pass. No new controller. The costs, which A3 understated: a case holds the operator's only reconcile worker for up to 10 s, on top of that pass's card fetch (5 s) and `-auth` probe (5 s). Any tenant can trigger it, with an image that sleeps on `POST /message:send`, or by re-digesting a suite against a held candidate. With k such Agents, every other Agent's pass waits about k × 10 s, and another tenant's `Lock` can miss its 4-minute deadline and page. It also contradicts the rule the card fetch already follows, that one agent must not delay every other agent's reconcile. Choosing (a) would need a global bound on eval concurrency, and it would still take a worker away from Agents.
  - (a′) A separate eval controller in the same manager, with its own queue and two workers, writing only `status.eval` by merge patch, while the Agent reconciler only reads the verdict. It adds no pod, no image, no ServiceAccount and no verb, because the role already grants `patch` on `agents/status`; it needs only read on `evalsuites`, which every option needs. A slow tenant delays only other evals, by an amount that grows with the number of slow tenants, and never another Agent's reconcile, `Create` or `Lock`. On the evaluated Agent itself, the eval waits for a `Create` or `Lock` (above). The costs: two writers of one status object, kept apart by field ownership and optimistic locking (above); and the operator still becomes an A2A client, with no gateway on the path.
  - (b) A Job in the run namespace, to the candidate's Service. The operator holds nothing while a case runs, and cases can run longer than 10 s. The costs: a runner image to build, sign and pin; Job RBAC; a pod in a namespace where the operator is today the only pod author (design 02 §3.5's `pods-by` label); and a new ingress allow rule.
  - (c) Through the gateway, on design 03's candidate header route. This keeps §1's promise. The costs: design 03 work outside its approved slice, and an eval principal, which needs design 06 or a key the operator holds.
  - **Decided on 2026-09-14, as recommended: (a′).** It removes (a)'s cross-tenant starvation at the cost of a second controller in a process that already runs one, and keeps the smallest real gate. (c) is the next step, once design 03's candidate route is approved. *(Changed by A4, from the critique's M2. A3 recommended (a).)*
- **Q2 — What does a failed verdict do to the candidate?** (a) Hold it at zero traffic, with its workload kept for inspection, until a new generation or a new suite digest. (b) Scale it to zero replicas, and keep its material. (c) Delete it, as §4 step 5 says.
  - **Decided on 2026-09-14, as recommended: (a).** (c) loops, as above. (b) saves capacity, but a candidate at zero replicas cannot be inspected, and it needs a scale rule the rollout step does not have. (a)'s cost: the held candidate stays a target for Q6's invocation grant, and for a pin (Q5).
- **Q3 — What stops a failed pair from being re-run?**
  - (a) A bounded record: `status.eval.failed[]` holds the last 10 failed pairs, and a recorded pair never starts a run again. This refuses the automatic re-run, and the edit-free one: reverting a failed revision B and re-applying it.
  - (b) (a), plus §6's flake policy: a case that failed as `Unreachable` is retried once before the verdict, and only `Mismatch`, `TaskNotCompleted` or `ProtocolError` is final. `Interrupted` is never retried under (b), because the candidate may have received it (A6, from the third critique's m3).
  - (c) An explicit re-run field on the Agent.
  - (d) No record. Only the automatic re-run is refused, and A→B→A→B re-runs B.
  - What none of them stops, stated plainly: **a re-run always follows a visible edit of the spec or the suite, and nothing prevents retry-until-pass by edits.** A one-character change to the suite gives a new pair. So does a later failure that evicts the pair from the record.
  - **Decided on 2026-09-14, as recommended: (a).** ADR-0006 names retry-until-pass as the one property that distinguishes this gate, and says handling it is unbuilt. (a) makes every re-run a visible edit, which is the most the slice can promise. The known costs: a network blip, or a Gateway-level policy or gateway fault that fails a tool call in the candidate's own egress, fails a good revision for that pair. Its owner must then edit the suite to re-run it. (b) is the natural next amendment, once non-determinism is handled on purpose. *(Restated by A4, from the critique's M1 and M5. A3 said (a) made a verdict final for its pair, and nothing enforced that.)*
- **Q4 — One gate per Agent: how is it enforced?** (a) CEL caps `spec.gates` at one entry at admission. (b) Accept several, and hold any Agent with more than one, reason `MultipleGatesUnsupported`.
  - **Decided on 2026-09-14, as recommended: (a)**, because an error at apply time names the fix. An Agent stored with several gates before the cap keeps them under CRD validation ratcheting, and holds as in (b).
- **Q5 — Which pinned rollback is evaluated, and which is refused?**
  - (a) **Only while a gate is declared**, a pin is refused when its digest is the current candidate's, or appears in `status.eval.failed[]` paired with the **current** suite digest. The refusal goes through the existing unresolvable-pin path, reason `PinnedRevisionNotEligible`: nothing is rolled back, and the current release is untouched. Any other pin promotes, not evaluated, with `GatesBypassed=True`, reason `PinnedRollback`. On an Agent with no gate, pins behave exactly as today, and no `GatesBypassed` is set. *(Narrowed by A5, from the re-critique's N5. A4 also refused any digest in `supersededCandidates` and any failure against any suite. That refused revisions that had served: one that failed an older suite and later passed, and a served revision that was re-entered as a candidate and superseded.)*
    - What (a) still refuses that served: a revision that is the current candidate again after serving earlier, and a served revision that has since failed the suite now in force. The second is arguably right, because it fails the suite the owner declared. The break-glass for both is to remove `spec.gates` and then pin. Q9's recommended answer allows that, and it is recorded under `GatesPassed=False/NoGatesDeclared`.
    - What (a) still admits that never served: a retained candidate that failed only an older suite, or whose failure was evicted from the 10-entry record.
    - **When there is no current suite digest**, because the suite is `EvalSuiteNotFound` or `EvalSuiteUnreadable`, only the current-candidate refusal applies, and a digest in `failed[]` is admitted. Refusing would err closed, but it would let a deleted or unreadable suite block every rollback during an incident, which is when a rollback is needed. Under `GatesSkipped=EvalSuiteCRDAbsent` the rule does not apply at all, because nothing is gated. *(A6, from the third critique's m7.)*
  - (a″) (a), plus a bounded record of served digests, `status.eval.served[]`, so that a digest that was ever active is always admitted. That removes (a)'s first false refusal. It also admits a served revision that now fails the suite in force, and it adds a field.
  - (b) Every pin is evaluated like a candidate. That delays a rollback during an incident by a whole run.
  - (c) Only a revision with a recorded pass is served. That needs `status.revisions[]`, which is not on the CRD (ADR-0031 Amendment 1).
  - **Decided on 2026-09-14, as recommended: (a), and (c) once `status.revisions[]` exists.** Instant rollback is ADR-0019's reason for retaining revisions, and ADR-0031 Amendment 1 already records the gate-evidence check as unbuildable. A3's (a) promoted every pin, and would have served the candidate that just failed, under a reason that calls it a rollback. By this draft's reading, today's code holds a pinned rollback under a declared gate with no exit. *(Changed by A4, from the critique's M7.)* A5's (a) keeps instant rollback for every revision that is neither the candidate under evaluation nor a failure against the suite in force, with no new field, and leaves ungated Agents untouched. (a″) is the alternative if the human judges the served-candidate refusal too costly.
- **Q6 — Who may hold the grant an EvalSuite write carries?** An EvalSuite write sends the held candidate up to 20 unauthenticated messages per edit, drives its real tools and LLM spend with no budget, reads one bit back per case, and can pass a revision by weakening the suite (above).
  - (a) Anyone with RBAC on EvalSuites in the namespace, and the slice states the grant.
  - (b) An admission policy reserves EvalSuite writes to named principals, as `assayd-api-keys` reserves key sets.
  - (c) An admission policy admits an EvalSuite create or update only when the requester may also `update` `agents` in that namespace. It is written as a ValidatingAdmissionPolicy using Kubernetes' CEL `authorizer` library. An Agent editor already controls the candidate's image, so the grant adds nothing an Agent editor lacks. Deletes stay RBAC's, as they are for the policies design 07 already reserves.
  - **Decided on 2026-09-14, as recommended: (c).** It closes the gap between EvalSuite writers and Agent editors at apply time, with one admission policy and no reviewer workflow. (b) needs a principal list someone keeps. (a) leaves a namespace-wide grant of unauthenticated invocation. The re-critique measured (c) on envtest v1.36.2. It used a ValidatingAdmissionPolicy with `authorizer.group('assayd.dev').resource('agents').namespace(request.namespace).check('update').allowed()`, `failurePolicy: Fail` and a `Deny` binding. A user who may only write suites was denied. A user who may `update` Agents only under `resourceNames` was also denied, which errs toward refusal: an editor scoped to named Agents cannot write suites. A user who may `update` Agents namespace-wide was admitted. (c)'s minimum Kubernetes version is the chart's floor, 1.30, where ValidatingAdmissionPolicy is GA and carries the `authorizer` variable. It is unmeasured on 1.30 and on the e2e's k3s v1.33.6, and a test on the e2e's version is owed (below). *(A5, from the re-critique's n1.)* *(Reframed by A4, from the critique's M8. A3 framed Q6 as passing a revision by weakening its suite, and recommended (a).)*

  - (c) Ship it under `templates/`, behind a value. `helm uninstall` then deletes the CRD, and every EvalSuite with it.
  - **Decided on 2026-09-14, as recommended: (a).** An Agent that declares a gate has asked for one, and a fresh install should honour that. On upgrade, (a) and (b) behave the same, so the choice only matters for fresh installs. *(Costs corrected by A4, from the critique's m5. - **Q9 — Does removing `spec.gates` release a held candidate?** *(New in A4, from the critique's M7.)*

  - (b) A candidate recorded while a gate was declared must still pass it. Removing the gate affects only revisions minted afterwards. That needs a status marker on the candidate, and the owner can still reach an ungated revision with one more spec edit.
  - **Decided on 2026-09-14, as recommended: (a).** Anyone with `agents/update` can already change the image, so a gate is not a control against the Agent's own editor. (b) costs a status field and buys one extra edit. "At least one gate in prod" is the real control, and it needs the admission binding design 02 §5 records as unbuilt.
- **Q10 — Does a gated candidate need a recorded card to promote?** *(New in A4, from the critique's M6.)*
  - (a) Yes: the fourth promotion condition. This is new enforcement, because today a card failure never withholds traffic. A gated Agent whose card will not validate holds, `EvalAwaitingCard`, until it does.
  - (b) No: promote on the verdict alone. A revision promoted with its card digest cleared leaves a `Lock` on that Agent unable to attribute its `401`, so it fails closed into `AuthLockUnverified`.
  - **Decided on 2026-09-14, as recommended: (a).** The run already needs the card, for its path. Requiring it again at promotion costs nothing a gated Agent had, and makes the `Lock`'s attribution guarantee true when the promotion happens.
- **Q11 — A case that was claimed and never recorded: send it again, or fail it?** *(New in A5, from the re-critique's N1.)* A claim with no outcome means the eval controller stopped between sending and recording. Nobody knows whether the candidate received the request.
  - (a) At most once. The case is recorded as failed, reason `Interrupted`, and never sent again. It counts against the threshold, so a failing verdict it causes is recorded in `failed[]` like any other (Q3), and the owner must edit the suite to re-run.
  - (b) At least once. The case is sent again, with a fresh `messageId`. A candidate that received the first request then runs the task twice, with its tool calls and spend twice.
  - **Decided on 2026-09-14, as recommended: (a).** A case is a real task with real side effects, and the slice does not assume any agent de-duplicates a re-sent message. Only a hard stop leaves a claim with no outcome, because a graceful stop lets the case in flight finish (step 10). A hard stop mid-case is rare, and its cost under (a) is one suite edit. *(Corrected by A6, from the third critique's P2. A5 called any restart rare, and a rolling update is not.)*
- **Q12 — Does the eval keep waiting for a `Create` or `Lock` that is past its deadline?** *(New in A6, from the third critique's P1.)* A transaction past its deadline stays in its stage and keeps working (design 03 §3.3.3). It has already paged, and the Agent is `Degraded`.
  - (a) Yes. No case is claimed while any `Create` or `Lock` is recorded, whatever its deadline. The eval waits, indefinitely if the transaction never finishes, and `EvalWaitingForAuth` says when the deadline passed.
  - (b) No. Once the deadline has passed, cases are claimed again. The stuck transaction then competes with eval patches, and each overlap costs it a pass. A pass during the transaction can then promote a new revision, which clears a `Lock`'s `beforeObserved`.
  - **Decided on 2026-09-14, as recommended: (a).** A transaction past its deadline is an incident that is already paged. Promoting a new revision beside it changes what the gateway serves while the incident is open. (a) is fail-closed and simple. Its cost is that an Agent with a wedged `Create` or `Lock` gets no new revision until an administrator clears the cause. A J2 or K2 `Lock` that cannot attribute its `401` for want of a serving card, and is under no Gateway-level or foreign-traffic hold, is exempt from the wait (A7, narrowed by A8 and A10), so Q12 does not reach it. One held by such a policy is not exempt, before its deadline or after it, because the exemption reads the hold itself and not a condition reason (A10, from the seventh critique's M1). A missing-policy `Lock` whose route names a revision with no recorded card is not exempt. Since design 03 A77 a new revision **does** clear it, once that revision is `status.activeRevision`, its card digest is recorded, **and a pass reaches the re-point at `ProbingAfter`** — Q13's statement of the same behaviour, below, carries that last condition, and this one now matches it. What no new revision clears is the residue in which `status.activeRevision` has no recorded digest either, or in which a foreign `traffic` policy on `<agent>-serving`, a fresh NACK or a `Lock` short of `ProbingAfter` keeps every pass above the re-point. Its policy is in place, and only the proof of its `401` is missing. Its two exits — an administrator deleting `<agent>-serving`, and a revert — stand whichever answer Q12 takes, and since A77 the state also ends with nobody acting once `status.activeRevision`'s card records **and a pass reaches the re-point** (A8 and A9, narrowed by A19). **Q12's decision does not move**: (a) still holds the eval for any recorded `Create` or `Lock`, and the exemption still excludes re-creations. And the rule holds the eval only for a recorded transaction, not for an incident. A served Agent with no transaction recorded, under W1 (design 03 A75) or beside a foreign traffic policy, is evaluated and promoted while that incident is open, as an ungated Agent is (A11, from the eighth critique's m4). *(Corrected by A7, from the fourth critique's R1. A6 said this cost was already true under A75's hold. That was true only because of this slice's own rule: an ungated Agent under A75's hold still promotes.)*
  - **The cost recorded with the decision.** The wait covers recorded transactions, not incidents. A served Agent with no transaction recorded, under W1 (design 03 A75) or beside a foreign traffic policy, is evaluated and promoted while that incident is open, as an ungated Agent is. An Agent with a wedged `Create` or `Lock` gets no new revision until an administrator clears the cause.
- **Q13 — Is the missing-policy wedge accepted in this slice, or is it removed first?** *(New in A9, from the sixth critique's "Noted, not counted". Revised by A10, from the seventh critique's m3 and m4.)* The wedge is stated under "Who runs the eval". On a gated Agent, a missing-policy `Lock` whose route names a revision with no recorded card cannot finish. The Agent pages and is `Degraded`, and no candidate is evaluated, while the route's policy is in place and enforcing, but unproven.
  - **Its trigger is not always two events at once.** A card failure never withholds traffic (design 02 §3.4). So a revision can serve with no card ever recorded, if it was served ungated, served before the gate was added, or promoted by a pin or by removing the gate (Q9). On such an Agent a deleted policy alone produces the wedge, and no revert ends it.
  - **Leaving it standing can cost an outage.** When the route and the active revision are apart, garbage collection deletes R and its Service once three more revisions are minted. Authenticated callers then fail. *(Narrowed by A19, and not removed. Since design 03 A77 a carded `status.activeRevision` ends the apart state, but only once a pass reaches the re-point at `ProbingAfter`; the outage survives wherever none does — a foreign `traffic` policy **on `<agent>-serving`**, which breaks the pass at the foreign check with the stage left at `ProbingAfter`; a fresh NACK; or a `Lock` short of `ProbingAfter`, which one stored **at** `<agent>-auth` produces by failing the intact read — and wherever a failed drift re-read clears that digest first. The enumeration is corrected here by A19's fifth draft: `reviews/16-a19-critique3.md`'s MINOR 3 was applied at "Leaving it standing" and not at this bullet, and §14 recorded it applied at both.)*
  - (a) Accept it in this slice, with its exits stated: an administrator deletes `<agent>-serving`, or, for a transient card failure, the spec is reverted to the route's revision. Put a design 03 amendment through design 03's own process, separately.
  - (b) Amend design 03 first, so that the missing-policy `Lock` re-asserts the route on `status.activeRevision`, as J2's and K2's do, and make this slice's approval depend on that amendment.
  - (c) Amend design 02 §3.4 so that the Agent reconciler also re-reads the card of the revision the serving route names while a `Lock` waits on it. That ends the wedge for a transient card failure on a gated Agent, without touching design 03. It does not help a card that never validates.
  - **Decided on 2026-09-14, as recommended: (a), unchanged.** The administrator's exit works in every case today, including a card that never validates, with no change to another design. ## 2. Doctrine & charter gates

- **Plane**: slow (gate controller = part of the agent-operator; the *runner* is a provider slot, fast-plane images; datasets/metrics/thresholds are data).
- **Pods**: 0 standing — eval runs are **Jobs**; nightly runs are CronJobs. **Stateful deps**: Postgres (eval results — substrate per ADR-0002), object store (dataset + report artifacts). ✓
- **Primitives**: Resource (CRDs), Artifact (datasets/reports as content-addressed OCI artifacts), Agent (the runner drives real A2A tasks), Event (`eval.completed`). ✓ **EvalRunner joins the charter's reserved-slot list as shipped** (architecture §15 erratum, like IdentityProvider before it).

## 3. The EvalSuite CRD

```yaml
kind: EvalSuite
metadata: {name: pa-regression, namespace: claims}
spec:
  runner: {type: deepeval}                # evalrunner/v1 slot: deepeval | inspect | byo image
  target: {agentRef: pa-reviewer}         # what this suite gates (or modelRef, P5)
  dataset:
    goldenSetRef: pa-golden-v3            # curated + ontology-derived (§5); content-addressed artifact
    fromSessions: {sample: 200, since: 7d, strata: {by: hop_outcome}}   # design 17 sampler
  metrics:
    - {name: task_completion, threshold: 0.85}
    - {name: tool_correctness, threshold: 0.9}
    - {name: faithfulness_to_kg}          # mechanical: citations verified via kg.cite (§6)
    - {name: cost_regression, maxIncrease: 15%}
    - {name: custom_geval, judge: {model: gpt-x@pinned, promptRef: pa-judge-v2}}   # LLM-judge, pinned
  gate: {minScore: 0.85, blocking: true}
  budget: {tokensPerRun: 500k, usdPerRun: 5}    # the eval principal's own budget (ADR-0028 pattern)
status:
  lastRun: {report: oci://…@sha256:…, datasetDigest: …, judgeDigest: …, scores: {…}, verdict: pass}
  conditions: [DatasetReady, LastRunPassed]
```

**A revision reference is `{name, digest}` everywhere in this design (A2).** Design 02 A37 separated the two: the ten-character `name` is what a workload is called and what `kubectl get agents` prints, and the **full digest** is the identity. Forty bits is not a security boundary against an attacker-controlled projection — a chosen collision between a safe and a malicious spec was found in **1.2 seconds** — and this design is where that distinction earns its keep, because a verdict here is what grants production traffic.

Comparing a bare `revision` name would let a colliding projection be promoted on the verdict a different one earned, and that decision is made **before any workload is inspected**, so design 02's workload-level collision guard never sees it. The typed reference is therefore carried through every step below: the EvalRun input, the report's bound digests, `GatesPassed`, the candidate route's admitted principal, the events, and the receipt attribution. A step that carries only the name is a step where the gate can be spent on the wrong revision.

**Owed:** the `EvalSuite`/`EvalRun` CRDs do not exist yet, so this is a contract for the types when they are written rather than a description of a schema. Design 02 already carries the digest in `status.evalStatus.revisionDigest` and `status.cards[].revisionDigest`, which is the half that could be built without them (design 02 A50).

## 4. The gate flow (with design 02's rollout machine)

1. Candidate reaches `Held` (02 §3.3) → gate controller sees `gates:` on the Agent CR → `DatasetReady?` (build/refresh if stale, §5) → launches the **eval Job**. The controller reads `status.candidateRevisionDigest`, not `status.candidateRevision`, and the EvalRun records both (A2).
2. The Job drives **real A2A tasks through the gateway** at the candidate header-route. **Identity model (r1 f1)**: SVIDs are per-pod attested identities, never lent — the eval Job pod gets **its own SVID** via the existing label template (`spiffe://…/eval/<suite>/<run>`), and the compiler adds that principal to the candidate route's **admitted set at Job launch, removing it at Job end** — a narrow, temporary, compiled grant (the design 01 A2 pattern applied to routes; recorded as a design 03 row + ADR-0028 note). The gate controller never proxies eval traffic. **Runner trust bar** (runners are third-party pack images): signed image required (18), and the eval principal's compiled reachability is exactly {candidate route, pinned KG version, judge LLM egress} — fail-closed; the budget bounds the blast radius. Eval traffic exercises the identical path as prod, and every eval task produces **receipts** (§6).
3. Runner writes the structured report (per-case results + scores) → report artifact (content-addressed) + Postgres rows + CR status; verdict per §7.
4. **pass** → controller signals the operator, naming the **digest** it evaluated: the operator promotes only if that digest still matches its own candidate, so a verdict cannot be spent on a revision that changed underneath it (A2). Weight shift begins (canary steps). **Canary progression is judged on golden signals (SLOs), not re-evaluation** — the eval gate runs once, pre-canary; live-traffic degradation is the drift/SLO machinery's job (10/20). Stated to kill scope creep.
5. **fail** → candidate deleted (02), report linked in status + PR annotation; `GatesPassed=False` with the failing metrics named.
6. **Nightly**: CronJob runs the full suite against the *active* revision → trend rows (drift feed, 20); never gates.

## 5. The dataset builder

Datasets are **content-addressed artifacts** — a report always names the exact dataset digest it ran against (reproducibility is a first-class property):

- **Ontology-derived seeds**: design 12 §3.8 — one case per probe, `via` + matchers carried verbatim. These are *floor* cases (the graph's known answers, asked through the agent).
- **Curated cases**: `golden/` files in the agent's repo (the design-09 golden-task test is the seed), promoted via `assayd eval promote <session>`.
- **Session-derived cases** (17): stratified sample of recorded production tasks (inputs replayed; recorded outcomes as reference). Sampling is pinned at build time — the dataset artifact embeds the chosen sessions, so reruns are stable.
- Builder runs as part of the eval Job's first step (no standing pod); rebuilt when refs change or `since:` windows roll; `DatasetReady=False` names what's missing (e.g. zero sessions matching strata — loud, not empty-pass).

## 6. Metric semantics (the honest column)

| Metric | Source | Nature |
|---|---|---|
| `task_completion` | runner judgment per case (DeepEval agentic metric / matchers for ontology-derived cases) | judged (LLM for open cases, mechanical for `via`-matched) |
| `tool_correctness` | **receipts of the eval run** — normative v1 variant: **target-sequence match** (works at any capture level); argument-aware matching available when the eval posture captures bodies | mechanical |
| `faithfulness_to_kg` | every citation in the agent's answer resolved via `kg.cite` on the *pinned graph version*; uncited claims counted | mechanical |
| `cost_regression` | eval-run receipts vs the active revision's **trailing 7-day median per-task cost** (from the design-04 aggregate; window/statistic stated in the report) (r1 f4) | mechanical |
| `custom_geval` etc. | LLM-judge with **pinned model + versioned prompt**; judge config digest in the report | judged |

**Eval-principal posture is pinned independently of the agent's** (r1 f2): capture `full` on eval-principal traffic (reports store at receipt capture rules) and KG scope mirroring the target agent's — compiled with the temporary grant, so `kg.cite` resolves and argument-aware checks are possible. Judge calls go through the gateway under the eval principal (receipted, budgeted). **Flake policy**: infra-failed cases retry ×1; semantically-failed cases never retry (that's the signal). Agent stochasticity is bounded by convention (templates default eval-mode temperature) but not assumed: the verdict rule (§7) tolerates case-level noise via the threshold, not reruns-until-green — rerun-shopping is structurally impossible because the report binds (dataset digest, judge digest, candidate revision).

## 7. Verdict rule

`gate.minScore` applies to the **weighted mean of metric scores** (equal weights v1); each metric's own `threshold` is a hard floor — one floor breach fails regardless of the mean. Blocking suites hold the rollout (02); non-blocking suites annotate only. A suite with zero cases **fails closed** (`DatasetReady=False` — an empty eval must never pass an agent).

## 8. The `evalrunner/v1` slot

A runner is a Job image implementing: input `(dataset artifact ref, target endpoint + credentials, metric config, budget)` → output `(report JSON schema evalreport/v1: per-case {id, input_digest, outcome, per-metric scores, receipts refs}, summary scores)`. DeepEval adapter first (its `evaluate()` API maps directly); Inspect AI second; `byo` = any image honoring the contract. **`evalrunner/v1` and `evalreport/v1` join the `assayd-contracts` ledger** (design 07 §4 — r1 f3; the ledger carries every socket contract, and doctor/upgrade checks cover them). Conformance: a fixture dataset + mock agent where expected scores are known; parity across runners on the mechanical metrics (judged metrics are runner-specific by nature — documented, not hidden).

## 9. Failure modes

| Failure | Behavior |
|---|---|
| Runner Job crash | Job restart; per-case idempotency by case id (re-running completed cases is safe — results content-addressed) |
| Judge model unavailable | Judged metrics `error`, mechanical metrics complete; verdict **fails closed** with `JudgeUnavailable` named |
| Eval budget exhausted | Run halts; verdict fail-closed (`budget`); operator alert — an eval that can't afford to finish never passes anyone |
| Dataset refs missing/stale | `DatasetReady=False`, rollout stays Held, loudly |
| Candidate crashes under eval | Receipts show it; verdict fail with the crash cases named — that's the gate working |
| Nightly run fails | Trend gap marked; never affects serving |

## 10. Security

Eval Jobs hold: the candidate-route credential (gate-controller SVID), read access to the pinned KG version, the eval budget. They never hold prod user tokens (synthetic principals: `eval:<suite>@<candidate>` in receipts). Reports may embed prompts/outputs → stored at the receipts capture level, same redaction rules (ADR-0014).

## 11. Testing

Fixture agent (scripted A2A responder) + fixture suite: pass/fail/floor-breach/empty-dataset/judge-down/budget-exhausted paths; report reproducibility (same digests ⇒ same verdict); e2e on k3d: the flagship demo — `assayd deploy` streams `HELD → eval 0.89 ✓ → canary 10% → 100%`, then a deliberately-broken revision fails with the report in the PR annotation.

## 12. Decisions for async review

- **D1 — The eval gate runs once, pre-canary; canary progression is SLO-judged** (no re-eval mid-rollout) — scope pinned.
- **D2 — Datasets and reports are content-addressed artifacts**; a verdict always names (dataset, judge, revision) digests — rerun-shopping structurally impossible.
- **D3 — Fail-closed everywhere**: empty dataset, judge down, budget out ⇒ the candidate does not pass.
- **D4 — EvalRunner is a provider slot** (`evalrunner/v1`), DeepEval first, conformance with cross-runner parity on mechanical metrics.
