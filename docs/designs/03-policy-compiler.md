## 1. Purpose & scope

The single translation layer between assayd's declarative intent (Agent/Workflow/KG/App CR fields) and agentgateway v1.4.1 configuration. Everything the platform promises "at the gateway" — budgets, tool access, KG scoping, exposure, candidate isolation — becomes real here, so **apply-time behavior is part of this design, not a detail** (r1 finding 1). **Out of scope**: loop-governance semantics (design 22; mappings reserved), receipt pipeline and spend aggregation (design 04 owns; consumed here).

### 1.1 The first slice — the approval boundary

**Only this first slice can be approved for implementation. The rest of this document is specified, not approved.** The human decided this on 2026-09-11 (G, ADR-0034 Amendment 1). The later scope is critiqued again when design 02 makes it reachable. **Nothing is approved today, the slice included.** The slice is approved only when the human approves it after a passing critique, and no critique has read this section yet.

**What the slice is.** The agent-operator emits one `AgentgatewayPolicy` per Agent, named `<agent>-auth`. It carries API-key authentication and one CEL authorization rule (§3.4.4). It targets the per-Agent `<agent>-serving` `HTTPRoute` the operator already emits (§3.2, design 07 A6.10), and it arrives through the `Create` transaction. The route is published only after an anonymous request through it gets `401` (§3.3.3).

Two facts fix what the slice can reach:

- **The key source is a constant.** The slice compiles `configMapSelector: {matchLabels: {assayd.dev/api-keys: "true"}}` into the operator. There is no chart value and no flag for it. So no key-source change can arise, and D2 (§3.4.4) is unreachable.
- **The admitted set cannot change.** Today's CRD has no `allowedGroups`, and the slice does not add it. Every Agent admits exactly the group named for its namespace (§3.4.4), and a namespace is immutable. So group narrowing and widening, E2, F2's group semantics and D2's migration cannot arise.

One change to a served Agent's `-auth` is still reachable: its mode. It can move between the API-key policy and `auth: none`, or to `oauth`, which the slice cannot compile. The slice applies none of these to a served Agent. It keeps the last good `-auth`, which is the human's rule I1 (§3.3.1), and names the change it did not apply.

## 3. Interfaces

### 3.1 Input: `PolicyIntent` (internal, versioned)

```
PolicyIntent {                      // ONE revision's material, not one per Agent
  target:      {kind, ns, name}
  revision:    {hash, weight, candidate: bool}
  identity:    Binding<{spiffeID | oauthClientID}>   // a Binding like the others: a non-spec
                                                    // producer's output, so it needs a
                                                    // resolution state to seal and to compare
  tools:       [Binding<{backendRef, toolAllowlist, requiresApproval}>]
  knowledge:   [Binding<{endpoint, scope: {entityTypes}}>]
  llm:         {providers[]: Binding<EndpointID>, egressAllowlist?: [AllowEntry],
                fallback?: Binding<EndpointID>, fallbackActive: bool}
  // Binding<T> = {requested: string, resolved?: T, state: Resolved|ProducerAbsent|Unresolvable}
  //   an empty slice means "requested none"; it can never mean "resolution failed"
  // EndpointID  = {arm, <arm's instance fields>, model?}   — design 02 §3.1, §3.4.1.1 below
  // AllowEntry  = EndpointID minus model, plus optional models[]
  budget:      {tokensPerDay, usdPerDay, taskTimeout, maxHops}
  expose:      [{protocol, visibility, auth, allowedGroups?}]   // allowedGroups: §3.4.4, owed to design 02
                                    // -auth reads the CURRENT spec's auth and allowedGroups,
                                    //   never this revision's (§3.2, ADR-0034)
  apiKeySource: {configMapSelector}  // chart-level, declared; a live change is refused — §3.4.4.
                                    //   A compiled-in constant in the first slice (§1.1)
  gatewayReplicas: int          // declared, never discovered — see "Field provenance"
}
```

**One `PolicyIntent` per revision, not one per Agent.** An earlier shape carried `revisions[]` alongside a **single** `budget`, `expose`, `tools` and `llm` at Agent scope. That cannot express what the behaviour surface requires: with `budget` and `expose` on it, a change mints a candidate whose policy differs from the active revision's, and the active revision must keep serving its own until the candidate passes its gate. One global value cannot describe both at once — so a pure compile either rewrote R1's serving policy before R2 was gated, letting a widening reach production ungated, or preserved R1 and could not compile R2 at all.

So the operator constructs **one intent per live revision** — the active one, and the candidate if any — and `Compile` returns that revision's `ResourceSet`. **A revision's intent is not a revision's resources.** The serving `HTTPRoute` the operator already emits is **per Agent** (design 07 A6.10): a revision is a `backendRef` inside it, not a route of its own. So a revision's `ResourceSet` holds the resources §3.2's granularity table marks per-revision, plus that revision's `backendRef` entry on the per-Agent route; the route itself belongs to no single revision's set. The serving route's `-auth` is per Agent too (§3.2, ADR-0034). It belongs to no single revision's set, and it is compiled from the Agent's **current** spec, never from a revision's intent, so a rollback does not change it (§3.2). Two rules follow, and both are contract:

- **What is persisted is the revision's INPUT, not its output.** Freezing the applied `ResourceSet` under the revision hash is too broad in one direction and too narrow in the other: the set also encodes policy-surface fields and non-spec resolution state that are *supposed* to change without a new revision, so freezing it ignores legitimate edits — while rebuilding it from current spec violates the safety rule standing beside it. The operator persists a **`RevisionRecord`** per live revision and recompiles from that record plus an explicitly-owned live overlay, **never** from undifferentiated current spec.
- **The receipt backstop reads the *active* revision's budget**, not the current spec's. Otherwise raising a held candidate's budget from \$10 to \$100 would clear the active revision's `BudgetExhausted` hold before the candidate was ever promoted — the spend never moved, only an ungated field did. `originalBudget` below is what it reads; a rate reverse-engineered from a gateway policy cannot serve, because §3.5's derivation floors and is not injective.

**`RevisionRecord` — the durable contract.** This lives in `status.revisions[]` on the Agent, written by the operator under the revision hash.

Status rather than a `ConfigMap`, and the reason is not the one an earlier draft gave. That draft said design 02 forbids state outside CR status and the directory KV; checked against the producing document, design 02 names **operator-owned state** outright, including one `ConfigMap` per run namespace and a per-revision immutable copy of every referenced `ConfigMap` and `Secret`. A `ConfigMap` was never forbidden, so the choice needs its own reason and has one: **the record must be readable wherever the compiler runs.** Design 26's hard mode puts the run namespace inside the vCluster while this compiler is host-side with read on tenant CRs only. Status is reachable on both sides of that split; an object in the run namespace is not.

```
RevisionRecord {
  schemaVersion:   int         // which decoder/compiler this record was written for
  hash:            string      // the revision identity; the record's key
  behaviourProjection: bytes   // the EXACT projected input that was hashed (design 02 §3.3),
                               //   canonical-JSON, including resolved env-source content digests
  originalBudget:  {tokensPerDay, usdPerDay, taskTimeout, maxHops}
  resolvedInputs:  {inline: bytes}   // ABSENT until the seal. At the seal the operator writes
                               //   the canonical-JSON of every SEALED binding's resolved
                               //   output — tools[].toolAllowlist, knowledge[].endpoint,
                               //   identity. Nothing is stored while a value can still move
  sealedBindings:  [string]    // which declared bindings were Resolved at the seal. Per
                               //   binding, not per record: a revision can go active with
                               //   one tool resolved and another's producer absent
  appliedDigest:   string      // SHA-256 over the canonical ResourceSet last applied
  recordDigest:    string      // SHA-256 over the SEVEN fields above — schemaVersion, hash,
                               //   behaviourProjection, originalBudget, resolvedInputs,
                               //   sealedBindings, appliedDigest. An earlier comment said
                               //   "six" while the struct above it listed seven; the property
                               //   table below has always said "every field", which is the
                               //   rule, and the count here is now the same count
}
```

| Property | Rule |
|---|---|
| Ownership | the agent-operator alone writes `status.revisions[]`; no other controller has a field manager on it |
| Immutability | **two writes, and the second is what freezes.** At revision mint the operator writes the spec-derived fields — `schemaVersion`, `hash`, `behaviourProjection`, `originalBudget` — immutable from that moment, because they project a spec that already exists. `resolvedInputs` and `sealedBindings` are **absent** until the seal and immutable after it; `appliedDigest` is then the only field that may still change. A write that would change a sealed field is a bug, rejected by the operator's own precondition rather than trusted |
| **What may change after the seal** | `appliedDigest` alone. `resolvedInputs` and `sealedBindings` are written once, in the seal's status update, and `recordDigest` covers **every** field including both — so a forged seal, or a seal added to a record that never went active, is a digest mismatch and `RevisionRecordUnreadable` |
| Size bound | One record per member of design 02 §3.3's **retained set** — `revisionHistoryLimit + 2 + holds`, at least four at the default — and every field except `behaviourProjection` and `resolvedInputs` is fixed-width or a digest. **Neither of the two variable fields is an unbounded external catalogue**, and they are bounded for different reasons. `tools[].toolAllowlist` is a list field on an assayd CRD, bounded with `maxItems` exactly as `AgentSpec` is; **that bound is owed to design 11 and is not yet set** (ADR-0032 makes the field required with `minItems: 1` and deliberately sets no ceiling). `knowledge[].endpoint` and `identity` need no such rule — a URL and a SPIFFE ID are single bounded strings by construction, and design 06 issues the SVID rather than assayd declaring it. `resolvedInputs` therefore carries a stated **4 KiB** bound and `behaviourProjection` a hard **8 KiB** cap, each a compile error on breach. **Neither bound is enforced today; §8 owes both tests** |
| Schema migration | the record carries **`schemaVersion`, covered by `recordDigest`**. "A shape change simply changes the hash" holds for new candidates and not for **retained** ones: R1 stays active across an operator upgrade and its old record is what rebuilds a deleted gateway resource, so the new operator must still decode the old projection. A permissive decoder reads missing fields under new defaults and emits a *different* policy for R1; a strict one sends every retained revision down the corruption path on upgrade and cannot self-heal. `recordDigest` cannot arbitrate: it detects bytes changing, not which schema unchanged bytes are written in. The operator **retains an immutable decoder and compiler for every version that can still be in the retained set**, and an unsupported version fails as `RevisionRecordUnsupported` — *not* as corruption, because "written by a version I no longer carry" and "damaged" call for different human actions. Version retirement is bounded by the retained set |
| Corruption | `recordDigest` mismatch ⇒ `RevisionRecordUnreadable` (design 02's condition vocabulary), the affected revision is **not recompiled**, and what is already serving keeps serving. The operator does **not** fall back to current spec — that is the ungated-widening path this section exists to close. Human action is required and NFR-8 says the condition names it |
| Rollback lookup | design 02's rollback target is found by hash in `status.revisions[]`; a rollback whose record is missing or corrupt is refused with the same condition, because rolling back to material nobody can reconstruct is a guess |
| GC | a record is deleted when its revision leaves the **retained set** (design 02 §3.3) — *not* when it has left "all three roles". History entries and design 20 holds are not roles, and they are exactly why the bound is not three: a revision that has left active, candidate and named-rollback can still be held for an open incident or sit inside the history window, and deleting its record there makes the rollback the retention contract promises unreconstructable. Record, material and resource references are removed **atomically** in the same status write, so a record never outlives its revision and never precedes it |

#### The seal, and the two things about it that are not settled

**The seal is a transition, evaluated once.** At the single reconcile in which this revision's digest *becomes* `status.activeRevisionDigest`, every binding then in state `Resolved` is written to `sealedBindings`, and `resolvedInputs` is written in the same status update. Nothing seals before that instant and **nothing seals after it**. A standing "sealed when active and resolved" would re-evaluate on every reconcile, so an absent producer installed months later would flip the second half and seal its newly-arrived value onto a route that has been carrying traffic since — which is the hole this rule exists to close, re-entered through the fix for it. Per **binding**, not per record, because §3.3.1's failure is route-scoped.

**Why sealing is necessary at all, and the reason is not "these producers cannot mint a revision".** That was the earlier justification and it does not survive: `toolAllowlist` is a field on somebody's CR, which a person edits under review, so "cannot mint" is the wrong frame for it. The rule that actually holds, and covers all three sealed values:

> **An Agent's revision gate covers that Agent's spec and nothing else.** Any input resolved from outside it — another CR's field, an identity another system issues, an endpoint another design resolves — can move with no revision minted here. So the value the evaluation saw must be frozen at the seal and compared against, never re-read.

That is stronger than the wording it replaces. It explains why `toolAllowlist` needs freezing even though a human edits it under review — the review is of the Connector, not of this Agent's evaluation — and it still covers `identity` and `knowledge[].endpoint`.

**`sealedBindings`' key is per-kind, because one grammar for all three is not injective.** An earlier version used `<kind>/<name>` with `name` the binding's `requested` string, uniformly. That collapses for `knowledge[]`, where `spec.knowledge[]` carries `{name, version}` and two versions of one graph share a `requested` name, and it has no meaningful value at all for `identity`, which is a singleton with no name. A non-injective comparator key would be the fourth in this design's lineage and §3.5 records what the last one cost. The key is therefore:

| kind | key | why |
|---|---|---|
| `tools` | `tools/<requested>` | **rests on a uniqueness rule that does not exist yet.** An Agent binds a tool by bare name with no kind discriminator; design 11 §11 records that the cross-namespace-unique-tool-name rule four documents assume is written nowhere and enforced by nothing. Until design 11 declares it, this key is unique by assumption |
| `knowledge` | `knowledge/<name>@<version>` | both components come from `spec.knowledge[]`, so two versions of one graph are two keys |
| `identity` | `identity` | one binding per revision; a name would be ceremony |

**Two things about the seal are OPEN and the body states them rather than implying a working mechanism.**

- **The seal is an edge, and a level-triggered reconciler has no memory of the previous pass.** "Becomes active" is not a predicate a reconciler can evaluate from current state alone. Any implementable detector — comparing against a previously-recorded digest, or a generation watermark — seals **late**, on the reconcile *after* the transition, and what is resolved then may not be what was resolved at the instant of the flip. The gap is small and is not zero, and nothing in this design closes it.
- **The canary is an unsealed window on the production route.** Design 02 shifts `backendRefs` weight to a candidate before `activeRevision` flips, so the revision serves real traffic **unsealed**, with its bindings re-resolving on every reconcile. Everything the seal guarantees is absent for exactly the period a canary is designed to last. Either the seal moves to first-traffic rather than first-active, or the canary window is stated as ungoverned; **this design does not choose, and neither should a reader assume it has.**

**Where the sealed value lives.** One form: **inline in the Agent's status**, always. A value that would exceed 4 KiB is a compile error naming the binding and the measured size, refused *before* the seal — the seal is evaluated once, so a write refused after it could never be retried and the revision would carry a silently incomplete `resolvedInputs` for the rest of its life.

An earlier draft offered a second, by-reference form for values believed to be unbounded producer catalogues. No such input exists. The by-reference form was already unusable in the two cases that matter — an **external** Agent has no run namespace to hold the object, and in design 26's hard mode the run namespace is inside the vCluster while this compiler is host-side with read on tenant CRs only (design 26 §4/§7) — so it survived only for the soft-mode middle, carrying a size that does not arise. Dropping it removes a kind, a name-shape debt owed to design 02, and a one-MiB bound that was a producer's size expressed as assayd's.

**What one form leaves open, and it is design 26's seam rather than this one's.** `resolvedInputs` is written in the Agent's status, and design 26 denies the host-side compiler `agents/status` on tenant CRs — the reason that design's teardown handshake is a `ConfigMap` marker rather than a status field. The seal write belongs to design 02's operator, not to this compiler, and in hard mode that operator is the tenant's own inside the vCluster, so the write is reachable. But **no document states that division for the seal specifically**, and a sealed field nobody is named to write is not a specification. This belongs to design 26's owed hard-mode producer contract.

**The live overlay is the policy surface, and it is enumerated.** Recompiling an active revision reads its `behaviourProjection` plus exactly these current-spec fields: `runtime.replicas`, `runtime.port`, `runtime.resources`, `card.path`, `external.inlineCard`, `gates`, `loop`. Nothing else. The list is closed for the same reason the comparator registry is: a field that drifts into the overlay without being named here is an ungated behaviour change wearing a policy-surface label. The per-Agent `-auth` is absent from the list because it is not a revision's recompile at all. It is compiled once per Agent, from the current spec's `expose.a2a.auth` and `allowedGroups` and the chart's key source (§3.2).

#### Every binding carries its resolution state, because an empty slice meant two things

A resolved `tools: []` represented both *"requested no tools"* and *"requested a tool whose producer could not resolve it"* — opposite required outcomes, identical to a pure function, so an Agent asking for a tool it never got could compile as one asking for none and report `Ready`. Each binding arrives as `{requested, resolved?, state}`:

| `state` | Meaning | Compiler |
|---|---|---|
| `Resolved` | the producer returned an endpoint | emit the route class |
| `ProducerAbsent` | the producing design is not installed — **11 for tools, 01/13 for KG, 06 for identity**. An earlier version of this cell enumerated only the first two, so `identity` — declared a `Binding<T>` in §3.1 and marked "Available at P1? no" with design 06 as its producer in the provenance table — had no state this cell could report it in | **do not emit** — with `identity` the stated exception, because the not-emitted branch applies to a route class whose *entire* input set is unavailable, and the A2A serving route's is not. An absent design 06 leaves that route emitted with a mandatory `-auth` input missing **where the Agent chose `auth: oauth`** — the P1 mechanism is API keys (§3.4.4), whose input exists — which is §3.3.1's compile error and is what "Absent input and unbuilt producer are different things" two paragraphs below already says. The tier gap is reported once at operator level (§5) — *and* `CapabilityUnavailable` is set on **every Agent that requested a binding from that producer**, feeding the same required/optional aggregation as `Unresolvable` |
| `Unresolvable` | the producer exists and the name does not resolve | `PolicyCompileFailed` naming the binding — the Agent asked for something real and did not get it |

**An uninstalled producer is a fleet-level fact; a requested capability is an Agent-level contract.** Suppressing the per-Agent condition entirely was right for the noise it avoided and wrong for what it erased. With gateway governance on and design 11 absent, an Agent declaring its only critical tool had that route omitted, no `PolicyCompileFailed`, and could report `Ready=True` — while the binding was dropped *before* aggregation could classify its impact. A user reading that Agent sees no reason its advertised task cannot complete; only `assayd doctor` reveals the tier gap.

Both are kept. The operator-level report stays, so an uninstalled tier is stated once rather than on every Agent. `CapabilityUnavailable` is added per Agent **only where that Agent requested something from the absent producer**, which is bounded by the Agents that actually asked. It carries the same required/optional weight as `Unresolvable` — so under §3.3.1's aggregation it takes `Ready` to `False` — and its message names the producing design, because "not installed" is an operator action and NFR-8 says the condition names it.

`Compile` never sees an ambiguous empty list. A field whose source does not exist yet is **absent**, and absence is governed by §3.3.1 — it is never silently defaulted.

**Absent input and unbuilt producer are different things, and conflating them makes P1 uncompilable.** Read literally, the two rules above plus §3.3.1 say: `identity` is unavailable at P1 → the candidate route's `-auth` is mandatory with no opt-out → every Agent fails to compile, in the phase being implemented now. That is not the intent. The rule is:

- A route class **whose entire input set is unavailable because the producing design is not installed** is **not emitted at all**. No route, no policy, no error — there is nothing to govern and nothing serving.
- A route class that **is** emitted, with one mandatory concern's input absent, is the compile error of §3.3.1. This is the dangerous case: a route exists and a guarantee does not.

#### Whether the compiler runs at all is declared, not discovered

The chart carries `gateway.enabled`, rendered today as the operator flag `--gateway-enabled` (`charts/assayd/templates/operator.yaml`); it is also to become the agentgateway subchart's `dependencies[].condition` in `Chart.yaml` — **the subchart and the dependency block do not exist yet**, and that delta is owed to design 07. Expressed as a subchart condition rather than a free-standing boolean so the switch and the install cannot diverge by typo, and `true` + CRDs absent can only mean a genuinely broken install. Architecture §17 puts agentgateway at core tier, so it is `true` once design 07 ships the subchart; **until then the chart has no such dependency and `values.yaml` ships `false`**, which is what makes P1 the declared-off row rather than the broken-install row.

| `gateway.enabled` | Gateway CRDs | Compiler | Meaning | Behaviour |
|---|---|---|---|---|
| `true` | present | **present** | normal | compile and apply; a route is **published** only once its mandatory concerns converge (§3.3.1); `GovernanceSkipped` follows the clearing rule below. **The route and policy status reads this depends on do not exist today** (§3.2) |
| `true` | present | **absent — the operator that ships today** | a path without governance | emit the per-Agent serving `HTTPRoute` and nothing else; **`GovernanceSkipped=True`, reason `PolicyCompilerAbsent`**; `Ready` is not withheld, and route status is not read (`internal/controller/httproute.go`, design 07 A6.10). An earlier version of this table had no such row, and the operator wrote a reason the design did not carry. The row exists because a route shipped before a compiler did, and it goes when the compiler lands |
| `true` | **absent** | either | **a broken install** — someone declared the gateway and it is not there | designed: `GatewayIncompatible=CRDsAbsent` per Agent, **withhold `Ready`**, page (design 10). Fail-closed, because the operator's intent was governed traffic. **Interim, and what ships: the operator refuses to start** when `HTTPRoute` is not served (`agent_controller.go`, `SetupWithManager`). That is fail-closed and loud, and it costs more than the row asks: it freezes **all** reconciliation and **all** deletion fleet-wide, not only governance, and design 10's reason-keyed page can never fire because the condition is never written (design 07 A6.10, A6.11). It reads `HTTPRoute` only; **before any `AgentgatewayPolicy` is emitted it must also read `AgentgatewayPolicy`**, and `AgentgatewayBackend` before any Backend is — §5's row names the set |
| `false` | either | — | **a deliberately ungoverned tier** — what P1 ships and what `local` uses | compile nothing; every Agent carries **`GovernanceSkipped=GatewayDisabled`**; **`Ready` is not withheld**. A `true → false` **transition** is designed to run §5's reverse-order teardown first — this table is total over states, not over transitions. **That teardown is not implemented**: declared off, the operator emits nothing and sweeps nothing, so a route left by an enabled install keeps serving until the operator is re-enabled or a human removes it |

**When `GovernanceSkipped` clears, per Agent.** The condition is normal-true and owned, so it flips rather than vanishes (`conditions.go`). With the compiler running it is `False`, reason `Governed`, exactly when **every route the operator publishes for this Agent carries every mandatory concern §3.3.1's registry names for its class, each converged by §3.3.2's tuple at the current generation**. For `-auth`, converged also means that its probe passed (§3.3.3). The reason is `Governed` when the probe covered every declared gateway replica, and **`AuthVerifiedOnOneReplica`** when more than one is declared or the number is unknown (H2, ADR-0034 Amendment 1). Both are `False`, so neither withholds `Ready` and neither pages. It is vacuously `False` for an Agent with no published route: nothing reaches it through the gateway, and `Ready` carries why. It stays `True` while a published route lacks one — and by §3.3.1 only a route the compiler did not publish can: `PolicyCompilerAbsent` (no compiler at all) and `CompilerUpgradeUnsupported` (§3.3.3's refused `Adopt`, a route published before the compiler existed). A concern this build of the compiler cannot emit is not a hole in the predicate either. Its field is refused at admission — `spec.budget` is the one in the slice (below), which is ADR-0030 step 1's "unsupported capabilities rejected at the boundary" — and a stored object that predates the refusal is `PolicyCompileFailed`, reason `ConcernNotBuilt`, with that route not published. **A foreign policy does stop the predicate holding.** While a `traffic` policy the operator did not emit targets a published route, `GovernanceSkipped` stays `True`, reason `ForeignTrafficPolicy`, because two same-level policies on one target resolve at random (§3.2). **What `False` claims is narrow, and its message must say so**: control-plane convergence of the gateway path (§3.3.2), not dataplane enforcement, and nothing about direct Pod reachability (no NetworkPolicy is materialized, design 07 A6.6) or about where an agent's egress goes. Nothing implements this predicate yet.

Declared-but-missing is an incident. Declared-off is a documented tier. **They are different condition types, not two reasons on one type**, and the reason is the condition machinery rather than the consumers. A condition type is classified once, for the whole type, as **abnormal-true** — droppable, because its absence means "not degraded" — or **normal-true**, which must stay in the list and flip to `False`, because its absence is indistinguishable from "never evaluated" (`internal/controller/conditions.go`, `stickyTypes`). `GovernanceSkipped=True` is the **normal** state of a declared-ungoverned tier; `GatewayIncompatible=True` is an incident. One type carrying both has no correct classification: drop it when it stops applying and the record of the tier choice is erased; keep it, and an abnormal-true condition sits `True` on every healthy P1 cluster for the life of the install. The split is forced by how conditions are stored, not by how anyone reads them.

**This split was once justified by claiming design 10's alerts and design 08's `deploy` stream key on the condition *type*. That claim is false and is withdrawn.** Design 10 §5 keys on the **reason**, in those words and twice — "`GatewayIncompatible=CRDsAbsent` (page — a declared gateway is missing; keyed on the **reason**, at every profile …)" and "`BudgetEnforcementDegraded=ReplicaSkew`" — and design 08 states no keying rule at all, though its terminal-condition list at `08:84` is reason-qualified the same way. Both consumers could in fact discriminate two reasons on one type. The conclusion survives its refuted argument because the real constraint was never theirs, and design 10's own sentence carries the load independently: `GovernanceSkipped` "is never an alert". `GatesSkipped` and design 24's `ReBACAvailable` are the same shape for the same reason.

Only the incident withholds `Ready`, so a stock `helm install` never produces a fleet that is permanently un-`Ready` — and an operator who asked for a gateway and did not get one is never told everything is fine. `GovernanceSkipped` is loud rather than silent: the condition is on every Agent, the chart's `NOTES.txt` states that agents are ungoverned and names what is not enforced (`charts/assayd/templates/NOTES.txt`, design 07 A6.9), and `assayd doctor` reports it (design 08 §8).

**At P1, `gateway.enabled` is `false` — shipped so, not defaulted so — and the compiler does not run.** When it is turned on with a compiler, exactly one route class is emittable: the A2A serving route, **and its mandatory `-auth` input exists without design 06**, because the slice authenticates by API key (§3.4.4). The input is the chart's key source plus the admitted groups the Agent declares or, absent a declaration, derives from its namespace. An earlier version of this paragraph made `identity` the only `-auth` input and declared it absent until design 06, which made every route the operator already serves a `PolicyCompileFailed`: implemented as written, the compiler would have withdrawn every Agent from the gateway. An Agent whose stored `expose.a2a.auth` is `oauth` still has that absent input, and is `PolicyCompileFailed`, reason `AuthInputAbsent`, naming `spec.expose.a2a.auth` and the fix — `apikey`, or design 06. If that Agent is already served, it keeps its last good `-auth` and its route keeps serving (§3.3.1, I1). An earlier version of this sentence said "explicitly selects". No choice is needed: every stored Agent with an `expose.a2a` block carries `oauth` whether or not a person wrote it, because the API server persisted the old default (§3.4.4). The candidate header route's `-auth` admits one SVID (§3.3.1), so it too has no input until design 06; it is needed only once design 16's gate runs (ADR-0030 step 4), and supplying it is that step's work. Tool, KG and LLM egress routes have no producer at all until designs 11, 01/13 and 06 land, so they are the not-emitted branch.

**`spec.budget` is refused at admission while nothing enforces it.** The human decided this on 2026-09-11 (ADR-0034, B2). The slice compiles no `-ratelimit`, and design 04's spend aggregation does not exist, so a budget written today limits nothing, at the gateway or anywhere else. ADR-0030 step 1 rejects an unsupported capability at the boundary, and the boundary is admission. An earlier version of this design compiled the field to `PolicyCompileFailed` instead. That was loud but asymmetric: with `gateway.enabled: false` the same field was accepted and silently unenforced, and turning the gateway on made those Agents un-`Ready` (`reviews/03-a53-critique.md`, "The three calls"). The refusal is removed in the change that ships enforcement.

- **Owed to design 02**, as CEL on `AgentSpec` so that the error names the fix: `!has(self.budget)`, with the message `spec.budget is not enforced yet: no gateway rate limit and no spend backstop exist (ADR-0030 step 1). Remove spec.budget; it is accepted again when design 03's -ratelimit and design 04's spend aggregation ship.` Design 02 is not edited here.
- **Stored Agents that already carry `budget` still reach the compiler.** Each is `PolicyCompileFailed`, reason **`ConcernNotBuilt`**, naming `spec.budget` and the same fix, and its serving route is not published. A served Agent that gains `budget` keeps its last good `-auth` and keeps serving (§3.3.1, I1). For a route published before the compiler existed, `Adopt` (§3.3.3) is evaluated first and wins, because it compiles nothing.
- **Unmeasured**: whether an update that leaves a stored `budget` unchanged is admitted depends on the API server's CRD validation ratcheting, which this project has not tested. The compile-time backstop covers both answers.

**`llm.egressAllowlist` is therefore not compiled at P1 either** — it rides the LLM egress route. It is nonetheless **classified as behaviour surface by design 02 and projected into the revision hash**, because gating it is the revision projection's job and does not wait on this compiler. That classification was itself a finding: design 02's original table classified `llm.providers` and `llm.fallback` and never named `egressAllowlist`, the projection dropped it, and a differential mutation confirmed two specs differing only in that field hashed identically. Widening an agent's egress allowlist changes what it can reach — which is what the behaviour surface *means*. The classification test missed it because it reflected over `AgentSpec` while the field lives one level down in `LLMSpec`: classification has to be **leaf-level**, not top-level. Recorded here because this design consumes the field; the projection and the rule belong to design 02.

#### Why `gatewayReplicas` is declared rather than read from the gateway Deployment

It is the divisor on every emitted rate limit (§3.4), so a wrong value under-enforces by exactly the factor it is wrong by. Discovering it by watching the Deployment would make one HorizontalPodAutoscaler event recompile the rate policy of every Agent in the cluster — an unbounded fan-out this design does not size. Declaring it keeps compilation pure and keeps a gateway scale event from touching any Agent's resource set.

**This reverses a review resolution, and says so.** `reviews/03-review.md` R2-a required both that `gatewayReplicas` be declared *and* that "a gateway scale change triggers recompile of all rate-limit policies (else the ÷replicas approximation silently drifts)". The first half is kept and the second is reversed: there is no recompile. The drift R2-a worried about is real and is not eliminated — it is made **visible** instead of corrected, via the `BudgetEnforcementDegraded=ReplicaSkew` row in §5. That is a deliberate trade of automatic correctness for a bounded blast radius, and a human should weigh it rather than find it.

The claim is *not* that the blast radius is zero: §5 has the operator observing the gateway Deployment read-only, which is a cluster-wide watch. What is bounded is that the watch never rewrites policy — it only sets a condition.

### 3.2 Output & naming

**Where each resource lives, and what owns it.** Design 02 §3.2 puts an Agent's workload, its Service and its revision material in `assayd-run-<agent-namespace>`, and requires the **route to move with the Service** rather than staying behind. This section is where that becomes implementable.

| Resource | Namespace | Why |
|---|---|---|
| `HTTPRoute` (revision weights, candidate header route, expose routes) | **run namespace** | a `backendRef` to a Service in another namespace needs a `ReferenceGrant`, and without one the route reports `Accepted=True` with `ResolvedRefs=False, reason: RefNotPermitted` — while §3.3.2's convergence tuple requires `ResolvedRefs=True` before `Publishing`. Leaving the route behind wedges **every Agent at every install**. Emitting a `ReferenceGrant` instead is foreclosed by design 02 §3.1, which puts cross-namespace consent out of scope until a design specifies it |
| `AgentgatewayBackend` (tool/KG/LLM) | **run namespace**, beside the route that references it | same rule: a Backend reference is namespace-scoped |
| `AgentgatewayPolicy` × N | **run namespace**, beside their `targetRef` | a policy attaches to a route and they cannot be split across namespaces. Confirmed against the API: `AgentgatewayPolicy.targetRefs` "selects one **same-namespace** object", so this is the CRD's own constraint and not only a convention |
| Gateway-scoped tracing policy (§3.4) | **the gateway's own namespace** | it targets a Gateway, is emitted once per Gateway by a single owner, and has never been per-Agent |

**The gateway's namespace is not the operator's, and conflating them breaks a security control.** Design 07 A6.2 measured this: the admission policy that reserves route authorship compared a route's `parentRef` against the namespace the *operator* runs in, so moving the Gateway elsewhere made the reservation match nothing and silently admit any author. The chart now carries `gateway.namespace` as a value distinct from `.Values.namespace`. Anything in this design that reasons about "the gateway's namespace" means that value.

**Ownership is a label, not an `ownerReference`.** A namespaced dependent whose owner is in another namespace has the reference **treated as absent**, and the API server emits an `OwnerRefInvalidNamespace` warning Event — so setting one would leak every emitted resource silently while looking correct. Design 02 §3.2 makes the same move for revision material and for the same reason.

So every emitted resource carries `assayd.dev/agent-uid`, and every resource that follows one revision carries `assayd.dev/revision`. The shipped serving route stamps the revision it is written for (`servingRouteFor`). The per-Agent `-auth` stamps none, because it follows the Agent's current spec and belongs to no revision (§3.2, §3.4.4). And — exactly as design 02 §3.2 requires for workloads — **the label is not the deletion authority**. A label is writable by anyone with `update`, so the sweep additionally requires the resource's NAME to match the deterministic shape below, which is the one property an attacker cannot forge because Kubernetes names are immutable. Nothing is deleted that fails both checks; it is logged instead.

- **Garbage collection** is therefore the operator's, not Kubernetes': design 02 §3.7's finalizer revokes routes in reverse apply order and then deletes the run-namespace resources, and a label-and-name sweep runs every reconcile so a crash between emitting a resource and recording it leaves something sweepable.
- **Status ownership**: the operator writes only the Agent's status, and nothing else has a field manager on the emitted resources. **Reading route, Backend and policy status is owed, not present.** The operator does not read route status today (`internal/controller/httproute.go`, `agent_controller.go`), so a route the listener rejects leaves its Agent `Ready`. That read is the first thing §3.3.2's barrier needs, and nothing in §3.3 works without it.
- **The watches are owed too.** Today the operator watches `HTTPRoute` alone, only when the gateway is enabled, and maps an event to its Agent by the `assayd.dev/agent` and `assayd.dev/agent-namespace` labels (`agent_controller.go`, `SetupWithManager`). An earlier version of this bullet said it already watched all three kinds, keyed on `assayd.dev/agent-uid`; neither half was true. The compiler needs an `AgentgatewayPolicy` watch before it emits a policy and an `AgentgatewayBackend` watch before it emits a Backend — each registered only when its CRD is served, for the reason the route watch is conditional — plus a watch on Warning Events in the Gateway's namespace for the NACK (§3.3). The mapping key is the shipped one, because a run namespace holds many Agents' objects and an object's own namespace identifies none of them.

**RBAC, and what is actually granted today.** `httproutes` is granted `create, delete, get, list, update, watch` and **no `patch`** (`config/rbac/role.yaml`); design 07 A6.11 removed `patch` and `httproutes/status: get` because no code called them. This compiler needs the same six verbs on `agentgatewaypolicies`, and on `agentgatewaybackends` once it emits a Backend. It does **not** need `patch`, because it writes by create/update over owned fields rather than server-side apply (below). It also needs `get, list, watch` on `events` for the NACK, where today only `create, patch` are granted. An earlier version of this paragraph listed `patch` among the verbs and presented the `httproutes` grant as the part already in place — a compiler built to the SSA stage table it then described would have been refused by that grant. None of these land ahead of the code that uses them, because a verb granted ahead of its consumer is a standing privilege with no consumer. The `create` on Namespaces that design 02's run namespace needs is granted and is a real escalation, named in design 07 A5.7 rather than buried in a generated file.

**Authoring a route is a reserved capability, and this compiler is the reserved identity.** A route attaching to the assayd Gateway publishes a path to a workload, so anyone who can author one can publish an ungoverned path. Design 07 A5.9's `assayd-gateway-routes` admission policy therefore refuses any author but the operator's ServiceAccount. Two consequences for this design: the compiler must run **as that identity** — it is a library inside the agent-operator (§2), so it does — and a future out-of-process compiler would need adding to that policy, not merely granting RBAC. Design 07 A6.1 records the failure mode when only one half is in place: the operator passed the admission policy and was then refused by RBAC that granted no `httproutes`, and neither half was wrong on its own.

**The Gateway listener must admit the run namespaces.** A Gateway's listener carries `allowedRoutes.namespaces`, and a route in a namespace the listener does not admit is rejected — silently from the client's side, as a 404 — so a listener admitting only its former set would wedge every moved route. The Gateway must set `allowedRoutes.namespaces.from: Selector` matching `assayd.dev/run-namespace: "true"`, a label design 02 §3.2's operator stamps at creation and which design 07 A5.9's second admission policy reserves to the operator, so a tenant cannot mint an admitted namespace. **Today only the e2e harness's Gateway sets it** (`hack/e2e.sh`), because the chart ships no Gateway.

**This is measured, not inferred** (design 07 A6): an agent answered a request through a real Gateway on that exact listener rule, and the negative control — a non-operator identity attempting to attach — was refused by the named policy. A route's `parentRef` to a Gateway in another namespace needs no `ReferenceGrant` — only `backendRef`s and Secret references do — so admitting the run namespaces on the listener is the whole of the cross-namespace consent this move needs. **The Gateway object itself still arrives with the agentgateway subchart, which the chart does not carry** (design 07 A1); the e2e's Gateway is created by its harness.

Deterministic resource set, ownership by label, **written by create/update over owned fields and not by server-side apply**: `HTTPRoute`s (revision weights, candidate SVID-bound header route, expose routes), `AgentgatewayBackend`s (tool/KG/LLM), `AgentgatewayPolicy` × N — **one concern per policy** (`-auth`, `-ratelimit`, `-toolfilter`, `-guard`, `-transform`), disjoint fields, compiler-side conflict check.

**Why one concern per policy, and the honest reason is worse than "undocumented".** The original argument was that agentgateway's same-level merge semantics on identical fields are not crisply documented, so splitting concerns avoids the ambiguity by construction and yields reviewable diffs. **Read from source, the answer is sharper**: same-level conflicts iterate a randomly-seeded `HashSet`, so the winning policy varies **per replica and per restart** while both report `Accepted` and `Attached`. One concern per policy is therefore **load-bearing, not a diffability preference**, and no reproducing test is owed — the source is the evidence. Anything in this document that describes it as resting on diffability is wrong and is superseded by this paragraph.

**A second `traffic` policy on an emitted route is detected, because one concern per policy binds only the compiler.** Anyone who can write an `AgentgatewayPolicy` in a run namespace can target `<agent>-serving` with their own `traffic.authorization`. Both policies then report `Accepted` and `Attached`, while the winner varies per replica and per restart. Nothing prevents that write today (§6), and `test/e2e/authz_test.go` does exactly this, hand-authoring `assayd-e2e-authz` on the operator's route. So, before `-auth` ships, the compiler lists the `AgentgatewayPolicy` objects in the run namespace that carry `traffic` and whose `targetRefs` name `<agent>-serving`, or whose `targetSelectors` match its labels. Any that is not the operator's `<agent>-auth`, judged by the name-and-label rule above, is reported:

- `PolicyApplyIncomplete`, reason **`ForeignTrafficPolicy`**, naming the policy. `GovernanceSkipped` stays `True` with the same reason (§3.1);
- a route not yet published is not published. That hands the policy's author a switch over new Agents, and it is accepted: the author already controls what the route admits, and publishing under two policies whose winner is random would claim an `-auth` the gateway may not apply;
- a published route is **not withdrawn**. Whoever can write a policy in a run namespace already controls what the route admits, and withdrawing on their write would hand them a switch that takes the Agent off the air. The condition, `Ready=False`, and design 10's page on `PolicyApplyIncomplete` open for more than 5 minutes make it loud instead;
- the compiler never deletes it, because it fails the name check;
- `Narrow` trusts no probe while it is set (§3.3.3). The winner of two same-level policies varies per replica, so a probe answer says nothing about which one served it. A `Narrow` that starts or is under way still writes the operator's narrowed `<agent>-auth`, because a revocation should reach whatever replicas take it. It then holds at `ProbingAfter` without evaluating, and status does not claim the narrowing. When the foreign policy goes, `ProbingAfter` runs under §3.3.3's re-entry rule. So a foreign policy holds every promotion whose edit narrowed groups (§3.2's ordering), and still does not take a serving Agent off the air.

**Detection covers route-level targets only**: `targetRefs` naming `<agent>-serving`, and `targetSelectors` matching its labels. The CRD also admits `traffic` policies that target a `Gateway` or a `ListenerSet`. Whether a Gateway-level `traffic.authorization` merges with the route's `<agent>-auth` or is overridden by it is unmeasured, so such a policy is neither detected nor claimed harmless. `make conformance-cluster` owes the case (§8.1).

The e2e's hand-authored policy must become the emitted one when `-auth` ships, and that is owed to design 07. So is the reservation that would refuse the write in the first place (§6).

**Why create/update and not SSA.** The shipped emitter writes the serving route by create/update and detects drift by comparing every field it writes (`ensureServingRoute`, `equalRoute` in `internal/controller/httproute.go`) — AGENTS.md rule 6: own the fields, then compare exactly. The compiler uses the same pattern for every kind. Server-side apply would need `patch`, which is not granted. And on the per-Agent route, an apply that omitted `backendRefs` under the operator's field manager would remove the serving revision's entry: the Agent would go off the air so that a candidate could be prepared. §3.3's `PreparingRoute` is restated for that reason.

#### Which resources are per Agent and which per revision

The serving route is **per Agent**. It is named `<agent>-serving` and is one object whose single rule's `backendRefs` move between revisions in place. This design **adopts** that choice rather than refuting it, because design 07 A6.10's reason holds: a route per revision puts two routes on one hostname for every rollout, and a listener merges them, so the revision being rolled out takes production traffic with no weight shifted. Deleting the old route first leaves the hostname unrouted instead. Every other resource is placed by one test: can two live revisions need different values of it at the same moment?

| Resource | Granularity | Name | Attachment | State |

Two same-level policies on one target resolve through a randomly-seeded `HashSet` (above). An earlier version of this sentence owed a case proving that two live revisions' `-auth` never share a target. Once there is one policy, that holds by construction, and it misses the property that matters for a per-Agent target.

##### The serving route's `-auth`: per revision or per Agent

**Decided by measurement: `-auth` is ONE policy per Agent, `<agent>-auth`, and it targets the per-Agent serving `HTTPRoute`.** The preferred shape was a per-revision policy on each revision's own Service, so that auth would ride the revision's candidacy. agentgateway 1.5.0's CRD refuses it: a policy carrying `traffic` may target only a Gateway, ListenerSet, GRPCRoute, HTTPRoute or InferencePool. That refusal was reproduced by server-side dry-run against a route-targeted control (`research/agentgateway-service-target-spike-2026-09.md`). A rule-level target cannot separate revisions that one rule weights between, and a per-revision route reopens the two-routes-one-hostname window A6.10 closed. So this fallback is what remains. **The rule is not new at 1.5.0.** The same CEL rule is in the vendored 1.4.1 CRD (`test/conformance/testdata/agentgateway-crds-1.4.1.tgz`, `agentgateway.dev_agentgatewaypolicies.yaml:10101`). `reviews/03-a53-critique.md` found it there, and it was re-read for this section. `make conformance` owes a case asserting it over the vendored CRD, so that ADR-0034's "revisit at the next agentgateway upgrade" is a test that fails rather than a reminder (§8.1).

**What keeps a per-Agent policy safe across a rollout: it follows the Agent's current spec, never a revision.** The human decided this on 2026-09-11 (ADR-0034, F2).

- **The admitted set is the current spec's.** `<agent>-auth` admits exactly the groups the Agent's current `spec.expose.a2a.allowedGroups` declares, or §3.4.4's derived default, under the key source recorded in `status.auth` (§3.3). No revision's record is read. Every revision carrying weight serves under that one policy, the canary included.
- **A rollback changes no auth.** A pinned rollback (`spec.release.targetRevisionDigest`, `internal/controller/release.go`, ADR-0031) restores a revision's workload material and nothing else. A group the current spec removed stays refused, whichever revision serves. So a rollback runs no `Narrow` and no probe, and its weight shift waits on no auth transaction. This is ADR-0031 Amendment 1's "recheck non-optional current security constraints", applied to groups: a group an administrator removed is a current access decision, not release material. The same amendment's "never recompute the target from current spec" governs a revision's retained material, and `-auth` belongs to no revision.
- **Narrowing is verified before the edit's revision takes weight.** An edit that removes a group runs `Narrow` at once, to the groups the applied set and the new set share (§3.3.3). A revocation does not wait for a gate. If the same edit also mints a revision, that revision gains no weight until `Narrow` reaches `Served`. *(Corrected by A56. A55 gave a reason: a release which narrows its audience may be safe only for the narrower one, for example a new skill fit for `audit` and no one else, so the release and its audience change land together. That reason does not hold, and the fifth critique's M4 is **OPEN**. Under E2, below, the removed group keeps access to the new release until `Narrow` reaches `Served`. Under F2, a pinned rollback serves an old revision's skills to the current admitted set. So this design does not promise that a release and its audience change land together. The choice between holding the shift through both transactions, loosening before the shift, and dropping the coupling claim is the human's, and it is out of the first slice (§1.1).)*
- **Widening waits for the edit's weight shift.** An edit that adds a group runs `Loosen` only after the revision the same edit minted carries all the weight on a converged route. A widening therefore reaches production only with the gated revision it arrived in. If that revision fails its gate, the widening never applies, and `status.auth` shows it pending. An edit that mints no revision has no shift to wait for, and its `Loosen` runs at once.
- **A mixed change narrows first.** `allowedGroups: [a, b]` → `[b, c]` narrows to `[b]` at once and widens to `[b, c]` after the shift.
- **A disjoint change is make-before-break** (ADR-0034, E2). `[a]` → `[b]` shares no group, so narrowing first would admit nobody. It runs as two transactions instead. First, `Loosen` to the union `[a, b]`, after the shift and with no probe. Then `Narrow` to `[b]`, whose probe sees a key in `a` go `200` → `403` while a key in `b` stays `200`. At no point is every caller refused. The cost is that `a` keeps its access until the gate passes and the shift lands, and then until `Narrow` reaches `Served`. That includes access to the new release, whatever it adds (M4, open, above). So the `-auth` policy never compiles to an empty admitted set, and the expression `false` is never emitted for it.
- **A change whose `-auth` is identical** runs no auth transaction, and its revision promotes normally.

**Today an edit to `auth` also mints a revision, and design 02 owes the choice.** Design 02 §3.3's classification table puts `expose` on the behaviour surface, and `expose.a2a.auth` is in the revision projection (`internal/revision/golden_test.go`). So an edit to `auth` alone mints a candidate that differs only in auth, and it pays a gate cycle. `allowedGroups` does not exist yet. Design 02 owes one of two answers:

- keep both fields projected, and the ordering above applies;
- or move both to the policy surface. That is a revision-hash migration. Afterwards a group edit mints nothing, and both transactions run at once.

This design prefers the second, because the gate evaluates behaviour and never reads the admitted groups. F2 holds under either answer. Design 02 is not edited here.

**The weight shift that waits for `Narrow` is owed by two other layers.** Two things perform the shift: design 02 §3.3's promotion step (step 4, "weights shift"), and design 07 A6.10's emitter, which writes the serving revision's single `backendRef` (`internal/controller/httproute.go`). Both must hold a `backendRef` change toward a revision while a `Narrow` started by the edit that minted it has not reached `Served`. Neither does so today. Without it, a promotion lands before the revocation it shipped with. Neither is edited here, and §8.1 owes the envtest case.

Earlier versions of this subsection got three things wrong:

- **A53 held a stricter candidate** at weight 0 and called holding "the fail-closed direction". It was the opposite (`reviews/03-a53-critique.md` B2). Narrowing `allowedGroups` is how a group's access to an Agent is revoked, so holding the narrowing kept the revoked groups admitted, with no condition and no exit. The human decided on 2026-09-11 to apply it in place and to trust it only after an enforcement probe (ADR-0034, A1). The same version applied a looser `-auth` at promotion, while the outgoing revision was still the one serving (critique M1).
- **A54 took the policy from the intersection of every serving revision's own set.** A rollback to a wider revision therefore re-admitted the groups the newer one had removed. A rollback's weight shift also proceeded at `Narrow`'s deadline (`reviews/03-a54-critique.md` M5, call 4). F2 withdraws both.
- **A54 passed a disjoint change through the empty set.** It compiled that set to `false` and called the outage "bounded by the two transactions' deadlines". The deadline is a condition, not a timeout (§3.3), so it bounded nothing (M4). E2 removes the window.

**Naming**: `<name>-<concern>[-<rev>]`, where `-<rev>` is present on a per-revision resource and absent on a per-Agent one (the table above), with a total-length rule — if longer than 63 characters, truncate `<name>` and append a **16-hex** (64-bit) hash of the untruncated name; deterministic, collision-checked, with a golden-file fixture at maximum length.

The suffix was 8 hex. **32 bits is not enough for a name that is also a security boundary** — a chosen collision against a 40-bit revision name took 1.2 seconds when it was measured, so two crafted long names could collide in the suffix and the second would map onto the first's resources. Within one namespace that is a nuisance; design 02 §3.2 imports this rule to name **run namespaces**, where a collision pools two tenants' material in one namespace, which is the exact property the per-namespace scheme exists to prevent. The collision check stays regardless: a suffix collision is a compile error naming both inputs, never a silent reuse.

### 3.3 Apply protocol — fail-closed, and event-driven

Order is part of the contract, and it is the stage table below — creating a route and *publishing* it are two different steps:

1. **The route is prepared first**, with `parentRefs` set and **no `backendRefs`**, so it exists to be targeted. A policy whose target route does not exist reports `Attached=False` (`research/agentgateway-v1.4.1-spike.md` §2.1), so nothing else could ever converge otherwise.
2. **Backends** next.
3. **Policies** next — they can attach, because the route now exists.
4. **Convergence barrier**, then **publication last**: `backendRefs` and weights are attached only after every mandatory concern has converged, so traffic only ever flows through fully-policied paths. Candidate isolation policies are converged before the candidate header route carries anything.
5. **Removal reversed**: routes detach (or zero-weight) before their policies and backends are deleted.

**An earlier version of this list read "1. Backends first. 2. Policies next. 3. Routes / weight changes last" and contradicted the stage table below it**, which has `PreparingRoute` before `ApplyingBackends`. It was not a charitable reading away from correct — item 1 said "Backends first" flatly, and the route is created before them. The reason the table has always been right is stated at "`PreparingRoute` exists because the policy barrier cannot be met without it" below: a cold create that leaves the route until last reaches `Converging` and can never leave it. What "routes last" was reaching for survives as step 4, and only as step 4 — the route is created early and **published** late.

The barrier at step 4 ranges over **every resource a mandatory entry names, Backends included** (§3.3.1) — never `Accepted=True` alone, which a policy targeting a not-yet-created route reports while emitting nothing (§3.3.2). §5 covers applied-but-not-converged and partial apply.

**The barrier is a state machine, not a wait.** An earlier draft polled for up to 30s *on the reconcile worker*, reasoning that controller-runtime's one-reconcile-per-object was the only thing serializing the sequence. It is — but a blocking wait is the wrong way to keep it. Each not-yet-converged Agent occupies a worker for the whole bound, requeues, and does it again, so a principal who may create Agents can keep more permanently-pending objects than there are workers and starve every other reconcile — kill, budget-hold, finalization — behind them. Raising `MaxConcurrentReconciles` changes how many bad objects are needed, not the outcome.

So the operator **applies once and returns**, and progress is driven by watches:

| Stage | Entered by | What it does | What advances it |
|---|---|---|---|
| `PreparingRoute` | `Create` | create the route with `parentRefs` set and **no `backendRefs`**. **Never entered for a route that exists**: the serving route is per Agent (§3.2), so a candidate's `Create` finds it serving, and rewriting it without `backendRefs` would take the active revision off the air to prepare its successor. For a candidate this stage prepares only that revision's own per-revision routes | route status watch |
| `Withdrawing` | `Withdraw` — a non-spec tightening its source does not enforce (§3.3.3) | update the serving route's `backendRefs[].weight` to `0`, then converge at the **new** generation before any policy is narrowed | route status watch |
| `ApplyingBackends` | `Create`, `Loosen` | create/update the Backends for the desired set | Backend status watch |
| `ProbingBefore` | `Narrow` (§3.3.3) | write the probe keys' `ConfigMap`, then probe until each key gets its "before" answer. Skipped once a narrowed policy has been written (§3.3.3's re-entry rule) | `RequeueAfter`, until the deadline |
| `ApplyingPolicies` | `Create`, `Loosen`, `Withdraw`, `Narrow` | create/update the Policies — they can attach, because the route now exists | Policy status watch |
| `Converging` | `Create`, `Loosen`, `Withdraw`, `Narrow` | evaluate §3.3.2's per-kind tuple over every mandatory resource | status watches; `RequeueAfter` for the deadline |
| `ProbingAfter` | `Create` of `-auth`, `Narrow` | for `Create`, send anonymous probes until one gets `401` on the prepared route (§3.3.3). For `Narrow`, probe until each key gets its "after" answer in the same round, then delete the probe `ConfigMap` | `RequeueAfter`, until the deadline |
| `Publishing` | `Create`, `Loosen`, `Withdraw` | attach `backendRefs` / shift weight so the route carries traffic — for `Withdraw` this is the weight **restored** | route status watch |
| `Served` | `Create`, `Loosen`, `Withdraw`, `Narrow` | steady state. For `Narrow` this is the first stage at which status records the narrowed policy as applied | spec change, or a NACK Event |
| `Refused` | `Adopt` (§3.3.3) | **nothing** — no write to the route or to any policy | a human recreating the Agent |

`status.apply` carries `{transaction, digest, generation, stage, deadline}` — the **transaction kind** as well as the digest, because the stages differ (§3.3.3). It carries one revision's transaction. **The per-Agent `-auth` has its own record, `status.auth`** (below). `-auth` belongs to no revision, and `status.apply` is one record, so a group edit's `Narrow` would otherwise collide with the candidate `Create` the same edit starts. **`status.apply` has no schema anywhere yet**, and unlike its sibling `status.revisions[]` no document says so: design 02 §5 carries a "not on the CRD" row for `status.revisions[]` and none for this field, and `status.apply` appears in no Go type in `api/v1alpha1`. This whole subsection reads and writes it as if it existed. **Owed to design 02** as the authoritative schema (§3.1), on the same footing as `status.revisions[]` and by the same rule (AGENTS.md 7): nothing enforces this field today.

**`status.auth` — the per-Agent `-auth`'s applied record.**

```
status.auth {                      // per Agent; the operator alone writes it
  keySource:      string           // canonical selector the served policy selects (§3.3.3)
  admittedGroups: [string]         // sorted; the set the last Served transaction verified
  appliedDigest:  string           // SHA-256 over the canonical -auth policy last Served
  verified:       {replicasProbed: int, replicasDeclared: int | unknown}   // §3.3.3
  transaction?: {                  // absent in steady state
    kind:            Create | Narrow | Loosen
    targetDigest:    string        // the policy being applied
    targetGroups:    [string]
    targetKeySource: string
    stage:           string        // §3.3's stage names
    written:         bool          // set in the status update that ENTERS ApplyingPolicies,
                                   //   before the write, so a crash between them reads as written;
                                   //   every re-entry then repeats the write (§3.3.3)
    afterShift:      bool          // a Loosen waiting for its edit's weight shift (§3.2)
    deadline:        time
    probe:           {before, after}   // the answers last observed; never the keys
  }
}
```

It is the comparator's applied operand for `-auth` (§3.3.3), and the key source that a refused key-source change keeps enforcing (§3.4.4). Its transaction is keyed on `targetDigest`, not on the Agent's generation. So an edit that leaves the desired `-auth` unchanged does not disturb it. **Owed to design 02** beside `status.apply`, and nothing enforces it today. An earlier version recorded the narrowing in `status.revisions[].appliedDigest`. That field is per revision, is computed over that revision's `ResourceSet`, and is not on the CRD (`reviews/03-a54-critique.md` M3).

**`PreparingRoute` exists because the policy barrier cannot be met without it.** An earlier draft ordered Backends → Policies → converge → *then* create the route. A policy whose target route does not exist reports `Attached=False` (`research/agentgateway-v1.4.1-spike.md` §2.1), so a cold create reached `Converging` and could **never** leave: the stage that creates the route sat behind the barrier that needed it. The route is therefore created first. Controller-runtime's per-key serialization is untouched, because each reconcile still returns before the next begins — what is removed is the sleeping.

**That first route is NOT dark, and calling it "inert" was wrong.** Measured (`research/agentgateway-v1.4.1-spike.md` §2.6): a route with `parentRefs` and no `backendRefs` reports `Accepted=True` and `ResolvedRefs=True`, **accepts a policy attachment**, and **returns HTTP 500 to a live request**. The spike says so in its own heading — the route is reachable and answering, just erroring. Two consequences, and an earlier version of this section stated neither because it described the shape as "attachable-but-not-serving":

- **On a `Create` this costs no availability and is still visible.** Nothing was serving that path before, so a 500 replaces nothing. But an operator watching a new Agent come up sees 500s for the convergence window, and NFR-8 says they should be told what that is rather than reading it as an outage. §5 carries the condition.
- **The downtime the spike warned about does not arise, and the reason is §3.3.3 rather than the route shape.** The spike observed that if a *tightening* transition made a serving route inert, that route would be down for the convergence window, and asked §3.3.2 to state the trade. There is no such transaction. A tightening is either a gated spec change on a **candidate** route, or §3.3.3's `Narrow`, which rewrites the per-Agent `-auth` policy and never the route's `backendRefs`, so a serving route is never stripped of them. The trade is dissolved, not accepted — but it would return the moment anyone reintroduced an in-place tightening path that removed `backendRefs`, which is the reason to record it here rather than to delete it.

**Stale state is discarded, and recovery re-enters the transaction's FIRST stage.** On every reconcile, if `status.apply.digest` is not the digest of the currently desired resource set, or its `generation` is not the CR's current generation, the record is dropped — and the transaction is **recomputed against the currently serving applied set**, then entered at *its own* first stage: `PreparingRoute` for a `Create`, `Withdrawing` for a `Withdraw`, `ApplyingBackends` only for a proven `Loosen`, and `Refused` for an `Adopt`, which writes nothing. The per-Agent `-auth` is not governed by this rule. Its record is `status.auth`, keyed on the desired policy's digest rather than the generation. Every `-auth` transaction re-enters at its write, by §3.3.3's rule. A `Narrow` re-enters at `ApplyingPolicies` once `written` is set, and at `ProbingBefore` before that. A `Create` re-enters at `ApplyingPolicies` when its prepared route exists, and at `PreparingRoute` when it does not. The write is idempotent, so no re-entry can skip it. An earlier version of this rule named two kinds and had no entry point for a stale `Withdraw` at all, which would have restarted a withdrawal at `ApplyingBackends` — narrowing a policy on a route nobody had re-sent to weight 0.

An earlier draft restarted unconditionally at `ApplyingBackends`, and a later one claimed that removing the `Tighten` transaction dissolved the problem. **That claim was wrong, and the retraction matters more than the fix.** Removing `Tighten` did not remove `Create`'s first stage. A superseding generation naming a new candidate route would drop the old record, start at `ApplyingBackends`, and attach policies to a route that had never been created — `Attached=False`, deadlocking on exactly the cold-create barrier this rule exists to fix. The route identity the transaction uses is persisted with the stage, so recovery knows which route it must prepare. Without that, reconcile N's recorded stage would let reconcile N+1 publish a route whose policies belong to the previous generation — the fail-open the blocking poll existed to prevent, arriving through the status field instead.

**The deadline is a condition, not a timeout.** Exceeding it sets `PolicyApplyIncomplete` naming the resource and its unmet condition, and the machine stays in its stage; it does not abandon or roll back. Withheld routes stay withheld, which is the fail-closed direction.

**A NACK is the sixth input, and it is not optional** (§3.3.2). `AgentGatewayNackError` is a Gateway-scoped Warning Event and the *only* observable of a dataplane rejection. The operator watches Events on the Gateways it emits to, parses the key — `policy/traffic/<ns>/<name>:<section>:<ns>/<route>` — and maps it to the owning Agent. A NACK naming a resource in the current desired set raises `PolicyApplyIncomplete` and returns the machine to `Converging`. It **cannot** advance anything: the key carries no generation, so a NACK proves a rejection happened, never that one did not.

**Fairness is a test, not an assertion.** More permanently-pending Agents than workers, while an unrelated Agent's kill transition must complete within a stated bound. A design that merely says it does not block has not shown it.

**Verified unchanged at v1.5.0.** The apply barrier of `research/agentgateway-v1.4.1-spike.md` §2.1 reproduces exactly on the newer release (`research/agentgateway-v1.5.0-delta-2026-09.md`), so nothing in this section rests on a behaviour that has since moved.

### 3.3.1 Required concerns — a route is never created without its guarantees

§3.3 orders the concerns that **exist**. It says nothing about a concern that was never emitted, and that gap is the second half of the hole §3.3's fail-closed ordering closes: a policy that fails acceptance stops the route, but a policy that was never compiled has nothing to fail, and the route is created onto an open door. §4's totality rule does not cover this either — "every field maps or errors" governs fields that are *present* in the `PolicyIntent`, not required concerns whose input is absent.

**That rule is ADR-0020's, not ADR-0028's, and an earlier version of this paragraph named the wrong one.** "Backends → Policies → verify Accepted → Routes last … `PolicyApplyIncomplete` on any gap — no fail-open windows" is **ADR-0020 decision (3)**. ADR-0028 supersedes ADR-0020, but what it changes is the barrier's *predicate*, not the ordering — and its own decision 2 points the other way, retiring `Accepted=True/programmed` and recording that a dataplane NACK surfaces only as a Warning Event. It **weakens** the acceptance signal rather than resting a guarantee on it, so citing it as the closure of a fail-open was exactly backwards. The ordering's live home is §3.3 of this design; the decision that established it is ADR-0020 (3). The ADR's words are quoted as it wrote them: read against §3.3's stage table, "Routes last" is the **publication** of a route — attaching `backendRefs` — and not its creation, which comes first and must.

**The unit is one revision.** `Compile` takes one `PolicyIntent` — one revision's material — and returns that revision's `ResourceSet`; one Agent's failure never touches another's, and a **candidate's** compile or apply failure can neither mutate nor delete the **active** revision's persisted record or applied set. Describing the unit as "one Agent" obscured exactly that isolation. Design 02 §4 reconciles per-CR, and anything wider would let one malformed Agent stop the fleet.

**The rule.** Every route class names the concerns that must be present and converged — §3.3.2's tuple, not `Accepted=True` alone — before that route may be **published**, meaning its `backendRefs` are attached. Creating the route comes first and must (§3.3's `PreparingRoute`). An earlier version of this sentence said "before that route may be created", which is the retired ordering, and built that way a cold create can never leave `Converging`. A mandatory concern whose input is absent is a **compile error** (`PolicyCompileFailed`, naming the missing input), never an omitted policy.

**Requiredness is a property of the binding, not of the route class.** An earlier draft made every tool, KG and LLM route *optional*, so an Agent whose sole knowledge source was unreachable reported `Ready=True`. That contradicts two canonical documents: architecture §04 says an Agent bound to a non-Ready graph gets no traffic, and design 02 §5 says an invalid **sole** knowledge source means no traffic (`KnowledgeBound=False` → `Degraded`). Answering HTTP while every declared capability is gone is not semantic readiness — it is the loud-and-wrong of rule 8, reported as health.

**Requiredness is DECLARATION, not a marker.** The table below once said a binding was required when it "is marked required". Nothing marks it: `Binding<T>` is `{requested, resolved?, state}` and the Agent CRD has no `required` field on `spec.tools[]` or `spec.knowledge[]`. Two cells the aggregation reports differently arrived in an identical shape, so the compiler could resolve the split either way — reporting `Ready=True` for an Agent whose essential tool was gone, or failing an Agent over an incidental one.

The total rule, for every kind: **a binding an Agent declared is required.** Writing `tools: [x]` is the demand; nothing in the CRD expresses "and it is fine if this one is missing", and inventing that meaning is how the optional column got read as the default. The rule is deterministic, needs no new field, and never reports readiness for an Agent missing a capability it asked for.

The optional column below is consequently **unreachable from the Agent CRD as it stands** and is kept only because design 26's tenant-scoped bindings and design 27's profile-added routes can populate it. If a user should be able to mark a tool optional, that is a CRD field and an ADR — not an inference from a shape that cannot carry it.

So each declared binding carries its own requiredness, and the Agent aggregates over its **actual contract**:

| Route | Required when |
|---|---|
| A2A serving, card | always — **every Agent with a serving revision, whether or not it sets `expose`**, because that is the route the operator emits (the card row below) |
| KG | **the binding is the Agent's sole knowledge source** (design 01 §5: agents "receive no traffic if the graph is their only knowledge source"), or the Agent declares any KG binding at all |
| LLM egress | the Agent declares `llm.providers` at all — an agent that cannot reach a model cannot answer |
| Tool | **every declared tool binding** |

An Agent with no declared capability of a kind has nothing required of that kind. The failing set is then split into required and optional, and aggregated as:

| Failing | `Ready` | `phase` | CLI |
|---|---|---|---|
| any serving-required route | `False`, reason **by cause** (below) | `Pending` (create) or `Degraded` (was serving) | terminal for `deploy` |
| optional routes only | stays `True` | `Degraded` | reported, **not** terminal |
| none | `True` | `Ready` | — |

**Conditions aggregate by cause, not by route.** An earlier draft gave every serving-required failure the reason `PolicyApplyIncomplete`, which would have named a cause that was never checked when the real one was a compile error. The two conditions are separate and both may be set:

| Cause | Condition |
|---|---|
| unresolved input, missing mandatory input, arithmetic, unresolvable identity | `PolicyCompileFailed` |
| not converged at the deadline, `Accepted`/`Attached` false, a NACK Event | `PolicyApplyIncomplete` |

`Ready`'s reason names the **winning** cause under a fixed precedence — `PolicyCompileFailed` outranks `PolicyApplyIncomplete`, because nothing was applied to fail — so a consumer reading one reason is never told the wrong one.

**One condition instance carries every failing path, and clears only when none remain.** A condition is one per type, so concurrent failures would otherwise overwrite each other's message and recovering one would hide the other. The message lists the failing resources in a **stable order** (route class, then name), so a second failure appends rather than replacing, and `PolicyApplyIncomplete` is cleared only when the set is empty — not when the most recent one recovers.

**The failure is route-scoped, not set-scoped.** An unresolvable tool withholds that tool's route and anything depending on it; the serving route and the card route still compile and apply. The alternative — one bad input voids the whole `ResourceSet` — trades a fail-open for a fail-stuck, where a typo in one tool name takes an agent off the air entirely. §5's rows say this consistently: `PolicyCompileFailed` means *the affected routes* are not emitted, never "nothing applied". **The one exception is a served `-auth`, below.**

**A served Agent whose `-auth` input becomes uncompilable keeps its last good `-auth`.** The human decided this on 2026-09-11 (I1, ADR-0034 Amendment 1). The case that forced it is the most ordinary edit on the CRD as it ships today (`reviews/03-a55-critique.md` B1). A four-line Agent has no `expose` block and is served under the derived `<agent>-auth`. Its owner adds `expose: {a2a: {visibility: org}}`. The CRD still carries `+kubebuilder:default=oauth` (`api/v1alpha1/agent_types.go`), so the API server persists `auth: oauth`, which the slice cannot compile. Read literally, the rules above left that Agent's policy out of the desired set, and the label-and-name sweep (§3.2) then deleted it. The route kept its `backendRefs`, so the Agent was reachable with no key. **Adding `expose.a2a` to a served Agent must not open it.** The rule:

- **A compile failure never deletes or rewrites an existing `<agent>-auth`.** For `-auth`, a failed compile means "the desired policy is unknown", never "no policy is desired". So the sweep keeps the object, whatever `status.auth` says. A status that a backup restore dropped therefore cannot turn a compile failure into a deletion. The only paths that delete `<agent>-auth` are the Agent's finalizer and a compiled, applied change to `auth: none`, which is out of the slice (§1.1). An out-of-band mutation of the kept object is re-asserted to the policy `status.auth` records. That policy is a pure function of `status.auth.keySource` and `admittedGroups`, checked against `appliedDigest`. With no `status.auth`, the object is left as found, and the message says so.
- **The route keeps serving under it.** A published route keeps its `backendRefs`. Withdrawing it would turn a typo into an outage, while the policy it serves under is still enforced. A route not yet published stays unpublished, and its `Create` does not advance.
- **The broken edit is contained, and never applied.** A revision whose projection carries an `-auth` input this build cannot compile gains no weight while that is so. The same edit usually mints one, because `expose` is on design 02's behaviour surface (§3.2). The hold is owed to design 02's promotion step and to design 07 A6.10's emitter (§1.1), and neither implements it today.
- **The Agent says so.** It reports `PolicyCompileFailed`, with a reason naming the input: `AuthInputAbsent` for `oauth`, and `ConcernNotBuilt` for a stored `spec.budget`. The message names the field and the fix, and says that the previous `-auth` is still enforced. `Ready` goes `False` and the phase `Degraded` (the aggregation below). `GovernanceSkipped` keeps the value the served policy earned, because the route is still governed by it.

**A mode change this build does not carry is kept out the same way.** In the slice, the only reachable change to a served Agent's compiled `-auth` is its mode, because the admitted set and the key source cannot move (§1.1). Moving from the API-key policy to `auth: none` would be a `Loosen`, and moving from `auth: none` to the API-key policy would be a `Narrow`. Neither is in the slice. So the served state stays: the policy in the first case, and the marker label in the second. The Agent reports `PolicyCompileFailed`, reason **`AuthTransitionNotBuilt`**. The message names both modes and the action: recreate the Agent, which then enters `Create` with the mode it asks for. In the second case the route serves without an `-auth` that the current spec makes mandatory, so `GovernanceSkipped` is `True` with the same reason. That is ADR-0034's `Adopt` principle, that a first policy is never written onto a route that is already serving. The refusal is withdrawn in the change that ships `Narrow` and `Loosen`.

`make test` owes the envtest case for I1. A served Agent is edited to `auth: oauth`. Its `<agent>-auth` must be neither deleted nor rewritten, the route must keep its `backendRefs`, and the revision the edit minted must gain no weight. The mutation that lets the sweep delete `<agent>-auth` on a compile failure must fail the case (§8.1).

| Route class | Mandatory concerns | Notes |
|---|---|---|
| A2A serving route (every Agent; `expose.a2a` configures it) | `-auth`, plus `-ratelimit` **when a rate is actually derived** (§3.5) | `auth: none` is an explicit opt-out — see below. With no `expose` block the `-auth` input is §3.4.4's derived default, not an absence |
| Candidate header route | `-auth` — always, no opt-out | admitted set is one SVID (design 02 §3.3 step 3); an unauthenticated candidate route is a bypass of the whole gate |
| Tool (MCP) route | `-auth` (as `traffic.jwtAuthentication.mcp`), `-toolfilter` (as `backend.mcp.authorization`, `action: Allow`) | A tool route without its filter grants the server's entire tool surface — and because the filter also prunes `tools/list`, its absence makes every tool *visible* as well as callable (§3.4.2) |
| KG (kgp) route | `-auth`, `-transform` (scope injection) | the provider enforces scope from a header the gateway must actually inject (§3.4) |
| LLM egress route | `-auth`, plus `-ratelimit` **when a rate is actually derived**, plus `-transform` (credential scrub), plus `AgentgatewayBackend(egressEnumerated)` | The Backend entry is **construction, not restriction** (§3.4.1). The predicate holds when the Backend enumerates the **requested** set (`providers[] ∪ {fallback}`) and every effective host in it — override included — is a **subset** of what the allowlist permits; a destination is never added because it is permitted (§3.4.1.1). No `dynamicForwardProxy` is ever emitted |
| Reserved — telemetry tap (10), webhook ingress and kgp-admin (11), replay-mock (17), approval interceptor (22), app projections (23), InferencePool and shadow candidate (25), tenant partition (26) | **unclassified — must not be emitted** | Each is named in §3.4 and none has a mandatory set yet. Listing them as explicitly unclassified is the difference between a deferral and an omission: the registry below refuses to emit an unclassified class, so a future design must add its row before it can ship a route |
| Card discovery route | **no separate route.** The card path rides the serving route, whose match is `PathPrefix: /`, so it carries the same `-auth`; `expose.a2a.auth: none` drops it for both together | Architecture §05 (Exposure) puts the card on the org/public A2A endpoint. **ADR-0019 does not make this route public** — it fixes the card's *source of truth* as the container, which is a different claim; an earlier draft cited it for this and was wrong. An agent at `visibility: cluster` would otherwise disclose its name, version and skill inventory to any unauthenticated caller. **An earlier version of this cell said that with no `expose` block "there is no external card route at all: nothing is externally reachable". The shipped operator refutes that**: it emits a serving route for every Agent with a serving revision and never reads `spec.expose` (`internal/controller/httproute.go`, design 07 A6.10), so ADR-0027's four-line Agent is reachable through the Gateway, card included. This design adopts that behaviour rather than withdrawing the route. It keeps the property the old sentence protected — no anonymous caller reads an Agent's card — by authentication instead of absence: the four-line Agent's route carries §3.4.4's derived `-auth`. Note the gate is `auth`, not `visibility`: the two are different enums, and `visibility: public, auth: oauth` is reachable and stays authenticated. `visibility` compiles to nothing in the slice, which has one listener |

**Explicit opt-outs are emitted, not absent.** `expose.a2a.auth: none` drops the `-auth` requirement, but the resource set still carries an explicit no-auth marker for that route. A reviewer diffing two resource sets must be able to tell "this route is deliberately unauthenticated" from "this route lost its auth policy", and two absences look identical. The marker is a **label on the route**, not a policy: an empty `AgentgatewayPolicy` would be subject to §3.3's acceptance gate and could be webhook-rejected, which would make `auth: none` unserveable — the opt-out must not be able to fail. The marker moves with `-auth`'s transactions. `auth: none` → `apikey` is a `Narrow` (§3.3.3), and it removes the label only at `Served`, because until the probe sees `401` the label's claim may still be true. `apikey` → `none` is a `Loosen`, and it adds the label when it deletes the policy.

**The table is compulsory, and the enforcement has a real anchor.** An earlier draft promised "a property test asserts that the set of route-class constants equals the set of table rows" — which is not mechanizable, because a markdown table is not a machine-readable artifact. In practice it degrades into two Go slices in one file that stay green when you delete from both, which is exactly the shape AGENTS.md rule 1 says is this repo's default failure. Design 02 A12's `TestEveryFieldIsClassified` works only because it reflects over a struct the compiler cannot avoid changing; route classes have no such struct.

So the anchor is built rather than assumed. Routes are emitted only through `emit(class RouteClass, …)`, which consults a **registry** mapping every `RouteClass` to its mandatory set; a class absent from the registry cannot be emitted. Because it is the emit gate rather than a checklist, deleting a registry entry disables the route instead of ungating it — the failure direction is closed.

**Mandatory sets range over emitted *resources*, not only policies.** An earlier draft scoped them to `AgentgatewayPolicy` kinds, which cannot express the one control ADR-0014 rests on: `llm.egressAllowlist` compiles to a **Backend**, not a policy, so "the LLM Backend must enumerate only allowed endpoints" (§3.4.1) was outside the stated extension point entirely, and a `hipaa` cluster could emit an LLM egress route with no BAA restriction and nothing in this design would stop it. A mandatory entry therefore names a resource and a predicate over it — `AgentgatewayPolicy(-auth)`, `AgentgatewayBackend(egressEnumerated)` — and both are checked before the route is **published** (its `backendRefs` attached).

**What actually pins the sets, and the shape it must NOT take.** A golden test renders the registry to markdown and diffs it against the table above, so the table is machine-checked. That catches divergence, not wrongness: the dangerous mutation is deleting `-auth` from the tool route's mandatory set *and* editing the row to match, which the golden diff passes.

An earlier draft answered that with "for every registered class, one test per mandatory entry" — **cases generated from the registry**, which deletes its own check along with the entry. That is the identical defect this repo has now shipped twice: once in the docs gate, where removing a rule left the suite green, and once here. Cases enumerated from production data cannot pin production data.

So the security cases are a **static catalog**, written independently of the registry and reviewable as a list: *tool route without `-auth` is withheld*, *LLM egress route without `egressEnumerated` is withheld*, and one line per mandatory entry in the table. A class present in the registry with no case in the catalog fails; a case naming an entry the registry no longer has fails. Both directions, or deleting an entry and its case together passes again.

`test/docs/superseded_test.go`'s `ruleFixtures` is the working precedent in this repo — independent fixtures that fail on deletion, on a weakened matcher, and on an over-broad exemption. The mutation harness deletes each production mandatory entry with the catalog untouched and requires a **compiled test failure**; a build error is INVALID, not KILLED (AGENTS.md rule 3).

**Every profile ships its own catalog, because the base one cannot pin what a profile adds.** Compliance profiles extend the mandatory sets *dynamically* (§3.3.1, design 27) and are deliberately absent from the base table — so deleting the `hipaa` profile's `-guard` extension leaves every base case green and the profile silently stops requiring PHI redaction. A profile or pack that adds a mandatory entry therefore ships a security catalog **for its own additions**, and the mutation harness deletes each profile-added entry with that catalog untouched. A profile whose additions have no catalog fails to install rather than shipping unpinned. An earlier draft claimed "deleting from both fails the exhaustive switch over `RouteClass` in Go": Go has no exhaustive switch checking, this repo runs `go vet` with no `.golangci.yml`, and an exhaustive switch would prove only that every class is *handled*, never that its mandatory set is *right*.

**Compliance profiles extend the mandatory sets; they do not appear here.** `-guard` is absent from every row above, which is right for P1 and wrong for ADR-0014: the `hipaa` profile makes PHI redaction mandatory at the gateway, and "compliance is a profile you enable, not an integration you build" has to stay literally true. The credential-scrub `-transform` on the LLM row is a different concern and does not cover it. The table therefore has no profile dimension by design — a profile contributes additional mandatory **entries** per route class through the same registry (design 27), which is expressible now that entries range over resources: the `hipaa` profile adds `AgentgatewayPolicy(-guard)` to the LLM egress row, on top of the `egressEnumerated` entry the base profile already carries. Admission (design 27 §3) rejects a non-conforming Agent CR, and this registry stops a conforming CR from compiling an unrestricted route; the two are different seams and both are needed.

### 3.3.2 What the barrier can and cannot prove

`Accepted=True/programmed` was not a predicate; the slash hid a missing contract, and the condition it named is **true in exactly the state §3.3 guarantees**. A policy whose target route does not yet exist reports `Accepted=True, reason: Valid, "Policy accepted"` beside `Attached=False`, with `output: []` — no policy emitted at all (upstream fixture `http-route-missing-not-attached.yaml`). Under the retired ordering, which created routes last, the old barrier was satisfied by a policy that had produced nothing. §3.3 now prepares the route first, and the tuple below is what stops the barrier passing on an unattached policy.

**The convergence tuple**, per kind, all at `observedGeneration == metadata.generation`:

| Kind | Required | Traps this closes |
|---|---|---|
| `AgentgatewayPolicy` | `Accepted=True` with `reason: Valid` **and** `Attached=True`, on a **Gateway**-shaped `ancestorRef` | The success ancestor is the Gateway, **not** the `targetRef`. Failures emit a synthetic `StatusSummary` ancestor — its presence is a negative signal. An unsupported target kind yields **zero ancestors and zero conditions**, so a poller waiting for `Attached=False` waits forever; empty ancestors is a failure, not a pending state |
| `AgentgatewayBackend` | `Accepted=True` at the current generation | This proves **translation only**. The controller sets it even when no gateway resolves and no dataplane resource is emitted |
| `HTTPRoute` | `Accepted=True` **and** `ResolvedRefs=True` | There is no `Programmed` condition to wait for |

**`reason == Valid` is controller-side translation validation, not a dataplane acknowledgement.** Requiring it is a strict improvement on `Accepted=True` alone — it rules out a policy the controller could not translate — but it is **not** positive proof that a proxy took the config. Two things were checked and are stated so nobody re-derives them: `PartiallyValid` exists identically at **v1.4.1** (`traffic_plugin.go`), so its presence is not a v1.5.0 behaviour change and nothing here may be justified by "the newer release reports more"; and the condition is written by the controller from its own translation result, never from a proxy ack. The only observable of a dataplane rejection remains the NACK Event below.

**What this proves is control-plane convergence, and not enforcement — measured, not argued.** A dataplane NACK is published as a Kubernetes **Warning Event** (`AgentGatewayNackError`) on the **Gateway**, never as a status condition. A tightening update carrying a dataplane-invalid value was observed reporting `Accepted=True`, `Attached=True` at `observedGeneration == generation` while the proxy rejected it and **the previous permissive rule kept serving**: eight requests under a limit that should permit one all returned 200 (`research/agentgateway-v1.4.1-spike.md` §2.8). **A NACK'd policy retains the old config; it does not fail closed.**

So the operator **must** watch that Event for its emitted resources and raise `PolicyApplyIncomplete` on it — mandatory, not defensive. The event key (`policy/traffic/<ns>/<name>:<section>:<ns>/<route>`) names the policy and the route, so a NACK **can** be attributed to a resource assayd emitted; it carries **no generation and no UID**, so an old NACK cannot be told from a new one and **absence of an Event is not success**. That makes the Event sufficient to raise degradation and insufficient as a success barrier. Until upstream publishes a positive dataplane acknowledgement, this design claims control-plane convergence only — and **no transaction tightens a serving route in place on the strength of its conditions**. The one that does tighten in place, `Narrow`, records the change only after a probe observes the refusal itself (§3.3.3). An earlier draft offered "or accept that a silent NACK leaves the old rule serving", which was a measured fail-open rather than an option; its replacement, a witness probe, could not attribute its own result. Both are withdrawn. A tightening is a spec change that mints a revision and is gated on a candidate route, so the serving path is never the thing being converged — except the per-Agent `-auth`, which `Narrow` converges in place and then probes. Two-phase publication — prepare the route with no `backendRefs` (reachable and answering 500, not dark: §3.3, spike §2.6), converge its policies, then attach — is what the ordering in §3.3 becomes; the alternative is a barrier that passes on an unattached policy.

**Update ordering was part of the contract, and §3.3.3 removed the case it governed.** An earlier draft required a tightening change (`auth: none → oauth`, a narrowed tool filter) to withdraw its dependent routes before applying, converge, then republish. There is no such transaction now: tightening is a gated spec change on a candidate route (§3.3.3), so a serving route is never stripped of its `backendRefs`, and the one serving-route policy converged in place — the per-Agent `-auth`, under `Narrow` — is trusted only on a probe. That is also what dissolves the availability trade the spike attached to this section — see the note in §3.3 on the route that answers 500. What remains is the kinds in §3.3.3's one table — `Create`, `Loosen`, `Withdraw`, `Narrow`, and the refused `Adopt` — and a `Loosen` that NACKs leaves the *stricter* old rule serving — a failure toward denial.

### 3.3.3 In-place tightening is trusted only on a probe

An earlier draft specified a `Tighten` transaction — quiesce the live route, converge, prove a witness, republish. **It is withdrawn.** Two measurements and one structural fact removed it:

- a NACK'd policy **retains the previous configuration** while every condition reports converged (`research/agentgateway-v1.4.1-spike.md` §2.8), so an in-place tightening can silently fail to apply;
- the witness that was meant to catch that **cannot attribute** its own result. A 401 can come from the backend, a rejected tool from an unhealthy MCP server, an unreachable host from DNS, a 429 from an upstream or an already-empty bucket. A NACK and a passing witness coexist, and `Publishing` then widened the match on a false positive (Codex r4 BLOCKER 2); and
- that draft's escape for an unwitnessable concern — "use the revision path" — was unavailable for exactly the fields that needed it, because a policy-surface change mints no candidate (r4 BLOCKER 4).

**So tightening is a compiler transaction in exactly one place.** Design 02 §3.3 puts `budget` and `expose` on the behaviour surface, which are the only two policy-surface fields feeding a mandatory concern; `tools[].name`, `knowledge[].scope` and `llm.egressAllowlist` were already there. Every tightening therefore mints a revision and runs through design 02 §3.3's existing blue-green machinery: the candidate gets **its own** per-revision resources (§3.2's granularity table), is gated at weight 0, and weights shift only on pass. The serving route is per Agent, so it *is* mutated — but only in its `backendRefs`, which is the weight shift itself. No **per-revision** policy the active revision serves under is rewritten, so there is nothing to quiesce, nothing to withdraw, and no NACK window on a serving path. An earlier version of this sentence said the old route is never mutated, which a per-Agent route cannot satisfy. **One policy is rewritten in place, and it is `-auth`.** The spike put it per Agent (§3.2), so a change to it rewrites the policy the serving route carries. A53 held a stricter one at weight 0, which failed open (§3.2). It is now applied as `Narrow`, below, which answers each of the three objections above. It is recorded only on a probe of the refusal itself, never on conditions, so a NACK that keeps the old rule leaves status unclaimed. Its probe attributes its result, where the withdrawn witness could not. And it needs no escape to the revision path, because the stricter policy arrives from the Agent's current spec, or from a key-source change the administrator accepted (§3.4.4).

**Five transaction kinds exist, and this is the only table of them.** `Narrow` and `Adopt` are explained below the table. An earlier version of this sentence said "four", then "three", and before that "two" — counted `Create` and `Loosen`, and left `Withdraw` — introduced later in this same subsection as "a real transaction with stages" — with no row, no `status.apply.transaction` value and no entry point in §3.3's stale-state recovery rule. Its justification is long and stays where it is; its row is here:

| Kind | When | Stages |
|---|---|---|
| `Create` | a revision's routes do not exist yet — a new Agent, or a gated candidate | `PreparingRoute` → Backends → Policies → `Converging` → `Publishing`. For the per-Agent `-auth` on a new Agent's serving route, `ProbingAfter` runs between `Converging` and `Publishing`: an anonymous request must get `401` first (below). This is the first slice's only transaction (§1.1) |
| `Loosen` | the new set is **provably** no stricter than the applied one | Backends → Policies → `Converging` → `Publishing`, route stays live. On the per-Agent `-auth` it runs only after any weight shift the same edit requires has landed on a converged route (§3.2), so its `Publishing` stage has no weight to move, and it never probes |
| `Adopt` | the compiler finds a published serving route with **no operator-emitted `-auth` and no `status.apply`** — a route the operator published before it carried a compiler. A foreign policy on the route does not count as governing (§3.2) | `Refused`: no write of any kind. Why, and the future path, are below |
| `Withdraw` | a non-spec tightening the source does **not** enforce (the per-producer table below) | `Withdrawing` (weight → 0) → converge **at the current generation** → `ApplyingPolicies` (the tightened policy, now on a route assayd has asked to be dark) → `Converging` → `Publishing` (weight restored). What this can and cannot prove is below |
| `Narrow` | the per-Agent `-auth` must admit fewer principals: the current spec removed a group or turned authentication on (§3.2), or the administrator accepted a key-source change (§3.4.4) | `ProbingBefore` → `ApplyingPolicies` → `Converging` → `ProbingAfter` → `Served`. `ProbingBefore` is skipped once a narrowed policy has been written (the re-entry rule below). A weight shift the same edit requires waits for `Served`. A pinned rollback runs no `Narrow` (§3.2). Specified below |

**`Narrow`: the one in-place tightening, trusted only on a probe.** It applies a stricter `-auth` to the serving route in place, and records the tightening only after the gateway is seen refusing what the change removes. It is entered in four cases:

- the Agent's current spec removes a group and keeps at least one it shares with the applied set. `Narrow` runs at once, to the shared groups (§3.2);
- the second half of a disjoint group change, once its `Loosen` to the union has reached `Served` (§3.2, ADR-0034 E2);
- the current spec moves `auth: none` → `apikey`;
- the administrator accepts a key-source change (§3.4.4). Each Agent whose served policy selects the old source runs one.

**The probe.** For each transaction the operator mints two keys of 256 random bits and holds them in memory only. It writes their hashes to one `ConfigMap` per selector involved, named `<agent>-auth-probe`, in the run namespace, carrying the key-source label, with `metadata.group` set as the table below says. Each probe is a `GET /.well-known/agent-card.json` carrying one key. The card path rides the serving route and its `-auth` (§3.2), so a probe sends no task to the agent. A `200` counts only when its body's digest equals the card digest the operator recorded for a serving revision in `status.cards[]` (design 02 A68).

**Where the probe goes.** To the Gateway's **serving** listener, the one `<agent>-serving` attaches to (listener `http`, design 07 A6.10), with the `Host` header set to the Agent's hostname. That is not the address in `--gateway-url`, which names the listener agents send their **egress** to. The e2e sets `--gateway-url` to the `tools` listener on port 8081, while `<agent>-serving` is on the `http` listener on port 8080 (`hack/e2e.sh`). A probe sent there would get no route for either key, and every `Narrow` would stall. So the address is its own declared operator input: chart value `gateway.servingUrl`, rendered as operator flag `--gateway-serving-url`. **Neither exists, and both are owed to design 07.** **The flag is required whenever the compiler runs.** The operator refuses to start with the compiler enabled and the flag unset, as it already refuses to start when `HTTPRoute` is not served (§3.1). *(A55 let `Narrow` write its policy and hold with the flag unset. Now that `Create` probes too, an unset flag would hold every new Agent unpublished, so the fifth critique's call 5 asked for the refusal.)*

**`Create`'s probe: a new Agent's route is published only after an anonymous request gets `401`.** `Create` prepares the serving route with no `backendRefs`, and such a route answers `500` to a live request (§3.3, spike §2.6). Once `<agent>-auth` is enforced, an anonymous request gets `401` before it reaches the missing backend. So after `Converging`, `ProbingAfter` sends an anonymous `GET /.well-known/agent-card.json` to the serving listener, with the Agent's `Host` header, until one gets `401`. Only then does `Publishing` attach `backendRefs`. The answer attributes itself: a route with no backend cannot produce a `401`, so the policy produced it. A `500` means the replica that answered has not taken the policy yet, and a `404` means the route is not attached yet. Either keeps the stage waiting, under the deadline below. The probe mints no key and writes no `ConfigMap`. This replaces publication on conditions alone, which §3.3.2 measured lying (`reviews/03-a55-critique.md` M2). It proves less than `Narrow`'s probe, in two ways:

- **Authentication, not the group rule.** An anonymous request never reaches the authorization rule, so it cannot show a key in the wrong group getting `403`. That rule sits in the same policy object as the authentication before it. Whether a proxy can take one half of one policy and not the other is unmeasured.
- **One replica.** The rule below applies (H2).

`make conformance-cluster` owes the case that `401` answers before the missing-backend `500` on a prepared route (§8.1). `auth: none` emits no policy and runs no probe.

| Change | Refused probe: before → after | Retained probe: before → after |
|---|---|---|
| admitted groups removed | a key in a group the last `Served` set admits and the new set does not: `200` → `403` | a key in a group both sets admit: `200` → `200` |
| `auth: none` → `apikey` | no credential at all: `200` → `401` | a key in an admitted group: `200` → `200` |
| accepted key-source move | a key under the **old** selector, in an admitted group: `200` → `401` | a key under the **new** selector, in an admitted group: `401` → `200` |

A fourth row, the empty intersection, had a refused probe and no retained one. E2 removed the case: a disjoint change narrows only after a `Loosen` to the union, so a kept group always exists.

**The stages.**

- **`ProbingBefore`**: write the probe `ConfigMap`, then probe until both keys get their "before" answers. This proves that the gateway has read the probe keys, and that the policy in force still admits the principal being removed. So the later refusal is a change, and not the state the transaction started in. It runs only while the policy object still holds the set `status.auth` records as `Served`.
- **`ApplyingPolicies`**: the status update that enters it sets `status.auth.transaction.written`, **before** the policy is written. So a crash between the two reads as written. Then the policy is written.
- **`Converging`**: to §3.3.2's tuple, as for every kind.
- **`ProbingAfter`**: probe until both keys get their "after" answers in the same round, then delete the probe `ConfigMap`.
- **`Served`**: only now does the operator record the narrowed set, in `status.auth`'s `admittedGroups`, `appliedDigest` and `keySource`. Until then status names the wider set, and a weight shift the same edit requires waits.

**Re-entry is one rule, keyed on what was written.** Once `written` is recorded, every later entry to a `Narrow` skips `ProbingBefore`. That covers:

- a generation change, including a second edit that changes the target;
- an operator restart or crash. The restarted operator has lost the in-memory keys, so it deletes the probe `ConfigMap` and mints new ones;
- a NACK;
- a `Narrow` over a policy that an earlier `Loosen` wrote and never verified.

Every such entry restarts at `ApplyingPolicies`, whether or not the target changed. The write is create/update over owned fields (§3.2), so repeating it is a no-op when it already landed. So a crash between the status update that sets `written` and the write itself cannot skip the write. *(A55 re-entered at `ProbingAfter` when the target had not changed. After exactly that crash the narrowed policy was never written, the removed key kept getting `200`, and the Agent wedged at `AuthNarrowingUnverified` with its weight shift held (`reviews/03-a55-critique.md` M1).)* A `Create` of `<agent>-auth` re-enters the same way: at `ApplyingPolicies` when its prepared route exists, and at `PreparingRoute` when it does not. No `-auth` transaction re-enters past its write. After the write, a `Narrow` accepts the **differential alone**: in one round, the removed probe is refused, with the answer the table gives, while the kept probe is served the recorded card. The message then says "transition not observed", so a consumer can tell that proof from the full one. That proof is weaker, and it still attributes: a `403`, not a `401`, on a fresh key whose sibling in the same `ConfigMap` gets the recorded card is authorization refusing that group.

An earlier version exempted a restart alone. An ordinary edit landing after the write then sent the transaction back to `ProbingBefore`. There it waited for a `200` that the written policy had already removed, and the Agent wedged `Degraded`, with the weight shift held (`reviews/03-a54-critique.md` B1).

**Why this probe attributes where the withdrawn witness could not.** That witness failed because a bare `401` or `403` has many producers (the bullets at the top of this subsection). This probe asserts three things together:

- a **transition** on the refused principal, so a backend that already refused it fails the "before" half. After a write, the re-entry rule above accepts the next two alone;
- a **differential**: the retained key must be served in the same round, so a backend or gateway that is failing fails the "after" half;
- a `200` that is the Agent's own card, by digest.

A refusal of exactly the removed principal, while the kept one is served the recorded card, is the narrowing itself, on the replica that answered. `Adopt`'s option (d), below, rests on the same argument.

**The deadline, the condition, and a NACK.**

- **Deadline: 4 minutes, unmeasured for `Narrow`.** `status.auth.transaction.deadline` is set on entering the first stage. The only timing this repository has is a test tolerance. `TestTheGatewayRefusesADisallowedPrincipal` allows 2 minutes for one policy to go from written to enforced, polling every 5 seconds (`test/e2e/authz_test.go:261`, `:268`), and it records no observed latency. A `Narrow` waits for two things of that kind: the gateway reading the probe `ConfigMap`, then the narrowed policy. So the deadline is twice the allowance. It is a constant, not a flag, and §8.1 case 6 owes the measurement that replaces it. At the deadline the machine stays in its stage (§3.3). An earlier version proposed 120 seconds with no argument, which is one allowance for two propagations (`reviews/03-a54-critique.md`, call 6).
- **Condition.** It sets `PolicyApplyIncomplete`, reason **`AuthNarrowingUnverified`**. The message names the principals being removed, the last probe answer (for example "a key in group `audit` still got 200"), and the action: read the policy's status and the Gateway's Warning Events. Status does not claim the tightening. Under §3.3.1's aggregation `Ready` goes `False` and the phase `Degraded`, because a revocation the gateway has not taken is a degraded serving route. Design 10 pages on `PolicyApplyIncomplete` open for more than 5 minutes.
- **NACK.** A NACK naming `<agent>-auth` at any stage returns the machine to `Converging` and re-runs `ProbingAfter`, under the re-entry rule. Status withdraws any recorded narrowing until the probe passes again. A NACK keeps the previous, wider configuration serving (§3.3.2), which is exactly what the probe will report.

**One probe proves one replica, and a pass is still a pass.** A request through a Service reaches whichever replica the load balancer picks, so a probe is evidence about the one gateway instance that answered. The human decided on 2026-09-11 what that evidence earns (H2, ADR-0034 Amendment 1). The rule is the same for `Create`'s probe and for `Narrow`'s:

- **A probe that passes reaches `Served`, and `Ready` is not withheld.** `status.auth.verified` records the replicas probed and declared, and `GovernanceSkipped` is `False`. Its reason is `Governed` when `gatewayReplicas` is 1, because the probe is then a proof. It is **`AuthVerifiedOnOneReplica`** when more than one replica is declared or the number is unknown, and the message names both numbers. That reason is informational.
- **A probe that fails is `Ready=False`, and a page.** At the deadline `PolicyApplyIncomplete` is raised, reason `AuthEnforcementUnverified` for `Create` and `AuthNarrowingUnverified` for `Narrow`, and `Ready` goes `False`. Design 10 pages on `PolicyApplyIncomplete` open for more than 5 minutes (`10:50`).
- **So a probed Agent is never worse off than an unprobed one.** A probe only adds evidence. That is why the qualification is a reason on `GovernanceSkipped`, and not on `PolicyApplyIncomplete` or on a new condition type. `PolicyApplyIncomplete` feeds `Ready` under §3.3.1 and pages. A reason on it made every narrowed Agent on an install with more than one replica, or with an unknown count, permanently un-`Ready`, which was every install. Meanwhile `Create`, which then ran no probe, reported `Ready=True` on less evidence (`reviews/03-a55-critique.md` M3). `GovernanceSkipped` feeds neither `Ready` nor a page: design 10 §5 says it "is never an alert". Its meaning is the claim being qualified, which is how far this Agent's gateway path is governed. It is normal-true and owned, so the reason flips when the evidence changes and does not linger (§3.1). A new condition type would need its own vocabulary entry and classification to say the same thing.
- **What a pass does not claim.** Another replica may not have taken the policy. A NACK Event naming it still returns the transaction to `Converging` (§3.3). A replica that has not taken the policy and raises no Event is not seen. `gateway.replicas` → `--gateway-replicas` is owed (§8.1), and it moves one-replica installs from `AuthVerifiedOnOneReplica` to `Governed`. It is not a prerequisite of the first slice: with no producer every count is unknown, and the informational reason is then true.
- **Per-Pod probing through the `EndpointSlice` is declined**, for the model-fallback table's reason below: it bypasses the production route whose admission is the thing being proved.

*(A55's rule, withdrawn by H2: with more than one replica, or an unknown number, a passing `Narrow` kept `PolicyApplyIncomplete`, reason `AuthNarrowingPartiallyVerified`, and `Ready=False` until a later proof on one replica. That reason is retired.)*

**What it costs, stated because it is new.**

- **The operator mints principals.** For the probe window each probe key is a real credential in a real group. It admits to every Agent whose policy admits that group and whose selector reaches the probe `ConfigMap`, and how far a selector reaches is unmeasured (§3.4.4). The keys are held only in memory, never logged, and deleted with the transaction. This adds no reach the operator lacks, because it can already write the policy, which can admit anyone. The alternative is to trust conditions, which §3.3.2 measured lying (`reviews/03-a54-critique.md`, call 5).
- **RBAC and reservation.** It needs `configmaps` create and delete in run namespaces, which the operator already holds for revision material (`config/rbac/role.yaml`). When design 07 reserves the key-source label (§3.4.4), the reservation must name the operator's identity as a permitted writer, or no probe can run.
- **A fleet fan-out on an accepted key-source change.** Once the administrator accepts the change, every Agent on the old source runs `Narrow`, bounded by the reconcile workers (§3.4.4). The change itself runs nothing, because it is refused while live.

**`Adopt` stays refused** (ADR-0034). The probe machinery its option (d) needed now exists in `Narrow`, and `Adopt` could later be rebuilt on it. That is not decided here.

**`Adopt`: a first policy on a route that is already serving is refused.** An operator with `gateway.enabled: true` and no compiler publishes an unauthenticated `<agent>-serving` route for each Agent (§3.1's `PolicyCompilerAbsent` row). An operator upgraded to carry the compiler finds those routes serving with no `-auth`. None of the other kinds fits. It is not `Create`, because the route exists. It is not `Loosen`. A first application classifies as `Tighten` (below), and `Tighten` mints a revision — but no Agent spec moved, so none mints. The obvious patch is to write the policy onto the live route and trust its conditions, and that is exactly the in-place tightening this subsection forbids: a NACK leaves the open configuration serving while every condition reports converged (§3.3.2, spike §2.8), so the slice would record authentication that is not enforced.

So it is refused. The trigger is a published serving route for an Agent that has **no operator-emitted `-auth`**, judged by §3.2's name-and-label rule so that a foreign policy on the route does not count, and whose `status.apply` is absent, meaning no compiler has ever recorded a transaction for it. An earlier version of this sentence, and of the table above, said "no governing policy". A foreign policy made that false while leaving the route exactly as ungoverned (`reviews/03-a53-critique.md` M3). The compiler then:

- writes **no policy** and attaches **nothing** to the route. It does not freeze the route either. The shipped emitter (design 07 A6.10) keeps owning the route's `backendRefs`, so the Agent serves as it did before the upgrade, and **new revisions of an Adopted Agent keep promoting onto an unauthenticated route** until the Agent is recreated. An earlier version of this bullet said `Adopt` "writes nothing to the route" and, in the same sentence, that its `backendRef` follows promotion. A promotion is a route write, so the first half was false;
- records `status.apply` as `{transaction: Adopt, stage: Refused}`;
- sets **`GovernanceSkipped=True`, reason `CompilerUpgradeUnsupported`**. The message names the route, says it is unauthenticated, and names the action: **recreate the Agent**. A recreated Agent has no route, so it enters `Create` and is published only once its `-auth` converges.
- re-derives `Adopt` after every spec edit. The edit bumps the generation, §3.3's stale-state rule drops `status.apply`, and the trigger holds again, because no spec edit emits a policy. The loop is consistent, and it is stated so that nobody "fixes" it.

**The name is a reason on `GovernanceSkipped`, not a new condition type, and that is deliberate.** The state is precisely "this Agent's gateway path is ungoverned", which is what that type means. Its normal-true, owned classification (§3.1) lets it flip to `False` once the Agent is recreated, rather than lingering. The reason sits beside the operator's own `PolicyCompilerAbsent`, in the same vocabulary. Design 10 keys on the **reason** (§3.1), so it **could** page on `CompilerUpgradeUnsupported` without paging on `GatewayDisabled`. **It does not.** Design 10 §5 says `GovernanceSkipped` "is never an alert" (`10:50`), so an unauthenticated serving route that shows only as this reason is silent in practice. **Owed to design 10**: an alert keyed on `GovernanceSkipped=CompilerUpgradeUnsupported`, a ticket at least since the Agent serves as before, and the same for `ForeignTrafficPolicy`. Design 10 is not edited here. An earlier version of this sentence said design 10 "can page" on it, which design 10's own §5 contradicts. `Ready` is not withheld: the Agent serves exactly what it served before, and a fleet that goes un-`Ready` on upgrade would read as an outage that did not happen. Nothing implements any of this yet.

**The documented future path is option (d), and it is NOT implemented.** `Narrow`'s probe (above) is the same machinery, so (d) no longer needs one of its own. Whether it replaces the refusal is not decided. Apply the `-auth` policy onto the serving route in place, converge it, then run an **enforcement probe**, and only then flip `GovernanceSkipped` to `False`. The probe is an anonymous request through the Gateway to the route's hostname, and it must get `401`. That is safe where the in-place tightening forbidden above is not, for two reasons:

- **The prior state was already open.** A NACK that leaves it serving changes nothing a caller can observe. The fail-open that rule exists to prevent is the state *before* this transaction, not a consequence of it.
- **The probe keeps status honest.** Until an anonymous request is refused, the condition keeps saying the route is ungoverned, so the worst outcome is a true statement that the upgrade has not taken yet.

The probe asserts a **transition**, not a value. Before the apply, the same anonymous request gets the agent's own answer, because the route is open and that is the state being adopted. After the apply, it gets `401`. A backend that returned `401` to anonymous callers would fail the "before" half, so the attribution gap this subsection names for a bare `401` does not arise here. `TestTheGatewayRefusesADisallowedPrincipal` already waits on exactly this probe (`waitForEnforcement`) before it trusts anything else. Two things (d) would still owe: a probe that runs with no credential at all, and a statement of what one probe proves when there is more than one gateway replica, which would be `Narrow`'s replica rule (above).

**`Loosen` needs a comparator, and "admitted set" is not one.** Rate limits are stateful quantities, transforms are functions, timeouts are neither, so "every concern's admitted set is a superset" is not implementable and two reasonable implementations classify the same edit differently. The comparator is a **closed registry, one entry per concern**:

| Concern | Ordering | `Loosen` when |
|---|---|---|
| `-auth` | **on the effective admitted-principal policy**, not the mode enum | the new policy admits a **proved superset** of principals — which in practice means `→ none`, byte-identical policy, or an `apikey` policy whose admitted groups are a superset under the same key source. Anything else is `Tighten`, and on the per-Agent serving `-auth` that is §3.3.3's `Narrow`, not a new revision |
| `-ratelimit` | numeric on the derived rate | the new rate is **≥** the applied one |
| `-toolfilter` | set inclusion on tool names | the new set is a **superset** |
| `egressEnumerated` | set inclusion on endpoint identities | the new set is a **superset** |
| `taskTimeout` | numeric | the new timeout is **≥** the applied one |
| `-transform`, `-guard` | **no ordering exists** | never — functions, not sets |

**`oauth == oauth` is not evidence about who is admitted.** The earlier ordering compared `expose.a2a.auth` as an enum, so two OAuth policies admitting disjoint principal sets both normalized to `oauth` and any change between them classified as no-stricter. An identity or IdP input moving the issuer or audience from one tenant to a broader tenant set is precisely that shape: the enum is unchanged, the admitted set is wider, and the update takes the in-place path onto a serving route that no gate ever approved for those principals.

The `-auth` comparator therefore normalizes to the **complete effective policy** — `{mode, issuer, audiences[], claim predicates, principal identity, key/JWKS source identity}`, assembled from `expose` and from design 06's identity inputs. **For the slice's `apikey` mode** the tuple is `{mode: apikey, key source identity, admitted groups}`. Its applied side is read from `status.auth` (§3.3), never from a revision's record, because `-auth` belongs to no revision. The key source is compared as its canonical selector (sorted `matchLabels`, plus the run namespace). The groups are compared as a sorted, de-duplicated set taken *after* §3.4.4's derivation, so an Agent that declares its own namespace and one that declares nothing normalize equal. **The keys themselves are not an operand.** The policy names the `ConfigMap` by selector and agentgateway reads the hashes live, so adding a key to an admitted group widens the admitted principals with no compile and no comparison at all (§3.4.4 names that cost). Three cases are `Loosen`. The two policies are byte-identical after normalization; or the new one removes authentication entirely; or both are `apikey` over the same key source and the new admitted groups are a superset. The last is a proof, not a heuristic: with one key source a key is admitted exactly when its group is in the set, so more groups admit more keys and never fewer. An earlier version of this sentence named only the first two, which classified adding a group as `Tighten`. Every other change, in any field, is `Unknown → Tighten` — and a tightening from a non-spec producer is withheld rather than applied (below), so a narrowing IdP change cannot silently reach a serving route either. Each field is property-tested **independently**: changing exactly one, with the rest held equal, must not classify as `Loosen`.

**Normalization is part of each comparator, because a default is not an absence.** Before comparing, both sides are normalized to their **effective** value: an `expose.a2a.auth` nobody wrote arrives as `oauth`, because the API server persisted the schema default into the stored object and removing the default migrates nothing (§3.4.4), an absent `expose` block is §3.4.4's derived `apikey` policy, an unset `budget` field is *no limit*, an unset `taskTimeout` is the gateway's own default. Comparing raw presence instead would read a field gaining its default as a change, and a field losing an explicit value equal to the default as a loosening.

**Unknown maps to `Tighten`.** A concern absent from the registry, a comparison it cannot make, and a **first application** — where there is no applied set to compare against — all classify as `Tighten` — except a first application to a route that is **already serving**, which no revision can carry and which is the refused `Adopt` above; and on the per-Agent serving `-auth`, where a stricter policy arrives from the current spec or an accepted key-source change, `Tighten` is `Narrow` — so adding a concern without a comparator entry fails safe rather than silently qualifying for the in-place path. Property-tested for reflexivity and transitivity, plus every boundary: a rate unchanged, a set unchanged, a default appearing or disappearing, and `nil` against a value.

**But `Tighten` means "mint a revision", and not every producer can.** §3.1's provenance table lists inputs that are **not Agent spec**: a Connector CR's `toolAllowlist` (11), a resolved KG endpoint (01/13), and `status.llmFallbackActive`, which design 20 sets deliberately. **One** of those three is somebody's spec on another CR — `toolAllowlist`, on the Connector. `status.llmFallbackActive` is a third category again: status on the Agent's *own* CR, controller-written, with no author and no review at all, and for it "cannot mint" is exactly right. Nor is the Connector case softened by review: **nothing gates a Connector edit today** — the repository's two admission policies reserve namespace labels and gateway routes, neither matches `Connector`, there is no webhook, and design 11 states no gate. So what that producer cannot do is mint a revision of **this** Agent; what it also cannot do, contrary to an earlier draft of this sentence, is be caught on the way in. (Tenant consumer budgets were a fourth until they were removed: a tenant's shared limit is not an Agent-scoped input.) Telling those producers to mint a revision points at a mechanism they do not have — so a tool server withdrawing a tool would narrow a mandatory filter with no path at all.

**The table is TOTAL over provenance × comparator result.** The earlier one had a row for non-spec *tightening* and none for non-spec *widening*, and the missing cell inherited the live path — which is the dangerous direction. `tools[].toolAllowlist` is **not** Agent spec, so a Connector author adding `wire_funds` to `spec.tool.toolAllowlist` produces a superset; the comparator calls a superset `Loosen`; and a `Loosen` applies in place. R1's live tool filter would publish a capability R1 was never evaluated with, with **no Agent edit** and no gate — the Agent's own spec and revision are untouched, which is the whole danger. **A later correction fixed the mechanism and left the conclusion standing**: an earlier draft of this paragraph said an MCP *server* that begins advertising a tool produces the superset. It does not — this compiler never reads a server's surface, only the Connector CR (design 11 §4). The superset arrives by a spec edit on a *different* CR, one the Agent's revision gate does not cover. The same shape applies to any externally resolved endpoint set that grows. No cell may inherit a path implicitly, so every cell is written:

| Provenance | `Equal` | `Loosen` (widening) | `Tighten` | `Unknown` |
|---|---|---|---|---|
| Agent spec, **behaviour** surface | no-op | mints a revision; gated | mints a revision; gated | mints a revision; gated |
| Agent spec, **policy** surface | no-op | in place | in place *(see below)* | mints a revision; gated |
| **Non-spec producer** | no-op | **frozen** | **per-producer contract** (below) | **frozen** |
| **`status.llmFallbackActive`** | — | the stated ADR exception, below | — | — |
| **Declared operator input** — a chart value rendered as an operator flag: `apiKeySource`, `gatewayReplicas` | no-op | **`apiKeySource`**: **refused while the old source is live** on every Agent already served under it (`PolicyInputDrifted`, reason `ApiKeySourceChangeRefused`), then applied as `Narrow` with the key-source probe once the administrator accepts it (§3.4.4). An Agent never served takes the new source at once. It is never a revision, which no Agent edit mints, and never a `Withdraw`. **`gatewayReplicas`**: no recompile; `BudgetEnforcementDegraded=ReplicaSkew` (§3.1, §5) | as `Loosen` | as `Loosen` |

**The declared-input row was missing** (`reviews/03-a53-critique.md` M2). A53 added `apiKeySource` without a cell, so a `helm upgrade` that edited `gateway.apiKeys.selector` fell to the per-producer table's "any producer not listed → fail closed". That meant a `Withdraw`, weight 0, on every Agent in the cluster, with no Agent spec moved. A key-source change is an administrator's decision about where keys live, taken outside every Agent's gate like the keys themselves (§3.4.4). So it is not withdrawn. A54 applied it to every Agent at once under the probe, which stopped every real key under the old selector, fleet-wide, the moment the chart moved and before anyone had copied a key (`reviews/03-a54-critique.md`, call 1). It is now refused while live, and applied only once the administrator accepts it (§3.4.4, ADR-0034 D2).

**"Frozen" needs somewhere to freeze FROM, and there was nowhere.** The rule said the compiler emits R1's filter from "the recorded allowlist" and called it §3.1's persistence rule applied to a new case. It was not: `behaviourProjection` is a projection of **`AgentSpec`**, and `tools[].toolAllowlist` is a field on the *Connector* CR — assayd spec, but not this Agent's, so it is outside the projection all the same. The live overlay is a closed list of seven policy-surface fields. `appliedDigest` is a hash, and §3.1 already says a value reverse-engineered from a gateway policy cannot serve. So **no non-spec producer output was persisted anywhere** — the same gap for `knowledge[].endpoint` and `identity`, both marked "Available at P1? no" in that table.

The comparator has the same problem one step earlier: classifying `Loosen` against `Tighten` needs the **applied** operand — the value that was live before the producer moved — and a digest detects *that* something changed without saying which direction. Without it every non-spec drift falls to `Unknown → Tighten`, including the tool-server *addition* the `Loosen` cell was written for, so the freeze rule and the per-producer contract would produce contradictory behaviour on one event.

`RevisionRecord.resolvedInputs` is that field. **"Frozen" means recompile from `resolvedInputs`**, and the comparator's applied operand for non-spec provenance is `resolvedInputs` — never the cluster, which is the thing that moved.

**Freezing requires something to have been gated, and an at-mint seal could freeze an absence.** `resolvedInputs` was written at mint, and `ProducerAbsent` and `Unresolvable` are legitimate states at that instant — so an Agent created while design 11 is not installed recorded "no tools resolved" as the value every later comparison was made against. Installing design 11 then produced a change from *absent* to *resolved*, which is a widening; the non-spec `Loosen` cell says **frozen**; and no Agent write could escape it, because the behaviour projection is a function of spec and the spec had not moved. The Agent stayed `CapabilityUnavailable` for as long as it existed.

**Nothing seals until the revision carries traffic, and then only the bindings that resolved.** Reaching the apply machine's `Served` stage is not the trigger and cannot be: §3.3.1's failure is route-scoped, so the serving and card routes compile and apply while an absent producer's route is simply not emitted — a transaction reaches `Served` with a declared binding unresolved, and sealing there would freeze the absence exactly as before. The trigger is the revision becoming `status.activeRevisionDigest`, and the seal is per binding. Precisely: the seal captures **the material the revision published with** — not material a gate inspected, since design 16 evaluates behaviour through the gateway and never reads a tool catalogue — so what freezing protects is the configuration that was live when traffic was admitted to it, which is the property the freeze needs and the strongest one available.

That leaves three states, and each is stated because two of them were previously one:

| Binding state | Applied operand | Behaviour |
|---|---|---|
| **Sealed** — `Resolved` at the instant the revision became active | the sealed value | The freeze applies: a producer moving is compared against the value the revision was **serving with when it was promoted**, and a widening is refused with `PolicyInputDrifted`. Not "what the gate approved": design 16 evaluates behaviour through the gateway and never reads a catalogue |
| **Unsealed on a revision that has never been active** | none | nothing carries production traffic, so nothing can be widened ungated. The binding re-resolves each reconcile and the revision recompiles as a **`Create`** — the comparator is not consulted, because `Create` is what a revision whose routes are not yet published runs, and a candidate's route admits only the eval principal. A re-resolution that *narrows* what that candidate offers is the same `Create` over a new desired set, and the eval then judges the narrowed set, which is correct: the gate must see what would actually serve. This is the recovery path an at-mint seal removed |
| **Unsealed on an active revision** — the producer was absent at that instant | none, and **none is manufactured** | the capability is **withheld**, not applied. The revision was promoted and has served without it, so the producer arriving later is an ungated widening exactly as the freeze rule describes; `PolicyInputDrifted` names the producer and the binding. The comparator must **not** fall back to comparing the current value against itself — that classifies every drift as `Equal`, never freezes, and lets a resolved sibling's catalogue widen a live route with no gate |

**One escape hatch exists, and it is named rather than left to be found.** A producer widening is frozen for the *active* revision, and the **next** revision compiles with whatever is current, because a new revision has nothing sealed. So an operator who sees `PolicyInputDrifted` and edits any behaviour field for any reason mints a revision that picks the widened catalogue up — gated on its *behaviour*, not on the catalogue. That is the `{A} → {A,B} → {B}` laundering shape in another place. It is the intended semantics, since a new revision should be evaluated as it will actually serve, catalogue included — but "the eval evaluated the new catalogue" holds only if the suite exercises the new tool, which nothing enforces. **Owed to design 16**: whether a suite must cover every tool its candidate can reach, or the gate's claim is narrower than it reads.

**The residual is a real one and is not solved here.** A revision that went active without a capability its Agent declared can never acquire it, because the behaviour projection is a function of spec and no spec moved — so `CapabilityUnavailable` is permanent for that revision, correctly, and there is no automatic path to a gated one. Two ways out exist and both are design 02's to choose: fold each declared binding's **resolution state** into the revision projection, so a producer appearing mints a candidate that gets gated (a projection change, and therefore a hash migration); or state that an Agent whose declared capability was unavailable at promotion must be given a spec edit to pick it up. **Owed to design 02**, with this design's preference recorded as the first, because the second asks a user to make a meaningless edit and to know why.

**§3.1 already says an active revision recompiles from its `RevisionRecord` plus the closed live overlay**, so this extends the record rather than adding a mechanism. So the compiler emits R1's filter from the **recorded** allowlist, exactly as it was gated, and the tool newly added to the Connector's allowlist simply does not appear in it. `PolicyInputDrifted` names the producer and the input. This is not a new mechanism — it is §3.1's persistence rule applied to the case the old table let slip past it.

Policy-surface tightening is listed as in place, and the surface no longer carries a concern where that is dangerous: `budget`, `expose` and `requiresApproval` all moved to the behaviour surface precisely because in-place tightening on them could NACK and leave the looser configuration serving. What remains — `replicas`, `port`, `resources`, `card.path`, `inlineCard`, `gates`, `loop` — feeds no mandatory concern.

**A "policy-input revision" was a noun and a hash, not a lifecycle.** An earlier row gave non-spec tightening a content-addressed candidate and said it was "gated like any other". Nothing supported that. The only revision lifecycle assayd has is design 02's behaviour revision keyed by `status.activeRevision` / `status.candidateRevision`, and every stage of it is missing for a policy-only candidate: there is no candidate workload to run, no card to register, no EvalRun binding, no rule saying which result promotes it, no rollback identity distinguishing R1+P1 from R1+P2, and no retention entry. Reusing `candidateRevision` collides with a real Agent-spec candidate; not reusing it makes the gate invisible to design 16.

So the change is **withheld** instead. The active revision keeps serving the material that passed its gate, and `PolicyInputDrifted` names the producer and the input that moved, so the divergence is loud (NFR-8) rather than silently applied or silently dropped.

**Withholding is safe only where the SOURCE enforces the same restriction, and that is a per-producer fact.** An earlier draft argued the general case from one example — an MCP server withdrawing a tool, where the capability is already gone at the source, so narrowing assayd's filter removes a name that no longer resolves and closes nothing. That reasoning is sound *for that producer* and was then applied to a generic row covering producers where it is false. Withholding there is fail-open: a condition is observability, not enforcement.

| Non-spec producer | Tightening path | Why |
|---|---|---|
| A Connector author removes a tool from `spec.tool.toolAllowlist`, or the tool server stops serving one (design 11) | **withhold**, `PolicyInputDrifted` | the tool server rejects the call whether or not assayd narrows the filter. **Owed: a kgp/MCP conformance case proving the withdrawn tool is refused at the source.** Until it passes, this row has no evidence and must behave as the row below |
| ~~Tenant consumer budget lowered (design 26)~~ | **not this design's row** | a tenant's limit is not a per-Agent input and cannot be transacted per Agent; it belongs to the tenant-scoped intent and record design 26 owes. Removed here rather than left pointing at a producer that does not exist |
| Identity / IdP issuer, audience or claim change (design 06) | **fail the affected route closed** | a revoked audience is not refused upstream — the gateway validates locally against JWKS, so the old, broader admitted-principal policy keeps admitting until assayd changes it |
| any producer not listed | **fail closed**. Declared operator inputs are not producers, and have their own row in the table above | the default is the safe one; adding a producer with a withhold path requires its source-enforcement evidence, not an argument by analogy |

**"Fail closed" is a THIRD TRANSACTION, not a weight patch.** Written as "the route's weight goes to zero" it collided with three rules in this same body: §3.3.3 then said no transaction tightens a serving route in place (it now names one, `Narrow`, trusted only on a probe), §3.3.3's table listed **two** kinds at the time so `status.apply.transaction` had no value for it — the table now carries `Withdraw` as its third row, which is what closed that collision — and the weight-shift rule below says a weight shift is a live mutation whose landing must be proved. Withdrawal as first written required no postcondition, and none is available: the witness for "this route is now closed" is the *absence* of receipts, which is the negative witness the withdrawn `Tighten` transaction was retracted for. A tenant cut from 1,000 to 1 req/hour could keep being served 1,000 while assayd recorded enforcement — worse than plain withholding, which at least reported the overspend it was not preventing.

`Withdraw` is therefore a real transaction with stages. It was justified on the ground that a weight-0 route is **no longer a serving route**, so applying to it is not §3.3.3's forbidden operation — and that justification holds only at the control plane, which is the reduction stated below: assayd applies to a route it has asked to be dark and cannot prove is dark, so `ApplyingPolicies` here may narrow a route that is, in the failure case, still carrying traffic. That is a smaller exposure than mutating a route known to be serving, and it is not zero:

Its row is the third one in this subsection's transaction table above, not a second table here — an earlier version of this passage restated the stages in a table of their own, which is how one rule comes to be stated twice and drift.

Two consequences are stated rather than left to an implementer. The **recovery is the same transaction's tail**, so lowering a tenant's budget is a brief withdrawal and not a permanent outage — without that sentence, read literally, the per-producer rule took every agent in a tenant offline forever. And the condition is **`PolicyInputDrifted` with reason `RouteFailedClosed`**, not `PolicyApplyIncomplete`: §3.3.1 separates conditions by cause precisely so an apply-failure type would stop naming causes that were never apply failures, and a deliberate refusal is a third cause.

**`Withdraw` withdraws at the control plane, and cannot prove the dataplane followed.** The stage list above says "converge at the current generation" and then applies the tightened policy to what it calls a non-serving route. Convergence is exactly the signal §3.3.2 measured lying: a NACK'd update reports `Accepted=True, Attached=True` at the current generation while the **previous configuration keeps serving**. So a weight-0 patch that NACKs leaves the route serving at its old weight, and the transaction would then apply a tightened policy to a route it wrongly believes is dark — and record enforcement that never happened.

There is no positive witness for "this route is not serving": absence of receipts is the negative witness the withdrawn `Tighten` transaction was retracted for, and it cannot distinguish a withdrawn route from an idle one. So this design does **not** claim the withdrawal is enforced. What it claims, and what the condition says, is:

- the withdrawal is **applied and converged at the control plane**, which is all any apply in this design proves;
- there **is** a sound positive witness for *failure*, and it is buildable now. A receipt attributing traffic to the withdrawn route after it converged proves the withdrawal did not take — presence proves failure even where absence proves nothing. An earlier draft of this amendment deferred it on the ground that nothing could attribute a receipt to a route, and a primary-source pass disproved that: agentgateway emits `route` as `<namespace>/<name>` **by default** (`research/agentgateway-otlp-attributes-2026-09.md` §5), and design 04 A5 adds `hop.route` to the envelope from that attribute. **An earlier version of this sentence said §3.2's names carry `-<rev>`, so the attribute names the revision's route. The serving route is per Agent (§3.2), so it does not.** `route` names `<agent>-serving`, which is the Agent, and `route_rule` does not separate revisions either, because their weights split within one rule. The witness survives at Agent granularity, and for `Withdraw` that is enough, because `Withdraw` zeroes every `backendRef` on the route: a receipt naming the route after it converged, outside the drain window, still proves the withdrawal did not take. What the receipt cannot say is which revision served. **Design 04 A5 rests on the same false premise** (`04:125`, which an earlier version of this sentence cited as `04:122` before the line moved: "`route` names the revision and not merely the Agent") and is owed the same correction; design 04 is not edited here. What is still owed is narrower and is only the **drain allowance**: a task in flight when the weight went to zero legitimately produces receipts afterwards, so the witness fires only outside a stated drain window, and until that window is specified the check would read a lawful drain as a failure;
- until upstream publishes a positive dataplane acknowledgement, a tightening on this path is **best-effort at the dataplane**, and every consumer of `PolicyInputDrifted=RouteFailedClosed` must read it as "assayd refused, and cannot prove the refusal reached traffic."

If the withdrawal cannot be shown to have converged at all, the route stays withdrawn and the condition stays — failing to restore traffic is the safe direction, and it is the one case where absence of evidence and absence of traffic agree. The condition keeps the single reason `RouteFailedClosed`, for a reason of its own. An earlier version of this sentence, and one beside `Withdraw`'s condition above, argued that a second reason would page identically because design 10 and design 08 key on the condition **type**. §3.1 withdraws that claim: design 10 keys on the **reason**, so it could page on a second one. What actually decides it is that the escalation a second reason would signal — a receipt proving the withdrawal did not take — has no producer until design 04 carries a drain allowance (§8.1). A reason nothing can set is vocabulary without a writer. When that witness is buildable, it earns its own reason. **This is a reduction in what an earlier draft claimed** and it is deliberate: the per-producer rule's only remaining fail-closed producer is design 06's identity path, where the gateway validates JWTs locally and no assayd-side enforcement point exists at all. Where a genuine guarantee is needed, it must come from a mechanism assayd itself runs — as the receipt backstop does for agent budgets — not from an apply the dataplane may reject.

This is a real reduction in what the design claims, and it is deliberate. If a future producer needs a tightening that is *not* already enforced at its source, that needs a composite revision identity `{behaviourHash, policyInputHash}` carried through status, candidate route, EvalRun binding, promotion, rollback, supersession, receipt attribution and GC — a design change with an ADR, not a table row.

**`tools[].requiresApproval` had no transaction at all, in the dangerous direction.** It was a policy-surface field and an input to `PolicyIntent`, but the closed comparator registry has no approval concern — so `Unknown → Tighten`, and a tightening on the policy surface has no revision to mint. `false → true` therefore reached **no transaction**: an implementation either wedges while the unguarded route keeps serving, or mutates the serving interceptor in place and can NACK, leaving the direct route live while status records the change as requested. That is the measured NACK-retains-old-configuration failure (§3.3.2, spike §2.8) landing on an approval boundary, and it is reached by turning approval **on** after an incident — the moment the field exists for.

`requiresApproval` moves to the **behaviour surface** and enters the revision projection injectively, exactly as `budget` and `expose` do (design 02 §3.3). Both directions gate: turning approval on mints a revision, and so does turning it off, because removing an approval requirement is a widening that should never reach production ungated. The alternative — a complete approval-policy comparator plus a real policy-input revision lifecycle — buys nothing this does not, and the policy-input revision lifecycle it would need has been withdrawn above. Design 02 §3.3's classification table is amended in the same change.

**`llmFallbackActive` is not covered by this machinery, and saying so is the point.** Design 20 flips status so an incident is not delayed by an eval cycle — the exemption design 02 §3.3 already records as making the answering model changeable ungated. Claiming this section's isolation covers it would assert protection the path does not have. What it owes instead is **pre-provisioning**: the fallback's Backend is emitted and converged *before* drift is detected, so activation is a weight shift over already-converged material rather than a live recompile that can NACK and leave the drifted primary serving while status records a remediation.

**A weight shift is still a live mutation, and the precheck does not prove it landed.** An earlier amendment removed the live Backend recompile and left the route patch, which is the same class of unverified apply one object over: this design already says route status proves control-plane convergence rather than enforcement, and that v1.4.1 exposes no `Programmed` condition. So `ModelDrifted` fires, both Backends pass the precheck, the `100/0 → 0/100` patch is accepted by Kubernetes and not programmed by the dataplane — and assayd records the fallback as active while the drifted primary keeps answering. That is the identical loud-and-wrong outcome the single-mechanism rule says it removed, relocated from the Backend to the route.

The canary is what closes it, and it is a **positive** witness rather than the negative one the withdrawn transaction was retracted for: a receipt naming the fallback's endpoint identity says *this* destination served the request. A 401, a 429 or an unreachable host has many possible producers, which is why the absence of an error proved nothing; a receipt attributing a response to a named endpoint has one.

**One mechanism, everywhere.** Two incompatible ones were authoritative at once: this paragraph required pre-provisioning and a weight shift, while §3.4's mapping row and design 20 §3 said the controller flips status and **recompiles the existing LLM Backend**. Those are not variants of one design — a recompile during an incident is exactly the live apply that can NACK, and the measurement above says the dataplane then keeps the old configuration while Kubernetes status reports converged. An implementer following design 20 would have built the failure mode this paragraph was written to avoid, and `llmFallbackActive` would report a remediation while the drifted primary kept answering. Every "recompile the existing Backend" instruction is removed (design 20 A3); the pre-provisioned pair and the weight shift are the only mechanism. Named concretely:

| | |
|---|---|
| Backends | `<agent>-llm-primary`, `<agent>-llm-fallback`, both emitted at revision publish |
| Activation | serving `HTTPRoute` → `spec.rules[].backendRefs[].weight` = `0` (primary) / `100` (fallback) |
| Precondition | the fallback Backend is `Accepted=True` **and** its route ancestor reports `ResolvedRefs=True` at the current generation. If it is not, activation does not proceed and `LLMFallbackUnavailable` says so — a fallback that was never converged is not a remediation |
| **Postcondition** | activation is a **staged reconcile with separate desired and applied state**, because the precondition only proves the state *before* the weight edit. After the route's generation changes, the operator requires convergence **at that new generation**, then runs the model canary **through the production route** and attributes the result by the **full endpoint identity in the receipt**. Only then does the remediated condition go true |
| **On timeout** | `ModelDrifted` **stays**, `LLMFallbackUnavailable` is raised, and it pages. The one thing that must not happen is recording a remediation that did not take |
| **The witness is bounded, and the replica-complete proof cannot be made** | One receipt witnesses **one gateway replica**. §3.1 declares `gatewayReplicas` may exceed one and §3.4 records that config resolution varies per replica and per restart, so a single canary proves one dataplane instance took the weights while the other N−1 may still be sending production traffic to the drifted primary. An earlier row required "a distinct instance per replica" and that requirement is **withdrawn here — but design 20's body still carries it** (`20:21`: "activation requires a distinct instance per replica or reports `LLMFallbackUnavailable/PartiallyProgrammed`"), and design 20 is owed the same withdrawal. Not for want of the field — measured against tag `v1.4.1`, `hop.gatewayInstance` has four default producers (design 04 A5) — but because it would not be a proof — nothing routes a canary to a *chosen* replica through a Service, so "N distinct instances seen" is a coincidence of load balancing rather than coverage, and a rollout leaves stale instance identities in recent receipts that inflate the count while a current replica sits unwitnessed. **The reason is no proof, not no input.** An earlier draft of this amendment said both fields had no producer; measured against tag `v1.4.1`, `hop.gatewayInstance` has four defaults and `hop.endpoint` has three of its four parts, so the canary *can* attribute — with three gaps, not the one an earlier draft named. Azure's `deploymentName` and Vertex's `projectId` are emitted nowhere, so two deployments on one endpoint differing only in deployment are indistinguishable in receipts and a fallback to such a pair cannot be witnessed at all; and the CRD arm is **not recoverable** either, since agentgateway emits `azure` where the CRD says `azureopenai` (design 04 A5). Outside those the canary attributes correctly, and what remains withdrawn is only the per-replica claim, for the routing reason above and not for want of a field. Once they exist, what activation may claim is bounded: with `gatewayReplicas == 1` a positive canary is a proof; with more than one it is evidence about **one** instance, so activation reports `LLMFallbackUnavailable` with a message naming the instances seen and the number expected, and `llmFallbackActive` is not recorded as a clean remediation. The **action** that message must name is concrete or the page is unactionable on every HA install: either accept the fallback as partially programmed and watch receipts, or scale the gateway to one replica to obtain a decidable answer. A per-replica proof **is** obtainable — resolve the gateway's `EndpointSlice` and dial each Pod directly — and this design **declines to build it**: per-Pod canary addressing is a new dataplane-probing mechanism costing N direct dials per activation plus a membership watch, and it bypasses the production route whose admission the canary was designed to go through. A declined option with a named cost, not an impossibility |
| **The canary must be admitted** | The canary runs through the **production** route, whose `-auth` admits the agent's SVID; design 20 §5 gives it the platform principal `drift:model-canary`. Adding that principal to a serving route's admitted set at activation time would be a widening of the behaviour surface, mid-incident. So the canary principal is admitted **at revision publish**, as part of the route's original gated admitted set. **An earlier version of this cell justified that by analogy — "like design 16's eval principal, which §3.4 already admits the same way" — and the analogy is backwards.** Design 16 admits its eval principal by a live add at Job launch and a live remove at Job end (`16:51`, "at Job launch, removing it at Job end — a narrow, temporary, compiled grant"), which is what §3.4's own eval row says too; the two sentences in this document disagreed with each other, and the one used as justification was the wrong one. The eval case is not a counterexample to §3.3.3's live-admission hazard, it is an **instance** of it — tolerable only because it runs on a **candidate** route whose admitted set is one SVID and which carries no production traffic. The canary runs on the **production** route, where the same live add is precisely the ungated mid-incident widening this cell exists to refuse, so it gets the opposite treatment for that reason and not by analogy. A fallback that requires a widening to verify itself cannot be verified |
| **The reverse shift** | Carries the **same postcondition**. An earlier row gave rollback "the reverse weight shift, gated on the primary's drift clearing" and no canary — so a shift back that did not land would clear `llmFallbackActive` while traffic still went to the fallback, typically a cheaper or weaker model, silently and indefinitely. The weight-shift argument applies unchanged and was not applied to the path that runs *after* the incident, when nobody is watching |
| Fallback convergence later lost | `LLMFallbackUnavailable`; weights are **not** shifted back automatically, because the primary is the thing already known to be drifted |
| Rollback | the reverse weight shift, gated on the primary's drift clearing; no recompile on this path either |

Being wrong toward `Create` costs a gate cycle. Being wrong toward `Loosen` is the bypass this section exists to remove.

**A NACK during `Loosen` is bounded by what a loosening can do.** It leaves the *stricter* old configuration serving — a failure toward denial, which is the direction §3.3's ordering has always preferred. It still raises `PolicyApplyIncomplete` (§3.3.2), because a loosening that silently did not apply is a stale guarantee even when it is a safe one.

### 3.4.1 Egress is enumeration, not restriction

`llm.egressAllowlist` was specified as compiling to "a Backend restriction". **No such field exists** — one grep of the whole CRD API returns a single unrelated hit (the MCP JSON-RPC method allowlist). There is no host, domain, provider or model allowlist on `AgentgatewayBackend`, so nothing can filter a wider set down to an allowed one.

What the schema does expose is a **closed set of destinations by construction**. `AgentgatewayBackendSpec` is `ExactlyOneOf=ai;static;dynamicForwardProxy;mcp;aws;a2a`; the `ai` arm holds one `LLMProvider` or `groups[]` of them (**max 8 groups × 16 providers** — a bound the compiler enforces, and a compile error past it). A Backend reaches the providers it names and nothing else. So the control compiles to: *emit a Backend enumerating exactly the endpoints the Agent **requested**, prove that set is a **subset** of what the allowlist **permits**, and ensure the route can reach no other Backend.*

Three consequences the old wording hid:

- **assayd owns the provider→endpoint catalog; agentgateway supplies none.** An allowlist entry is meaningless until it resolves to a concrete arm plus an effective host, and the arm it may name is **assayd's** six-member enum: `anthropic`, `openai`, `azureopenai`, `vertexai`, `bedrock`, `custom` (`api/v1alpha1/agent_types.go`, `+kubebuilder:validation:Enum` on `LLMArm`). An earlier draft listed **eight** here, adding `gemini` and `azure`, by copying agentgateway's own `LLMProvider` one-of — which does carry those two, primary-source verified (`research/agentgateway-v1.4.1-2026-08.md`, "What the Backend schema actually exposes"). **The two sets are not the same set, and the one that governs is assayd's**: `spec.llm.egressAllowlist[].arm` is `LLMArm`, so an entry naming `gemini` or `azure` is refused at admission and a Gemini destination is not expressible in the CR at all. An entry that resolves to nothing is `PolicyCompileFailed` naming it — never dropped, because a dropped entry silently widens nothing but a dropped *deny* silently widens everything.
- **`dynamicForwardProxy` is the anti-control and is forbidden outright.** Its own doc comment: *"this backend type can send requests to arbitrary destinations."* The compiler never emits it and rejects any intent that would require it.
- **The predicate reads the effective host, not the provider name.** `host`/`port` **override managed-provider defaults**, so a Backend naming `openai` is not pinned to OpenAI's endpoint. `egressEnumerated` is therefore a predicate over the resolved endpoint set — provider default, or the override where one is set — and a `custom` provider must carry `providerBackend` or `hostOverride` or translation fails anyway.

**This is a design change, not a wording fix, and it is not finished here.** The catalog's contents, its versioning, and how it stays correct as vendors move endpoints are unspecified — and the allowlist entry grammar (host? provider id? model id?) is still undefined, which is Codex BLOCKER 6's substance. What this section settles is the *mechanism*: enumeration, with a assayd-owned resolver and a `dynamicForwardProxy` ban. ADR-0014's "enforced at the gateway" wording carries the same error and now carries the correction, as that ADR's Amendment 1.

#### 3.4.1.1 The entry grammar, the catalog, and the subset rule

§3.4.1 settled the mechanism and left the language undefined, which is not an implementable control. Three things follow.

**Entries carry the provider's own identity, because a name and a host are both too weak.** An earlier draft used `provider:` or `host:`, which the shipped CRD refutes: a managed provider's destination depends on **instance** fields, not on the arm alone. Read from the shipped assayd CRD — `LLMEndpoint`, `LLMAllowEntry` and the four instance types in `api/v1alpha1/agent_types.go` — the instance block is **named for its arm** and is required by CEL whenever that arm is named:

| Arm | Instance block | Fields, exactly as the CRD declares them |
|---|---|---|
| `anthropic`, `openai` | none | `model` on the entry itself (`models[]` on an allowlist entry) |
| `azureopenai` | `azureopenai:` | `endpoint` (required), `deploymentName`, `apiVersion` — and **no `model`**, refused by CEL on `LLMEndpoint` |
| `vertexai` | `vertexai:` | `projectId`, `region` (both required), plus `model` on the entry |
| `bedrock` | `bedrock:` | `region` (required), `guardrail`, plus `model` on the entry |
| `custom` | `custom:` | `host` (required), `port`, `pathPrefix`, plus `model` on the entry |

**An earlier version of this table was read from the v1.4.1 `AgentgatewayBackend` schema instead**, and gave `custom` as `backendRef, formats, model`. Those are agentgateway's `LLMProvider` fields, not the CR's: assayd's `custom` arm is `{host, port, pathPrefix}`, and **no `scheme` field exists anywhere in `api/v1alpha1`**. The table is the CR's, because the CR is what a user writes and what admission checks.

Two Azure OpenAI resources therefore share the `azureopenai` arm and differ in `endpoint` and `deploymentName` — and may differ in BAA status. An arm-level entry cannot tell them apart, so it must either reject a valid endpoint or permit both. A host-only entry is no better: it carries no port, and two services on one host at different ports are indistinguishable.

Entries are therefore an **endpoint identity**, discriminated by arm and carrying that arm's instance fields:

```yaml
egressAllowlist:
  - arm: anthropic                              # every model this arm serves
  - arm: openai
    models: [gpt-4o, gpt-4o-mini]               # narrowed
  - arm: azureopenai
    azureopenai: {endpoint: acme.openai.azure.com, deploymentName: gpt4o-prod}
  - arm: custom
    custom: {host: llm.internal.example.com, port: 8443, pathPrefix: /v1}
```

**An earlier version of this example wrote `instance: {…}` and `endpoint: {scheme: https, …}`, and none of the three exists.** The block is named for its arm — `azureopenai:`, `vertexai:`, `bedrock:`, `custom:` — there is no `instance:` wrapper, no `endpoint:` wrapper on `custom`, and no `scheme` field in `api/v1alpha1` at all. Written the old way the CR is rejected outright by `LLMAllowEntry`'s `(self.arm == 'custom') == has(self.custom)` rule: not a gap in enforcement, a shape that does not exist.

**`models` is enforceable on some arms and not others, and the difference is in the table above.** `anthropic`, `openai`, `vertexai`, `bedrock` and `custom` each carry a `model` field, so a narrowed set compiles into the emitted provider block. **`azureopenai` does not** — it carries `apiVersion`, `deploymentName` and `endpoint`, and at `apiVersion: v1` the model may be supplied by the request, so nothing in the provider block pins it. An earlier draft claimed "every arm carries its own `model` field" **twenty lines below the table that shows otherwise**, which would have let a `models:` permission on an Azure endpoint pass the tuple check while enforcing nothing. So: a `models`-scoped entry is **rejected at compile time for `azureopenai`** unless a non-v1 `deploymentName` is given and treated as the constrained model identity. Pinning v1 model selection would need a request-level guard this design does not emit, and inventing one here is what the retraction above exists to stop. Anything unresolvable is `PolicyCompileFailed` naming the entry — **never dropped**, because a dropped entry silently widens the emitted set.

**The catalog is assayd's, because agentgateway ships none.** A `ConfigMap assayd-provider-endpoints`, chart-shipped and versioned exactly like the pricing table (§3.5), maps each `LLMArm` — the closed **six**-member set `anthropic openai azureopenai vertexai bedrock custom`, read from the enum on `LLMArm` in `api/v1alpha1/agent_types.go` — to its effective host(s). An earlier draft wrote `openai azureopenai azure anthropic gemini vertexai bedrock custom` here and called it "verified in the shipped CRD": eight is agentgateway's `LLMProvider` count, six is assayd's, and the shipped CRD is assayd's. The catalog is keyed on what an allowlist entry can carry, so two of those eight had no key to occupy. It carries the same staleness and single-writer rules as the pricing table, and for the same reason: two writers inside one YAML scalar cannot be given disjoint ownership.

**Requested ⊆ permitted, and never equality.** §3.4.1 says the emitted Backend's provider set must *equal* the allowlist. That conflates two different things: `llm.providers` is what the Agent **requested**, `egressAllowlist` is a **ceiling** on what it may reach. Under equality, a compliance profile permitting `{A,B,C}` for an Agent that requested only `{A}` would emit a Backend that can reach B and C — turning a permission into a destination. The rule is:

- the emitted Backend enumerates the resolved **requested** set, `providers[] ∪ {fallback}` (§3.5);
- `egressEnumerated` holds iff every emitted provider's **resolved endpoint identity** — the tuple `{arm, that arm's instance block, model}`, which for `custom` is where `host`, `port` and `pathPrefix` live — is matched by an allowlist entry. An earlier draft wrote that tuple as `{arm, scheme, host, port, pathPrefix, instance fields, model}`, naming a `scheme` the CRD does not have and hoisting three `custom`-only fields to the top level; `internal/revision/revision.go`'s `endpointIdentity` is the canonical form and is `arm | instance | model`;
- a destination is **never** added because it is permitted.

The predicate compares **tuples, not hostnames**. An earlier draft compared effective hosts, which cannot separate two ports on one host or two Azure deployments behind one endpoint.

**What this guarantee does not cover, stated rather than implied.** The predicate is over **names**, not addresses: assayd does not resolve DNS, so a permitted hostname that later repoints is outside the control, and pinning addresses would break every managed provider. `host`/`port` overrides are themselves checked against the allowlist, since a managed-provider Backend is not pinned to its vendor's endpoint (§3.4.1). `internal/*` resolves inside any allowlist by construction — an in-cluster Service is not egress. And `dynamicForwardProxy` is never emitted at all.

### 3.4.2 MCP tool filtering is first-class CEL

`Mcp-Name` header matching was the mechanism when the superseded note was written. At v1.4.1 there is a real one: **`AgentgatewayPolicy.spec.backend.mcp.authorization`**, a CEL `Authorization` at the MCP layer whose context exposes `mcp.tool.name` and JWT claims together.

It is strictly stronger than header matching in the way that matters: *"List operations, such as `list_tools`, will have each item evaluated. Items that do not meet the rule will be filtered."* A tool the agent may not call is **absent from `tools/list`**, not merely rejected on call — an agent cannot attempt what it cannot see, and header matching could never do that.

Three rules the emission must follow:

- **`action: Allow`, never `Deny`.** Once any allow rule exists the policy is default-deny, which is the shape a tool allowlist needs. Upstream warns that *"`Deny` is not recommended because expression failures fail to deny"* — a CEL error under `Deny` fails **open**, which is the one failure mode this design cannot accept.
- **Auth moves to `traffic.jwtAuthentication.mcp`.** `backend.mcp.authentication` is deprecated in favour of it *"which ensures authentication runs before other policies such as transformation and rate limiting"* — directly the ordering §3.3.1 needs for `-auth` before `-toolfilter`. The two may not appear in the same policy, which one-concern-per-policy already prevents.
- **Targeting constraints**: `backend.mcp` may not target a `Service`, and may not target an `AgentgatewayBackend` `sectionName`. Both are compile-time checks.

**Emission is total at the CRD's bounds** — `minItems: 1`, `maxItems: 256`, `maxLength: 16384` per expression, verified in the shipped chart and pinned by `test/conformance`. Three cases an earlier draft left undefined, each with a wrong-but-plausible answer:

| Case | Emission |
|---|---|
| **no tools allowed** | one expression `false`. **Not an empty list** — `minItems: 1` rejects it — and **not an omitted policy**, which restores upstream's default-allow and turns "no tools" into *every* tool |
| **more than 256 tools** | `PolicyCompileFailed` naming the count; truncating would silently deny the remainder while reporting success |
| **a name with a quote, backslash or newline** | a real CEL string encoder, never concatenation. A broken expression under `action: Allow` denies everything — a self-inflicted outage — and under `Deny` fails **open**, which is why §3.4.2 forbids `Deny` |

Golden fixtures pin 0, 1, 256 and 257 tools, and names carrying quotes, backslashes, slashes and non-ASCII.

#### 3.4.2.1 MCP backends compile `sessionRouting: Stateless`

This design was **recorded as owing** an answer here (`research/agentgateway-v1.5.0-delta-2026-09.md`, addendum 3): are assayd's MCP backends `Stateful` or `Stateless`, and what does a stateful session do to design 02's weighted revision shifting? The answer landed in `research/mcp-session-statefulness-2026-09.md` on 2026-09-09 and did not reach this document's 2026-09-10 consolidation. It is stated here rather than left owed.

**The decision, and it is a ratification rather than a choice.** Every emitted `AgentgatewayBackend.spec.mcp` carries `sessionRouting: Stateless`. Three measured facts force it and one of them removes the alternative:

- **MCP revision `2026-07-28` removed protocol-level sessions from the wire entirely** — `Mcp-Session-Id` is gone, not deprecated, along with the `initialize` handshake (SEP-2575, SEP-2567). There is no session to pin, so the question is no longer "which should assayd pick".
- **agentgateway defaults this field to `Stateful`.** A default is not an absence (§3.3.3), so the compiler must emit the value explicitly or inherit the posture the spec deleted. `test/e2e/mcp_test.go` already sets `Stateless` by hand, with a comment saying assayd had not decided; that fixture stops being a shortcut and becomes the specified emission.
- **A stateful session defeats `backendRefs` weight shifting, by specification.** GEP-1619: persistence "MUST be maintained across services, **even if the weight is set to 0**", and "a persistent session takes precedence over traffic split weights". Design 02 uses weight 0 as a *containment* action on four failure paths, so a session-persistent backend would make weight 0 stop containing.

**Two things stay OPEN, and neither is this design's alone.**

- **A Connector whose tool server predates `2026-07-28` and requires statefulness is ineligible for weighted shifting**, because GEP-1619 says its sessions will ignore the weights including weight 0. Nothing marks such a Connector today. **Owed to design 11**: a declared field, or a statement that its tool facet is uncompilable under weighted shifting. Until then the compiler emits `Stateless` and a genuinely stateful upstream is bridged rather than pinned — agentgateway synthesizes a fresh per-request initialization against it — which is the research note's item 7 and is not a guarantee this design can make about the upstream's own correctness.
- **The gateway half is unmeasured.** Nobody here has driven a `2026-07-28` exchange through the pinned gateway; the dual-path claim is agentgateway's blog, not an observation on this cluster. What *has* been measured is the containment base case and the reachability of the hazard: `TestWeightZeroActuallyContains` shows weight 0 stops traffic where no persistence exists, and `TestGatewayAPIHasNoSessionPersistenceHere` shows `sessionPersistence` is an experimental-channel field absent from the standard install, so GEP-1619's rule is currently **unreachable** rather than mitigated — and that test fails the day that stops being true.

**What statelessness does not solve, stated so it is not read as solved.** Tool-set drift across revisions survives it: a client holding revision A's cached `tools/list` can still call revision B. That is the same shape as §3.3.3's `Loosen` cell one layer down — a session is itself a cache of what a backend offered — so the freeze discipline this design already argues for `toolAllowlist` is corroboration, not a new problem, and the cross-revision half remains owed.

### 3.4.3 Evaluation order is not known, and is not asserted

An earlier draft asserted a native `auth → rate-limit → guards` order in the AuthN row **and disclaimed the same ordering two rows below**, in the Guards row. Both cannot be design. The assertion came from a blog post carried over by the superseded research note; the v1.4.1 re-verification listed it as one of the claims it could **not** establish from a primary source, and the design kept it anyway.

It is removed rather than softened, because two things depend on the answer:

- **whether an auth-rejected request consumes quota.** If the limiter runs first, a flood of unauthenticated requests exhausts a paying agent's budget — a denial-of-wallet an attacker needs no credential to run. If auth runs first, it cannot.
- **where a compliance profile's `-guard` must attach** for PHI redaction to see a request that a rate limit would otherwise have already rejected (ADR-0014).

**The experiment, written down so it is reproducible rather than re-derived.** One route carrying both a failing `traffic.jwtAuthentication` and `rateLimit.local: [{requests: 1, unit: Hours}]`. Send three unauthenticated requests:

| Observed | Conclusion |
|---|---|
| `401, 401, 401` | auth precedes the limiter, and rejected requests **do not** consume quota |
| `401, 429, 429` | the limiter precedes auth, or counts rejected requests — the denial-of-wallet path is real |

Until that runs, no row in §3.4 states an order, and no design sentence may depend on one. Owed to `make conformance-cluster`, where the harness already exists.

### 3.4.4 The slice's `-auth` is API keys

ADR-0030 commits the slice to "one identity mechanism". **It is API keys**, decided on 2026-09-11, and it is the only `-auth` mechanism the slice compiles. It is also the only one this repository has measured. `TestTheGatewayRefusesADisallowedPrincipal` (`test/e2e/authz_test.go`) hand-authors exactly the shape below on the operator's serving route and gets:

- `200` for a permitted key;
- `403` for a valid key in the wrong group;
- `401` for no key or an unknown key.

Removing the authorization rule while keeping authentication moves the wrong-group caller to `200`, so authentication and authorization are two controls, and both are emitted. Design 06 later replaces the mechanism with JWT and SPIFFE **without changing where the policy lives**: the same `-auth` concern, the same name and target, a different `traffic` block.

**The input, and what is owed for it.** It has two parts, and neither exists:

| Input | Source | Owed to |
|---|---|---|
| **Key source** — which `ConfigMap`s hold key hashes | **In the first slice, a constant**: `{assayd.dev/api-keys: "true"}`, compiled into the operator, with no chart value and no flag, so D2 below is unreachable (§1.1). Later: chart value `gateway.apiKeys.selector`, a `matchLabels` map with that default, rendered as operator flag `--gateway-api-key-selector` | this design and design 07's chart. It is declared, never discovered, and it is the same for every Agent. A change is refused while the old source is live, and applied once the administrator accepts it (below) |
| **Admitted groups** — which keys may call this Agent | `spec.expose.a2a.auth: apikey` with a sibling `spec.expose.a2a.allowedGroups: [string]` — `minItems: 1`, `maxItems: 16` (the reason is below), each a DNS label, with CEL `has(self.allowedGroups) == (self.auth == 'apikey')`. `auth` is **required, with no default** (below) | **design 02 — OWED, not implemented.** `expose.a2a.auth` is `Enum=none;oauth` with `+kubebuilder:default=oauth` today (`api/v1alpha1/agent_types.go`), so `apikey` cannot be written |

**`expose.a2a.auth` is required, and has no default.** The human decided this on 2026-09-11 (ADR-0034, C2). An earlier version of this design asked design 02 to move the default from `oauth` to `apikey`. That would have changed the product's default identity story from OAuth to shared bearer secrets through a schema default, and it would not have reached one stored object (`reviews/03-a53-critique.md` MINOR 2). So an Agent that writes an `expose.a2a` block now states its authentication. An Agent with **no** `expose` block still compiles to the derived default below, because the operator emits a serving route for it regardless (§3.3.1), and that route must carry `-auth`. The two no longer compile the same way: the block written without `auth` is refused at admission. This departs from write-spec's rule that "required is a demand" (`.claude/skills/write-spec/SKILL.md`), deliberately: this is the one field whose default would be a security decision nobody made.

**Owed to design 02**, as CEL on `ExposeProtocol` so that each error names the fix. Design 02 is not edited here.

- Drop `+kubebuilder:default=oauth`, add `apikey` to the enum, and add `allowedGroups` with the bounds above.
- `has(self.auth)`, message: `spec.expose.a2a.auth is required and has no default: set apikey (and allowedGroups), none (an unauthenticated route), or oauth (not compilable until design 06 ships)`.
- `has(self.allowedGroups) == (self.auth == 'apikey')`, message: `spec.expose.a2a.allowedGroups is set exactly when auth is apikey: add allowedGroups for apikey, or remove it for none and oauth`.

**Stored Agents keep `oauth`.** The API server wrote the old default into every stored Agent that has an `expose.a2a` block. Removing the default migrates nothing, so those objects read `auth: oauth` whether a person chose it or not. The slice cannot compile `oauth`, whose input is design 06 (§3.1). Such an Agent is `PolicyCompileFailed`, reason **`AuthInputAbsent`**. If it has never been served, its serving route is not published. If it is served, it keeps its last good `-auth` and its route keeps serving (§3.3.1, I1). Adding an `expose.a2a` block to a served Agent reaches this state through the persisted default, and it must not open the Agent. The message names `spec.expose.a2a.auth`, says the value may be the default the API server persisted, and names the fix: `apikey` with `allowedGroups`, or `none`. An Agent whose route was published before the compiler existed is `Adopt` instead, which compiles nothing and so outranks the error. Today the only such installs are the e2e harness's, because `gateway.enabled` defaults to `false`.

**Why `maxItems: 16`.** The number is a judgement, not a derivation, and it is stated so that nobody mistakes it for one. The hard ceiling is the emitted expression. Each group adds at most `apiKey.group == "<63 characters>" || `, about 85 characters, against the CRD's `maxLength: 16384` per expression (§3.4.2), so about 190 groups would fit. The CEL admission rule needs no bound for its cost. Sixteen keeps the expression under 1,400 characters, and keeps `allowedGroups` near 1 KiB of `behaviourProjection`'s 8 KiB cap (§3.1). Past 16 groups a per-Agent list is the wrong tool, and widening a group is the right one. **Owed**: design 02's admission tests at 16 (admitted) and 17 (refused), and a golden file here compiling 16 groups to one expression.

**How the admitted principals derive from the Agent.** A principal is a key. Its group is the `group` field of the metadata stored beside the key's hash. The admitted set is:

- `spec.expose.a2a.allowedGroups`, where the Agent declares it;
- otherwise — including an Agent with no `expose` block, and every Agent until design 02 lands the field — **the one group named for the Agent's own namespace**. ADR-0030's slice is single-team, and the namespace is the team: a key minted for group `payments` admits to every Agent in namespace `payments` — and to nothing else **only if** `configMapSelector` reaches the policy's own namespace alone. **That is unmeasured.** The CRD states no scope: it "selects multiple Kubernetes `ConfigMap` resources", and the e2e measures one `ConfigMap` in the policy's own namespace (`test/e2e/authz_test.go`). If selection spans namespaces, a labelled `ConfigMap` anywhere mints a principal for any group. Until the two cases §8.1 owes pass, this design claims no tenancy isolation from the group rule.

**A key-source change is refused while the old source is live.** The human decided this on 2026-09-11 (ADR-0034, D2). Moving `gateway.apiKeys.selector` makes every real key under the old selector stop at once, fleet-wide, unless the administrator has already copied each key under the new one. The operator cannot know whether that happened, so it asks.

| Chart value | Operator flag | Meaning |
|---|---|---|
| `gateway.apiKeys.selector` | `--gateway-api-key-selector` | the source the administrator wants |
| `gateway.apiKeys.acceptedSelector` | `--gateway-api-key-selector-accepted` | empty by default. Set it to the new selector, exactly, once every key the old source held exists under the new one |

- **The source in force for an Agent is the one its `-auth` was last served with**, `status.auth.keySource` (§3.3). It is not the flag, which has already moved by the time the operator restarts on `helm upgrade`.
- **Refused.** Take an Agent whose recorded source differs from the desired one, while the accepted selector does not equal the desired one. Its policy keeps selecting the recorded source, and it gets `PolicyInputDrifted`, reason **`ApiKeySourceChangeRefused`**. The message names both selectors and the action: copy every key into `ConfigMap`s carrying the new label, then set `gateway.apiKeys.acceptedSelector` to the new selector. `Ready` is not withheld, because the Agent is enforced exactly as before.
- **Accepted.** Once the accepted selector equals the desired one, compared in §3.3.3's canonical selector form, each such Agent runs `Narrow` with the key-source probe (§3.3.3). An old-source key must go `200` → `401` while a new-source key goes `401` → `200`, and only then does `status.auth.keySource` move. The acceptance names a selector rather than saying yes, so a value left set after one migration cannot accept the next.
- **Agents created meanwhile take the desired source at once.** An Agent with no `status.auth` has never been served, so it has no callers the change can cut off. Giving it the old source would only add it to what the administrator must migrate. So during a refused change the fleet selects two sources, and the message on each refused Agent says so.
- **Agents with no `-auth` to move are not affected.** `auth: none` emits no policy. A refused `Adopt` compiles nothing. An Agent that is `PolicyCompileFailed` and has never been served takes the desired source when it compiles. *(Corrected by A56: this sentence said every `PolicyCompileFailed` Agent "has never been served". A served one whose `-auth` input became uncompilable is served, and keeps its last good `-auth`, recorded source included (§3.3.1, I1; `reviews/03-a55-critique.md` B1).)*

**The emitted policy.** One `AgentgatewayPolicy`, the `-auth` concern, in the run namespace beside its target (§3.2). The minimal case, an Agent with no `expose` block in namespace `payments`:

```yaml
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: <agent>-auth                    # per Agent, so no -<rev> (§3.2)
  namespace: assayd-run-payments
  labels:                               # no assayd.dev/revision: the policy follows
    assayd.dev/agent-uid: <uid>         #   the Agent's current spec (§3.2)
    assayd.dev/agent: <agent>
    assayd.dev/agent-namespace: payments
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: <agent>-serving             # the shipped per-Agent route (design 07 A6.10)
  traffic:
    apiKeyAuthentication:
      mode: Strict                      # the CRD default, emitted anyway (below)
      configMapSelector:
        matchLabels: {assayd.dev/api-keys: "true"}   # the chart's key source
    authorization:
      action: Allow                     # default-deny once any Allow rule exists
      policy:
        matchExpressions:
          - 'apiKey.group == "payments"'
```

**The target is the per-Agent route.** An earlier version of this example targeted the revision's `Service`, commented "pending the spike". That is the shape the CRD refuses (§3.2), so a compiler copied from it would have had every policy refused at admission. The `HTTPRoute` target is the one the spike and the third critique both admitted by server-side dry run.

**`mode: Strict` is emitted, not defaulted.** The CRD defaults `apiKeyAuthentication.mode` to `Strict` and also admits `Optional` and `Permissive` (read in the vendored 1.4.1 CRD, which describes neither). A default is not an absence (§3.3.3), so the golden file pins the value. The e2e's hand-authored policy omits it, so the explicit form is unmeasured at the gateway. `location` is left to its default, which reads the key from the `Authorization` header with the `Bearer ` prefix. That is where the e2e sends it, and the golden file pins the field's absence.

With more than one admitted group — for example `allowedGroups: [payments, audit]` — the compiler emits **one** expression, `apiKey.group == "audit" || apiKey.group == "payments"`, in sorted order, built with the real CEL string encoder §3.4.2 requires and never by string concatenation. The measured case is the single `==`. A multi-group expression is standard CEL but unmeasured at this gateway, so `make conformance-cluster` owes one case with two groups. `action: Allow` is used for §3.4.2's reason: a CEL error under `Deny` fails open. `auth: none` emits no policy and puts the no-auth marker label on the route (§3.3.1).

**The key set is written by an administrator and never emitted.** Each entry in a selected `ConfigMap` is `{"keyHash": "sha256:<hex>", "metadata": {"group": "<group>"}}`. The API refuses a raw key in a `ConfigMap`, so only the hash is stored (`applyAPIKeys` in the e2e). The `ConfigMap` lives in the run namespace, beside the policy that selects it; that is where the e2e puts it, and it is the only placement measured. assayd writes none of them, except `Narrow`'s short-lived probe keys (§3.3.3).

**What it costs, stated because the slice chose it.**

- **Shared secrets.** A key is a bearer credential. Whoever holds it is the principal, with no binding to a workload, a user or a session. Keys are handed out out of band.
- **Manual rotation.** Nothing expires a key. Rotating one means a human edits a `ConfigMap` in every run namespace that holds it and hands out the new key; revoking one means deleting its entry.
- **The key set is outside every gate.** The policy references keys by selector and agentgateway reads them live. Adding an entry widens who is admitted with no compile, no revision and no comparator, and anyone who can write a `ConfigMap` carrying the selected label in a run namespace can mint a principal. **Nothing reserves that label today**: design 07 A5.9's admission policies reserve namespace labels and gateway routes, not this. That reservation is owed to design 07. Until it lands this is a real bypass for anyone with `configmaps` write in a run namespace — **and, if a selector reaches across namespaces, in any namespace**, which is unmeasured (above). A duplicate is worse than an addition. The CRD says that if the same key is defined in multiple `ConfigMap`s "the behavior is undefined", so writing a known key's hash under another group re-groups that credential rather than adding one. §8.1 owes a case for it.
- **A group is only as narrow as its members.** A key admitted by group `payments` reaches every `payments` Agent. Per-Agent keys need an `allowedGroups` naming a group of one.

**Nothing here is implemented.** No `-auth` policy is emitted, `apikey` is not a CRD value, `auth` still defaults to `oauth`, `spec.budget` is still admitted, the chart value and the flag do not exist, `Narrow`'s probe does not exist, neither do `status.auth`, `--gateway-serving-url` or `--gateway-api-key-selector-accepted`, and `agentgatewaypolicies` RBAC is not granted (§3.2).

### 3.5 Pricing table and the usd→token computation

**Two ConfigMaps** (see "Two ConfigMaps" below for why one cannot work): `assayd-model-pricing`, chart-owned and versioned, carrying external endpoints and the single `updated` timestamp; and `assayd-model-pricing-internal`, operator-owned, carrying in-cluster endpoints. **Design 25 has caught up, and an earlier version of this paragraph said it had not.** Its §3 once had the model-operator "upsert an `internal/<model>` row into `assayd-model-pricing`" — the chart-owned map, which is precisely the write the two-map split exists to prevent. **Design 25 A3 (2026-09-04) removed it**, prompted by this design's own amendment, and its §3 no longer contains that write. The correction was made in the producing design and never propagated back to here, which is how a document ends up asserting a defect that was fixed before it was next read. The rule stands unchanged: the model-operator writes only to the operator-owned map.

**Shape.** One row per **endpoint identity** — the same `{arm, instance fields, model}` tuple `providers[]`, `fallback` and the allowlist use (design 02 §3.1) — carrying two prices in **USD per 1,000,000 tokens**, the unit vendors publish, chosen so no price is written as `0.000003` and rounded into nothing.

An earlier draft keyed this on `<provider>/<model>`. That string was deleted everywhere else, so the table was the last thing requiring a canonical join — and the join is the non-injective one: `{azure, openai/gpt-4}` and `{azure/openai, gpt-4}` collapse to one row while being different endpoints with potentially different prices and different BAA status. Two Azure deployments on one endpoint collapse the same way.

Rows are therefore a list, not a map, and matching is on the tuple:

```yaml
data:
  updated: "2026-08-19T00:00:00Z"        # RFC 3339; drives PricingStale
  models: |
    - id: {arm: anthropic, model: claude-opus-5}
      price: {input: "15.00", output: "75.00"}
    - id: {arm: azureopenai, azureopenai: {endpoint: acme.openai.azure.com, deploymentName: gpt4o-prod}}
      price: {input: "5.00",  output: "15.00"}
    - id: {arm: anthropic}                          # arm-wide default: no model field
      price: {input: "15.00", output: "75.00"}
```

**Matching is most-specific-wins over the tuple**, which is total and admits no tie: a row whose `id` is a subset of the requested identity matches, and the row matching on the most fields wins. Two rows matching on the same field count is a **load error**, not a runtime tie-break — the ambiguity is caught where a human can fix it rather than resolved silently per request.

**Grammar.** Prices and `spec.budget.usdPerDay` are decimal strings matching `^[0-9]{1,6}(\.[0-9]{1,6})?$` — at most **six** integer digits and six fractional, no exponent, no currency symbol, no `resource.Quantity` suffixes. Six fractional digits make the arithmetic exact in integer **micro-USD**, so golden files pin exact integers rather than whatever a float happened to produce.

**Six integer digits, and the number is load-bearing.** The computation multiplies micro-USD by 10⁶, so the largest admissible value must satisfy `U × 10¹² ≤ 2⁶³−1`. At six digits the maximum is `999999.999999` → `999999999999 × 10⁶ = 9.99999999999×10¹⁷`, comfortably inside int64's `9.223×10¹⁸`. An earlier draft derived the true threshold (~9,223,372) correctly and then wrote a *seven*-digit grammar, which admits `9999999` → `9.99999999999×10¹⁸`, which **wraps to a negative** `tokensPerDay` — and the zero-rate guard below tested `rate == 0`, so a negative rate escaped it entirely. A regex cannot express `U ≤ 9223372`; six digits is the largest bound a regex *can* express that is also safe, which is why the schema carries it rather than the code. At $999,999.99 per agent per day the ceiling is far above any real budget.

The `usdPerDay` half belongs on the CRD as CEL and is landed by design 02 §3.1, since that section is the authoritative schema; the ConfigMap half is validated at load. **Neither is implemented yet** — `config/crd/assayd.dev_agents.yaml` currently has a bare `type: string`.

**Resolution is by endpoint identity, and no string is ever joined or split.** Design 02 §3.1 makes `providers[]`, `fallback` and every allowlist entry the same tuple — `{arm, instance fields, model}` — so the flat-string key an earlier draft resolved by longest prefix no longer exists. That draft canonicalized `{provider, model}` with a `/`, which `internal/revision/revision.go` already records as non-injective, in the comment above `endpointIdentity` (line 66 when this sentence was written; the note is now at `:91`): `{azure, openai/gpt-4}` and `{azure/openai, gpt-4}` collided on one row while being different endpoints, and a golden fixture pinning "a slash-containing model in both forms" could not have detected it, because production had already collapsed them.

Lookup matches on the tuple. An entry matching nothing is `PolicyCompileFailed` naming it; a wildcard is expressed as an entry that omits `model`, not as a string suffix. The pricing rows are keyed on that same tuple — an earlier draft carried a "still owed" note here, which the schema above discharges.

A model that resolves to nothing is `PolicyCompileFailed` naming the offending `spec.llm.providers[i]` (or `spec.llm.fallback`) — never a default price, because a guessed price is a guessed budget.

**`PricingStale` means the table is old, not that a row is missing.** A *missing row* is the compile error above. Design 02 §5's row said otherwise and is corrected there — one condition cannot mean two things without meaning neither.

**What staleness can honestly claim.** The table is chart-shipped with `updated` baked in and **nothing refreshes it automatically**, so `updated > 30d` becomes permanently true on every install of a chart older than a month — an alarm that is always on for everyone, which trains operators to ignore the one signal that matters when prices actually move. Three narrowings make it mean something:

- It is raised only for agents whose usd budget resolves to an **externally-priced** model. In-cluster endpoints are upserted by the model-operator at serve time (design 25 §5) into its **own** ConfigMap and are never stale by this measure. `updated` lives in the chart-owned map alone, so an in-cluster model going live cannot clear the alarm that fires when vendor prices move.
- Refreshing is a **documented human action** — `helm upgrade`, or editing the operator-writable ConfigMap directly. The condition's message names it. Nothing auto-refreshes external vendor prices, and this design does not pretend otherwise.
- The condition is **advisory**: it never withholds traffic or fails a compile. A stale table skews the gateway tier's approximation — and the receipt tier does **not** bound that, because it prices from the same table (ADR-0028). A stale or tampered table skews both tiers identically.

**The computation.** Let `U` be `usdPerDay` and `P` the **conservative price**: the maximum, across every model the agent is allowed to use, of that model's `max(input, output)`. Maximum of both directions because the emitted limiter counts total tokens without distinguishing them, and maximum across models because the real traffic mix can only be cheaper. That is conservatism on **price alone**, and says nothing about *when* the limiter acts — the claim ADR-0028 withdrew.

Two degenerate cases are defined rather than left to panic, because §4 calls `Compile` **total** and integer division does not forgive:

- **`P = 0`.** Design 25 D2b lets the model-operator write an `internal/<model>` row priced at explicit `0` where the org does not charge back. An agent whose allowed models are all free gives `P = 0`, and `Uµ × 10⁶ / 0` panics in the reconcile path. A zero price is not an error and not a missing row: a free model imposes no monetary ceiling, so the usd-derived rate is unbounded and the emitted limit is the `tokensPerDay`-derived one, or none. **`-ratelimit` is mandatory on a *derived rate*, not on the presence of a budget field** — keying it on the field would make a usd budget over an all-free model set withhold the route, falsifying design 25 §5's guarantee that in-cluster models always compile.
- **Empty model set.** A `usdPerDay` with no `providers[]` and no `fallback` has no maximum to take. `PolicyCompileFailed` names `spec.budget.usdPerDay` — there is no `providers[i]` to name — and says a usd budget requires at least one priced model.

`P` is taken over `providers[] ∪ {fallback}`, **not** `providers[]` alone. Design 20 activates `llm.fallback` by setting status, which mints no revision and fires no eval — deliberately, so an incident does not wait for a gate. If the fallback were outside `P`, activation would leave a limiter sized for a cheaper model and the gateway would cut **late**, breaking the one property §3.4 and D3 both promise. Pricing the fallback in up front also moves its failure to declaration time: **an unpriced `llm.fallback` is a compile error when the Agent is written**, never a `PolicyCompileFailed` raised mid-incident during the remediation design 02 §3.3 exempts from gating.

The same argument applies to reachability, and an earlier draft made the pricing check and missed it. When `llm.egressAllowlist` is set, **`llm.fallback` must be one of the providers the emitted Backend enumerates** (§3.4.1) — under construction-not-restriction the failure is total rather than partial: a fallback outside the enumerated set is not merely blocked, it is unreachable, because the Backend has no route to it at all. Checked at compile time on the same footing as pricing, failing with `PolicyCompileFailed` naming `spec.llm.fallback`. **`internal/*` resolves inside any allowlist by construction** — an in-cluster Service is not an egress endpoint, and design 25 §5 calls self-hosted models "the allowlist's easiest member"; the check applies only to externally-resolved providers, or design 02 §3.1's own `fallback: {provider: internal, …}` example would fail it. Otherwise design 20 activates a fallback the gateway's Backend restriction blocks: `ModelDrifted` reports the remediation applied while the agent serves nothing, which is rule 8's loud-and-wrong at the worst possible moment. Design 20 §6 has a row for "fallback provider also drifted" and none for "fallback was never reachable".

With `U`µ and `P`µ as integer micro-USD:

```
tokensPerDay(usd) = floor(Uµ × 1_000_000 / Pµ)
tokens            = floor(tokensPerDay / (24 × gatewayReplicas))       # emitted as unit: Hours
```

**The emitted shape is fixed by the real CRD, and it is narrower than earlier drafts assumed** (ADR-0028). `LocalRateLimit` carries `requests`, `tokens`, `unit` and `burst`; `unit` is **required** and is one of `Seconds|Minutes|Hours`, so **a per-day budget is not directly expressible** — hourly is the coarsest available window and is what assayd emits. `ExactlyOneOf=requests;tokens` means one policy cannot carry both a request limit and a token limit. **`burst` applies only to `requests`** ("This setting only works with `requests`, not with `token` rate limits"), so the token bucket has no burst allowance and the `rate × 3600` capacity of earlier drafts is void — as is the 90 000 divisor that existed to pay for it.

`requests`, `tokens` and `burst` are all **`*int32`**. A computed value outside `1 … 2 147 483 647` is a compile error naming the field; that ceiling caps an expressible daily budget at ~5.15×10¹⁰ tokens per replica. At tag v1.4.1 `burst` carries **no `Minimum`**, so a negative burst is schema-valid and assayd validates `burst >= 0` itself rather than relying on the API. `gatewayReplicas < 1` is likewise to be rejected **at the flag**, not discovered by dividing by zero — "at the flag" is where the check belongs and not where it is: §3.1's provenance table records that `--gateway-replicas` does not exist yet, so nothing rejects it today.

**"Cuts early, never late" is withdrawn, and nothing replaces it** (ADR-0028). The property was never achievable: `LocalRateLimit.tokens`' own doc comment says *"token counts are not known until the request completes. As a result, token-based rate limits will apply to future requests only."* The request that crosses the budget **completes and is returned**; only the next one gets a 429. Pre-dispatch estimation exists in agentgateway (`tokenize: true`) but is **unreachable from Kubernetes** — absent from the CRD API, absent from every published k8s doc page, and hardcoded `false` on the xDS path. Earlier drafts of this section proved an arithmetic invariant that was internally exact and externally irrelevant, because the mechanism it constrained does not enforce at request time.

**No overshoot bound is published, because the measured excess is unbounded**. An earlier draft published `gatewayReplicas x maxOutputTokens(model)`, reasoning that one crossing request per replica can be in flight. That was measured against v1.4.1 and is false: with a 1,000-token hourly budget where each request consumes exactly 1,000 tokens, **20 concurrent requests all returned 200, and 100 concurrent requests all returned 200** — 100,000 tokens admitted against a 1,000-token budget, on **one** gateway replica (`research/agentgateway-v1.4.1-spike.md` §2.7). Enforcement is a read-only availability check before dispatch and a decrement after the response, so every request that starts while the bucket is positive is admitted. Serial traffic is limited correctly; concurrent traffic is not limited at all until the first response lands.

So the gateway tier bounds **sustained** rate and nothing else, and the excess tracks *concurrency*, which neither `PolicyIntent` nor the emitted policy constrains. Publishing any figure would be the third retracted budget guarantee in this design. **The honest statement, and what the CLI and `status.budget` say, is that gateway-tier excess is unbounded at v1.4.1 and the receipt tier is the only real limit.** Bounding it would require a assayd-side per-replica concurrency cap and a request-size maximum — neither exists in the CRD surface — and that is a design change, not a wording fix.

**Capacity is part of the emitted policy, not an afterthought.** §3.4 emits a token *bucket*, and a bucket has both a refill rate and a burst capacity; an earlier draft gave only the rate, which meant no golden file could be written at all. One hour's refill absorbs the bursts real agent traffic produces — a multi-tool task spends its tokens in seconds, not evenly across the day — while keeping §3.4's promise meaningful: at `capacity = tokensPerDay` the gateway would be a daily ceiling rather than a rate, and an agent could spend the whole budget in the first minute and then be dark until 00:00 UTC.

Two edges the arithmetic forces, both previously unstated:

- **Both budget fields may be set.** `tokensPerDay` and `usdPerDay` each derive a rate; the compiler emits **one** `-ratelimit` policy at the **minimum** of the two. Emitting two policies would put the same field in two policies and break §3.2's disjointness by construction.
- **A rate below 1 token/second is a compile error.** `usdPerDay: "0.50"` against a model priced at `75.00`/M tokens with two gateway replicas floors below 1 token/second — a bucket that denies everything. The test is `rate < 1`, not `rate == 0`: with the grammar bounded at six digits a negative rate is now unreachable, but a guard that only catches exact zero was how the overflow above stayed invisible, and the cheap predicate is the total one. Denial is fail-closed and therefore "safe", but an agent that answers nothing because of a rounding step is rule 8's loud-and-wrong: the condition would name a budget when the cause is arithmetic. `PolicyCompileFailed` names the floor and the smallest budget that clears it.

**Two ConfigMaps, because two controllers cannot own rows inside one string.** Kubernetes field ownership stops at `data.models`; it cannot give the chart and the model-operator disjoint ownership of YAML rows within that scalar, so a Helm upgrade refreshing external prices and a model-operator upserting an in-cluster row would conflict or lose each other's work in a read-modify-write race. So:

- **`assayd-model-pricing`** — chart-owned, external endpoints, `updated` lives here and only here;
- **`assayd-model-pricing-internal`** — operator-owned, in-cluster endpoints the model-operator upserts at serve time (design 25 §5).

The compiler reads both and merges. **An identity appearing in both is a load error**, never a precedence rule: silently preferring one writer is how a stale external row would shadow a live internal one, or the reverse. Staleness is evaluated on the chart-owned map alone, so an internal upsert cannot clear the alarm that fires when vendor prices move.

**RBAC**: both are operator-writable only by default. A tampered table skews the gateway tier **and the receipt tier together**, since both price from it — so the receipt tier is **no longer** describable as a backstop for pricing at all, and §6 states that rather than implying protection that does not exist.

## 4. Behavior

`Compile(intent) → ResourceSet` — one **revision** intent in, that revision's resource set out (§3.3.1) — is pure, deterministic (golden files), and **total**: every field maps or errors (`PolicyCompileFailed` with field path) — including the multi-model pricing rule and unmatched patterns (r1 f4). `Apply(ResourceSet)` follows §3.3. `Diff` drives create/update over owned fields (§3.2), not server-side apply.

## 6. Security

Emitted policies are meant to be the only capability-change path, and **today nothing makes them so**. The chart's admission policies reserve two things (`charts/assayd/templates/admission.yaml`): routes that attach to the assayd Gateway, and the run-namespace label. Neither matches an `AgentgatewayPolicy` or a key `ConfigMap`. An earlier version of this sentence said admission denies non-operator writes on assayd-labelled gateway resources, which was false (`reviews/03-a53-critique.md` M3). Two things are owed before `-auth` ships. **Design 07** owes a third admission policy that refuses `CREATE` and `UPDATE` of `agentgatewaypolicies` in any namespace labelled `assayd.dev/run-namespace: "true"` from any identity but the operator's, with the key-source label's reservation (§3.4.4) beside it. **This design** owes the detection in §3.2, because a reservation does not remove policies written before it, and a cluster administrator can delete it. `Narrow`'s probe makes the operator a principal-minting identity for each probe window (§3.3.3). On the create path, the route carries no `backendRefs` until an anonymous request through it gets `401` (§3.3.3). That removes the unauthenticated window on the gateway replica that answered, and only there. On a gateway with more than one replica, a replica that has not yet taken `<agent>-auth`, and raises no NACK, can serve the new Agent unauthenticated after `Publishing`, and nothing detects it. **That window is stated, not removed.** *(An earlier version of this sentence said fail-closed ordering removes the unauthenticated windows "on the create path", while `Create` published on conditions that §3.3.2 measured lying (`reviews/03-a55-critique.md` M2).)* Ordering does not remove the windows on a change to a serving route either. So every tightening but one goes through the revision gate, on a candidate route. The exception is the per-Agent `-auth`, which `Narrow` tightens in place and trusts only once a probe sees the removed principal refused while a kept one is served (§3.3.3). Until then status does not claim the revocation, and on a gateway with more than one replica it claims it for one replica only. An earlier version of this sentence said §3.3.3 withdrew in-place tightening entirely, which `Narrow` made false (`reviews/03-a54-critique.md` MINOR 1). Scope header is added by the gateway *after* authn and cannot be supplied by clients (transform strips inbound occurrences). Pricing ConfigMap RBAC (§3.5) — and **no backstop**: both tiers price from that table, so tampering skews them together (ADR-0028).

- **A13 (2026-08-27) — the overshoot bound is withdrawn, refuted by measurement.** A9's replacement for the withdrawn "cuts early, never late" was `gatewayReplicas × maxOutputTokens(model)`. An execution spike against v1.4.1 measured it: against a 1,000-token hourly budget where each request consumes exactly 1,000 tokens, **20 concurrent requests all succeeded, then 100 concurrent requests all succeeded** — 100,000 tokens admitted on **one** replica. Serial traffic is limited correctly (429 once spent), so the limiter works; concurrent traffic is not limited at all until the first response lands, because the check is read-only before dispatch and the decrement happens after. The excess tracks concurrency, nothing constrains concurrency, and so **no bound is published**. This is the third budget guarantee this design has retracted and the first retracted by measurement rather than review — which is the argument for the spike, not against it. Bounding it needs a assayd-side concurrency cap and request-size maximum that the CRD surface cannot express; that is owed and undrafted.
- **A14 (2026-08-27) — the NACK branch is measured, and it is the fail-open one.** Research §9 left open whether a NACK'd policy retains the previous config or fails closed; §3.3.2 was specified but not safe to build without it. An execution spike forced the case with `burst: -1` — a value the API server and the controller both accept and the dataplane rejects — and observed the answer: the proxy NACKs, **the old configuration keeps serving**, and every Kubernetes-visible signal reports converged at the current generation. A tightening from 1000 req/hour to 1 req/hour never applied while the CR said `Accepted=True, Attached=True`. This is Codex r2 BLOCKER 2 reproduced end to end. The Event is the only observable and is Gateway-scoped; its key attributes a NACK to the emitting policy and route but carries no generation, so it can raise degradation and cannot confirm success. §3.3.2 now says exactly that, and the update transaction is unblocked to the extent that it can be honest about what it cannot prove.
- **A15 (2026-08-27) — the apply barrier is an event-driven state machine.** §3.3 polled for up to 30s on the reconcile worker. Each not-yet-converged Agent held a worker for the full bound and requeued, so a principal who may create Agents could keep more permanently-pending objects than there are workers and starve kill, budget-hold and finalization behind them; `MaxConcurrentReconciles` changes the number of bad objects needed, not the outcome (Codex r2 BLOCKER 7). The operator now applies once and returns, with `status.apply = {digest, generation, stage, deadline}` and watches driving progress. Per-key serialization is untouched — what is removed is the sleeping. Two rules make it safe: **stale state is discarded before anything advances** (a recorded stage whose digest or generation is not current is dropped and the machine restarts, or reconcile N's stage would let N+1 publish a route policied by the previous generation — the same fail-open by another route), and **the deadline sets a condition rather than abandoning**, so withheld routes stay withheld. The NACK Event is a sixth input and cannot advance anything: it proves a rejection happened, never that one did not (A14). Fairness is required as a *test* — more pending Agents than workers while an unrelated kill completes within a stated bound.
- **A16 (2026-08-27) — the egress entry grammar, the catalog, and requested-⊆-permitted.** A11 settled that egress is enumeration and left the language undefined, which Codex r2 BLOCKER 4 correctly called unimplementable. Entries become **typed** (`provider` + optional `models`, or `host`), because a bare string is ambiguous exactly where it decides reachability. The provider→endpoint **catalog is assayd's**, chart-shipped and versioned like the pricing table, since agentgateway ships none. And A11's requirement that the Backend's provider set **equal** the allowlist is corrected: that conflated the Agent's **requested** providers with the **ceiling** the allowlist expresses, so a profile permitting `{A,B,C}` for an Agent requesting `{A}` would have made B and C reachable. The emitted Backend enumerates the requested set and must be a **subset** of the permitted one; a destination is never added because it is allowed. The DNS limit is stated rather than implied — the predicate is over names, not addresses.
- **A17 (2026-08-27) — the transaction, and the witness that replaces a fail-open arm.** Codex r3 BLOCKER 1 and 2, both of which A15 had created or left.

  **A15 could not complete a cold create.** Its stages applied Backends and Policies, converged, and only then created the route — but the spike measured that a policy whose target route does not exist reports `Attached=False` (§2.1). The stage that creates the route sat behind the barrier that needed it, so a new Agent reached `Converging` and could never leave. `PreparingRoute` now creates the route first, in the attachable-but-not-serving shape §2.6 measured. (`Quiescing`, added here for tightening updates, is **withdrawn by A19** — there is no in-place tightening for it to serve.)

  **Transaction kind is now persisted, because the stages differ.** `Create` costs nothing; `Tighten` quiesces first and the route answers **HTTP 500** for its whole convergence window; `Loosen` keeps the route live. Anything not *provably* a loosening is a `Tighten` — fail-closed by default, because being wrong that way costs availability while the other way serves the old permissive rule. The 500 is documented rather than discovered, since §2.6 measured it and an operator who is not told will read it as an outage.

That second arm is not an option: §2.8 measured exactly that state reporting fully converged while the removed rule stayed callable. It was replaced by a `Witnessing` stage — **also withdrawn, by A19**. - **A24 (2026-08-28) — the last of r4's contract gaps.** Five holes where a sentence read as a rule but could not be implemented from what it said.

  **An empty slice meant two things** (MAJOR 1). A resolved `tools: []` represented both "requested none" and "requested one and its producer failed" — opposite required outcomes, identical to a pure function, so an Agent asking for a tool it never got could compile as an Agent asking for none and report `Ready`. Three things follow and each was a way to wedge every Agent at every install. **Namespace**: routes, Backends and policies go where the Service is, because a cross-namespace `backendRef` without a `ReferenceGrant` yields `ResolvedRefs=False, RefNotPermitted` and §3.3.2 requires `ResolvedRefs=True` before publishing. **Ownership**: a cross-namespace `ownerReference` is *treated as absent* with an `OwnerRefInvalidNamespace` Event, so it would leak every emitted resource while looking correct — provenance is a label, and per design 02 A57 the label is **not** the deletion authority, because a label needs only `update` to forge; the name is. **Listener admission**: a Gateway listener rejects routes from namespaces its `allowedRoutes` does not admit, so the chart's Gateway selects on a `assayd.dev/run-namespace` label (owed to design 07). The naming suffix also widens from 8 hex to 16: 32 bits is not enough for a name that design 02 A42 uses to separate tenants, which is the lesson A37 already paid for once.
- **A45 (2026-09-03, from design 26 A1 and `reviews/02-a60-codex-review.md` BLOCKERs 8–9) — two hard-mode producer contracts this design does not have, recorded here so the consumer's requirement is visible where the producer lives.** Design 26 A1 has this compiler write routes into a vCluster's host sync namespace and reference the synced Service, and has it write a routes-revoked marker when an Agent inside a vCluster is deleted. Neither is specifiable from this design's inputs: `PolicyIntent` carries `target: {kind, ns, name}` from the Agent CR, vCluster rewrites synced Service names to opaque ones, and nothing here watches tenant Agent deletion, owns a vCluster client, or defines what "revoked" means as a postcondition. **Owed, in this design, before hard mode is implementable**: (1) a **resolved host mapping** input — `{tenantUID, virtualNamespaceUID, virtualServiceUID, hostNamespace, hostServiceName, hostServiceUID, mappingGeneration}` — produced by the tenant-operator, consumed by `TenantPolicyIntent`, with the compiler refusing a stale or ambiguous mapping; and (2) a **hard-mode deletion lifecycle** — the watch, the client, the exact resource-set postcondition for "drained and revoked", and the single writer of the marker ConfigMap named in design 26 A1. Nothing here is designed by this entry; it names what is missing so that design 26 A1 is read as a requirement on this design rather than as a description of it.
