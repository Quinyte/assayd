## 1. Purpose & scope

The Agent CRD is the platform's front door: one object that turns "a container that speaks A2A" into a governed, discoverable, eval-gated workload. The agent-operator reconciles it into workload, identity, directory entry, gateway routes/policy, and rollout gating.

**In scope**: CRD schema, reconcile behaviour, the revision/rollout state machine, registration, identity wiring, external agents, **finalization**.
**Out of scope**: policy compilation internals (design 03), receipt tap (04), eval execution (16 — only the *holding mechanism* here), KG binding validation details (01/13).

## 2. Doctrine & charter gates

- **Plane**: slow (engine) — one of the three core operators.
- **Pods added**: the agent-operator itself — the single plume-code pod in the core-tier weight budget (`docs/architecture.md` §17). Workload pods are user workloads.
- **Stateful deps**: none added — no database, no queue, no volume. Operator-owned state, named rather than counted as zero, because two of these cannot be reconstructed:
  - the Agent's own `status`, and the directory KV (design 05);
  - **one `ConfigMap` per run namespace** — §3.2's binding record. Durable, authoritative, and **not reconstructable by the operator**: losing it needs a human;
  - **per revision, an immutable copy of every referenced `ConfigMap` and `Secret`** in the run namespace (§3.3). These hold credential bytes, and once the user's source has drifted the copy cannot be reproduced either — which is exactly why the revision reads it. Bounded by the retained set and collected with the revision;
  - `plume-mirror-*` `ResourceQuota`/`LimitRange` objects, which *are* reconstructable from their sources.

  Read-only reconcile inputs: design 04's per-agent daily spend aggregate (which lives in design 04's audit index), the source namespace's `ResourceQuota`, `LimitRange` and Pod Security labels, and the two admission policies §3.2 fail-closes on.
- **Primitives**: Agent (A2A), Tool (MCP), Resource (CRD), Artifact (OCI images). ✓

**Two names this design uses elsewhere are not fields of this schema**, and they are not the same kind of absence. `revisionHistoryLimit` — which §3.3's retention arithmetic is written in terms of — is an **operator constant defaulting to 2**, so the arithmetic holds and only the tunability is missing. `registrationDeadline` (§3.4) is **neither a field nor a constant**: registration and card handling are unimplemented, so nothing counts down and nothing frees a retention slot. Adding either is an additive schema change; §5 carries both.

**`EnvSourceProtectionUnavailable` is in that list and is never raised by this operator.** It announced the env-source bypass while the run namespace was still design; the move closed it. The type stays in the vocabulary so an operator built after the move **clears a stale `True`** left by one built before — the operator's owned-condition set is what does the clearing — and removing it from this list would break that path and fail the closure test in both directions.

**The condition vocabulary is closed, and this list is where it is closed.** `[]metav1.Condition` accepts any string, so nothing in the API schema can bound it: the enforcement is a typed constant per condition in the Go API plus a test that parses *this list* out of *this document* and compares both directions — a constant with no entry here fails, and an entry here with no constant fails. A CEL enum on the status subresource was considered and deliberately withdrawn: one unrecognised type would reject the **whole** status write, so a controller emitting a typo would silence the object entirely rather than mis-name one condition. A condition the code cannot name is one no controller can set, which is how a degraded path goes quiet (NFR-8).

`kubectl get agents` printer columns: `PHASE · ACTIVE · CANDIDATE · EVAL(last score) · COST/DAY · AGE`, sourced from `status.phase`, `status.activeRevision`, `status.candidateRevision`, `status.eval.score`, `status.budget.usdSpentToday` and the creation timestamp. The set is a contract, pinned by a test against the generated CRD: the case for a status carrying this many conditions rests on these six answering the common questions, and `EVAL`/`COST/DAY` are precisely the two a developer could otherwise reach only by reading conditions.

**Tool and graph names resolve in the agent's own namespace, and only there.** A tool name may be served by a Connector tool facet or by an `MCPServer` CR, and the two share one name space per namespace, which is why the binding carries no kind discriminator. There is deliberately no `namespace` field on either binding: design 24 §4 derives the `can_call` tuple **from** the binding, so a cross-namespace reference would authorize itself — anyone able to create an Agent in one namespace could reach a tool in another. Cross-namespace use requires consent published by the target namespace (the `ReferenceGrant` shape) and is out of scope until a design specifies it. **The uniqueness that makes a discriminator-free binding safe is enforced by nothing** — nor does any design yet define the `MCPServer` kind that half of it names. Design 11 §11 records the gap and owes the definition and its enforcement; ADR-0027, which cites this uniqueness to justify the flattening, retracts its "enforced at admission" clause and points at the same owed item. Until it lands, a Connector facet and an `MCPServer` may collide on a name in one namespace. §5 carries the row.

### 3.2 Workload materialization

**What is created.**

- **Default: Deployment** — A2A servers are stateless HTTP; replicas scale; fits every SDK.
- **`runtime.sandbox` ⇒ agent-sandbox `Sandbox` (v1beta1)** — singleton, stable identity, persistent scratchpad; for agents that execute code or hold local state. `replicas>1` with `sandbox` is rejected at admission (CEL).
- **Sandbox runtime class absent** (local distros) ⇒ hardened Deployment (seccomp, non-root, read-only rootfs) + `SandboxDowngraded=True`. Never silent (NFR-8).
- **Scratchpad lifecycle**: the volume is **revision-independent** — reattached read-write to the promoted revision. A candidate under eval attaches it **read-only**, so a cold candidate cannot corrupt live state. This needs an access mode permitting concurrent attach (`ReadOnlyMany`/`ReadWriteMany`) or co-scheduling; where the storage class cannot provide it — notably `local-path` in the `local` profile, which is `ReadWriteOnce` and node-bound — the candidate runs **without** the scratchpad and `ScratchpadDegraded=True` names the reason. **Eval consequence, and it is this design's to state**: a candidate is therefore evaluated cold against a warm active, so an EvalSuite must not assume warm local state.
- **Task state with `replicas>1`** — detected, not assumed: the A2A card is the declaration point (a capability/extension asserting shared task state). Absent that assertion with `replicas>1`, the operator sets **`TaskStateUnverified=True`** with the consequence named, and the CLI warns at deploy. Design 09's templates ship the JetStream-KV store **and emit the declaration**, so template-built agents never raise it.

**Where it is created: an operator-owned run namespace** (ADR-0029). The Agent CR stays where the user created it. The Deployment, its Pods, the Service — one **per revision** (A64), sharing the workload's name — the emitted routes and §3.3's revision copies are created in **`plume-run-<agent-namespace>`** — one run namespace per Agent namespace, so the tenancy boundary is preserved rather than pooled.

The reason it must be a whole namespace is a Kubernetes fact, not a preference: **a ConfigMap or Secret can only be used by Pods in its own namespace.** So material is out of an editor's reach only if the *Pod* is too. Without the move, a namespace editor holding ordinary `create`/`delete` on ConfigMaps deletes a revision's copy and recreates it under the same name — `immutable: true` forbids an update and permits exactly that — and a node drain then serves the new bytes under a gate result they never earned. `ownerReference` does not help: it does not protect deletion.

What the user keeps in their own namespace is what they are supposed to edit: the Agent CR, and the ConfigMaps and Secrets it references. Editing those still works and still means what it meant — it mints a candidate, which passes a gate. What they lose is the ability to reach the material a *gated, serving* revision is already reading.

| Consequence | Rule |
|---|---|
| **Naming** | `plume-run-<agent-namespace>`, **truncated and hashed** by design 03 §3.2's rule when it would exceed 63 characters: a namespace name is a DNS label, `plume-run-` is ten characters, and an Agent namespace may legally be 63. Naive truncation is **forbidden** — it is non-injective, and two tenants pooled into one run namespace is the exact property this scheme exists to prevent |
| **No `ownerReference`, anywhere** | A namespaced dependent whose owner is in another namespace has the reference *treated as absent*, and the API server emits `OwnerRefInvalidNamespace` — so a reference set here would look like ownership and leak every object silently. Nothing in a run namespace carries one. The consequence is that **Kubernetes garbage collection does not apply to any of it**, and §3.7's finalizer is the only thing that collects workloads, copies and the namespace itself |
| **Workload provenance** | The **name** `<agent>-<revision>` is the deletion authority — Kubernetes names are immutable, so a victim object cannot be renamed into the shape, and that is the one property an attacker cannot forge. The `plume.dev/agent-uid` label and the `plume.dev/revision-digest` annotation corroborate it, and `status` vouches for the digest. None of this is a proof of *creation*: every element is public and predictable, so `AlreadyExists` is never provenance — an existing object must equal the desired one in full, or it is a collision and nothing is mutated. The watch maps by the `plume.dev/agent-namespace` and `plume.dev/agent` labels, since there is no owner to watch |
| **Read access** | Users cannot `kubectl logs` across a namespace they have no rights in, and the operator does not grant them any. Deriving "every subject that may read this Agent" is **not implementable**: Kubernetes answers "may this subject do this?" and never "who may do this?" — access arrives through Roles, ClusterRoles, aggregation, ClusterRoleBindings, groups, impersonation and external authorizers, so any derived list is incomplete in one direction and stale in the other. The supported path is a CLI verb that performs a `SubjectAccessReview` for the calling identity against `get` on the Agent and streams the run-namespace Pod's logs under the operator's credentials. **Design 08 does not describe that verb yet and nothing implements it**, so run-namespace logs are currently reachable only by a cluster administrator (§5) |
| **Pod Security** | The operator **mirrors all six Pod Security labels** (`enforce`, `audit`, `warn` and their `-version` variants) from the source namespace onto the run namespace at creation and on every reconcile, removing any the source no longer carries. Otherwise a tenant admin who sets `enforce: restricted` would find Agent Pods — running arbitrary user images — admitted under no level at all. Changing a namespace's labels does **not** re-evaluate running Pods; Kubernetes only warns. So a tightened level takes effect on the next Pod, and this design says so rather than implying eviction |
| **Quota and limits** | Every `ResourceQuota` and `LimitRange` in the source namespace is copied, spec for spec, to `plume-mirror-<name>` in the run namespace, reconciled on change and deleted with its source. Mirrored **together**, because a quota that constrains CPU rejects any Pod without a CPU request and the LimitRange is what supplies the default. The cost is stated: a quota is accounted per namespace, so a tenant's ceiling applies to each namespace separately and the pair can reach **2×** the stated limit. That is a decision, not an oversight — the Tenant API defines compute quotas as per-namespace ceilings and says so in `QuotasEnforced` (design 26 A1, ADR-0026 Amendment 1) — and the alternative, no quota in the run namespace, lets an Agent escape its tenant's ceiling entirely. Mirror names are DNS subdomains capped at 253, so the same truncate-and-hash rule applies past that, with the source name in an annotation so the reverse mapping never depends on a truncated name |
| **Identity** | The SVID path segment comes from a `plume.dev/agent-namespace` **label** carrying the Agent's own namespace, so the move is invisible to authorization. §3.5 states the template and why a label rather than the Pod's namespace |
| **Service and route** | Both move **with** the workload. Not a preference: a `backendRef` to a Service in another namespace requires a `ReferenceGrant` in the target namespace, and without one the route reports `Accepted=True` with **`ResolvedRefs=False, reason: RefNotPermitted`** — while design 03's convergence tuple requires `ResolvedRefs=True` before publishing. Leaving the route behind would wedge **every Agent at every install**. Emitting a `ReferenceGrant` instead is foreclosed by §3.1, which puts cross-namespace consent out of scope. Design 03 §3.2 states the namespace of every emitted resource and requires the Gateway listener to admit run namespaces |
| **Network policy** | §6 requires a default-deny NetworkPolicy with egress to the gateway only, and it follows the Pods here. It cannot be a chart template — run namespaces are created at reconcile time and a chart renders at install time — so the **operator** materializes it from a shape the chart's values supply, and only when `gateway.enabled` is true: "egress to the gateway only" on a cluster with no gateway is "no egress", which would break every P1 Agent silently. **Nothing renders or materializes it today** (§5, design 07 A5.4) |
| **Tenancy** | In soft mode the run namespace is a host namespace owned by this operator, exactly as here. In hard mode the tenant's own agent-operator creates it **inside** the vCluster, and the host-side objects land in the vCluster's sync namespace, which the tenant-operator labels so the Gateway admits its routes (design 26 A1) |

#### The binding record: how the operator proves it created a run namespace

"Created, never adopted" needs something durable to check against, and a label is not it: Kubernetes records no "created by", a label needs only `update` to forge, and after a restart the operator cannot tell its own namespace from a pre-created one wearing the same label. Without a proof, a principal holding cluster-scoped `create` on Namespaces pre-creates `plume-run-team-a` with a RoleBinding granting itself `admin`, and waits for the operator to write Secret copies into it — defeating the entire security claim before the first Agent exists.

For every source namespace `S` the operator keeps a **binding**: a `ConfigMap` named `plume-run-binding-<run-namespace>` in its own namespace, learned from a `--operator-namespace` flag that defaults to the ServiceAccount namespace file every Pod mounts; with neither, the operator refuses to start. A ConfigMap rather than a CRD because the record is operator-private bookkeeping that no user reads or writes.

| Field | Meaning |
|---|---|
| `sourceNamespace`, `sourceNamespaceUID` | the tenant namespace this run namespace serves, by name **and** UID, so a deleted-and-recreated tenant is a different tenant |
| `runNamespace`, `runNamespaceUID` | the run namespace, and the UID it had when the operator created it |
| `nonce` | 128 bits from `crypto/rand`, generated before the namespace exists and stamped on it at creation as the **annotation** `plume.dev/binding-nonce` — an annotation, not a label, because nothing selects on it |
| `state` | `Creating` · `Bound` · `Terminating` · `Deleting` — exactly these |
| `schemaVersion` | `1`. The record decides namespace deletion and credential placement, so decoding is **strict**: a missing field, an unknown state, or a version this operator does not carry is `RunNamespaceUnavailable=BindingRecordInvalid`, terminal, naming the field. **Nothing defaults** — a permissive decoder would reach a decision arm on a value nobody wrote. One field is state-conditional and a decoder that misses it wedges the operator on its first reconcile: `runNamespaceUID` is **absent while `Creating`**, by construction, and **required in every other state** |

**Two proofs, because neither covers the other.** The **nonce** defeats *pre-creation*: the attacker moves first and cannot stamp a value that does not exist yet. It defeats nothing afterwards — once stamped it is readable by anyone with `get` on Namespaces, one of the commonest grants a cluster hands out. The **UID** defeats *delete-and-recreate*: the attacker moves second, and a recreated namespace has a UID the API server chose, which nobody can reproduce. So the nonce is consulted only while `Creating`; from `Bound` onward every reconcile compares the live namespace's `metadata.uid`, and the nonce is never read again.

The gap between the two is the time from the namespace `Create` returning to the binding recording its UID — one API write normally, and **a whole outage** if the operator crashes between them, which a rolling update makes routine. No point-in-time inspection closes it: an "empty now" check does not freeze later writes, and the RoleBinding simply arrives after the check. So the rule is **a namespace is bound only by the reconcile that received its `Create` response**, from that response's UID. A successor that finds `Creating` and a namespace present — nonce matching or not — **never binds it**: matching nonce ⇒ delete the namespace it evidently created and did not record, rotate the nonce, retry; different nonce ⇒ refuse. The cost is one namespace churn per crash inside a one-write window; what it buys is that no namespace is ever adopted on the strength of being observed.

The record, the run namespace and the source namespace are read **live** through the API reader, never from the informer cache: a recreated namespace's old object sits in the cache between the API server's recreate and the next watch delivery, and a UID compared against a stale object is no proof at all. The protocol needs no cluster-wide lock; it needs **one process-local mutex per run namespace**, held across the checks by every writer of a binding — the Agent reconcile, the finalizer, the Namespace-keyed reconciler — because a peer mid-creation is otherwise indistinguishable from a crashed predecessor and would have its namespace deleted. Leader election gives one *intended* writer; the mutex plus live reads plus compare-and-swap on the record is what actually fences the protocol, and it is why more than one reconcile worker is safe.

**The checks run in this order, and the first that applies decides.** Precedence matters because the conditions overlap: a colliding tenant's binding is also `Bound` with a matching UID, so reading state first would pool two tenants.

| # | Reconcile finds | The operator does |
|---|---|---|
| 1 | no binding, a namespace of that name exists **with a deletion timestamp** | wait (`RunNamespaceUnavailable=Terminating`). The operator's own handler removes the binding before the namespace is gone, so refusing here would wedge its own recovery |
| 2 | no binding, a namespace of that name exists | **`NotCreatedByOperator`, terminal.** A binding is always written before its namespace, so a namespace with no binding is one this operator did not make. Nothing is written into it. The message spells out the re-bind record field by field |
| 3 | no binding, no namespace | create the binding in `Creating` with a fresh nonce. `AlreadyExists` means another reconcile of `S` won: re-read and continue from check 4 with **its** nonce — the nonce is always read from the record, never from memory, so the loser stamps the winner's value |
| 4 | the binding's `sourceNamespace` ≠ `S` | **`NameCollision`, terminal for the *second* tenant**: two source names truncate-and-hash to one run name. Nothing is deleted — the first tenant's material is live. The message names both namespaces |
| 5 | the binding's `sourceNamespaceUID` ≠ `S`'s current UID | the tenant was deleted and recreated, so the old run namespace is a different tenant's. From `Bound`: compare-and-swap to `Terminating` and run the handler. From `Creating`: nothing was ever bound, so there is nothing to terminate — and a `Terminating` record without a UID is one the strict decoder refuses; the crash-gap namespace, if one carries this nonce, is deleted and the record discarded, so the next pass meets check 1 or 3. From `Terminating` or `Deleting`: teardown is already under way, so fall through to check 6 rather than swapping again — a compare-and-swap *from* `Bound` would fail there and turn progress into an error. The Agent waits with `Terminating` |
| 6 | state `Terminating` or `Deleting` | the handler below runs, whoever is reconciling |
| 7 | `Creating`, namespace absent | create it, carrying the nonce annotation, the labels `plume.dev/run-namespace: "true"`, `plume.dev/pods-by: agent-operator`, `plume.dev/agent-namespace: <S>`, `plume.dev/owned-by: <install-uid>`, and the mirrored Pod Security labels. Then, **in the same reconcile and from the `Create` response's UID**: mirror `ResourceQuota` and `LimitRange`, record the UID, move to `Bound`. Mirrors precede `Bound` so the first Pod cannot precede its quota. `AlreadyExists` on the namespace create means someone else holds the name: return, and checks 8, 9 or 10 decide on the next pass — this is the create the bind-only-from-the-response rule exists to fence, so it is never treated as success |
| 8 | `Creating`, namespace present **with a deletion timestamp** | wait (`Terminating`), whatever nonce it carries — check 9's own delete from a previous pass, or someone else's |
| 9 | `Creating`, namespace present, nonce matches | **not bound.** The crash gap: a namespace this operator created and did not record, or a copy of it. Delete it (name shape and nonce verified), rotate the nonce, requeue |
| 10 | `Creating`, namespace present, nonce absent or different | **`NotCreatedByOperator`, terminal** — pre-creation |
| 11 | `Bound`, namespace absent | someone with cluster rights deleted it, and every copy and workload went with it. There is nothing to adopt: the binding returns to `Creating` with a fresh nonce and the namespace is recreated. Material is re-minted from the current sources **if they still hash to the desired digest**; a retained revision whose sources have drifted since it was gated cannot be reproduced, and §3.3 sends it to weight 0 with `RevisionMaterialUnavailable`. A cluster-rights deletion is recorded as the material loss it can be |
| 12 | `Bound`, namespace present **with a deletion timestamp** | someone else is deleting it. Compare-and-swap to `Terminating` and run the handler. Every create into it would fail 403 with cause `NamespaceTerminating` |
| 13 | `Bound`, namespace present, **UID differs** | **`NotCreatedByOperator`, terminal** — deleted and recreated by someone with cluster rights, whatever the nonce says |
| 14 | `Bound`, namespace present, UID matches | reconcile labels and mirrors; proceed |

**The `Terminating`/`Deleting` handler is idempotent and has one owner: whoever reads the state.** It runs from any Agent reconcile in `S` that reaches check 5, 6 or 12; from a **Namespace-keyed reconciler** registered for namespaces carrying `plume.dev/pods-by: agent-operator` and the `plume-run-` name shape — not `plume.dev/run-namespace`, which a vCluster's host sync namespace also carries — which exists precisely so the handler runs when `S` holds no Agent at all; and from the finalizer's last step. A crash anywhere re-enters the same code:

0. The handler acts only on `Terminating` or `Deleting`. In any other state it returns: checks 7 and 11 own an absent namespace under `Creating` and `Bound`, and a handler that deleted the binding there would race check 11's rebuild into check 2's terminal refusal with no attacker and no crash.
1. Namespace **absent, or present with a UID other than the binding's** → delete the binding; whatever holds the name now is foreign. This is the first check in every pass, before any list and before any flip back to `Bound`: restoring `Bound` on a live Agent's say-so without comparing the UID walks check 14 into a namespace somebody recreated while the delete was completing.
2. Namespace present with a **deletion timestamp** → requeue. Creates into it fail 403 with cause `NamespaceTerminating`, and the operator treats that cause as "wait", never as an error to retry against.
3. State `Terminating`: **live-list** the Agents in `S`, counting only if `S`'s current UID equals the binding's `sourceNamespaceUID` — a recreated tenant's list is empty by definition — and excluding any with a deletion timestamp; then list the workloads and copies in the run namespace whose `plume.dev/agent-uid` belongs to one of *those* Agents, other than the one reconciling. Objects matching no such Agent are orphans and go with the namespace: counting them would let one bypassed finalizer hold a namespace open forever and make check 5 flap on a dead tenant's leftovers. Either list non-empty ⇒ compare-and-swap back to `Bound` and proceed as check 14. A failed swap means the record moved: re-read and re-enter.
4. Both empty ⇒ compare-and-swap `Terminating` → **`Deleting`**. A failed swap means the record moved: re-read and re-enter.
5. State `Deleting`: delete the namespace after verifying its name has the `plume-run-` shape **and** its UID matches the binding. A UID mismatch means the namespace this record named is already gone: delete the record instead. The delete is idempotent; then step 2 applies until step 1 does.

**Two states rather than one, because the delete must be fenced against a flip-back.** With only `Terminating`, a creator could read it, list, find itself, flip to `Bound` and write material in the instant between another worker's empty list and its delete. Nothing flips back from `Deleting`, and a creator that reads it waits. An **external** Agent never uses the run namespace and is counted by neither list. A create that fails with cause `NamespaceTerminating` after the checks — the namespace went away between them and the write — is `RunNamespaceUnavailable=Terminating` and a requeue, never a material error.

**Teardown.** An Agent's finalizer deletes its own workloads and copies, then asks whether it was the last:

1. **Live-list** as the handler's step 3 does, excluding this Agent. "Last" means **no other Agent is declared and no declared Agent's workload remains** — a deleting Agent is not a reason to keep the namespace, but its workload still draining under `taskTimeout` is, or "nothing is force-killed silently" fails for any `kubectl delete -f dir/`.
2. If last, **compare-and-swap** `Bound` → `Terminating`. A failed swap because the record is already `Terminating` or `Deleting` is not an error — another finalizer, or this one before a crash: proceed.
3. Run the handler, and release the finalizer once it has issued the delete, found it issued, or restored `Bound`. The finalizer does not wait for the namespace to disappear.

The ordering is what makes it correct: the record changes state **before** the confirming list, and every reader sees it live. For a creator to write material into a namespace being deleted it would have to have read `Bound` before the swap *and* be absent from the list that ran after it — and an Agent that exists at the time of a live list is in it. A creator that read `Terminating` instead is either in the next list or waiting on `Deleting`.

**Losing the binding is recoverable by a human, and only by a human.** If the record is lost — a restore, an admin mistake — every Agent in `S` reports `NotCreatedByOperator`, and the operator does not guess its way back: it never vouches for a namespace it cannot prove it created. Recovery is a human recreating the record in `Bound` from the run namespace's own `metadata.uid` and the source namespace's UID (the nonce is not needed; `Bound` never reads it), then annotating each Agent in `S` to trigger a reconcile, because nothing watches an uncached ConfigMap. The human is vouching, the condition message says exactly that, and the harsh path is chosen on purpose.

#### Label authority

Three consumers act on run-namespace labels and none of them reads the binding record: the `ClusterSPIFFEID` selects on `plume.dev/pods-by`, the Gateway listener admits on `plume.dev/run-namespace`, and the Namespace-keyed reconciler keys on both. A label is writable by anyone who can create or update the namespace, so without something reserving them the labels are a convention, and a namespace-`create` principal could mint a SPIFFE-selected or route-admitting namespace the operator never made.

The chart therefore ships a `ValidatingAdmissionPolicy` and binding on Namespaces **and their `status` and `finalize` subresources** — both of which write metadata, so a rule naming only the main resource is bypassed through either. It denies any create or update that sets or changes `plume.dev/pods-by`, `plume.dev/run-namespace`, `plume.dev/tenant-sync`, `plume.dev/agent-namespace`, `plume.dev/owned-by` or the `plume.dev/binding-nonce` annotation unless the requester is one of the identities rendered **into** the policy: the operator's ServiceAccount, plus whatever the installer lists. **Not a params object** — a params ConfigMap that went missing would turn the policy into a cluster-wide denial of every namespace write. A second policy admits an `HTTPRoute` whose `parentRefs` name the plume Gateway only from those identities, so an admitted namespace is not a route-authoring grant; a `parentRef` without a namespace refers to the route's own, and the rule resolves it that way rather than skipping it.

**The operator fail-closes on their absence, by name.** At startup it logs, and on every reconcile it checks, that both policies and their bindings exist; if not, `RunNamespaceUnavailable=LabelAuthorityAbsent` and no run namespace is created, clearing when they appear. **Presence by name is all that is checked** — the content is the chart's, and a policy of the right name that validated nothing would pass. That limit is stated rather than implied. `ValidatingAdmissionPolicy` is GA from Kubernetes 1.30, which is the chart's declared floor, so the mechanism this whole boundary rests on is available on every cluster the chart admits. Design 07 A5.9 owns the rendered policies.

**The injected environment contract (A65).** §11 says this design owns it and design 09 §3 says templates "consume, never define" it. Until 2026-09-05 the contract was one sentence naming three variables, nothing injected any of them, and nothing reserved the namespace either — so a user could set `PLUME_GATEWAY_URL` in `spec.runtime.env` and, because a container keeps the **last** duplicate, redirect their agent's egress off the chokepoint where every budget, tool grant and egress rule is enforced. Written by exactly the person those rules constrain.

| Variable | Producer | Grammar | Available? |
|---|---|---|---|
| `PLUME_GATEWAY_URL` | **operator configuration** — the `--gateway-url` flag, so one cluster has one answer and no Agent can disagree | absolute base URL | **yes**, when the flag is set. Empty is the default: the chart ships no agentgateway subchart (design 07 §3) and `gateway.enabled` is `false` |
| `PLUME_KG_ENDPOINTS` | the resolved endpoint per `knowledge[]` binding | undefined | **no.** There is no `KnowledgeGraph` CR in any design to resolve one from — design 01 is the `KnowledgeGraphProvider` protocol, design 13 the Graphiti adapter, and neither declares the kind. **Owed to design 01/13** |
| `PLUME_NATS_URL` + task-store credentials | the tenant's JetStream account | undefined; the credential's Secret shape is undefined too | **no.** No NATS ships in the chart at all. **Owed to design 07.** `TaskStateUnverified` is the condition that already says an agent's shared task state is unproven |

Three rules, each of which was a hole:

- **`PLUME_` is reserved.** Admission rejects a `spec.runtime.env[].name` or a `spec.runtime.envFrom[].prefix` beginning with it. Injection also appends *after* user env, so the operator's value wins a duplicate even on a path that reached the workload without admission — defence in depth, pinned by a unit test because no envtest can construct the duplicate the CRD now refuses.
- **Nothing is injected without a producer.** A placeholder address makes an absent tier look like an outage: an agent that dials it reports a connection failure, where an agent that finds the variable absent takes its documented fallback. The two unavailable rows are in §5, not filled with a guess.
- **Injected values are not revision material, and that is a decision.** They are operator-owned, identical for every Agent, and unsettable by a user. A gate stops a *user* publishing capability an evaluation never saw; an administrator moving the cluster's gateway is a cluster operation, and gating it would make every Agent in the cluster mint a candidate at once and wait for an eval **during an infrastructure migration** — the worst possible moment to freeze every rollout. Same shape as `runtime.resources`: the gate covers named release material and capability configuration, and this is neither. The running workload does follow a repointed gateway, converged in place, because that is what the exception has to mean to be useful.

### 3.3 Revisions & the holding mechanism (entailed by ADR-0006)

A Kubernetes rolling update mixes old and new traffic and would defeat eval gating, so the operator owns revisions.

#### Identity: the name is forty bits, the identity is the whole digest

`revisionHash` truncates SHA-256 to ten hex characters. The projection it hashes is **attacker-controlled**, so the question is never accidental collision but *chosen* collision, and forty bits costs about `2^20` trials: a colliding pair of specs, one referencing a safe image and one a malicious image, was found in **1.2 seconds** on a laptop. (`internal/revision/collision_test.go` records 2.1 seconds for its own reproduction on different hardware; the argument is the order of magnitude, and either number makes it.) The bypass would be total — the safe member passes evaluation as revision H, the principal writes the colliding malicious spec, the operator computes the same H, sees `activeRevision == desired`, skips candidate gating entirely, and converges the Deployment named H to the malicious image while status still names the revision that passed its gate.

So name and identity are separated. `status.activeRevisionDigest` and `status.candidateRevisionDigest` carry the **full** digest and are the only values compared to decide whether two specs are the same revision; the ten-character form stays for object names and the `ACTIVE` column, where 64 characters are unreadable and a name is all that is needed.

**`status` is the authority; the annotation corroborates.** The digest in status is written only by this operator, through the status subresource, under separate RBAC. An annotation on the workload cannot be the authority: anyone with `deployments/patch` can set `plume.dev/revision-digest` to the digest of the spec they are about to write — a pure function of that spec, no secret needed — and the operator would then install the attacker's image on the gated revision itself, surviving drift correction. The annotation is a second, corroborating check for the one case status cannot cover: a stamped workload for which status holds no record, which happens when status and the cluster disagree about history. An **absent** annotation is **refused**, never adopted — legacy identity is never reconstructed from current spec, which is the collision payload with an extra step.

So the rule is: **a desired revision whose NAME matches a recorded one while its digest does not is `RevisionHashCollision` before the workload is touched at all.** Terminal: no adoption, no rewrite. The condition is **owned**, so it clears when the collision is resolved — an agent that reported `Ready=True` while still carrying a stale `True` collision condition is what teaches an operator that conditions mean nothing.

Two corollaries follow from the same principle, that the operator may only act on evidence it produced:

- **`AlreadyExists` on create is a race, not a success.** Something took the name between the read and the write, and the name derives from the Agent name and a public digest, so it is guessable by anyone holding `deployments/create`. The operator re-reads and applies the full invariant rather than accepting an object it never validated.
- **Availability alone does not authorize promotion.** It answers "is a workload available?"; the question that matters is "is an available workload of *this* revision?" A squatting object reports `AvailableReplicas` just as well, so the digest stamp and the Agent's UID label are checked before its status is believed.

#### The rollout

1. Spec change → `revisionHash(projection)` — a projection of the behaviour surface **plus the resolved contents of every env source it references**; the card digest is status, and card drift triggers re-registration, never a new revision → creates a parallel workload `<name>-<hash>`.
2. Candidate registers, gets identity, passes readiness — gateway route weight **0** (`phase: Held`).
3. The gate controller (design 16) runs the EvalSuite against the candidate through the gateway on a **candidate-only route** whose admitted set is exactly the eval run's own SVID, granted at Job launch and revoked at Job end. Eval traffic otherwise uses the identical path as production.
4. Pass → weights shift (canary steps, default `10 → 100`); `activeRevision` flips; superseded revisions are collected per the retained set below.
5. Fail → candidate deleted, report in status and PR annotation; `GatesPassed=False` naming the failing metrics.

**Spec change while a candidate is in flight**: the new generation **supersedes** the old candidate. It drains to weight 0 respecting `taskTimeout` (the drain design 22's kill switch uses), `GatesPassed` resets, and the abandoned revision is appended to `status.supersededCandidates` and emitted as an event (§5 — no recorder is wired, so nothing is emitted, and the list's cap of 10 is therefore a hard loss rather than a relocation). At most one candidate is ever in flight.

**Rollback** = re-point to a retained revision. Instant, no rebuild.

**Whether gates apply is discovered, not declared — and what is enforced is the gate an Agent declares, not that it declares one.** CRD-level CEL cannot observe whether another CRD is installed, so nothing about gating can be an admission rule. Instead the operator asks the cluster whether the `EvalSuite` CRD is present, caches the answer with a bounded TTL, and re-checks — a CRD installed after the operator starts must take effect without a restart. A discovery failure never becomes an answer: the previous answer stands, or "installed" if there is none, because holding is recoverable and ungated promotion is not.

Three outcomes, and the third is a gap this design states rather than hides:

| | |
|---|---|
| CRD absent | rollouts proceed with a loud `GatesSkipped=True`, naming whichever reason applies — the absent CRD, or no gates declared, which is checked first. A tier that was never installed is not an incident |
| CRD present, gates **declared** | the candidate holds at weight 0 until the gate controller passes it. This is the ADR-0006 mechanism |
| CRD present, **no gates declared** | the candidate **promotes**, with `GatesSkipped=True/NoGatesDeclared`. **Nothing requires an Agent to declare a gate**, in any profile. "≥1 gate required in prod" is a policy this design has stated and no component enforces (§5); enforcing it needs an admission rule that can see the cluster, which CRD CEL cannot, so it needs the same policy-controller binding §6 already owes for signatures |

#### The retained set, defined once

> **retained set** = `{active}` ∪ `{candidate}` ∪ *the `revisionHistoryLimit` most recent superseded revisions* ∪ *explicit holds*.

Its size is `revisionHistoryLimit + 2 + holds`, **at least four at the default of 2**, and it is what bounds `status.revisions[]` records (design 03 §3.1) and the revision copies below alike. History is *additional* to active and candidate because otherwise a rollout would garbage-collect its own rollback target and destroy the instant-rollback property ADR-0019 exists for. A design 20 retention hold — pinning the last eval-passing revision while a `Degraded` window is open — **extends** the set; it does not occupy a history slot, because a hold that displaced a history entry would silently shorten the rollback window during exactly the incident the hold exists for.

No other count appears anywhere in this design: everything that needs a bound derives it from this definition. §8 owes a maximum-overlap test — a candidate arriving while a hold is open and the history window is full.

#### What the projection covers, and what it does not

Two surfaces share one CR:

- **Behaviour surface** — a change to **what the agent can do, produce, or reach**. It must pass a gate, so it mints a revision.
- **Policy surface** — a change to **how much, how fast, or who may call**, without changing capability. It is applied in place.

The discriminator is *capability*, **not** the compile path. `knowledge[].scope`, `tools[].name` and `llm.providers` all compile to gateway resources via §3.6 and are all behaviour-surface, because narrowing what an agent may retrieve changes what it answers exactly as removing a tool does. Defining the policy surface as "whatever §3.6 compiles" would classify those three as policy and reintroduce the under-gating this rule exists to prevent. Hashing the whole spec instead would make `replicas: 2 → 3` pay for an eval-and-canary cycle; hashing too little would let someone swap the model or the knowledge-graph version under a running agent with no gate, hollowing out ADR-0006 and ADR-0005 together.

| Behaviour surface — **mints a revision** | Policy surface — **applied in place** |
|---|---|
| `runtime.image` | `runtime.replicas` — a scale operation |
| `runtime.env`, `runtime.envFrom` — **by resolved content** | `runtime.replicas` is the only wiring row left; see ADR-0031 |
| **`runtime.port` (ADR-0031)** — one approved image may serve the evaluated A2A implementation on one port and an administrative or simply different handler on another. Kubernetes does not require two ports of one container to serve the same program, route set or authorization | `runtime.resources` — **the documented exception**, see below |
| `runtime.sandbox.profile` | `card.path` — a path change is re-registration, exactly as card drift is |
| `knowledge[].name`, `.version`, `.scope` | `gates` — a gate that re-gated itself on edit could not converge |
| `tools[].name`, **and `tools[].requiresApproval`** | |
| **`loop` (ADR-0031)** — design 22 compiles `allowReentry` and `maxVisits` into in-proxy CEL that admits or denies each request by its lineage. Flipping `allowReentry` on a serving revision lets it execute cycles its evaluation forbade: capability widening, like a tool name | |
| `llm.providers`, `llm.fallback`, `llm.egressAllowlist`, `budget`, `expose` | |
| `external.endpoint` | `external.inlineCard` — a description, not a grant |
| `external.oauthClientRef` — **identity**, see below | |

**Changing this table is a hash migration, not a table edit.** Every existing revision hash moves, so every Agent mints a candidate and every active workload is orphaned by name. `internal/revision/golden_test.go` records the migrations taken so far and why the golden constant may not simply be bumped. The most recent, MIGRATION 3, is this table's own last change.

**`runtime.resources` stays in place, and `resourceFieldRef` is refused for it (A63, ADR-0031).** Resources are the one policy-surface row that can reach behaviour, because `runtime.env[].valueFrom.resourceFieldRef` reads a limit or request into the container: the selector is projected, the value it resolves to is not, so a CPU edit could change what the program reads under an unchanged digest. Gating resources would close that and cost the capacity-repair path during an OOM or throttling incident, so the field is **refused at admission** instead and resources stay editable. State the consequence rather than a stronger claim: **the gate covers named release material and capability configuration; live capacity is a documented operational exception.** An OOM-killed agent still fails tasks and throttling still changes `taskTimeout` terminations — design 20's drift automation does not exist and is not this row's backstop.

Six rules that are easy to get wrong:

1. **`tools[].requiresApproval` is behaviour in BOTH directions.** Turning approval on after an incident must not be applied in place: design 03's comparator registry has no approval concern, so an in-place tightening either wedges while the unguarded route keeps serving, or mutates the live interceptor and can NACK, leaving the direct route serving while status records the change as applied. Turning it *off* is a widening and must never reach production ungated either.
2. **`external.oauthClientRef` is behaviour, not credential rotation.** It selects *which client* an external agent authenticates as — the principal design 24 §3 keys `can_invoke`, `can_call` and the act-chain check on — so repointing it reaches a different set of tools. Rotating the credential *behind* a client is a Secret update the hash never sees, which is correct.
3. **Env sources are hashed by CONTENT.** Every `ConfigMap` and `Secret` reachable through `envFrom` or `env[].valueFrom` contributes a digest of its resolved contents to the projection. Referent identity alone was never sufficient: anyone with `update` on a referenced object could replace a system prompt or a provider endpoint, the pod would restart, and the new behaviour would serve under the old revision and the old gate result — with no permission to touch the Agent at all.

   Requiring referenced ConfigMaps to be `immutable: true` does not fix it, and the reason is the fact this whole area rests on: *"Once a ConfigMap is marked as immutable, it is not possible to revert this change nor to mutate the contents … You can **only delete and recreate** the ConfigMap."* Delete-and-recreate keeps the same name, so the referent and the hash are unchanged. **Immutability binds contents to an object; it never bound a name to contents.**

   Hashing also only *detects*. If a retained workload still references the user's object by name, a node drain recreates a Pod that reads the new content under the old gated hash and route, with no Agent write. The digest in status protects nothing by itself — which is why a revision reads its own copy (below).
4. **List order is not semantic.** Nothing in the corpus treats tool or provider order as meaningful — design 03 compiles tools to a set-semantics filter and providers to a commutative max-price — while kustomize, helm and `kubectl apply` round-trips all re-serialize lists. The projection therefore **sorts** `tools`, `llm.providers` and `knowledge`, so a re-serialized manifest does not re-gate. `env` keeps its order, which is semantic for interpolation.
5. **`llm.egressAllowlist` is behaviour, and the gate is symmetric.** It is the set of endpoints an agent may reach, so widening it changes what the agent can do — the same argument as `knowledge[].scope`. It is also the control ADR-0014's compliance profiles pin, so an ungated edit would widen egress on a HIPAA cluster with no eval.

   **Any change to the set mints a revision, in both directions.** An asymmetric gate — removals applied in place, additions minting — launders a widening: allowlist `{A}` gated and serving as R1 → edit to `{A,B}` mints candidate R2, held at weight 0 → edit to `{B}`, a *removal* relative to `{A,B}`, applied in place, R2 abandoned by supersession — and R1, the serving gated revision, now reaches `B`, which passed no eval. The predicate is also not expressible: a content-addressed digest is a function of one spec, and "is this set a subset of the previous one" needs both, so a subset rule would give up the content-addressing that "no double-create" and instant rollback both rest on. And the operational premise for asymmetry is false: design 27 §5 ships the BAA allowlist as a **pack filter** in the `compliance` priority band, so a coverage change is a pack change compiled at profile scope, not 200 Agent edits.
6. **`runtime.resources` is policy for a specific reason.** "Capacity, not behaviour" is too glib — an OOM-killed agent fails tasks and CPU throttling changes `taskTimeout` terminations, both observable in `task_completion`. The real argument is that resource regressions are caught by design 20's behavioural drift path (SLO burn on success rate → `Degraded`), and gating capacity changes would block incident response — the same reasoning that exempts fallback activation below.

**Classification is compulsory, never defaulted, and it is LEAF-level.** Every leaf of `AgentSpec` is classified: a table row may name an aggregate (`runtime.env`), and the aggregate's class is the **default** for the leaves beneath it, but an explicitly classified leaf **overrides** its aggregate and the override must appear in the table above. That precedence is not academic: `external` is a behaviour aggregate and `external.inlineCard` is policy — a description, not a grant — so without the override rule "the aggregate binds every leaf" and "fail unless the leaf is explicitly classified" give opposite answers for it. Overrides exist only for leaves of plume's own types; **no leaf inside a third-party struct is overridden today**, and one would have to be added to the table like any other.

Defaulting an unclassified field to policy-surface is **not** the safe direction: a behaviour field added without classification reaches production ungated and silently, which is the ADR-0006 hole itself. Adding a field to `AgentSpec` must fail the build until someone classifies it.

The test that proves exhaustiveness has a required shape, and each clause is there because its absence was demonstrated:

- **Reflect over PATHS, enumerate over TYPES.** These are `corev1` structs that gain fields between Kubernetes releases. A hand-maintained path list has already failed once: an env-source union naming four arms while the dependency carried five let `fileKeyRef` collapse to a constant, so repointing `prod.env → staging.env` minted no revision. Paths are therefore always discovered by reflection. Measured across `k8s.io/api` v0.28 → v0.36: **+1 named type and +5 leaves in eight minor releases, and zero new unexported-state types** — so the path walk is what catches drift, and the type registry is not.
- **The perturber registry fails closed.** Reflection alone cannot perturb every leaf: `resource.Quantity` holds its value in unexported fields, and the only reflect-settable leaf beneath `env[].valueFrom.resourceFieldRef.divisor` is `Format`, a display hint — so perturbing `Format` alone turns the walk green while `divisor: 1m` and `divisor: 1` still hash identically. A type the walk reaches that it cannot perturb through a public API therefore **fails the test** rather than being skipped, and a registered perturber **terminates the walk at that type**, or the walk descends into `Quantity`'s internals and the registry has to carry `math/big.nat`. The graph was enumerated, not estimated: **68 type nodes, 38 named, depth 10, no cycles, no interface leaves**, and **exactly one type carries unexported state** — `resource.Quantity`, at three paths, one of them on the behaviour side.
- **Recursion is guarded, not assumed away.** "`AgentSpec` must not gain a self-recursive type" is a precondition, not a guard: nothing enforces it and the failure mode is a hang. `apiextensions-apiserver` is already a direct dependency and its `JSONSchemaProps` has twelve self-recursion points. So the walker carries a **stack of the types on the current branch** and fails immediately on meeting one already there, naming the path that closed the cycle. A key that included the path could never match — the path grows at every step — so it would reintroduce the hang it exists to prevent. A type reached twice on *sibling* branches is not a cycle and must not fire: `AgentSpec` reaches several that way. A hang is an **INVALID** mutation, not a killed one — CI crashes instead of naming the new field.
- **A perturbed variant must be API-valid**, and differ only at the named leaf, or the API server rejects the mutant for an unrelated schema violation and the suite reports a kill where nothing was tested.
- **Map-kinded leaves** (`ResourceRequirements.Limits/Requests`) are perturbed over their key set and their value set (§5); either must mint if the leaf is behaviour. Both map paths hang off `runtime.resources`, which is policy, so they are moot today. Classification must *reach* every leaf; **projection** is what never descends into a policy aggregate.

A cheap reflection sweep is not this test. One run over the projection reached 31 leaves and correctly showed the non-minting ones to be genuine policy surface, but its depth cap and pointer seeding never reached `env[].valueFrom.*` at all — four of seven known leaves missed. The gap between "a sweep that finds something" and "a sweep that proves absence" is the whole difficulty.

**One exception, stated because the compulsory-gating claim above is otherwise false.** Design 20's `ModelDrifted` remediation activates `llm.fallback` by setting **status**, not spec, so it mints no revision and no eval fires — deliberately, since an eval cycle mid-incident is the last thing wanted. So **the model actually answering requests can change without a gate**, as incident response, with design 20's four guardrails (correlation, rate limit, receipt, override) as the compensating control. A reader who concluded that the serving model can *never* change ungated would be wrong.

Hashing is over the projection's canonical JSON. The projection struct's field order, JSON tags and `omitempty` are part of the revision contract — `encoding/json` emits in declaration order, so a cosmetic reorder would re-mint every revision in every cluster. The golden test pins the encoding; a change there is a **migration, not a test edit**.

#### Env sources: resolved before identity, copied before publication

A revision identity cannot be produced from a spec by itself: the hash and digest functions take the resolved sources and **refuse** without them. Three refusals, each closing a way the guarantee could have had a hole:

| Case | Behaviour |
|---|---|
| A referenced source does not exist, or the operator may not read it | `EnvSourceUnresolved`, **no revision and no workload**. A missing referent is *unresolved*, never a zero digest — a zero would let deleting an object mint the same hash as never having referenced it |
| An env source arm this operator does not recognise | the same refusal. Hashing only the arms it happens to know is a guarantee with a hole nothing reports, and `corev1` gains arms between releases. Any union arm the implementation does not name explicitly must hash **injectively** — over-gate — and never collapse to a constant |
| Content resolved | folded into the projection in a fixed sorted order, length-prefixed, with `data` and `binaryData` tagged separately so the same key in each cannot collide |

**A revision reads its own immutable copy, and the copy is what is hashed.** At mint, **before publication**, the operator copies every referenced `ConfigMap` and `Secret` into revision-scoped material in the run namespace, and the revision's PodSpec references only the copies. The user's object is never referenced by a published revision, so editing it, deleting it, or losing every guard that protected it cannot change what that revision serves. A change to the original is *detected* — it mints a candidate — and reaches production only through a gate.

The alternative considered was sealing the source in place with a finalizer and a fail-closed admission policy. It closes the planned case and cannot close the unplanned one: if the admission binding is removed, an authorised editor writes new content and a Pod replacement serves it before any watch fires, and no reactive remedy helps because the original bytes are already gone. **Sealing is a control, and a control that is removed stops controlling. A copy is an invariant** — the revision reads material the editor never had a reference to, whatever happens to the guard afterwards.

| | |
|---|---|
| Name | `<agent>-<revisionHash>-env-<n>`, `n` the source's index in the projection's sorted order — derived from inputs, so a re-reconcile converges rather than duplicating |
| Namespace | the run namespace (§3.2), which is what puts it out of the source-namespace editor's reach |
| Kind | preserved: a `Secret` copies to a `Secret`, **never** to a `ConfigMap`. The copy must not be readable by a wider set of principals than the original, and kind is what RBAC keys on |
| Immutability | `immutable: true`, so not even the operator can rewrite it in place. Kubernetes then permits only delete-and-recreate, and the operator does not recreate a published revision's material — the objection that sank sealing becomes a *property* here, because the name carries the revision hash rather than being reused. **One branch does recreate, and it is safe for a stated reason**: a copy whose bytes match but which is **not** immutable is deleted and recreated from the buffer, because the flag cannot be enabled after creation and matching bytes mean nothing is lost. Such an object can only have come from someone who won the create race with byte-identical content |
| Hashing | the projection hashes the **copy's** content, which equals the original's at mint. There is no second source of truth to drift |
| Optionality | a resolved copy is **always rewritten non-optional**, whatever the original said. `optional: true` on a copy means deleting the copy starts a replacement Pod with the variable simply absent — a silent change to the process environment achieved by a delete rather than an edit. Non-optional turns the same act into a visible failure to start, which is the observable this design wants |
| **Integrity authority: the bytes** | An existing copy is judged by its **content** first. `immutable: true` freezes `data` and **not** metadata, so a principal with `update` can rewrite labels and annotations; if metadata were the integrity check they could Degrade the agent permanently, converting the content edit this design prevents into a denial of service. The bytes are the only thing the Pod reads: if they match the buffer the revision was minted from, this **is** that material whatever the metadata says, and the operator **restamps** the labels and annotations rather than refusing. Content that does **not** match is `RevisionMaterialCollision` and the revision is not published |
| **Deletion authority: the name** | Nothing is ever deleted for wearing a label. The operator deletes only objects whose **name** has the derived `<agent>-<revisionHash>-env-<n>` shape — names are immutable, so renaming a victim into that shape requires the delete the attacker is trying to obtain — corroborated by the `plume.dev/agent-uid` label and the source annotation. Selecting on the label alone would turn `configmaps/update` into `configmaps/delete` across the namespace, executed with the operator's credentials |
| Missing copy | a copy that is **absent** sends the revision's route to **weight 0** with `RevisionMaterialUnavailable` naming the revision and the copy. Availability loss is the correct direction: the alternative is serving a revision whose material nobody can vouch for |
| Retention | copies for a revision are deleted in the same pass that retires the revision. The bound is **|retained set| × sources-per-Agent**, from the definition above and from nowhere else |

**One read, one buffer, one publish.** The rules above are implementable only if a single GET produces one immutable byte buffer used for **both** the hash and the Create. The natural two-read implementation — hash the original, read it again to build the copy — races an editor between the reads: the first GET reads safe bytes and computes H, the editor writes malicious bytes, and the operator creates the copy from the malicious content under a name and a gate identity that say H. The copy would be faithfully immutable and faithfully wrong. The order is fixed:

1. **GET once**, recording `uid` and `resourceVersion` with the content.
2. **Canonicalize and buffer** the exact bytes. Nothing re-reads the source after this point.
3. **Compute the full revision digest** over those buffers.
4. **Create** the immutable copies *from those buffers* — never from a second read.
5. **Read back and verify** kind, the immutable bit, and the bytes; restamp metadata that has drifted.
6. **Only then publish** the revision and its workload.

`AlreadyExists` on step 4 is a race, not an adoption: the operator re-reads and applies the whole invariant above rather than accepting an object it never validated.

**The residual costs are real, and are accepted with bounds rather than argued away.** Copies retain historical credential *material* for the retention horizon — bounded by the retained set, deleted with the revision, never longer than the rollback target survives. A rollback re-runs the material its revision was gated with, which can resurrect a credential its owner rotated away; that is the direct consequence of rollback meaning "run R1 again". The mitigation is a **typed credential binding** whose stable facts (issuer, principal, audience, scope, destination) mint a revision while short-lived bytes rotate under a trusted issuer. **That field does not exist** (§5), so an operator rotating a credential should expect a rollback past the rotation to use the old one.

The exemption question — whether rotating a value inside a Secret should be exempt from gating — is settled by fact, not preference. Exempting it would exempt the bypass, since `envFrom.secretRef` carries a system prompt exactly as well as an API key. And the cost of not exempting it is nil: **Kubernetes does not refresh a process environment when a ConfigMap or Secret changes.** `envFrom` and `env[].valueFrom` require container replacement either way; only *mounted volumes* update live, and this API does not expose them. There was never a no-restart rotation path on this surface to lose.

### 3.4 Registration & card handling

**The card is served by the container — the source of truth is the agent's code.** After a candidate is Ready the operator fetches it in-cluster (3 retries, backoff), validates it (parseable, name matches the CR, A2A version supported, and **signature** per design 09: required for plume-built agents, `CardUnsigned=True` for BYO/external), stores a per-revision digest in `status.cards[]`, wraps it in an OASF record and writes it to the directory (JetStream KV, `agents.<ns>.<name>.<revision>` plus the `.active` pointer; collected with revisions).

- **Card-vs-CR cross-check**: a card advertising a skill that requires a tool or graph the CR does not grant is a registration failure (`Registered=False`) naming the mismatch — otherwise it registers cleanly and fails at runtime.
- **Terminal unregistrable state**: retries continue with backoff for a `registrationDeadline` of 30 minutes; past it the candidate is **failed and deleted**, freeing its retention slot, with the reason recorded, so nothing holds a slot indefinitely — **which nothing counts down** (§5's first table). That deadline is **neither a spec field nor an operator constant** — registration is unimplemented, so nothing counts down (§3.1, §5).
- **Card drift** at runtime (digest change without spec change) → re-fetch, directory update, event.
- **External agents**: the card is fetched from the external endpoint; a CR-inline override is permitted only where the endpoint cannot serve one.

### 3.5 Identity wiring

One platform-owned **ClusterSPIFFEID** (spire-controller-manager) with a selector template — no per-agent registrar code:

```
spiffe://{{ .TrustDomain }}/agent/{{ index .PodMeta.Labels "plume.dev/agent-namespace" }}/{{ index .PodMeta.Labels "plume.dev/agent" }}
```

**`index` is required.** spire-controller-manager parses the template as Go `text/template` with no functions or options of its own, so `{{ .PodMeta.Labels "key" }}` is not a map lookup and its webhook rejects a template that does not parse (`docs/research/tenant-namespace-primitives-2026-09.md` §1).

**The path segment is a LABEL, not the Pod's namespace, and that is an authorization decision.** The Pod runs in `plume-run-<agent-namespace>`, so a template reading `.PodMeta.Namespace` would silently re-issue every agent's SVID under a new identity — `spiffe://…/agent/plume-run-team-a/reviewer` where every existing grant says `…/agent/team-a/reviewer`. Design 24 §3 keys `can_invoke`, `can_call` and the act-chain check on that principal, and design 03 compiles admitted sets from it, so every route would stop admitting the workload it was written for and the failure would read as a routing bug. The operator therefore stamps `plume.dev/agent-namespace` with the **Agent's own** namespace on every workload Pod: the move is meant to be invisible to authorization, and only an explicit label makes it so.

**A missing label must fail closed, and the template's shape is what makes it so.** `index` on an absent key yields the empty string, not an error. Because each label is a **whole path segment**, an absent label renders an empty segment (`…/agent//reviewer`), go-spiffe rejects the ID, and the Pod gets no entry and no SVID — the correct outcome for a Pod that cannot say which agent it is. That property is shape-dependent: a template writing `agent-{{ index … }}` would render a *valid* ID from an absent label. So the rule is that every label-derived value is a whole segment, **and** the `podSelector` additionally requires both labels to exist, so a Pod without them is never selected at all. Both halves, or the property is gone.

**What makes a label-derived identity sound.** A principal who chooses a Pod's labels chooses this identity, so **anyone who can create a Pod in a selected namespace can claim any agent identity in any tenant**. That is acceptable only because the selector admits namespaces in which *only the operator creates Pods* — labelled `plume.dev/pods-by: agent-operator`, deliberately distinct from `plume.dev/run-namespace`, which the Gateway listener selects on and which a vCluster's host sync namespace also carries, where a **tenant** creates the Pods (design 26 A1). One label cannot carry two trust boundaries. Nothing grants Pod `create` in a run namespace: the chart renders no such Role or RoleBinding, and §3.2's admission policy is what makes the label itself the operator's. If a future change ever grants a write verb in a run namespace, the hardening is one `ClusterSPIFFEID` per run namespace with the segment as a literal and a `kubernetes.io/metadata.name` selector — per-namespace registrar code, which this section exists to avoid.

Pods are labelled `plume.dev/agent`, `plume.dev/agent-namespace` and `plume.dev/revision`; SVIDs are delivered via spiffe-csi. The operator additionally provisions a per-agent **`agent-actor` OAuth client** (design 06) so exchanged tokens' `act` chains name real agents. External agents get no SVID — they authenticate with OAuth client credentials. Hard-mode tenancy uses per-tenant SPIRE federated to the host trust domain (design 26; design 06 A3 records that premise as unmeasured).

**Nothing installs SPIRE today.** Design 07 A5.2 specifies the `ClusterSPIFFEID` the chart will render when the SPIRE subchart lands; until then no Agent has an SVID, and §5 says so.

### 3.6 Gateway handoff (interface with design 03)

The operator normalizes **one revision's** material (tools, budget, `llm`, expose, KG scopes, that revision's weight, `gatewayReplicas`) into a `PolicyIntent` — one **per live revision**, never one per Agent — and calls the policy compiler as an **in-process library**, which emits agentgateway resources under fail-closed apply ordering. The operator owns their lifecycle by **label and name**, not by `ownerReference`: they live in the run namespace, where a cross-namespace owner reference is treated as absent (design 03 §3.2). The gateway CRD surface is pinned by the chart (design 07) at a minimum version carrying OSS token exchange.

### 3.7 Finalization

On delete, an operator finalizer gates ordered teardown. Nothing here goes with an `ownerReference` — under §3.2 no run-namespace object carries one — so this step is the only thing that collects any of it. A copy left behind is a snapshot of a Secret's bytes outliving the Agent that justified reading them.

The ordered steps: **drain traffic** (weights 0, respecting `taskTimeout`) → **revoke** routes and policies in design 03's reverse apply order → **deactivate, never delete**, the `agent-actor` OAuth client (design 06 D3) → **collect** directory entries and SPIRE pod labels → **delete this Agent's workloads and copies in the run namespace, and the run namespace itself if this was its last Agent**, by §3.2's binding protocol → release the finalizer. In-flight tasks drain or time out; nothing is force-killed silently.

Design 26's hard mode splits this: workload teardown inside the vCluster, route teardown host-side, ordered by a marker the compiler writes when revocation completes (design 26 A1).

## 4. Behavior — reconcile outline

```
observe Agent CR + workloads/material in the run namespace + spend aggregate (read-only, design 04)
→ validate what admission could not: §6's list names what CEL enforces and what it cannot
→ ensure the run namespace and its binding (§3.2); refuse rather than adopt
→ resolve every env source; refuse to mint without content (§3.3)
→ ensure revision material, then the workload for the desired revision (Deployment | Sandbox)
→ ensure identity labels / agent-actor client / oauth client (external)
→ candidate Ready? fetch + validate + cross-check card → directory upsert
→ compile PolicyIntent → apply gateway resources (weights per rollout state)
→ hold/advance rollout per gate-controller signals; supersede in-flight candidate on new generation
→ evaluate budget backstop; guard states (BudgetHeld, Killed) win over rollout state
→ update conditions + phase; emit events
```

Idempotent. Writes are `Create`/`Update` under **optimistic concurrency**, not server-side apply: §3.2's fence is a compare-and-swap that needs a `resourceVersion` conflict to fire, and an apply from the operator's **own** field manager produces none — SSA conflicts on another *manager's* fields, and every writer of the binding record is this one process. So "a failed swap means the record moved" would never fire and `Terminating`→`Deleting` would stop fencing. Operator state is as §2 lists it.

**Stated but not enforced.** Every guarantee this body states **in the present tense** that nothing in the repository implements is here, so a reader never has to infer it from silence. Whole subsystems still waiting on another design are named in the header rather than repeated per row: registration and card handling (§3.4) have no code at all, and neither does the directory write §3.4 describes.

Digest pinning is what will make that verification meaningful, because a signature is verified *against* a digest |

**Failure modes.**

| Failure | Behavior |
|---|---|
| Image is a tag, not a digest | Rejected at admission by CEL; never reconciled |
| `envFrom`/`valueFrom` referent missing or unreadable | `EnvSourceUnresolved=True` naming it; **no revision is minted and no workload is created**. `optional: true` does not change this: the operator cannot know what the pod will see |
| Rollback target's env content in the *user's* object has changed since gating | **Irrelevant.** The revision reads its own copy, so the original moving says nothing about whether the revision can be rerun — that is the property copies were chosen for. Refusing here would decline a recovery that is perfectly available |
| Rollback target's revision COPIES are missing, or their bytes do not match | Rollback is **refused**, naming the revision and the copy. The material either exists and hashes to what the revision was gated with, or the revision cannot be rerun. Refusing is the fail-closed direction; rolling back to material nobody can vouch for reintroduces the bypass through the recovery path |
| A copy exists with the right bytes and drifted metadata | Metadata is **restamped**, not refused: `immutable: true` does not freeze labels, so treating metadata as the integrity check would let `update` become a permanent Degrade (§3.3) |
| The label-reserving admission policies are absent | `RunNamespaceUnavailable=LabelAuthorityAbsent`, terminal until they are installed; no run namespace is created, because the labels SPIRE and the Gateway act on would be forgeable |
| Binding record missing a field, unknown state, or an undecodable schema version | `RunNamespaceUnavailable=BindingRecordInvalid`, terminal, naming the field; recovery is the human re-bind in §3.2 |
| A run namespace exists that the binding record does not vouch for — no record, a different nonce while binding, or a different UID once bound | `RunNamespaceUnavailable=NotCreatedByOperator`, **terminal**; `Ready=False`, `phase: Degraded`. Nothing is written into it. The message says what to check: pre-creation, or deletion and recreation outside the operator |
| Two source namespaces truncate-and-hash to one run namespace name | `RunNamespaceUnavailable=NameCollision` on the **second** tenant's Agents, terminal, naming both. The first tenant is untouched |
| Run namespace being torn down — last Agent deleted, or the source namespace recreated | `RunNamespaceUnavailable=Terminating`, `phase: Pending`, requeued; clears when the namespace is gone and a fresh one is created |
| Declared gates, EvalSuite CRD installed, gate controller has not passed the candidate | The candidate **holds at weight 0** with `GatesPassed=False`; a reconcile-time hold, never an admission rejection (§3.3) |
| **No** gates declared, EvalSuite CRD installed | The candidate **promotes**, with `GatesSkipped=True/NoGatesDeclared`. Loud, and not a hold — nothing requires a gate to be declared (§5's first table) |
| Card fetch fails | `Registered=False` with a reason naming which check failed, and retried every 15 s. **The candidate is NOT held and is NOT deleted at a deadline** (A68): §3.4 says both, the code promotes anyway, and nothing counts the deadline. That divergence is deliberate for now — the deadline is the mechanism that would make holding safe, and without it a held candidate never converges — but it is a divergence, not an implementation of this row |
| Card advertises an ungranted capability | `Registered=False` naming the mismatch (§3.4) |
| Card unsigned (BYO/external) | Registers with `CardUnsigned=True` — the BYO promise holds, the gap is visible |
| Sandbox runtime absent | Hardened-Deployment fallback + `SandboxDowngraded` |
| Scratchpad access mode unavailable | Candidate runs without it + `ScratchpadDegraded`; the active revision is unaffected |
| `replicas>1` without a shared-task-state declaration | `TaskStateUnverified` + CLI warning |
| New generation during canary | In-flight candidate drains to 0, recorded in `supersededCandidates` + event |
| Rollback target collected | Prevented by §3.3's retained set and design 20's hold; if it still occurs, rollback is refused and the escalation names the gap |
| Kill switch during rollout | `Killed` guard state wins over every rollout state; the gate controller observes and abandons cleanly (design 22) |
| Budget exhausted (backstop tier — not exact in USD, ADR-0028) | `BudgetExhausted` + `phase: BudgetHeld`; serving weights 0 until the 00:00 UTC window resets |
| Spend aggregate unavailable (design 04 down) | Gateway approximation still enforcing; `BudgetEnforcementDegraded` — the exact-tier gap is visible |
| Pricing row missing for a usd budget | `PolicyCompileFailed` naming the model (design 03 §3.5). **Not** `PricingStale`, which means the table is older than 30 days — one condition cannot carry both meanings and mean either |
| Receipt pipeline gaps affecting this agent | `ReceiptsDegraded` (design 04) |
| IdP unavailable at `agent-actor` provisioning | `IdPUnavailable`; machine mTLS paths continue, human/on-behalf-of paths fail closed (design 06) |
| Gateway API **unreachable** (control plane down), CRDs still installed | Last-applied config stands; `Ready` degrades to stale-but-serving; retry. Scoped to unreachability: **deleting the CRDs garbage-collects the routes**, so nothing stands and design 03 §5's `CRDsAbsent` row governs instead |
| **Gateway CRDs absent, `gateway.enabled: true`** | A **broken install**: `GatewayIncompatible=CRDsAbsent`, `Ready=False`, `phase: Pending`, page — at every profile, `local` included |
| **`gateway.enabled: false`** — the declared-ungoverned tier (P1, `local`) | **`GovernanceSkipped=GatewayDisabled`**, a separate condition type, not a reason on an error type. `Ready` unaffected, no page. Same shape as `GatesSkipped` for a missing EvalSuite CRD and design 24's `ReBACAvailable=False` — a tier that was never installed is not an incident, and consumers keyed on error conditions must not fire on it |
| Policy compile or apply fails for this agent | `PolicyCompileFailed` / `PolicyApplyIncomplete` (design 03 §3.3, §3.3.1); routes withheld, so no ungoverned traffic path exists |
| SPIRE down | Existing SVIDs valid until expiry; new revisions held (`IdentityIssued=False`) |
| KG binding invalid or not `active`/`superseded` | `KnowledgeBound=False` → `Degraded`, and **no traffic if that graph is the agent's sole knowledge source** (design 01 §5, which carries both halves). Architecture §04 states the stronger unqualified rule — a non-Ready graph means no traffic — and design 03 already records the pair as a place two documents disagree; this design follows the narrower rule and says so rather than silently choosing |
| Finalization stalls (drain or revoke blocked) | Finalizer holds; `Degraded=True` with reason `FinalizationStalled`, the message naming the stuck step; never force-deleted |

## 6. Security

**Admission, and what enforces each.** CEL on the schema enforces: a digest-pinned `runtime.image`; exactly one of `runtime`/`external`; `sandbox` excluding `replicas>1` (ADR-0027); each LLM arm carrying its own instance block, and no other's; an Agent name of at most 52 characters, so the derived workload name fits a DNS label. **Prod-gate presence is not admission and cannot be** — CRD-level CEL cannot observe whether another CRD is installed — so it is a reconcile-time hold (§3.3). **Cosign signature verification is not CEL-expressible and is not shipped** (§5): it needs the Sigstore policy-controller binding design 07 A2 chose, whose *effective enforcement* contract A3 defines, since a present controller verifies nothing by itself.

Workload pods run non-root with a read-only root filesystem, a `RuntimeDefault` seccomp profile, all capabilities dropped and no service-account token mounted — applied to **every** agent, not only sandboxed ones, so the sandbox fallback path is no weaker than the default path. A default-deny NetworkPolicy is required and **is not applied today** (§5).

Directory writes are the operator's identity alone. External-agent OAuth secrets live in Kubernetes Secrets (ESO-compatible), never in spec. The candidate-only eval route admits exactly one principal (design 16). The operator's own escalations are named rather than buried: cluster-wide `create`/`update`/`delete` on Namespaces, ConfigMaps and Secrets, bounded in code by the name shapes it derives and the binding record it verifies — an operator compromise yields Secret *creation*, not only reads — and design 07 A5.7 carries the full grant table.

## 7. Observability

Conditions as above. **Everything else in this section is specified and unbuilt** (§5): events on every transition; metrics: reconcile latency, rollout duration, held-revision count, superseded-candidate count, card-drift count, registration-deadline failures, and gauges for `SandboxDowngraded` / `TaskStateUnverified` / `ScratchpadDegraded` / `RunNamespaceUnavailable`. Shipped alerts: candidate held >1h, repeated card-fetch failures, identity issuance failures, budget-held agents.

## 8. Testing & conformance

What each layer may honestly claim is fixed by what it runs: unit tests assert against the *generated* artifact, never a fixture in the test file; envtest runs a real API server and **no kubelet**, so every availability assertion there is against a status the test itself wrote; only the k3d e2e can claim a Pod actually runs, and only it runs under the operator's real RBAC.

- **Revision identity**: golden encoding, the four recorded migrations, leaf-level classification over the reflected path walk with its fail-closed perturber registry, and chosen-collision cases proving a colliding name is refused with and without a workload present.
- **Revision material**: the one-read order, kind preservation, non-optionality, content-first integrity with metadata restamped, name-authority deletion with fully-labelled bystanders left alive.
- **Run namespace**: one envtest case per numbered check in §3.2; one per crash point with a paused reconciler — after the record create, after the namespace create (the successor must delete, not bind), between teardown steps 2 and 3, and between handler steps 4 and 5.
- **On a real cluster**: that a principal with `create`/`delete` on ConfigMaps in the Agent's namespace cannot delete or recreate a revision's copy, **with that principal's own-namespace delete as the control** — "it was refused" is not evidence about *which* rule refused; that a cluster-admin identity outside the policy's list cannot create a namespace carrying the reserved labels; and a `SubjectAccessReview` for every verb the run-namespace code calls, since envtest runs as admin and cannot see a missing grant.
- **Every security predicate above carries a mutation**: the predicate is negated alone, the fixture differs from a valid state in exactly one way, and the named test must fail. A mutation that does not compile is **INVALID**, never KILLED.
- **Owed**: an exhaustive transition matrix over the four binding states, rather than the per-check cases that exist; the maximum-overlap retention case (§3.3); an Agent in `team-a` receiving `…/agent/team-a/<name>` whatever namespace its Pod runs in, which needs SPIRE; and the real-cluster cases envtest cannot reach because it has no namespace controller to finish a deletion — operator restart mid-protocol, a paused delete racing a new Agent, and a chosen name collision.
- e2e on k3d+kind (NFR-3): sample echo-A2A agent → registered / identity / routed; sandbox fallback asserted on kind; scratchpad read-only attach and its degraded path; rollout hold/advance with a fake gate controller; spec-change-during-canary; kill during eval; external-agent registration against a mock endpoint; card cross-check negative test; registration-deadline expiry frees the slot.

## 9. Decisions (veto async)

1. **Deployment default; Sandbox opt-in** (singleton; mutually exclusive with `replicas>1`).
2. **Card SoT = container-served**, per-revision digests in status; inline override only for external agents.
3. **Gateway-weighted blue-green revisions owned by the operator** — required by eval-as-admission; retention counts *in addition to* active and candidate.
4. **Identity via one templated ClusterSPIFFEID + pod labels**, plus a per-agent `agent-actor` client; zero custom registrar code.
5. **Detection over assumption** for multi-replica task state, and **loud degradation** for every unavailable guarantee.
6. **Finalization deactivates identity objects, never deletes them** (design 06 D3).
7. **Workloads and revision material live in an operator-owned run namespace** the operator proves it created (ADR-0029), because a copy is only out of an editor's reach if the Pod is too.

A26 (2026-08-27, from `reviews/03-codex-review-r4.md` BLOCKER 5 and 6) — **who holds a sealed source, and what happens when the guard goes away.** A23 named both as owed. The scoped B3 review had made the first a *precondition* of the seal rather than a test detail, and the second is a live gap in a mechanism already committed.

**The finalizer list is the reference count.** Rather than a side-car lease object with its own consistency problem, each retaining revision adds its **own** finalizer to the source and removes only that one.

**The lease name cannot contain the revision hash (A28).** An earlier draft named it `plume.dev/src.<agent-uid8>.<revision8>` while the same section required *seal first, then read* — and A20 makes the sealed content part of the revision digest. So `revision8` did not exist at the moment the finalizer had to be written. That is the **circular identity defect this project's own history already records** (a hash depending on a value knowable only after the thing it identifies), reintroduced in the mechanism meant to prevent content moving underneath a hash. An implementer resolving it by hashing first reopens the exact race the seal closes: the editor changes the source between the read and the finalizer write, and the candidate is named for content its Pod will not see.

The lease is therefore named for something knowable **before** any content is read — `plume.dev/src.<leaseUID>`, where `leaseUID` is durable and random, recorded on the Agent *before* the source is touched.

**The identity is not truncated (A29).** An earlier draft used `src.<agent-uid8>.<revision8>` — 64 bits across two truncated halves, in a list Kubernetes treats as a **set**. Two holders whose truncations collide share one string, so the first release removes the second's hold and unseals a source a live revision still references, silently. `leaseUID` is a full 128-bit value rendered to fit the qualified-name segment limit — **63 characters, not 253 (A33)**: 253 is the optional DNS-subdomain prefix *before* the `/`, and the segment after it is capped at 63. `src.<UUID>` is 36 characters and fits either way, so the mechanism was never at risk, but the stated bound would have blessed a longer name that admission rejects. The rendered finalizer is pinned by an admission test rather than by arithmetic in prose. A `leaseUID` already present on a source when this Agent did not put it there is a **collision that is refused and reported**, never coalesced — a lease is per-holder or it is not a refcount.

**Ownership is a server-side reservation, not a self-report (A32).** "A `leaseUID` this Agent did not put there is refused" needs the operator to *know* which it did — and a status record it wrote itself cannot answer that after a crash between recording the UID and adding the finalizer. Both a genuine holder and a colliding one hold an identical record. Scanning every Agent's status can reveal a duplicate but resolves nothing: neither side can prove priority, and if both proceed, one release removes the set-valued finalizer while the other revision still references the source.

So the UID is reserved through an object whose uniqueness the **API server** enforces: a `coordination.k8s.io/v1` `Lease` named `plume-src-<leaseUID>` in the operator namespace, created with `Create` — which fails `AlreadyExists` atomically — and carrying an `ownerReference` to the Agent. The reservation is what makes ownership independently verifiable: any party can read the Lease and see which Agent owns it, without trusting a self-report. `AlreadyExists` means the UID is taken, whatever the reason; the operator draws a new UID and retries rather than reasoning about whether the collision was its own.

Two properties fall out for free, which is the argument for using a core object rather than inventing a registry. The `ownerReference` makes Kubernetes garbage-collect the reservation when the Agent is deleted, so a deleted Agent cannot strand a name. And a `Create` is a single round trip with no read-then-write window to lose.

**Acquisition order, and why the sweep cannot race it.** The order is: **draw a lease UID → `Create` its Lease (`AlreadyExists` ⇒ draw again) → record the UID in Agent status → add and observe the finalizer → read and hash the sealed source → associate the lease UID with the resulting revision hash.** The reservation *precedes* both the status record and the source write, so at every step the durable state is unambiguous:

| Crash after | Durable state | Recovery |
|---|---|---|
| the `Create` | a Lease owned by this Agent, no status record | re-record and continue; the reservation is already this Agent's |
| the status write | Lease + record, no finalizer | add the finalizer and continue |
| the finalizer add | Lease + record + seal, no revision | read, hash and associate — the pre-revision hold the withdrawn sweep rule would have reclaimed |
| the association | complete | nothing |

Release is the reverse and is ordered: remove the finalizer, **then** delete the Lease. A Lease outliving its finalizer costs a stale object the sweep removes; a finalizer outliving its Lease would leave a seal no reservation explains. §8 owes a **forced-collision** test: two Agents driven to draw the same UID must produce exactly one successful `Create`, one retry, two distinct reservations, and no shared finalizer string.

The startup orphan sweep therefore keys on that record, **not on whether a revision exists** (A29). An earlier draft swept entries whose revision no longer existed — but between adding the finalizer and minting the revision there legitimately is no revision, so a leader change in that window would classify a valid in-flight hold as an orphan and unseal a source mid-acquisition. The sweep instead removes only a `leaseUID` that appears on **no Agent's status at all**, and it runs **before** the reconcilers start, so it cannot observe a half-written acquisition from a live worker. A crash at any step leaves either a recorded-but-unsealed lease, which the next reconcile completes, or a sealed-and-recorded one, which is live; never a source sealed under a name nothing can resolve.

The rest is deliberate:

- Add and remove **must be an explicit read-modify-write carrying `resourceVersion`, with retry** — this is *not* free, and the obvious implementation is badly wrong. Measured: **20 concurrent naive JSON-patch appends left ONE finalizer**, losing 19 of 20 holds. The same 20 writers doing read-modify-write with `resourceVersion` and retry produced all 20. A26's first draft said the list was "compare-and-swap by construction"; it is compare-and-swap only if the writer supplies the precondition.
- "Release only after an authoritative list of all live leases" collapses to "remove your own entry", because the object *is* the list. The source is sealed while any `plume.dev/src.*` finalizer remains, and becomes deletable when the last one goes.
- The admission policy already denies finalizer removal by every principal but the operator (spike §4), so a holder cannot be evicted by the source's editor.
- Finalizers are durable in etcd, so a crashed operator's holds survive the crash. Orphan reclamation is a startup sweep, not a liveness protocol, and it keys on the **recorded lease UID** — the rule stated above. The earlier wording, *"drops entries whose agent-UID or revision no longer exists"*, is **withdrawn (A32)**: it contradicted the paragraph seven lines above it, and following it would reclaim a valid pre-revision acquisition after a leader restart, unsealing a source mid-acquisition. Two rules for one sweep is worse than either rule alone, because an implementer picks one.

Acquire order is fixed and matters: **seal first, then read.** Add the finalizer and observe it, *then* re-read the source's UID and content and hash it. Reading first would hash content that could change before the seal landed, which is the same before-and-after race the seal exists to close. The recorded material is `{uid, resourceVersion, selected keys, digest}`; a UID change means delete-and-recreate happened while unsealed and is treated as divergence, not as the same source.

**The digest in status is keyed, because a raw one is a guessing oracle (A27).** `status` is readable by anyone with `get` on Agents, which is a far wider set than those who can read the Secret. A raw `sha256` of a low-entropy value — a feature flag, a username, a short token, `true`/`false` — is trivially reversed offline by anyone holding it. So the digest published in status is `HMAC(cluster-key, content)`, with the key in an operator-only Secret; equality comparison still works, offline guessing does not. **Rotation is keyed, staged and interruptible — it is not one atomic pass (A29).** Agent statuses cannot be rewritten atomically across a fleet, so an earlier draft's "re-derives every retained digest in one pass" had no safe failure point: changing the key before every digest is rewritten makes unchanged sources fail comparison and go to weight 0, and changing it after leaves new digests unverifiable with the old key.

Each recorded digest therefore carries the **key ID** that produced it, and rotation is staged. Verification accepts **any retained key**, so a half-finished rotation compares correctly in both directions and can be interrupted, resumed, or abandoned.

**A scan is not a write barrier (A31).** An earlier rule retired K1 once a sweep observed no K1 digests remaining. That orders the *rotator* against the fleet and leaves the **writers** unordered: a reconcile worker that started before the rotation, holding a cached view naming K1 active, can commit a K1 digest after the final scan. Nothing re-scans, K1 is retired, and the next verification raises `VerificationKeyMissing` on content that never changed — withholding new revisions for that Agent until a human restores a key the cluster believes it retired. The window is not narrow: it is the lifetime of any in-flight reconcile.

Key state is therefore an explicit machine with an **epoch**, and every digest write is conditional on it:

| State | Writers | Verifiers |
|---|---|---|
| `active` (epoch *N*) | the only key a digest may be written under | accepted |
| `verify-only` | **never** written under | accepted |
| `retired` | never | rejected — `VerificationKeyMissing` |

- Every digest status write **compares and swaps against the current active epoch**. A writer whose cached epoch is stale loses the CAS, re-reads, and retries under the new key. This is the same read-modify-write-with-precondition the finalizer list needs, for the same reason: the precondition is what makes the operation safe, and the obvious unconditional write is the bug.
- Retirement order is: K2 becomes `active` at epoch *N+1* → K1 becomes `verify-only` → **drain or fence every writer at epoch ≤ N** → re-derive remaining K1 digests → a final consistent rescan → retire K1. A write that loses the CAS after the rescan is retried under K2, so it cannot land under a retired key.
- Nothing enforces the drain today; it is stated so the implementation carries it. §8 owes the test: a **paused** worker holding epoch *N*, resumed after K1 is retired, must produce a K2 digest and no `VerificationKeyMissing`.

**Missing key is unverifiable, not divergent.** If a digest names a key ID that no longer exists, the operator cannot conclude the source changed — it can only conclude it cannot tell. That raises `EnvSourceProtectionUnavailable` with reason `VerificationKeyMissing` and **withholds new revisions**; it does **not** set `RevisionMaterialChanged` or weight 0, because treating "cannot verify" as "has changed" would take a healthy fleet down on a lost Secret.

**Guard loss does not keep serving blindly, and does not nuke the fleet either.** The spike measured that deleting the admission Binding immediately restores the editor's write (§4.2), and A23's response — withhold new revisions, raise `EnvSourceProtectionUnavailable` — protects only future revisions while retained ones keep resolving a now-mutable object by name. That is truthful and not fail-closed.

The correction distinguishes *possible* from *realised* compromise, because the operator already watches every sealed source for A20's content hashing:

| State | Response |
|---|---|
| Guard absent or skewed, every sealed source still matches its retained `{uid, digest}` **at the instant it was read** | `EnvSourceProtectionUnavailable`; **no new revisions**; serving continues **only under a planned, overlap-only guard transition** (below). Outside one this row does not apply — the race does. Two limits on the predicate itself, so it is not read as a safety proof (A34): a match is a point-in-time observation, and an edit plus a kubelet restart can invalidate it between the read and anything done about it; and if the digest names a retired key the predicate is not false but **unknowable** (`VerificationKeyMissing`), which is a third state this row does not have |
| Guard absent **and** any sealed source diverges from its retained digest or UID | **`RevisionMaterialChanged`, weight 0 for every revision referencing it**, `phase: Degraded`. The bypass has occurred, so the affected revisions stop serving — via the existing rollout weight machinery, not a new route mutation (A19 removed those) |
| Guard restored | Re-verify every retained source against its recorded material **before** republishing. Divergence found on restoration is treated as the row above, never repaired in place |

**`EnvSourceProtectionUnavailable` is abnormal-true, and its full contract (A27).** It is in §3.1's vocabulary; here is what consumers may rely on:

| Guard | Sources verified? | Condition | `Ready` | Route | Clears when |
|---|---|---|---|---|---|
| present | — | absent | unaffected | unaffected | — |
| absent or skewed | all match | `True`, reason `GuardAbsent` | **unaffected** | unaffected; **no new revisions** | guard restored *and* re-verified |
| absent or skewed | any diverges | `True` + `RevisionMaterialChanged` | `False` | **weight 0** for referencing revisions | divergence cannot clear — the revision is gone |
| restored, not yet re-verified | pending | `True`, reason `VerificationPending` | unaffected | unaffected; no new revisions | re-verification completes |
| restored and verified | all match | absent | unaffected | unaffected | — |

Abnormal-true, so it is **dropped** when it stops applying rather than set `False` — its absence is the signal (A13). `phase` is unchanged by it alone; only the divergence row moves phase, via `Degraded`. The CLI treats it as a warning and **not** terminal for `deploy`, because a healthy fleet with a missing guard is still serving; design 10 alerts on it as a ticket, and on `RevisionMaterialChanged` as a page.

**"The exposure is prospective" was false (A28).** The spike measured that removing the Binding makes `data` updates immediately admissible, and the finalizer stops a *delete*, not a write. So: Binding gone, an editor who is legitimately allowed to edit the ConfigMap changes a prompt, and a node drain or Pod deletion replaces an R1 Pod — all before the operator processes the source watch. The replacement Pod serves changed content under R1's gated hash, and the divergence check sets weight 0 **after requests have been served**. Detection is a controller reaction racing an admission gap, and a reaction cannot be fail-closed against one.

- **Planned guard changes are overlap-only**: establish and verify the replacement Policy and Binding **before** removing the old ones, so no window exists in which no guard is installed. That is the only case the table's first row covers.
- **Unplanned guard loss cannot be handled by reacting, and "fall back to snapshots" was not a fix (A34).** The sentence that stood here made A23's snapshot fallback the thing that closes this race. It cannot be, because it is *reactive*: at the moment of loss no snapshot exists, no PodSpec references one, and once the editor has won, the original bytes are gone. A fallback triggered afterwards can only copy the attacker's new content or fail for want of the old. A remedy that runs after the loss cannot restore a pre-loss invariant.

  **The race is closed by A35, and not by anything reactive.** The user chose **immutable revision-scoped copies created before publication** (§3.3): the revision's PodSpec references material the editor never had a reference to, so guard loss, an authorised edit and a Pod replacement leave what that revision serves unchanged. The alternative considered and not taken was a separately protected Pod admission control; it was rejected on two counts — a `ValidatingAdmissionPolicy` cannot read another object from CEL, so it needs a webhook on the Pod-creation path with a `failurePolicy: Fail` blast radius, and it very likely does not cover an **in-place container restart**, which re-resolves `envFrom` without creating a Pod object and so never reaches admission at all.

  What remains true is narrower and is not a bypass: while the guard is absent, an editor can change the **original** object freely. That mints a candidate and passes a gate, which is the designed path.
- **Not claimed until measured**: the seal is not described as fail-closed against unplanned guard loss until the Binding-removal + edit + Pod-replacement sequence runs with a kubelet. Envtest has none; `make conformance-cluster` is where it belongs.

**The residual, stated because it is the honest part.** Detection rides the source watch, so a change that is applied and reverted between watch events is not observed, and a running Pod that already read the changed value keeps it. The seal is what makes that window small; it is not zero, and no arrangement of conditions makes it zero while the guard is absent.

**Vocabulary.** `EnvSourceProtectionUnavailable` was named by A23 and never added to §3.1's closed list — caught here by the count, which is what that list is for; both it and `RevisionMaterialChanged` are abnormal-true. **No count is restated here (A34).** The number written in this sentence was 29 while the list above held 30, and a prose count that drifts from the list is worse than none: it reads as a check and is a second place to be wrong. §3.1's list is the count, and §11's closure test is what should enforce it — which, as the amendment on `schema_contract_test.go` records, it does not yet do.

Four conditions enter the list in this round: `RevisionRecordUnreadable` (design 03 A28 — a revision's persisted record fails its integrity check, so it is not recompiled and what is serving keeps serving), `PolicyInputDrifted` (A29 — a non-spec producer's tightening is withheld, naming the producer and the input), `CapabilityUnavailable` (A33 — this Agent requested a binding from a producer that is not installed) and `LLMFallbackUnavailable` (A34 — the pre-provisioned fallback Backend is not converged, so an activation did not happen). All four are abnormal-true.

**Measured** (k3d, ConfigMap finalizers):

| Check | Result |
|---|---|
| 20 concurrent **naive** appends | **1 of 20 survived** — the obvious implementation silently drops holds |
| 20 concurrent `resourceVersion` CAS adds with retry | **20 of 20** |
| 19 concurrent releases while one holder remains | the remaining holder survived; each writer removed only its own entry |
| `delete` while one holder remains | blocked — `deletionTimestamp` set, object retained |

So the refcount is sound *with* CAS and unsound without, which makes the retry loop a contract rather than an implementation detail. The lossy variant is the one an implementer reaches for first, so it is named here and belongs in the mutation battery.

**Still unmeasured**: orphan reclamation after an operator crash, and the divergence→weight-0 transition. Codex's condition stands, but its remedy does not: showing the lease race-free is necessary and **not sufficient**, because unplanned guard loss defeats the seal whether or not the refcount is correct (A34).

A27 (2026-08-28, from `reviews/03-codex-review-r4.md` MAJOR 4, 12, 17, 20) — **four corrections to the seal and the image contract, three of which narrow a privilege I had granted.**

**The operator exception was wider than the seal needs (MAJOR 4).** The admission policy exempted the operator from `data` mutation as well as from protection-metadata maintenance — and the spike measured it: as the operator, a `data` patch on a sealed ConfigMap was **ALLOWED**. That is a privileged path to change a retained revision's behaviour under its old hash, which is the bypass the seal exists to close, granted to the one principal nobody audits. The exception now covers **only** label and finalizer transitions; `data`/`binaryData` are immutable while any lease exists, **for everyone including the operator**. A legitimate behavioural change is a new object and an Agent reference change, which mints a revision as it should. The operator data patch and the label/finalizer maintenance are mutation-tested separately, because one passing does not imply the other is denied.

**The digest in status was a guessing oracle (MAJOR 20).** `status` is readable by anyone with `get` on Agents — a far wider set than those who can read the Secret. A raw `sha256` of a low-entropy value (a feature flag, a username, a short token) is reversed offline in seconds. The published digest is now `HMAC(cluster-key, content)` with the key in an operator-only Secret: equality still works, guessing does not, and key rotation is a re-derivation pass rather than a migration.

**Recursion is guarded rather than assumed away (MAJOR 12).** A16 made "`AgentSpec` must not gain a self-recursive type" a *precondition*, which is not a guard — nothing enforces it and the failure mode is a hang, which AGENTS.md rule 3 classifies as INVALID rather than killed. §3.3 now requires a `(type, path)` stack that fails naming the offending field, and requires a perturbed variant to be API-valid so an unrelated schema rejection is never misreported as a killed classification mutation.

A28 (2026-08-28, from `reviews/03-codex-review-r5.md` BLOCKER 4, 5, 7) — **three places where a mechanism asserted a property it did not have.**

**The lease name required the hash the lease exists to make safe.** `plume.dev/src.<agent-uid8>.<revision8>` could not be written, because A26 says *seal first, then read* and A20 makes the sealed content part of the digest — so `revision8` did not exist at the moment the finalizer had to be added. That is the **circular identity defect this project's history already records**, reintroduced inside the mechanism built to stop content moving underneath a hash, and an implementer resolving it by hashing first reopens exactly the race the seal closes. The lease is now named for a durable random `leaseUID` recorded before the source is touched, associated with the revision hash afterwards; a crash leaves an unassociated lease the startup sweep reclaims, never a source sealed under an unresolvable name.

**"The exposure is prospective" was false** — see §3.3's guard-loss table. A finalizer stops a delete, not a write, so Binding-gone plus a legitimate editor plus a node drain serves changed content under a gated hash *before* the watch fires. Planned guard changes are overlap-only; **unplanned loss is an open race with no chosen remedy (A34)**, and the snapshot fallback this paragraph once named cannot be one, because it would run after the bytes it needed were already overwritten.

**Sigstore's presence is not enforcement.** policy-controller enforces per namespace, only where the namespace opts in and a matching `ClusterImagePolicy` is in enforce mode — so a healthy controller proves nothing about the namespace an Agent's workload runs in. Design 07 A3 now verifies the **effective enforcement contract** element by element, and requires the integration test to reject an unsigned image **in the namespace an Agent actually uses**; testing it elsewhere would pass while the gap was live.

A29 (2026-08-29, from `reviews/03-codex-review-r5.md` MAJOR 5, 6, 7) — **three ways the seal's own bookkeeping could unseal a live source.**

**A truncated lease identity can collide, and Kubernetes treats finalizers as a set.** `src.<agent-uid8>.<revision8>` gave 64 bits across two truncated halves; two holders that collide share one string, so the first release removes the second's hold and unseals a source a live revision still references — silently, and in the direction of the bypass. The lease is a full-width `leaseUID`, and a UID already present that this Agent did not record is a **collision refused and reported**, never coalesced.

**The orphan sweep could reclaim a lease mid-acquisition.** Sweeping entries whose *revision* does not exist raced the acquire order, which deliberately seals **before** the revision is minted — so a leader change in that window classified a valid in-flight hold as an orphan. The sweep now keys on the durable acquisition record in Agent status, not on revision existence, and runs **before** the reconcilers so it cannot observe a half-written acquisition.

**HMAC rotation was described as one atomic pass over a fleet that cannot be written atomically.** Rotating before every digest is rewritten makes unchanged sources fail comparison and go to weight 0; rotating after leaves new digests unverifiable. Each digest now records its **key ID**, verification accepts any retained key, new digests are written before old keys retire, and a **missing key is `VerificationKeyMissing` — unverifiable, not divergent**, because treating "cannot verify" as "has changed" would take a healthy fleet down over a lost Secret.

- **A35 (2026-08-31, decided by the user) — a revision reads its own immutable copy; A23's seal is superseded.** Closes Codex r6 BLOCKER 1. - **A34 (2026-08-29) — the snapshot fallback is deleted, and the guard-loss race is recorded as OPEN.** Codex r6 BLOCKER 1. A28 correctly proved that Binding removal plus an authorised source edit plus Pod replacement serves changed material before any watch reaction, and then named A23's snapshot fallback as the closure. It cannot be: the fallback is **reactive**, and at the moment of loss no snapshot exists, no PodSpec references one, and the original bytes are already gone — so anything triggered afterwards copies the attacker's content or fails for want of the old. A remedy that runs after the loss cannot restore a pre-loss invariant, and calling it the closure made a bypass look handled. Every sentence naming snapshots as the fallback is corrected. The two candidate pre-loss invariants — immutable revision-scoped material created before publication, or a separately protected Pod admission control — are tabled with their costs; **neither is chosen, and the design no longer claims the seal is fail-closed against unplanned guard loss.** The guard-loss condition table also gains the two limits on its own predicate: a match is point-in-time and races an edit plus a kubelet restart, and under a retired key it is not false but unknowable.
