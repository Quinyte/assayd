## 1. Purpose & scope

The Agent CRD is the platform's front door: one object that turns "a container that speaks A2A" into a governed, discoverable, eval-gated workload. The agent-operator reconciles it into workload, identity, directory entry, gateway routes/policy, and rollout gating.

**In scope**: CRD schema, reconcile behaviour, the revision/rollout state machine, registration, identity wiring, external agents, **finalization**.
**Out of scope**: policy compilation internals (design 03), receipt tap (04), eval execution (16 — only the *holding mechanism* here), KG binding validation details (01/13).

## 2. Doctrine & charter gates

- **Plane**: slow (engine) — one of the three core operators.
- **Pods added**: the agent-operator itself (the single plume-code pod in the §17 budget). Workload pods are user workloads.
- **Stateful deps**: none. Operator state = CR status + JetStream KV (directory). One additional **read-only** reconcile input: design 04's per-agent daily spend aggregate (the exact-tier budget backstop) — that state lives in design 04's audit index, not here.
- **Primitives**: Agent (A2A), Tool (MCP), Resource (CRD), Artifact (OCI images). ✓

`kubectl get agents` printer columns: `PHASE · ACTIVE · CANDIDATE · EVAL(last score) · COST/DAY · AGE` (A14), sourced from `status.phase`, `status.activeRevision`, `status.eval.score`, `status.budget.usdSpentToday` and the creation timestamp. The set is a contract, pinned by `TestPrinterColumnsMatchTheDesign`: the case for a status carrying this many conditions rests on these five answering the common questions, and `EVAL`/`COST/DAY` are precisely the two a developer could otherwise reach only by reading conditions.

**Tool and graph names resolve in the agent's own namespace, and only there.** A tool name may be served by a Connector tool facet or by an `MCPServer` CR; the two share one namespace-unique name space, enforced at admission (design 11 §4), which is why the binding carries no kind discriminator. There is deliberately no `namespace` field on either binding: design 24 §4.1 derives the `can_call` tuple **from** the binding, so a cross-namespace reference would authorize itself — anyone able to create an Agent in one namespace could reach a tool in another. Cross-namespace use requires consent published by the target namespace (the `ReferenceGrant` shape) and is out of scope until a design specifies it.

### 3.2 Workload materialization

**A20, A35 and A42 ARE IMPLEMENTED (A54, A55, A61).** The operator resolves every referenced `ConfigMap` and `Secret` before computing an identity, and a digest of their contents is part of the projection. So an editor changing a referenced ConfigMap from a safe system prompt to an injected one now **mints a candidate**, which is gated before it can be promoted — where before the identity did not move at all and the change was invisible.

   A revision identity can no longer be produced from a spec alone: `Hash` and `Digest` take the resolved sources and **refuse** without them. Three refusals, each closing a way the guarantee could have had a hole:

   | Case | Behaviour |
   |---|---|
   | A referenced source does not exist, or the operator may not read it | `EnvSourceUnresolved`, **no revision and no workload**. A missing referent is *unresolved*, never a zero digest — a zero would let deleting an object mint the same hash as never having referenced it |
   | An env source arm this operator does not recognise | the same refusal. Hashing only the arms it happens to know is a guarantee with a hole nothing reports, and `corev1` gains arms between releases. `fileKeyRef` is the case today: it reads from a volume this API renders none of |
   | Content resolved | folded into the projection in a fixed sorted order, length-prefixed, with `data` and `binaryData` tagged separately so the same key in each cannot collide |

   **A35 is implemented too (A55).** At mint, before publication, every referenced source is copied to `<agent>-<revision>-env-<n>` — immutable, kind-preserving, created from the buffer the digest was computed over rather than from a second read — and the workload references the copy. Editing the user's object therefore mints a candidate *and* leaves the published revision's material untouched, which is what closes the Pod-replacement window A20 alone left open.

   Provenance is a **label plus an annotation**, not an `ownerReference`, so A42's namespace move does not change the invariant. Two Kubernetes limits shaped the split, and both were hit rather than anticipated: a label VALUE is capped at 63 bytes and a SHA-256 is 64, and a source name may be 253 — so labels carry only what the GC sweep selects on (the Agent UID and the 10-character revision name) and annotations carry the full digest and the source reference, which are what get verified.

   **A42 closes the last half (A61).** Copies and workloads live in the operator-owned run namespace, where a principal with `create`/`delete` on ConfigMaps in the Agent's namespace has no rights at all; `TestANamespaceEditorCannotReplaceTheRevisionsCopy` proves it on a real cluster with real RBAC, with the same principal's own-namespace delete as the control. `EnvSourceProtectionUnavailable` is **no longer raised**; the type stays in §3.1's vocabulary so an operator built after A42 clears a stale one left by an operator built before.

 **They ship in an order, and each step shrinks the bypass (A46).** An earlier sentence here called the three "one implementation" and said partial delivery "closes nothing". That is false in two of the three directions, and it turned a sequence into a stall — A42 is the step blocked on unwritten amendments in designs 03, 06, 07 and 26, and bundling the other two behind it keeps a live bypass live for however long that takes.

| Step | What it closes | Residual |
|---|---|---|
| **A20** — hash resolved content | a source edit now mints a candidate and is gated before promotion; today the edit is *invisible* | a retained workload still resolves by name, so Pod replacement can still serve changed bytes |
| **A35** — the revision reads its own copy | an ordinary `kubectl edit` on the source no longer changes what a published revision serves | a namespace editor can still delete and recreate the copy — narrower and noisier than an edit |
| **A42** — run namespace | the delete-and-recreate path; the editor has no rights where the material lives | **none of the three**: implemented (A61) after the design 03, 07 and 26 amendments and A60 |

A42 without A35 is genuinely impossible — a Pod cannot reference a ConfigMap in another namespace, which is A42's own premise. The other two are independently deliverable and each is strictly better than what shipped before them. All three are implemented; the cluster test A42 owed is in `test/e2e`.

**Revision workloads and their material live in an operator-owned namespace (A42).** The Agent CR stays where the user created it; the Deployment, the Pods and A35's revision copies are created in **`plume-run-<agent-namespace>`**, one run namespace per Agent namespace so the tenancy boundary is preserved rather than pooled.

This is what makes A35 an invariant rather than a guard, and the reason it needs a whole namespace is a Kubernetes fact, not a preference: **a ConfigMap or Secret can only be used by Pods in its own namespace.** So material can only be out of an editor's reach if the *Pod* is too. Without the move, a namespace editor holding ordinary `create`/`delete` on ConfigMaps deletes `agent-H-env-0` and recreates it with the same name and different content — `immutable: true` forbids an update and permits exactly that, the same distinction that refuted A20 — and a node drain then serves the new bytes under H's gate result. `ownerReference` does not help: it does not protect deletion.

What the user keeps in their own namespace is the thing they are supposed to edit: the Agent CR, and the ConfigMaps and Secrets it references. Editing those still works and still means what it meant — it mints a candidate and passes a gate. What they lose is the ability to reach the material a *gated, serving* revision is already reading.

| Consequence | Rule |
|---|---|
| **Naming** | `plume-run-<agent-namespace>`, **truncated and hashed** by design 03 §3.2's rule when it would exceed 63 characters: a namespace name is a DNS label, `plume-run-` is ten characters, and an Agent namespace may legally be up to 63 — so the naive form is unconstructable for any source namespace over 53. Naive truncation is **forbidden**: it is non-injective and would pool two tenants' material in one run namespace, which is the exact property this scheme exists to avoid. §8 owes a max-length fixture |
| **Provenance — NOT `ownerReference` (A44)** | A cross-namespace `ownerReference` is disallowed: the reference is *treated as absent* and the API server emits `OwnerRefInvalidNamespace`. So no run-namespace object carries one, and **every rule that tested a copy's owner UID is rewritten against a label**: the operator stamps `plume.dev/agent-uid` and `plume.dev/revision-digest` at creation, both covered by the `RevisionRecord`'s digest, and the record is the *only* provenance. This matters more than it reads — A35's ownership row, A41's missing-copy check, A39's `AlreadyExists` invariant and A38's rollback test all read "owner UID", and under A42 that predicate is unsatisfiable. An implementer running them as written gets `RevisionMaterialUnavailable` on every revision; one who drops the clause has adoption-by-name, which is the hole A39 exists to close |
| **Garbage collection** | Without an ownerReference nothing is GC'd automatically, so cleanup is **finalizer-driven**: §3.7's ordered teardown gains a run-namespace deletion step *before* the finalizer is released, and a **label-based sweep runs on every reconcile**, not only at startup. Copies are labelled *before* the record is written, so a crash between A39's step 4 (Create) and step 6 (publish) leaves sweepable objects rather than unreferenced Secret material that no record names and no sweep looks for. The run namespace is deleted when its last Agent is |
| **The namespace is created, never adopted (A44), and the proof is a nonce before binding and the namespace UID after it (A60)** | The operator creates the run namespace with `plume.dev/owned-by: <install-uid>` and **refuses to use one it did not create**. A principal holding cluster-scoped `create` on Namespaces could otherwise pre-create `plume-run-team-a` with a RoleBinding granting itself `admin` and wait for the operator to write Secret copies into it — defeating the entire security claim before the first Agent exists. A stale run namespace surviving its source namespace's deletion and recreation is refused for the same reason: its RoleBindings were built for a different tenant's subjects. **The label is not the proof** — Codex r8 BLOCKER 7: Kubernetes records no "created by", a label needs only `update` to forge, and after a restart the operator cannot tell its namespace from a pre-created one wearing the same label. The proof is the **binding record** below: a 128-bit nonce written into the operator's own namespace *before* the run namespace exists and stamped on it at creation, which a pre-creator cannot know; and, once bound, the namespace's own UID, which a recreator cannot reproduce. The nonce is read once; the UID is compared on every reconcile, against a live read |
| **Workload provenance moves off the `ownerReference` too (A60)** | The Deployment is in the run namespace and the Agent is not, so the controller reference `ownedWorkloads` decided ownership by is *treated as absent* exactly as A44 said for copies. Ownership of a workload is now: the **name** `<agent>-<revision>`, the `plume.dev/agent-uid` label, and a `plume.dev/revision-digest` annotation that `status` vouches for. The name is the **deletion-safety** authority — immutable after creation, so a victim object cannot be renamed into the shape (A57) — and not a proof of creation: every element of the tuple is public and predictable, so a principal with `create` in the run namespace could pre-create the expected object. That principal does not exist by construction — nothing but the operator has write access to a run namespace, and the admission policy row below is what makes the labels that scope that claim the operator's — and **`AlreadyExists` is never provenance**: an existing object must equal the desired one in full, or it is a collision and nothing is mutated. The operator's Deployment watch maps by the `plume.dev/agent-namespace` and `plume.dev/agent` labels rather than by owner, and **nothing collects a workload but the finalizer** — "workloads go with the ownerReference" is no longer true anywhere in this design |
| **Read access (A60, corrected)** | Users cannot `kubectl logs` across a namespace they have no rights in. An earlier version of this row had the operator derive "every subject that can read Agents in the source namespace" by watching RoleBindings and mirror a read-only RoleBinding. **That is not implementable**: Kubernetes answers "may this subject do this?" and never "who may do this?" — access arrives through Roles, ClusterRoles, aggregation, ClusterRoleBindings, groups, impersonation and external authorizers, so any derived list is incomplete in one direction and stale in the other. **The supported path is `plume logs`** (design 08): it performs a `SubjectAccessReview` for the calling identity against `get` on that Agent and streams the run-namespace Pod's logs under the operator's credentials. Direct `kubectl logs` in a run namespace is **not supported**, and nothing grants it. The operator's RBAC therefore needs `pods/log` `get` for itself, not for anyone else |
| **Quota, limits and Pod Security (A44, decided by A60)** | A namespace boundary carries three things a moved Pod does not inherit: **ResourceQuota**, **LimitRange**, and the **Pod Security admission labels**. A tenant admin who sets `pod-security.kubernetes.io/enforce: restricted` and a CPU quota on their namespace would otherwise find Agent Pods — running arbitrary user images — scheduled under neither, so anyone who can create an Agent escapes their own quota and admission level. The operator **mirrors all six Pod Security labels** (`enforce`, `audit`, `warn`, and their `-version` variants) from the source namespace onto the run namespace at creation and on every reconcile, removing any the source no longer carries. Changing a namespace's labels does not re-evaluate running Pods — Kubernetes only warns — so a tightened level takes effect on the next Pod, and this design says so rather than implying eviction. **ResourceQuota and LimitRange are mirrored too (A60)**: every `ResourceQuota` and `LimitRange` in the source namespace is copied, spec for spec, to `plume-mirror-<name>` in the run namespace, reconciled on change and deleted when the source is. The cost is stated: a quota is accounted per namespace, so a tenant's ceiling now applies to each namespace separately and the pair can reach **2×** the stated limit. The alternative — no quota in the run namespace — lets an Agent escape its tenant's ceiling entirely, and Kubernetes offers no third option short of a custom admission webhook. The two are mirrored together because a quota that constrains CPU rejects any Pod without a CPU request, and the LimitRange is what supplies the default. **Mirroring is not implemented until the sentence in §3.2's implementation note says it is** |
| **Identity** | The `ClusterSPIFFEID` template is **design 02 §3.5's**, not design 06's, and it read `.PodMeta.Namespace` — so the move would have re-issued every agent's SVID under a new identity and broken every grant design 24 keys on it. Fixed by A59: the path segment comes from a `plume.dev/agent-namespace` label carrying the Agent's own namespace, so the move is invisible to authorization. **Design 07 A5** records the template and selectors the chart renders, and the trust boundary that makes a label-derived identity sound |
| **Tenancy** | Design 26's hard mode splits workload teardown into the vCluster and route teardown host-side. **Design 26 A1** decides: in soft mode the run namespace is a host namespace owned by this operator, exactly as here; in hard mode the tenant's own agent-operator creates it *inside* the vCluster, and the host-side objects land in the vCluster's sync namespace, which the tenant-operator labels as a run namespace so the Gateway admits its routes |
| **Network policy** | §6 already requires a default-deny NetworkPolicy with egress to the gateway only — the ADR-0014 control A16 calls load-bearing — and it follows the Pods to the run namespace. **The chart ships no NetworkPolicy at all today**, so that control is currently decorative in either namespace; that is a pre-existing gap, named here rather than discovered later. **Design 07 A5** decides that the chart cannot render it — run namespaces are created at reconcile time, and a chart renders at install time — so the **operator** materializes it into each run namespace from a shape the chart's values supply, and only when `gateway.enabled` is true, because "egress to the gateway only" on a cluster with no gateway is "no egress", which would break every P1 Agent silently. **At P1 no NetworkPolicy is applied anywhere**; `GovernanceSkipped` says so on every Agent today, and the `NOTES.txt` design 07 A1 owes is to say so at install |
| **Service and route (A45)** | Both move **with** the workload. This is not a preference: a `backendRef` to a Service in another namespace requires a `ReferenceGrant` in the target namespace, and without one the route reports `Accepted=True` with **`ResolvedRefs=False, reason: RefNotPermitted`** — while design 03's convergence tuple requires `ResolvedRefs=True` before `Publishing`. Not a params object: a params ConfigMap that went missing would have turned the policy into a cluster-wide denial of every namespace write. A second policy admits an `HTTPRoute` whose `parentRefs` name the plume Gateway only from the operator's identity, so an admitted namespace is not a route-authoring grant. **The operator fail-closes on their absence, by name**: at startup it logs, and on every reconcile it checks, that both policies and their bindings exist, and refuses to create a run namespace with `RunNamespaceUnavailable=LabelAuthorityAbsent` if they do not — a label nobody reserves must not be treated as evidence. Presence is what is checked; the content is the chart's, and a policy of the right name that validated nothing would pass the check. The condition clears when the policies appear. `ValidatingAdmissionPolicy` is GA from Kubernetes 1.30, the chart's floor |
| **What did NOT move** | The Agent CR, and the user's own ConfigMaps and Secrets — the things they are meant to edit |

A41's detection stays, now testing the **label**, not an owner reference. An operator bug or a cluster-admin can still remove a copy, and a missing one must send the route to weight 0 rather than start a Pod without it — which is also why A41 rewrites copies as **non-optional**: Kubernetes starts a Pod with a *missing optional* reference silently, and fails to start on a missing required one. Failing to start is the observable this design wants.

**The binding record: how the operator proves it created a run namespace (A60).** Codex r8 BLOCKER 7 and MAJOR 3 are the same gap seen twice: A44 said "created, never adopted" and gave the operator nothing durable to check that with, and said "deleted when its last Agent is" with no protocol for two Agents deciding that at once. Both are answered by one record.

For every source namespace `S` the operator keeps a **binding**: a `ConfigMap` named `plume-run-binding-<run-namespace>` in the **operator's own namespace** (`plume-system` by default). The operator is to learn that namespace from a `--operator-namespace` flag, defaulting to the ServiceAccount namespace file every Pod mounts, and refuse to start with neither; the flag does not exist yet. A ConfigMap rather than a new CRD because the record is operator-private bookkeeping, never something a user reads or writes, and a kind nobody else may touch needs no schema of its own. It carries:

| Field | Meaning |
|---|---|
| `sourceNamespace`, `sourceNamespaceUID` | the tenant namespace this run namespace serves, by name **and** UID, so a deleted-and-recreated tenant is a different tenant |
| `runNamespace`, `runNamespaceUID` | the run namespace, and the UID it had when the operator created it — **compared on every reconcile**, see below |
| `nonce` | 128 bits from `crypto/rand`, generated before the namespace exists and stamped on it at creation as the **annotation** `plume.dev/binding-nonce` (an annotation, not a label: nothing selects on it) |
| `state` | `Creating` · `Bound` · `Terminating` · `Deleting` — exactly these, decoded strictly |
| `schemaVersion` | `1`. The record decides namespace deletion and credential placement, so it is not a loose bag of strings: a missing field, an unknown state, or a version this operator does not carry is **`RunNamespaceUnavailable=BindingRecordInvalid`**, terminal, naming the field, and the human procedure below is the recovery. Nothing defaults |

**Two proofs for two attacks, because neither covers the other.** The **nonce** defeats *pre-creation*: the attacker moves first, and cannot stamp a value that does not exist yet. It defeats nothing after that — once stamped, the nonce is readable by any principal with `get` on Namespaces, which is among the commonest grants a cluster hands out. The **UID** defeats *delete-and-recreate*: the attacker moves second, and a recreated namespace has a UID the API server chose, which nobody can reproduce. So the nonce is consulted only while the binding is `Creating`, and from `Bound` onward every reconcile compares the live namespace's `metadata.uid` to `runNamespaceUID`; the nonce is never read again.

The gap between the two is the time from the namespace `Create` returning to the binding recording its UID — one API write in the normal case, and **the whole outage** if the operator crashes between them, which design 07 A4's own rolling update makes routine. Inside that gap a recreator who read the nonce could present a namespace that passes the nonce check, and no point-in-time inspection of its contents proves who made it: an "empty now" check does not freeze later writes, and the cross-family review showed the RoleBinding simply arrives after the check. So the rule is **a namespace is bound only by the reconcile that received its `Create` response**, from that response's UID. A successor that finds the binding `Creating` and a namespace present — nonce matching or not — **never binds it**: if the nonce matches it deletes the namespace it evidently created and did not record, rotates the nonce, and retries; if the nonce does not match it refuses. The cost is one namespace churn per crash inside a one-write window; what it buys is that no namespace is ever adopted on the strength of being observed.

The record, the run namespace and the source namespace are all read **live** through the API reader, never from the informer cache: a recreated namespace's old object sits in the cache between the API server's recreate and the next watch delivery, and a UID compared against a stale object is no proof at all. The protocol needs no cluster-wide lock. It does need **one process-local mutex per run namespace**, held across the checks by every writer of a binding — the Agent reconcile, the finalizer, the Namespace-keyed reconciler — because a peer mid-row-6 (namespace created, UID not yet recorded) is indistinguishable from a crashed predecessor by any observation the protocol makes, and row 7 would delete its namespace. Leader election guarantees one operator process, so the process-local mutex is what makes more than one reconcile worker safe; the Terminating/Deleting fence never needed it.

**The checks run in this order, and the first that applies decides.** Precedence matters because the conditions overlap: a colliding tenant's binding is also `Bound` with a matching UID, and reading state first would pool two tenants.

Otherwise **`RunNamespaceUnavailable=NotCreatedByOperator`, terminal.** A binding is always written before its namespace, so a namespace with no binding is one this operator did not make. Nothing is written into it. The message names the namespace and spells out the re-bind record field by field |
| 2 | no binding, no run namespace | creates the binding in `Creating` with a fresh nonce. `AlreadyExists` on that create means another reconcile of `S` won; re-read and continue from **3** with **its** nonce — the nonce is always read from the binding, never from memory, so the loser stamps the winner's value, and a colliding tenant still meets row 3 |
| 3 | binding's `sourceNamespace` ≠ `S` | `RunNamespaceUnavailable=NameCollision`, terminal for the *second* tenant: two source names truncate-and-hash to one run name. Nothing is deleted — the first tenant's material is live |
| 4 | binding's `sourceNamespaceUID` ≠ the current namespace `S`'s UID | the tenant was deleted and recreated; the old run namespace is a different tenant's. From **`Bound`**: compare-and-swap to `Terminating` and run the handler. From **`Creating`**: nothing was ever bound, so there is nothing to terminate — and a `Terminating` record without a UID is one the strict decoder refuses; the crash-gap namespace, if one carries this nonce, is deleted (row 7's authority) and the record is discarded, so the next pass meets row 1's wait or row 2. From `Terminating`/`Deleting`: the handler is already on its way. The Agent waits with `RunNamespaceUnavailable=Terminating`. Both of the handler's lists are scoped by the binding's source UID, so neither the Agent that triggered this row nor the dead tenant's leftover workloads count against the deletion — leftovers exist here by construction, since this row is reachable only when the old tenant's finalizers never ran, and they go with the namespace |
| 5 | `Terminating` or `Deleting` | the handler below runs, whoever is reconciling |
| 6 | `Creating`, namespace absent | creates it with the binding's nonce as the annotation `plume.dev/binding-nonce`, the labels `plume.dev/run-namespace: "true"`, `plume.dev/pods-by: agent-operator` (design 07 A5.2 — the SPIFFE selector's label, distinct from the listener's), `plume.dev/agent-namespace: <S>`, `plume.dev/owned-by: <install-uid>` and the mirrored Pod Security labels; then, **in the same reconcile, from the `Create` response's UID**: mirrors ResourceQuota and LimitRange, records the UID, moves to `Bound`. The mirrors come before `Bound` so the first Pod cannot precede its quota. `AlreadyExists` means someone else holds the name; row 7 or 8 decides on the next pass |
| 7 | `Creating`, namespace present, **deletion timestamp set** | wait (`Terminating`), whatever nonce it carries: row 7's own delete from the previous pass, or someone else's. Refusing here wedged the operator's own recovery terminally, because the pass after the delete met its own Terminating namespace with a rotated nonce |
| 7 | `Creating`, namespace present, nonce matches | **not bound.** This is the crash gap: a namespace this operator created and did not record, or a copy of it. Delete it (name shape and nonce verified), rotate the nonce, requeue; the next pass waits on the deletion and row 6 follows |
| 8 | `Creating`, namespace present, nonce absent or different | `RunNamespaceUnavailable=NotCreatedByOperator`, terminal — pre-creation |
| 9 | `Bound`, namespace absent | someone with cluster rights deleted it, and every copy and workload went with it. There is nothing to adopt: the binding returns to `Creating` with a new nonce and the namespace is recreated. Material is re-minted from the current sources **if they still hash to the desired digest**; a retained revision whose sources have drifted since it was gated cannot be reproduced, and A41 sends it to weight 0 with `RevisionMaterialUnavailable` — a cluster-rights deletion of a run namespace is recorded as the material loss it can be |
| 10 | `Bound`, namespace present, **deletion timestamp set** | someone else is deleting it. Compare-and-swap to `Terminating` and run the handler, which waits for it to be gone, deletes the binding, and the next pass takes row 2's path. Every create into it would fail 403 with cause `NamespaceTerminating` |
| 11 | `Bound`, namespace present, **UID differs** | `RunNamespaceUnavailable=NotCreatedByOperator`, terminal — deleted and recreated by someone with cluster rights, whatever the nonce says |
| 12 | `Bound`, namespace present, UID matches | reconciles labels and mirrors; proceeds |

**The `Terminating` and `Deleting` handler is idempotent and has one owner: whoever reads the state.** It runs from any Agent reconcile in `S` that reaches row 4, 5 or 10; from a **Namespace-keyed reconciler** the operator registers for namespaces carrying `plume.dev/pods-by: agent-operator` and the `plume-run-` name shape (not `plume.dev/run-namespace`, which a vCluster's host sync namespace also carries — design 26 A1), which exists precisely so the handler runs when `S` holds no Agent at all; and from the finalizer's last step. A crash anywhere in it re-enters the same code:

0. The handler acts only on a binding in `Terminating` or `Deleting`. In any other state it returns: rows 6 and 9 own an absent namespace under `Creating` and `Bound`, and a handler that deleted the binding there would race row 9's rebuild into row 1's terminal refusal with no attacker and no crash.
1. Run namespace **absent, or present with a UID other than the binding's** → delete the binding. The namespace this binding named no longer exists; whatever holds the name now is foreign, and the next reconcile meets row 2 or row 1. This is the first check in every pass, before any list and before any flip back to `Bound`: a handler that restored `Bound` on a live Agent's say-so without comparing the UID would walk row 12 into a namespace somebody recreated between the delete completing and the handler observing it.
2. Run namespace present with a **deletion timestamp** → requeue. Creates into it fail 403 with cause `NamespaceTerminating`, and the operator treats that cause as "wait", never as an error to retry against.
3. State `Terminating`: **live-list** the Agents in `S` through the uncached API reader, counting only if `S`'s current UID equals the binding's `sourceNamespaceUID` (a recreated tenant's list is empty by definition), excluding any with a deletion timestamp; and **list the workloads and copies in the run namespace** whose `plume.dev/agent-uid` belongs to one of *those* Agents — an Agent that exists in `S` under the binding's source UID — other than the one reconciling. Objects whose UID matches no such Agent are orphans and go with the namespace; counting them would let one bypassed finalizer hold a namespace open forever, and would make row 4 flap between `Terminating` and `Bound` on the dead tenant's leftovers. If either list is **non-empty** → compare-and-swap back to `Bound` and proceed as row 12: someone arrived, or someone is still draining, and the namespace stays. A failed swap means the binding moved — re-read and re-enter.
4. Both **empty** → compare-and-swap `Terminating` → **`Deleting`**. Nothing flips back from `Deleting`; a creator that reads it waits. A failed swap means the binding moved — re-read and re-enter.
5. State `Deleting`: delete the run namespace after checking its name has the `plume-run-` shape **and** its UID matches the binding. A UID that does not match means the namespace this binding named is already gone and something else holds the name: delete the binding, and the next pass meets row 1. The delete is idempotent; then step 2 applies until step 1 does.

Two states rather than one because the delete must be fenced against a flip-back: with only `Terminating`, a creator could read it, list, find itself, flip to `Bound` and write material in the instant between another worker's empty list and its delete. The second swap is what the delete waits on. An **external** Agent (`spec.external`) never uses the run namespace and is not counted by either list. A create that fails with cause `NamespaceTerminating` anywhere after the checks — the namespace went Terminating between them and the write — is reported as `RunNamespaceUnavailable=Terminating` and requeued, never as a material error to retry against.

**Teardown, and the race MAJOR 3 named.** An Agent's finalizer deletes its own workloads and copies in the run namespace, then asks whether it was the last:

1. **Live-list** Agents in `S` as the handler's step 3 does, excluding this one, and list the workloads and copies in the run namespace that belong to those Agents. "Last" means **no other Agent is declared and no declared Agent's workload remains** — a deleting Agent is not a reason to keep the namespace, but its workload still draining under `taskTimeout` is, or "nothing is force-killed silently" would fail for any `kubectl delete -f dir/`.
2. If last: **compare-and-swap** the binding from `Bound` to `Terminating`. A failed swap because the binding is already `Terminating` or `Deleting` — another finalizer, or this one before a crash — is not an error: proceed to step 3.
3. Run the **handler**, and release the finalizer once the handler has issued the delete or found it issued, or has restored `Bound`. The finalizer does not wait for the namespace to be gone.

The order is what makes it correct: the binding changes state **before** the confirming list, and every reader sees the binding live. The window r8 described — B writes material while A deletes — needs B to have read `Bound` before A swapped and to be absent from A's second list, and an Agent that exists at the time of a live list is in it; a B that read `Terminating` instead is either in the next list or waiting on `Deleting`. A crash between steps 2 and 3 leaves `Terminating`, which the handler owns. No state is reachable in which the delete is issued without a list having run after the swap that fenced it.

**Losing the binding is recoverable by a human, and only by a human.** If `plume-run-binding-<name>` is lost from the operator's namespace — a restore, an admin mistake — every Agent in `S` goes `NotCreatedByOperator`, and the operator does not guess its way back: it never vouches for a namespace it cannot prove it created. The recovery is a human recreating the binding in `Bound` from the run namespace's own `metadata.uid` and the source namespace's UID (the nonce is not needed: `Bound` never reads it), then annotating each Agent in `S` to trigger a reconcile, because the binding is an uncached ConfigMap nothing watches — the same trigger `cmd/operator` documents for the EvalSuite cache. The human is vouching, and the condition message says exactly that. The harsh path is chosen on purpose.

**Mirror names.** `ResourceQuota` and `LimitRange` names are DNS subdomains, up to 253 characters; `plume-mirror-<name>` overflows for a source name over 240. Design 03 §3.2's truncate-and-hash rule applies, with the 16-hex suffix; the mirror carries the source name in an annotation so the reverse mapping does not depend on the name.

**What §8 owes for this block, by name (A60, from the critiques).** One envtest case per numbered row above and an exhaustive transition-matrix test over the four states; one per crash point with a paused reconciler — after the binding create, after the namespace create (the successor must delete, not bind), between teardown steps 2 and 3, between handler steps 4 and 5; and, on a real cluster, Codex r8's four (pre-creation with a self-granting RoleBinding, source namespace delete-and-recreate, operator restart mid-protocol, a **chosen** name collision) plus r8 MAJOR 3's paused delete racing a new Agent, plus the first critique's run-namespace delete-and-recreate with the nonce copied, plus a scoped attacker holding Namespace and RBAC `create` who cannot obtain a SPIFFE-selected or route-admitting namespace. **And the mutation ledger the tests must survive**, because a fixture that is wrong in two ways proves neither: each of these is deleted or negated independently and the named test must fail — the nonce comparison; the bind-only-from-the-Create-response rule; the `Bound` UID comparison; the handler's UID-first check; the source-UID scoping of both lists; the remaining-workload count; the `Terminating→Deleting` swap; the no-flip-from-`Deleting` rule; the strict record decode; and each clause of the label-reserving admission policy. Every fixture differs from a valid state in exactly one predicate; a mutation that does not compile is INVALID, never KILLED.

**A42 IS IMPLEMENTED (A61's implementation note).** What runs, in `internal/controller/runnamespace.go`: the name rule with its 16-hex truncation; the binding record as a strictly decoded ConfigMap in the operator's namespace with `schemaVersion`, nonce and UID; the twelve ordered checks above, including bind-only-from-the-`Create`-response and the row-7 delete-not-adopt; the `Terminating`/`Deleting` handler with its UID-first step, source-UID scoping of both lists and the remaining-workload count; the finalizer's teardown; the Namespace-keyed reconciler; Pod Security label mirroring; ResourceQuota and LimitRange mirroring; the label-authority fail-close; workload provenance by name and UID label with no `ownerReference`. Every row envtest can reach has a case in `test/envtest/runnamespace_test.go`, and the sixteen-entry mutation ledger in the A61 history entry was run — each predicate negated alone, compile-checked, all killed. The chart renders design 07 A5.9's two admission policies and the `plume-operators` params, and passes `--operator-namespace` from the downward API. On a real cluster (`make e2e`, k3d): the delete-and-recreate e2e with its own-namespace control, the admission policy refusing a `pods-by` label from a cluster-admin identity, and a `SubjectAccessReview` for every verb the run-namespace code calls. **Not implemented**: the read-access path (`plume logs` is design 08's), the NetworkPolicy (design 07 A5.4, with the gateway), the Sigstore opt-in stamp (A5.6), and the real-cluster cases that need a namespace controller to finish a deletion — operator restart mid-protocol, the paused delete racing a new Agent, the chosen name collision — which envtest cannot reach and the e2e does not yet cover.

- **Default: Deployment** — A2A servers are stateless HTTP; replicas scale; fits every SDK.
- **`runtime.sandbox` ⇒ agent-sandbox `Sandbox` (v1beta1)** — singleton, stable identity, persistent scratchpad; for agents that execute code or hold local state. `replicas>1` + `sandbox` is an admission error.
- **Sandbox runtime class absent** (local distros) ⇒ hardened Deployment (seccomp, non-root, read-only rootfs) + `SandboxDowngraded=True`. Never silent (NFR-8).
- **Scratchpad lifecycle**: the volume is **revision-independent** — reattached read-write to the promoted revision. A candidate under eval attaches it **read-only**, so a cold candidate cannot corrupt live state. This needs an access mode permitting concurrent attach (`ReadOnlyMany`/`ReadWriteMany`) or co-scheduling; where the storage class cannot provide it — notably `local-path` in the `local` profile, which is `ReadWriteOnce` and node-bound — the candidate runs **without** the scratchpad and `ScratchpadDegraded=True` names the reason. Eval consequence, stated: design 16 gates a **cold** candidate against a warm active; suites must not assume warm local state.
- **Task state with `replicas>1`** — detected, not assumed: the A2A card is the declaration point (a capability/extension asserting shared task state). Absent that assertion with `replicas>1`, the operator sets **`TaskStateUnverified=True`** with the consequence named, and the CLI warns at deploy. Admission may require the assertion for `expose: public`. Design 09's templates ship the JetStream-KV store **and emit the declaration**, so template-built agents never raise it.

### 3.3 Revisions & the holding mechanism (entailed by ADR-0006)

k8s rolling update mixes old/new traffic and would defeat eval gating, so the operator owns revisions:

**The revision NAME is forty bits; the revision IDENTITY is the whole digest (A37).** `revisionHash` truncates SHA-256 to ten hex characters, and an earlier justification defended that with the number of revisions that coexist — which answers an accidental-collision question nobody asked. The projection is **attacker-controlled**, so the question is a *chosen* collision, and forty bits costs about `2^20` trials: a colliding pair of specs, one referencing a safe image and one a malicious image, was found in **1.2 seconds** on a laptop.

The bypass is total. The safe member passes evaluation as revision H. The principal then writes the colliding malicious spec; the operator computes the same H, sees `activeRevision == desired`, skips candidate gating entirely, and converges the Deployment named H — including the block that exists to correct out-of-band drift — to the malicious image, while status still names the revision that passed its gate. Nothing in the flow ever compares more than forty bits.

So the name and the identity are separated. `status.activeRevisionDigest` and `status.candidateRevisionDigest` carry the **full** digest and are the only values compared to decide whether two specs are the same revision; the ten-character form stays for object names and the `ACTIVE` column, where a 64-character string is unreadable and a name is all that is needed. **`status` is the authority, and the annotation corroborates it (A47).** An earlier version of this rule made the annotation authoritative and said nothing about who may write it. That closed the collision against an `agents/update` principal and left it open to a **weaker** one: anyone with `deployments/patch` can set `plume.dev/revision-digest` to the digest of the spec they are about to write — a pure function of that spec, no secret needed — or simply delete it, which the adoption sentence blessed. Either way the *operator itself* installs the attacker's image on the gated revision, and unlike a raw image patch it survives drift correction. The guard was defeatable by the same principal the drift-correction rule exists to defeat.

So the check is: `status.activeRevisionDigest` (and the candidate's) is written only by the operator through the status subresource, under separate RBAC, and **a desired revision whose NAME matches a recorded one while its digest does not is a `RevisionHashCollision` before the workload is touched at all.** Terminal: no adoption, no rewrite. The annotation is a second, corroborating check for the one case status cannot cover — a stamped workload for which status holds no record, which happens when status and the cluster disagree about history. An **absent** annotation is **refused**, not adopted (A48). The adoption branch existed for a workload predating the field, and there is no such workload — plume is unreleased, so the migration had nothing to migrate and was purely an attack surface: stripping the stamp made the operator rewrite the pod template from whatever spec was current and stamp the result as legitimate. Legacy identity is never reconstructed from current spec.

Two further rules follow from the same principle, that the operator may only act on evidence it produced. **`AlreadyExists` on create is a race, not a success**: something took the name between the read and the write, and the name is derived from the Agent name and a public digest, so it is guessable by anyone holding `deployments/create`. The operator re-reads and applies the same invariant rather than accepting an object it never validated. And **availability alone does not authorize promotion** — it answers "is a workload available?", the question that matters is "is an available workload of *this revision*?", and a squatting object reports `AvailableReplicas` just as well. The digest stamp is checked before its status is believed.

The condition is **owned**, so it clears when the collision is resolved. It was in neither the owned nor the sticky set, which meant a repaired Agent reported `Ready=True` while still carrying a `True` collision condition with a stale message — the loud-and-wrong of rule 8, and what teaches an operator that a condition means nothing.

1. Spec change → `revisionHash(projection)` — a projection of the behaviour surface **plus the resolved contents of every env source it references** (A20); the card digest is status, and card drift triggers re-registration, never a new revision → creates a parallel workload `<name>-<hash>`.

   **The hash covers a projection of spec, not all of it (A12, r2).** Two surfaces share one CR:

   - **Behaviour surface** — a change to **what the agent can do, produce, or reach**. It must pass a gate, so it mints a revision.
   - **Policy surface** — a change to **how much, how fast, or who may call**, without changing capability. It is applied in place.

   The discriminator is *capability*, **not** the compile path: `knowledge[].scope`, `tools[].name` and `llm.providers` all compile to gateway resources via §3.6 and are all behaviour-surface, because narrowing what an agent may retrieve changes what it answers exactly as removing a tool does. An earlier wording defined the policy surface as "whatever §3.6 compiles", which would have classified those three as policy and reintroduced the very under-gating this amendment exists to prevent.

   Hashing the whole spec would make `replicas: 2 → 3` pay for an eval-and-canary cycle; hashing too little would let an operator swap the model or the knowledge-graph version under a running agent **with no gate**, hollowing out ADR-0006 and ADR-0005 together.

   | Behaviour surface — **mints a revision** | Policy surface — **applied in place** |
   |---|---|
   | `runtime.image` | `runtime.replicas` — a scale operation |
   | `runtime.env`, `runtime.envFrom` — **by resolved content** (A20) | `runtime.port` — wiring; the operator dials it |
   | `runtime.sandbox.profile` | `runtime.resources` — see the note below |
   | `knowledge[].name`, `.version`, `.scope` | `card.path` — a path change is re-registration, exactly as card drift is |
   | `tools[].name` — a capability grant, **and `tools[].requiresApproval`** (A30) | `gates`, `loop` |
   | `llm.providers`, `llm.fallback`, **`llm.egressAllowlist`**, **`budget`** (A25), **`expose`** (A25) | |
   | `external.endpoint` | `external.inlineCard` — a description, not a grant |
   | `external.oauthClientRef` — **identity**, see below | |

   **Changing this table is a hash migration, and the code has now caught up (A30).** `internal/revision` classified `budget` and `expose` as policy-surface — the pre-A25 split — and excluded `tools[].requiresApproval` entirely, with tests pinning all three. The table above said the opposite for over a round, so the shipped hash and the approved design disagreed about which edits pass a gate, and the tests made the disagreement look deliberate. All three now enter the projection.

   The consequence is stated rather than discovered: **every existing revision hash changes**, so every Agent mints a candidate and every active workload is orphaned by name. It is taken now because P1 is unshipped and the affected set is empty. After the first install the same edit needs a carry-forward mapping old hashes to new; `internal/revision/golden_test.go` records this as MIGRATION 1 and its comment says why the constant may not simply be bumped.

   Six rules that are easy to get wrong:

   0. **`tools[].requiresApproval` is behaviour in BOTH directions (A30).** It was policy-surface, and design 03's closed comparator registry has no approval concern — so `false → true` classified as `Unknown → Tighten`, and a tightening on the policy surface has no revision to mint. The field had **no transaction at all**, in the direction it exists for: turning approval on after an incident either wedged while the unguarded route kept serving, or mutated the live interceptor and could NACK, leaving the direct route serving while status recorded the change as applied. Turning it *off* is a widening and must never reach production ungated either. Both directions now mint a revision, exactly as `budget` and `expose` do (design 03 A31).

   1. **`external.oauthClientRef` is behaviour, not "credential rotation".** It selects *which client* an external agent authenticates as — the principal design 24 §3 keys `can_invoke`, `can_call` and the act-chain check on. Repointing it reaches a different set of tools. (Rotating the credential *behind* a client is a Secret update the hash never sees, which is correct and is what the earlier wording confused it with.)
   2. **Env sources are hashed by CONTENT, not by referent (A20, revised).** Every `ConfigMap` and `Secret` reachable through `envFrom` or `env[].valueFrom` contributes a digest of its resolved contents to the projection. Referent identity alone was never sufficient: anyone with `update` on a referenced object could replace a system prompt or a provider endpoint, the pod would restart, and the new behaviour would serve under the old revision and the old gate result — with no permission to touch the Agent at all.

   **The first fix for this was wrong and is retracted.** A20 originally required referenced ConfigMaps to be `immutable: true`, reasoning that a change would then need a *new* object and therefore a new referent. Kubernetes says otherwise: *"Once a ConfigMap is marked as immutable, it is not possible to revert this change nor to mutate the contents … You can **only delete and recreate** the ConfigMap."* Delete-and-recreate keeps the **same name**, so the referent and the hash are unchanged and the bypass survives untouched. Immutability binds contents to an *object*; it never bound a name to contents.

   **Hashing detects a change; it does not stop the serving revision consuming one (A23).** Content hashing mints a *candidate* when a source changes, but if the retained active workload still references the object **by name**, a node drain recreates an R1 Pod that reads the new content under R1's gated hash and route — no Agent write required. The digest recorded in status protects nothing by itself.

   **A revision reads its own copy, and the copy is what is hashed (A35).** At revision mint, **before publication**, the operator copies every referenced `ConfigMap` and `Secret` into revision-scoped material, and the revision's PodSpec references only the copies. The user's object is never referenced by a published revision, so editing it, deleting it, or losing every guard that protected it cannot change what that revision serves. A change to the original is *detected* — it mints a candidate, as A20 says — and it reaches production only through a gate.

   | | |
   |---|---|
   | Name | `<agent>-<revisionHash>-env-<n>`, `n` the source's index in the projection's sorted order — derived from inputs, so a re-reconcile converges rather than duplicating |
   | Kind | preserved: a `Secret` copies to a `Secret`, **never** to a `ConfigMap`. The copy must not be readable by a wider set of principals than the original, and kind is what RBAC keys on |
   | Immutability | `immutable: true` on the copy, so not even the operator can rewrite it in place. Kubernetes then permits only delete-and-recreate, and the operator does not recreate a published revision's material — the objection that sank A20's first attempt becomes a *property* here, because the name carries the revision hash rather than being reused |
   | Ownership / GC | **A label, not an `ownerReference` (A44)** — `plume.dev/agent-uid` and `plume.dev/revision-digest`, stamped at creation and covered by the `RevisionRecord` digest. A42 puts copies in another namespace and a cross-namespace owner reference is *treated as absent*, so the reference this row originally specified cannot exist. Copies for a revision are deleted in the same pass that retires the revision. The bound is **|retained set| × sources-per-Agent**, where the retained set is defined once below (A40) — *not* three, which counted named roles and contradicted this design's own retention arithmetic |
   | Hashing | the projection hashes the **copy's** content, which equals the original's at mint. There is no second source of truth to drift |
   | Optionality | a successfully resolved copy is **always rewritten as non-optional** (A41), whatever the original said. `optional: true` on a copy means deleting the copy starts a replacement Pod with the variable simply absent — a silent change to the process environment, achieved by a delete rather than an edit. Non-optional turns the same act into a visible failure to start |
   | Missing or wrong copy | if a copy is absent, or its `plume.dev/agent-uid` label or content digest disagrees with the record (A44), the revision's route goes to **weight 0** with `RevisionMaterialUnavailable` naming the revision and the copy (A41). Availability loss is the correct direction: the alternative is serving a revision whose material nobody can vouch for |
   | Operator privilege | the operator needs `create` on `Secrets` in agent namespaces, on top of the `get` A20 already required to hash contents. That is a real escalation surface and is stated rather than buried: an operator compromise now yields Secret *creation*, not only reads |

   **One read, one buffer, one publish (A39).** The rules above are only implementable if a single GET produces one immutable byte buffer that is used for BOTH the hash and the Create. The natural two-read implementation — hash the original, read it again to build the copy — races an editor between the reads: the first GET reads safe bytes and computes H, the editor writes malicious bytes, and the operator creates `<agent>-H-env-0` containing the malicious content under a name and a gate identity that say H. The copy would then be faithfully immutable and faithfully wrong.

   The acquisition order is therefore fixed:

   1. **GET once**, recording `uid` and `resourceVersion` with the content.
   2. **Canonicalize and buffer** the exact bytes. Nothing re-reads the source after this point.
   3. **Compute the full revision digest** over those buffers.
   4. **Create** the immutable copies *from those buffers* — never from a second read.
   5. **Read back and verify** kind, owner UID, the immutable bit, and the bytes.
   6. **Only then publish** the revision and its workload.

   `AlreadyExists` on step 4 is **not** an adoption. A copy named for this revision that this operator did not just create must satisfy the whole invariant — same kind, **matching `plume.dev/agent-uid` and `plume.dev/revision-digest` labels (A44)**, immutable, byte-identical — or it is `RevisionMaterialCollision` and the revision is not published. The labels are load-bearing here: without them the check reduces to kind + immutable + bytes, which any principal with write access to the run namespace can satisfy by getting there first. Adopting by name is how a name that looks right comes to hold content nobody hashed.

   **This reverses A23's "no bytes are copied", and the reason it was reversed matters more than the reversal.** A23 chose to seal the source in place — a finalizer plus a fail-closed admission policy — precisely to avoid copying. That closes the *planned* case and cannot close the unplanned one: if the admission binding is removed, an authorised editor writes new content and a Pod replacement serves it before any watch fires, and no reactive remedy helps because the original bytes are already gone. Sealing is a **control**, and a control that is removed stops controlling. A copy is an **invariant**: the revision reads material the editor never had a reference to, whatever happens to the guard afterwards.

   **The residual costs A23 named are real, and are accepted with bounds rather than argued away.** Copies retain historical credential *material* for the retention horizon — bounded by the **retained set** (§3.3, A40), deleted with the revision, and never longer than the rollback target survives. No number is written here: "three" survived A40's own rewrite twenty lines below the definition, which is how a reader going top-to-bottom meets the wrong count first. A rollback re-runs the material its revision was gated with, which can resurrect a credential its owner rotated away; that is the direct consequence of rollback meaning "run R1 again", and the mitigation is the **typed credential binding** that A23 already records as owed, under which short-lived bytes rotate through a trusted issuer while only the stable facts are hashed. Until that exists, an operator rotating a credential should expect a rollback past the rotation to use the old one.

   **The exemption question is settled by fact, not by preference.** An earlier version said rotating a value inside a Secret is not a behaviour change; that exempted the bypass, since `envFrom.secretRef` carries a system prompt exactly as well as an API key. But the cost of removing it was also overstated here: **Kubernetes does not refresh a process environment when a ConfigMap or Secret changes.** `envFrom` and `env[].valueFrom` require container replacement either way — only *mounted volumes* update live, and this API does not expose them. There was never a no-restart rotation path on this surface to lose. What genuine credentials need is a **typed credential binding** whose stable facts (issuer, principal, audience, scope, destination) mint a revision while short-lived bytes rotate under a trusted issuer; that field does not exist yet and is owed (A23). Any union arm the implementation does not name explicitly must hash **injectively** (over-gate), never collapse to a constant — a constant let `fileKeyRef` repoints through ungated.
   3. **List order is not semantic.** Nothing in the corpus treats tool or provider order as meaningful — design 03 compiles tools to a set-semantics filter and providers to a commutative max-price — while kustomize, helm and `kubectl apply` round-trips all re-serialize lists. The projection therefore **sorts** `tools`, `llm.providers` and `knowledge`, so a re-serialized manifest does not re-gate. `env` keeps its order, which is semantic for interpolation.
   4. **`llm.egressAllowlist` is behaviour, and was in neither column (A16).** It is the set of endpoints an agent may reach, so widening it changes what the agent can do — the same argument A12 already makes for `knowledge[].scope`, where narrowing what an agent may retrieve changes what it answers exactly as removing a tool does. It is also the control ADR-0014's compliance profiles pin, so an ungated edit would let an operator widen egress on a HIPAA cluster with no eval and no gate. Design 03 §3.1 consumes it, which is how the omission surfaced. The gate is **symmetric** — any change to the set mints a revision — and compared as a set, since the projection already sorts `llm.providers`.

   **A17 briefly made this gate asymmetric and A18 retracts it.** The argument was that revoking an endpoint that lost BAA coverage would queue behind an eval cycle on every agent, so removal should apply in place while addition mints. It was wrong three ways, and the first is the one that matters: **`revisionHash(spec)` is computed from spec alone** (`internal/revision/revision.go:12`), and "is this set a subset of the previous one" needs `(old, new)`. The predicate is not expressible in a content-addressed digest without giving up the content-addressing §5's "no double-create" and instant rollback both rest on. Second, it laundered a widening: allowlist `{A}` gated and serving as R1 → edit to `{A,B}` mints candidate R2, Held at weight 0 → edit to `{B}`, a removal relative to `{A,B}`, applied in place, R2 abandoned by supersession — and R1, the *serving, gated* revision, now reaches `B`, which passed no eval. That is the ADR-0006 hole this rule exists to close. Third, the premise was false: design 27 §5 ships the BAA allowlist as a **pack filter** (`egress-allowlist.yaml`, `compliance` priority band), and ADR-0014 puts it "enforced at the gateway" — so a BAA list change is a pack/values change compiled into the LLM Backend at profile scope, not 200 Agent edits. The 200-candidate scenario cannot arise, so nothing was bought for the hole it opened.
   5. **`runtime.resources` is policy for a specific reason.** "Capacity, not behaviour" is too glib — an OOM-killed agent fails tasks and CPU throttling changes `taskTimeout` terminations, both observable in `task_completion`. The real argument is that resource regressions are caught by **design 20's behavioural drift path** (SLO burn on success rate → `Degraded`), and gating capacity changes would block incident response — the same reasoning that exempts fallback activation below.

   **Classification is compulsory, not defaulted, and it is LEAF-level (A16).** Every `AgentSpec` field is named in exactly one column, and `TestEveryFieldIsClassified` reflects over the struct to prove the table is exhaustive: adding a CRD field fails the build until someone classifies it and amends this table.

   That test walks **top-level** `AgentSpec` fields only, which is the wrong shape and made the exhaustiveness claim false. The table's rows are top-level names (`llm`, `runtime.env`), but behaviour lives in leaves several levels down inside embedded Kubernetes structs, and the projection drops leaves the table never named. Confirmed by direct differential mutation — two specs differing in exactly one leaf, same revision hash:

   | Leaf | Reaches the running pod? | Found by |
   |---|---|---|
   | `llm.egressAllowlist[]` | no — it reaches the **gateway**, and it is the ADR-0014 egress control | Codex M5; independently reproduced |
   | `runtime.envFrom[].configMapRef.optional` | yes | Codex M3 |
   | `runtime.envFrom[].secretRef.optional` | yes | Codex B1 |
   | `runtime.env[].valueFrom.resourceFieldRef.divisor` | yes | Codex M4 |
   | `runtime.env[].valueFrom.secretKeyRef.optional` | yes | Codex B1 |
   | `runtime.env[].valueFrom.configMapKeyRef.optional` | yes | Codex B1 |
   | `runtime.env[].valueFrom.fieldRef.apiVersion` | yes | Codex B1 |

   So the rule is: **classification and projection are over the transitive leaf graph of `AgentSpec`, not its top-level fields.** A table row may still name an aggregate (`runtime.env`), and the aggregate's classification is the **default** for every leaf beneath it — but an explicitly classified leaf **overrides** its aggregate, and the override must appear in the table above.

That precedence is not academic. `tools` is a behaviour aggregate and `tools[].requiresApproval` is in the policy column; `external` is behaviour and `external.inlineCard` is policy. Without the override rule, "the aggregate binds every leaf" and "fails unless the leaf is explicitly classified policy" give opposite answers for both, and toggling an approval flag would pay an eval-and-canary cycle. Overrides exist only for leaves of plume's own types; **no leaf inside a third-party struct is overridden today**, and one would have to be added to the table like any other.

   **The test must reflect over PATHS, and enumerate over TYPES.** These are `corev1` structs that gain fields between Kubernetes releases, and the trap has been sprung once already: A12 rule 2 records `envSourceRef` naming four arms while k8s v0.36.4 had five, so `fileKeyRef` collapsed to a constant and repointing `prod.env → staging.env` minted no revision. A hand-maintained *path* list reintroduces that on the next dependency bump, so paths are always discovered by reflection.

But reflection alone cannot perturb every leaf, and a walk that silently skips what it cannot reach is worse than no walk. **`resource.Quantity` holds its value in unexported fields**; the only reflect-settable leaf beneath `env[].valueFrom.resourceFieldRef.divisor` is `Format`, a display hint. A critic demonstrated the consequence: projecting `Divisor.Format` alone turns the leaf walk **green** while Codex M4 (`divisor: 1m` vs `1`) still hashes identically. The mandated shape was satisfiable without doing its job — the same defect this amendment set killed twice already, relocated.

So: a **type-keyed perturber registry**, and it **fails closed** — a type the walk reaches that it cannot perturb through a public API **fails the test** rather than being skipped. A registered perturber also **terminates the walk at that type**; without that the walk descends into `resource.Quantity`'s internals and the registry has to carry `math/big.nat`.

The graph was enumerated rather than estimated, and it corrects this amendment's first draft on every count. `AgentSpec`'s transitive graph has **68 type nodes, 38 named, depth 10, no cycles and no interface leaves** — so it terminates. (A leaf *count* is deliberately not stated: it depends on whether the walk terminates at a registered perturber's type or descends into it, and two independent walks produced different figures under different rules. The counting rule is what matters and it is above; the number would only look authoritative.) **Exactly one type carries unexported state: `resource.Quantity`**, at three paths, one of which (`env[].valueFrom.resourceFieldRef.divisor`) is on the behaviour side and therefore required today, not hypothetical. Of the four types the first draft named, three were wrong: `metav1.Time` and `intstr.IntOrString` are **not in `AgentSpec`'s graph at all**, and `metav1.Duration`'s `time.Duration` is exported and reflect-settable. A registry written literally from that text would have had four entries, one load-bearing, two pointing at types that never appear — and would have looked complete.

**The path walk is what catches drift; the registry is not, and the first draft claimed otherwise.** Measured across `k8s.io/api` v0.28 → v0.36: **+1 named type and +5 leaves in eight minor releases**, and **zero new unexported-state types**. The one arrival — `corev1.FileKeySelector` in v0.34 — has all-exported fields, so a registry keyed on unexported state would have stayed *silent* on exactly the class of regression A12 rule 2 records as having already shipped. Reflected paths caught it. So the claim is narrowed to what is true: enumerating **paths** is unsafe and they are always discovered; enumerating **types** is safe *because the set is one*, and it exists to stop a silent skip, not to announce a new field.

**Map-kinded leaves.** `ResourceRequirements.Limits/Requests` are `map[ResourceName]Quantity`. A map-kinded leaf is perturbed twice — over its key set (`{cpu:1} → {memory:1Gi}`) and over its value set (`{cpu:1} → {cpu:2}`) — and either must mint if the leaf is behaviour. The value perturbation *is* a `Quantity` perturbation, so the map rule composes with the registry rather than sitting beside it. Both map paths hang off `runtime.resources`, which is policy, so they are moot today — but "the walk prunes there" was doing double duty in the first draft: the **classification** walk must reach a field to classify it, so pruning is an output of classification and not an input, and it is the **projection** that never descends.

**Recursion is guarded, not assumed away (A27).** An earlier draft made "`AgentSpec` must not gain a self-recursive type" a *precondition* — which is not a guard, because nothing enforces it and the failure mode is a hang. `apiextensions-apiserver` is already a direct dependency and its `JSONSchemaProps` has twelve self-recursion points; a walk with no type stack meets one and exhausts the stack or spins. That is an **INVALID** mutation, not a killed one: CI crashes instead of naming the new field, and AGENTS.md rule 3 says a mutation that does not run proves nothing.

So the walker carries a stack keyed by `(type, path)`. Meeting a type already on the stack **fails immediately**, naming the full field path and demanding an explicit classifier and perturber for it. A cycle becomes an assertion failure that says which field introduced it — the outcome the test exists to produce — rather than a hang someone has to diagnose.

**A perturbed variant must also be API-valid**, and differ only at the named leaf. Otherwise the API server rejects the mutant for an unrelated schema violation and the suite reports a killed classification mutation when nothing was tested. That is the same INVALID-versus-SURVIVED distinction, in the other direction.

   **A cheap reflection sweep is not this test.** One was run over the current projection: it reached 31 leaves, correctly showed the other 16 non-minting leaves are all genuine policy surface (`budget.*`, `expose.*`, `loop.*`, `runtime.replicas/port/resources`, `card.path`, `gates`, `tools[].requiresApproval`, `external.inlineCard`), and confirmed `llm.egressAllowlist` — but its depth cap and pointer seeding never reached `env[].valueFrom.*` at all, so it would have missed four of the seven leaves above. The gap between "a sweep that finds something" and "a sweep that proves absence" is the whole difficulty, and it is why this is a design rule with a required test shape rather than a one-off fix.

   An earlier version of A12 said new fields *default* to policy-surface and called that the safe direction — it is not. A behaviour field added without classification reaches production ungated, silently, which is precisely the ADR-0006 hole; the critic demonstrated it by adding a `SystemPrompt` field and watching the whole suite stay green.

   **Exception, stated because A12's headline claim is otherwise false.** Design 20's `ModelDrifted` remediation activates `llm.fallback` by setting **status**, not spec, so it mints no revision and no eval fires — deliberately, since an eval cycle mid-incident is the last thing wanted. The consequence is that **the model actually answering requests can change without a gate**, as incident response, with design 20's four guardrails (correlation, rate limit, receipt, override) as the compensating control. That is the right design; a reader who concluded from A12 that the serving model can *never* change ungated would be wrong.

   Hashing is over the projection's canonical JSON. The projection struct's field order, JSON tags and `omitempty` are part of the revision contract — `encoding/json` emits in declaration order, so a cosmetic reorder would re-mint every revision in every cluster. `TestGoldenDigest` pins the encoding; a change there is a **migration, not a test edit**.

2. Candidate registers, gets identity, passes readiness — gateway route weight **0** (`phase: Held`).
3. The gate controller (16) runs the EvalSuite against the candidate through the gateway on a **candidate-only route** whose admitted set is exactly the eval run's own SVID, granted at Job launch and revoked at Job end. Eval traffic otherwise uses the identical path as prod.
4. Pass → weights shift (canary steps, default `10 → 100`); `activeRevision` flips; superseded revisions GC'd per `revisionHistoryLimit`.
5. Fail → candidate deleted, report in status + PR annotation; `GatesPassed=False` naming the failing metrics.

**Spec change while a candidate is in flight**: the new generation **supersedes** the old candidate. `C1` drains to weight 0 respecting `taskTimeout` (the drain design 22's kill switch uses), `GatesPassed` resets, the abandoned revision is appended to `status.supersededCandidates` and emitted as an event. At most one candidate is ever in flight.

**`revisionHistoryLimit: 2` means two retained revisions *in addition to* active and any in-flight candidate** — otherwise a rollout would GC its own rollback target and destroy the instant-rollback property ADR-0019 exists for. Design 20's retention hold (pin the last eval-passing revision while `Degraded` is open) is this operator's behaviour and is honoured here.

**The retained set is defined ONCE, and everything else is sized from it (A40).** Three documents had been counting it differently: this rule says history is *additional* to active and candidate, while design 03 A28 capped `status.revisions[]` at three records "active, candidate, rollback target" and A35 bounded credential copies at "three live revisions". At the default `revisionHistoryLimit: 2` the legal set is already **four** — R1 and R2 retained, R3 active, R4 candidate — every member of which the documented rollback contract requires. An implementer following the three-record cap would have to reject a legal candidate, delete a promised rollback target, or retain material for a revision whose record it cannot store. All three violate an authoritative rule, which is what a bound derived from role names rather than from the set does.

> **retained set** = `{active}` ∪ `{candidate}` ∪ *the `revisionHistoryLimit` most recent superseded revisions* ∪ *explicit holds*.

Its size is `revisionHistoryLimit + 2 + holds`, **at least four at the default**, and it is what bounds `status.revisions[]` records (design 03 A28) and A35's copies alike. A **design 20 retention hold EXTENDS the set**; it does not occupy a history slot — a hold that displaced a history entry would silently shorten the rollback window during exactly the incident the hold exists for. §8 owes a maximum-overlap transition test: a candidate arriving while a hold is open and the history window is full.

**Rollback** = re-point to a retained revision (instant, no rebuild).

**Core tier**: the gates-required admission rule applies iff the EvalSuite CRD is installed; on core-only installs rollouts proceed with a loud `GatesSkipped=True`. `local` profile only: `GatesBypassed=DevProfile`.

### 3.4 Registration & card handling

**The card is served by the container — source of truth is the agent's code.** After a candidate is Ready the operator fetches it in-cluster (3 retries, backoff), validates (parseable, name matches CR, A2A version supported, **signature** per design 09: required for plume-built, `CardUnsigned=True` for BYO/external), stores a per-revision digest in `status.cards[]`, wraps it in an OASF record, and writes it to the directory (JetStream KV, `agents.<ns>.<name>.<revision>` plus the `.active` pointer; GC'd with revisions).

- **Card-vs-CR cross-check**: a card advertising a skill that requires a tool or graph the CR does not grant is a registration failure (`Registered=False`) naming the mismatch — otherwise it registers cleanly and fails at runtime.
- **Terminal unregistrable state**: retries continue with backoff for `registrationDeadline` (default 30m); past it the candidate is **failed and deleted**, freeing its retention slot, with the reason recorded. Nothing holds a slot indefinitely.
- **Card drift** at runtime (digest change without spec change) → re-fetch, directory update, event.
- **External agents**: card fetched from the external endpoint; a CR-inline override is permitted only where the endpoint cannot serve one.

### 3.5 Identity wiring

One platform-owned **ClusterSPIFFEID** (spire-controller-manager) with a selector template — no per-agent registrar code:

```
spiffe://{{ .TrustDomain }}/agent/{{ index .PodMeta.Labels "plume.dev/agent-namespace" }}/{{ index .PodMeta.Labels "plume.dev/agent" }}
```

**The template uses `index` (A60, correcting A59).** A59 wrote `{{ .PodMeta.Labels "plume.dev/agent-namespace" }}`, which Go's `text/template` does not accept as a map lookup — spire-controller-manager parses the template with no functions or options of its own, and its webhook rejects a template that does not parse (`docs/research/tenant-namespace-primitives-2026-09.md` §1). The corrected form is above, and design 07 A5 renders it.

**A missing label must fail closed, and the template shape is what makes it so.** `index` on an absent key yields the empty string, not an error. Because each label is a **whole path segment**, an absent label renders an empty segment (`…/agent//reviewer`) and go-spiffe rejects the ID, so the Pod gets **no entry and no SVID** — which is the correct outcome for a Pod that cannot say which agent it is. That property is shape-dependent: a template writing `agent-{{ index … }}` would render a valid ID from an absent label. So the rule is: every label-derived value is a whole segment, and the `ClusterSPIFFEID`'s `podSelector` additionally requires both labels to **exist**, so a Pod without them is never selected at all.

**The path segment is a LABEL, not `.PodMeta.Namespace` (A59), and this is an authorization change disguised as a move.** A42 puts the Pod in `plume-run-<agent-namespace>`, so a template reading `.PodMeta.Namespace` would silently re-issue every agent's SVID under a new identity: `spiffe://…/agent/plume-run-team-a/reviewer` instead of `spiffe://…/agent/team-a/reviewer`. Design 24 §3 keys `can_invoke`, `can_call` and the act-chain check on that principal, and design 03 compiles admitted sets from it — so every existing grant would stop matching, every route would stop admitting the workload it was written for, and the failure would look like a routing bug rather than an identity change.

The operator therefore stamps `plume.dev/agent-namespace` with the **Agent's own** namespace on every workload Pod, and the identity stays what it was before the Pod moved. The move is meant to be invisible to authorization, and only an explicit label makes it so.

**What makes a label-derived identity sound, stated (A60).** Before A59 the namespace segment was the Pod's own namespace, which a principal can only choose by holding `create` on Pods there. After A59 it is a label, which a principal choosing the Pod's labels also chooses. So the boundary moves: **anyone who can create a Pod in any namespace the `ClusterSPIFFEID` selects can claim any agent identity**, in any tenant. That is acceptable only because the selector admits **namespaces in which only the operator creates Pods** — labelled `plume.dev/pods-by: agent-operator`, a label deliberately distinct from `plume.dev/run-namespace`, which the Gateway listener selects on and which design 26 A1 also puts on a vCluster's host sync namespace, where a *tenant* creates the Pods. One label carrying two trust boundaries was the critique's first blocker. Only the operator creates Pods in a `pods-by: agent-operator` namespace — no Role or RoleBinding granting Pod `create` in a run namespace is rendered by the chart, and the read-only RoleBinding this section's table owes must stay read-only. A cluster-scoped Pod `create` grant already permitted impersonation *within* a namespace before A59; A59 widens what such a grant reaches to *across* namespaces, and that widening is the price of the move. The alternative that avoids it — one `ClusterSPIFFEID` per run namespace with the namespace segment as a literal and a `kubernetes.io/metadata.name` selector — keeps the per-namespace boundary but is per-namespace registrar code, which this section was written to avoid. It is recorded here as the hardening to take if the read-access RoleBinding ever grows a write verb.

**Done and owed:** design 07 A5 records the `ClusterSPIFFEID` the chart renders; §8 still owes the case that an Agent in `team-a` gets `…/agent/team-a/<name>` whatever namespace its Pod runs in, and it needs SPIRE, which nothing installs today. Design 06 is **not** affected — it owns the IdP glue and the `agent-actor` OAuth client, neither of which derives from the workload's namespace. An earlier note listed a design 06 amendment as owed for this; checking the text rather than the note, the SPIFFE template was never design 06's.

Pods are labelled `plume.dev/agent` + `plume.dev/revision`; SVIDs delivered via spiffe-csi. The operator additionally provisions a per-agent **`agent-actor` OAuth client** (design 06) so exchanged tokens' `act` chains name real agents. External agents get no SVID — they authenticate with OAuth client credentials. Hard-mode tenancy uses per-tenant SPIRE federated to the host trust domain (design 26).

### 3.6 Gateway handoff (interface with design 03)

The operator normalizes **one revision's** material (tools, budget, `llm`, expose, KG scopes, that revision's weight, `gatewayReplicas`) — one `PolicyIntent` **per live revision**, never one per Agent (design 03 A26) — into a `PolicyIntent` and calls the **policy compiler as an in-process library**, which emits agentgateway resources under fail-closed apply ordering; the operator owns their lifecycle — by **label and name**, not by `ownerReference`, because under A42 they live in the run namespace and a cross-namespace owner reference is treated as absent (design 03 A44, A60). The gateway CRD surface is pinned by the chart (design 07) at a minimum version carrying OSS token exchange and virtual models.

### 3.7 Finalization

On delete, an operator finalizer gates ordered teardown, and **revision material is deleted here because nothing else will** (A56) — A44 chose labels over an `ownerReference` so A42's namespace move would not change the invariant, and the price of that choice is that Kubernetes garbage collection does not apply. A copy left behind is a snapshot of a Secret's bytes outliving the Agent that justified reading them. The ordered steps: **drain traffic** (weights 0, respect `taskTimeout`) → **revoke** routes and policies in design 03's reverse apply order → **deactivate** (never delete) the `agent-actor` OAuth client, per design 06 D3 → **GC** directory entries and SPIRE pod labels → **delete this Agent's workloads and copies in the run namespace, and the run namespace itself if this was its last Agent, by the binding protocol in §3.2 (A60)** → release the finalizer. Workloads are deleted here explicitly: under A42 they carry no `ownerReference` to the Agent, so Kubernetes will not collect them either. In-flight tasks drain or time out; nothing is force-killed silently. Design 26's hard mode splits this: workload teardown in the vCluster, route teardown host-side via the compiler's labelled resources.

## 4. Behavior — reconcile outline

```
observe Agent CR + owned objects + spend aggregate (read-only, design 04)
→ validate. **Admission has already enforced only what CEL can express** (A21): digest-pinned image, prod-gate presence, sandbox/replicas exclusivity, the `usdPerDay` grammar. It has **not** verified an image signature — that needs the Sigstore policy-controller binding design 07 A2 chose and the chart does not ship, so the reconciler must not treat signature as a settled precondition
→ ensure workload for the desired revision (Deployment | Sandbox); scratchpad per §3.2
→ ensure identity labels / agent-actor client / oauth client (external)
→ candidate Ready? fetch + validate + cross-check card → directory upsert
→ compile PolicyIntent → apply gateway resources (weights per rollout state)
→ hold/advance rollout per gate-controller signals; supersede in-flight candidate on new generation
→ evaluate budget backstop; guard states (BudgetHeld, Killed) win over rollout state
→ update conditions + phase; emit events
```

Idempotent; server-side apply with field ownership; no state outside CR status + directory KV.

## 5. Failure modes & degraded states

| Failure | Behavior |
|---|---|
| Image is a tag, not a digest | Rejected at admission by CEL; never reconciled (A21) |
| `envFrom`/`valueFrom` referent missing or unreadable | `EnvSourceUnresolved=True` naming it; **no revision is minted and no workload is created** (A20). A missing referent is *unresolved*, never a zero digest — a zero would let deleting an object mint the same hash as never having referenced it. `optional: true` does not change this: the operator cannot know what the pod will see |
| Rollback target's env content has changed since it was gated | **Irrelevant (A38).** A35's revision reads its own copy, so the user's object moving does not make the revision unreproducible — that is the property copies were chosen for. The pre-A35 rule refused the rollback here, which would extend an incident by declining a recovery that is perfectly available |
| The label-reserving admission policies of design 07 A5.9 are absent (A60) | `RunNamespaceUnavailable=LabelAuthorityAbsent`, terminal until they are installed; no run namespace is created, because the labels SPIRE and the Gateway act on would be forgeable |
| Binding record missing a field, carrying an unknown state, or a schema version this operator does not decode (A60) | `RunNamespaceUnavailable=BindingRecordInvalid`, terminal, naming the field; recovery is the human re-bind procedure in §3.2 |
| Run namespace exists and the operator holds no binding for it, or — while binding — its nonce disagrees, or — once bound — its UID disagrees with the binding (A60) | `RunNamespaceUnavailable=NotCreatedByOperator`, **terminal**; `Ready=False`, `phase: Degraded`. Nothing is written into the namespace. The message names the namespace and says what to check: whether it was pre-created, or deleted and recreated outside the operator |
| Two source namespaces truncate-and-hash to one run namespace name (A60) | `RunNamespaceUnavailable=NameCollision` on the **second** tenant's Agents, terminal, naming both source namespaces. The first tenant is untouched |
| Run namespace is being torn down — last Agent deleted, or the source namespace was recreated (A60) | `RunNamespaceUnavailable=Terminating`, `phase: Pending`, requeued; clears when the handler has removed the namespace and a fresh one is created, which needs no human unless the delete itself is refused |
| Rollback target's revision COPIES are missing, or do not match | Rollback is **refused**, naming the revision and the copy whose content digest or `plume.dev/agent-uid` label disagrees (A38, A44). This is the reproducibility test that replaces referent drift: the material either exists, is owned by this Agent, and hashes to what the revision was gated with, or the revision cannot be rerun. Refusing is the fail-closed direction; rolling back to material nobody can vouch for reintroduces the bypass through the recovery path |
| Image unsigned | **Nothing enforces this today.** CEL cannot verify a signature and the chart ships no admission policy; the guarantee arrives with the Sigstore policy-controller binding design 07 A2 chose and A3 gives an enforcement contract (§6) |
| Prod gates missing | Rejected at admission when the EvalSuite CRD is installed; never reconciled |
| Card fetch fails | `Registered=False`, candidate held, backoff; **failed and deleted at `registrationDeadline`** so no retention slot leaks |
| Card advertises ungranted capability | `Registered=False` naming the mismatch (§3.4) |
| Card unsigned (BYO/external) | Registers with `CardUnsigned=True` — the BYO promise holds, the gap is visible |
| Sandbox runtime absent | Hardened-Deployment fallback + `SandboxDowngraded` |
| Scratchpad access mode unavailable | Candidate runs without it + `ScratchpadDegraded`; active revision unaffected |
| `replicas>1` without shared-task-state declaration | `TaskStateUnverified` + CLI warning; admission may block for `expose: public` |
| New generation during canary | In-flight candidate drains to 0, recorded in `supersededCandidates` + event |
| Rollback target GC'd | Prevented by §3.3's retention arithmetic and design 20's hold; if it still occurs, rollback is refused and the escalation names the gap |
| Kill switch during rollout | `Killed` guard state wins over every rollout state; gate controller observes and abandons cleanly (design 22) |
| Budget exhausted (backstop tier — not exact in USD, ADR-0028) | `BudgetExhausted` + `phase: BudgetHeld`; serving weights 0 until the 00:00 UTC window resets |
| Spend aggregate unavailable (design 04 down) | Gateway approximation still enforcing; `BudgetEnforcementDegraded` — the exact-tier gap is visible |
| Pricing row missing for a usd budget | `PolicyCompileFailed` naming the model (design 03 §3.5). **Not** `PricingStale`, which means the table is older than 30 days — one condition cannot carry both meanings and mean either (A15) |
| Receipt pipeline gaps affecting this agent | `ReceiptsDegraded` (design 04) |
| IdP unavailable at `agent-actor` provisioning | `IdPUnavailable`; machine mTLS paths continue, human/on-behalf-of paths fail closed (design 06) |
| Gateway API **unreachable** (control plane down), CRDs still installed | Last-applied config stands; `Ready` degrades to stale-but-serving; retry. Scoped to unreachability: **deleting the CRDs garbage-collects the routes**, so nothing stands and design 03 §5's `CRDsAbsent` row governs instead (A18) |
| **Gateway CRDs absent, `gateway.enabled: true`** | A **broken install**: `GatewayIncompatible=CRDsAbsent`, `Ready=False`, `phase: Pending`, page — at every profile, `local` included |
| **`gateway.enabled: false`** — the declared-ungoverned tier (P1, `local`) | **`GovernanceSkipped=GatewayDisabled`**, a separate condition type, not a reason on an error type. `Ready` unaffected, no page. Same shape as `GatesSkipped` for a missing EvalSuite CRD and `ReBACAvailable=False` in design 24 — a tier that was never installed is not an incident, and consumers keyed on error conditions must not fire on it (A18) |
| Policy compile or apply fails for this agent | `PolicyCompileFailed` / `PolicyApplyIncomplete` (design 03 §3.3, §3.3.1); routes withheld, so no ungoverned traffic path exists |
| SPIRE down | Existing SVIDs valid until expiry; new revisions held (`IdentityIssued=False`) |
| KG binding invalid or not `active`/`superseded` | `KnowledgeBound=False` → `Degraded`; no traffic if it is the sole knowledge source (design 01 A5) |
| Finalization stalls (drain or revoke blocked) | Finalizer holds; `Degraded=True` with reason `FinalizationStalled` and a message naming the stuck step (design 26 A1 names `AwaitingRouteRevocation` as one); never force-deleted |
| Operator crash | Reconcile resumes from CR/status; revisions are content-addressed (no double-create) |

## 6. Security

Admission, **and what actually enforces each** (A21 — an earlier version of this line asserted all four as enforced and none was): digest-pinned image (CEL on the schema) · prod-gate presence (CEL) · sandbox/replicas exclusivity (CEL, ADR-0027) · `expose: public` requires an approval label (CEL). **Cosign signature verification is not CEL-expressible and is not shipped** — it needs the Sigstore policy-controller binding design 07 A2 chose, whose *effective enforcement* contract A3 defines (presence alone verifies nothing). Digest-pinning is what makes that verification meaningful when it lands, because a signature is verified *against a digest*. Workload pods: default-deny NetworkPolicy (egress = gateway only), non-root, read-only rootfs. Directory writes: operator identity only. External-agent OAuth secrets in k8s Secrets (ESO-compatible), never in spec. The candidate-only eval route admits exactly one principal (design 16).

## 9. Decisions (veto async)

1. **Deployment default; Sandbox opt-in** (singleton; mutually exclusive with `replicas>1`).
2. **Card SoT = container-served**, per-revision digests in status; inline override only for external agents.
3. **Gateway-weighted blue-green revisions owned by the operator** — required by eval-as-admission; retention counts *in addition to* active and candidate.
4. **Identity via one templated ClusterSPIFFEID + pod labels**, plus a per-agent `agent-actor` client; zero custom registrar code.
5. **Detection over assumption** for multi-replica task state, and **loud degradation** for every unavailable guarantee.
6. **Finalization deactivates identity objects, never deletes them** (design 06 D3).

A26 (2026-08-27, from `reviews/03-codex-review-r4.md` BLOCKER 5 and 6) — **who holds a sealed source, and what happens when the guard goes away.** A23 named both as owed. The scoped B3 review had made the first a *precondition* of the seal rather than a test detail, and the second is a live gap in a mechanism already committed.

**The finalizer list is the reference count.** Rather than a side-car lease object with its own consistency problem, each retaining revision adds its **own** finalizer to the source and removes only that one.

**The lease name cannot contain the revision hash (A28).** An earlier draft named it `plume.dev/src.<agent-uid8>.<revision8>` while the same section required *seal first, then read* — and A20 makes the sealed content part of the revision digest. So `revision8` did not exist at the moment the finalizer had to be written. That is the **circular identity defect this project's own history already records** (a hash depending on a value knowable only after the thing it identifies), reintroduced in the mechanism meant to prevent content moving underneath a hash. An implementer resolving it by hashing first reopens the exact race the seal closes: the editor changes the source between the read and the finalizer write, and the candidate is named for content its Pod will not see.

The lease is therefore named for something knowable **before** any content is read — `plume.dev/src.<leaseUID>`, where `leaseUID` is durable and random, recorded on the Agent *before* the source is touched.

**The identity is not truncated (A29).** An earlier draft used `src.<agent-uid8>.<revision8>` — 64 bits across two truncated halves, in a list Kubernetes treats as a **set**. Two holders whose truncations collide share one string, so the first release removes the second's hold and unseals a source a live revision still references, silently. `leaseUID` is a full 128-bit value rendered to fit the qualified-name segment limit — **63 characters, not 253 (A33)**: 253 is the optional DNS-subdomain prefix *before* the `/`, and the segment after it is capped at 63. `src.<UUID>` is 36 characters and fits either way, so the mechanism was never at risk, but the stated bound would have blessed a longer name that admission rejects. The rendered finalizer is pinned by an admission test rather than by arithmetic in prose. A `leaseUID` already present on a source when this Agent did not put it there is a **collision that is refused and reported**, never coalesced — a lease is per-holder or it is not a refcount.

**Ownership is a server-side reservation, not a self-report (A32).** "A `leaseUID` this Agent did not put there is refused" needs the operator to *know* which it did — and a status record it wrote itself cannot answer that after a crash between recording the UID and adding the finalizer. Both a genuine holder and a colliding one hold an identical record. Scanning every Agent's status can reveal a duplicate but resolves nothing: neither side can prove priority, and if both proceed, one release removes the set-valued finalizer while the other revision still references the source.

So the UID is reserved through an object whose uniqueness the **API server** enforces: a `coordination.k8s.io/v1` `Lease` named `plume-src-<leaseUID>` in the operator namespace, created with `Create` — which fails `AlreadyExists` atomically — and carrying an `ownerReference` to the Agent. The reservation is what makes ownership independently verifiable: any party can read the Lease and see which Agent owns it, without trusting a self-report. `AlreadyExists` means the UID is taken, whatever the reason; the operator draws a new UID and retries rather than reasoning about whether the collision was its own.

Two properties fall out for free, which is the argument for using a core object rather than inventing a registry. The `ownerReference` makes Kubernetes garbage-collect the reservation when the Agent is deleted, so a deleted Agent cannot strand a name. And a `Create` is a single round trip with no read-then-write window to lose.

**Acquisition order, and why the sweep cannot race it.** The order is: **draw a lease UID → `Create` its Lease (`AlreadyExists` ⇒ draw again) → record the UID in Agent status → add and observe the finalizer → read and hash the sealed source → associate the lease UID with the resulting revision hash.** The reservation *precedes* both the status record and the source write, so at every step the durable state is unambiguous:

| Crash after | Durable state | Recovery |
|---|---|---|
| the `Create` | a Lease owned by this Agent, no status record | re-record and continue; the reservation is already this Agent's |
| the status write | Lease + record, no finalizer | add the finalizer and continue |
| the finalizer add | Lease + record + seal, no revision | read, hash and associate — the pre-revision hold the withdrawn sweep rule would have reclaimed |
| the association | complete | nothing |

Release is the reverse and is ordered: remove the finalizer, **then** delete the Lease. A Lease outliving its finalizer costs a stale object the sweep removes; a finalizer outliving its Lease would leave a seal no reservation explains. §8 owes a **forced-collision** test: two Agents driven to draw the same UID must produce exactly one successful `Create`, one retry, two distinct reservations, and no shared finalizer string.

The startup orphan sweep therefore keys on that record, **not on whether a revision exists** (A29). An earlier draft swept entries whose revision no longer existed — but between adding the finalizer and minting the revision there legitimately is no revision, so a leader change in that window would classify a valid in-flight hold as an orphan and unseal a source mid-acquisition. The sweep instead removes only a `leaseUID` that appears on **no Agent's status at all**, and it runs **before** the reconcilers start, so it cannot observe a half-written acquisition from a live worker. A crash at any step leaves either a recorded-but-unsealed lease, which the next reconcile completes, or a sealed-and-recorded one, which is live; never a source sealed under a name nothing can resolve.

The rest is deliberate:

- Add and remove **must be an explicit read-modify-write carrying `resourceVersion`, with retry** — this is *not* free, and the obvious implementation is badly wrong. Measured: **20 concurrent naive JSON-patch appends left ONE finalizer**, losing 19 of 20 holds. The same 20 writers doing read-modify-write with `resourceVersion` and retry produced all 20. A26's first draft said the list was "compare-and-swap by construction"; it is compare-and-swap only if the writer supplies the precondition.
- "Release only after an authoritative list of all live leases" collapses to "remove your own entry", because the object *is* the list. The source is sealed while any `plume.dev/src.*` finalizer remains, and becomes deletable when the last one goes.
- The admission policy already denies finalizer removal by every principal but the operator (spike §4), so a holder cannot be evicted by the source's editor.
- Finalizers are durable in etcd, so a crashed operator's holds survive the crash. Orphan reclamation is a startup sweep, not a liveness protocol, and it keys on the **recorded lease UID** — the rule stated above. The earlier wording, *"drops entries whose agent-UID or revision no longer exists"*, is **withdrawn (A32)**: it contradicted the paragraph seven lines above it, and following it would reclaim a valid pre-revision acquisition after a leader restart, unsealing a source mid-acquisition. Two rules for one sweep is worse than either rule alone, because an implementer picks one.

Acquire order is fixed and matters: **seal first, then read.** Add the finalizer and observe it, *then* re-read the source's UID and content and hash it. Reading first would hash content that could change before the seal landed, which is the same before-and-after race the seal exists to close. The recorded material is `{uid, resourceVersion, selected keys, digest}`; a UID change means delete-and-recreate happened while unsealed and is treated as divergence, not as the same source.

**The digest in status is keyed, because a raw one is a guessing oracle (A27).** `status` is readable by anyone with `get` on Agents, which is a far wider set than those who can read the Secret. A raw `sha256` of a low-entropy value — a feature flag, a username, a short token, `true`/`false` — is trivially reversed offline by anyone holding it. So the digest published in status is `HMAC(cluster-key, content)`, with the key in an operator-only Secret; equality comparison still works, offline guessing does not. **Rotation is keyed, staged and interruptible — it is not one atomic pass (A29).** Agent statuses cannot be rewritten atomically across a fleet, so an earlier draft's "re-derives every retained digest in one pass" had no safe failure point: changing the key before every digest is rewritten makes unchanged sources fail comparison and go to weight 0, and changing it after leaves new digests unverifiable with the old key.

Each recorded digest therefore carries the **key ID** that produced it, and rotation is staged. Verification accepts **any retained key**, so a half-finished rotation compares correctly in both directions and can be interrupted, resumed, or abandoned.

**A scan is not a write barrier (A31).** An earlier rule retired K1 once a sweep observed no K1 digests remaining. That orders the *rotator* against the fleet and leaves the **writers** unordered: a reconcile worker that started before the rotation, holding a cached view naming K1 active, can commit a K1 digest after the final scan. Nothing re-scans, K1 is retired, and the next verification raises `VerificationKeyMissing` on content that never changed — withholding new revisions for that Agent until a human restores a key the cluster believes it retired. The window is not narrow: it is the lifetime of any in-flight reconcile.

Key state is therefore an explicit machine with an **epoch**, and every digest write is conditional on it:

| State | Writers | Verifiers |
|---|---|---|
| `active` (epoch *N*) | the only key a digest may be written under | accepted |
| `verify-only` | **never** written under | accepted |
| `retired` | never | rejected — `VerificationKeyMissing` |

- Every digest status write **compares and swaps against the current active epoch**. A writer whose cached epoch is stale loses the CAS, re-reads, and retries under the new key. This is the same read-modify-write-with-precondition the finalizer list needs, for the same reason: the precondition is what makes the operation safe, and the obvious unconditional write is the bug.
- Retirement order is: K2 becomes `active` at epoch *N+1* → K1 becomes `verify-only` → **drain or fence every writer at epoch ≤ N** → re-derive remaining K1 digests → a final consistent rescan → retire K1. A write that loses the CAS after the rescan is retried under K2, so it cannot land under a retired key.
- Nothing enforces the drain today; it is stated so the implementation carries it. §8 owes the test: a **paused** worker holding epoch *N*, resumed after K1 is retired, must produce a K2 digest and no `VerificationKeyMissing`.

**Missing key is unverifiable, not divergent.** If a digest names a key ID that no longer exists, the operator cannot conclude the source changed — it can only conclude it cannot tell. That raises `EnvSourceProtectionUnavailable` with reason `VerificationKeyMissing` and **withholds new revisions**; it does **not** set `RevisionMaterialChanged` or weight 0, because treating "cannot verify" as "has changed" would take a healthy fleet down on a lost Secret.

**Guard loss does not keep serving blindly, and does not nuke the fleet either.** The spike measured that deleting the admission Binding immediately restores the editor's write (§4.2), and A23's response — withhold new revisions, raise `EnvSourceProtectionUnavailable` — protects only future revisions while retained ones keep resolving a now-mutable object by name. That is truthful and not fail-closed.

The correction distinguishes *possible* from *realised* compromise, because the operator already watches every sealed source for A20's content hashing:

| State | Response |
|---|---|
| Guard absent or skewed, every sealed source still matches its retained `{uid, digest}` **at the instant it was read** | `EnvSourceProtectionUnavailable`; **no new revisions**; serving continues **only under a planned, overlap-only guard transition** (below). Outside one this row does not apply — the race does. Two limits on the predicate itself, so it is not read as a safety proof (A34): a match is a point-in-time observation, and an edit plus a kubelet restart can invalidate it between the read and anything done about it; and if the digest names a retired key the predicate is not false but **unknowable** (`VerificationKeyMissing`), which is a third state this row does not have |
| Guard absent **and** any sealed source diverges from its retained digest or UID | **`RevisionMaterialChanged`, weight 0 for every revision referencing it**, `phase: Degraded`. The bypass has occurred, so the affected revisions stop serving — via the existing rollout weight machinery, not a new route mutation (A19 removed those) |
| Guard restored | Re-verify every retained source against its recorded material **before** republishing. Divergence found on restoration is treated as the row above, never repaired in place |

**`EnvSourceProtectionUnavailable` is abnormal-true, and its full contract (A27).** It is in §3.1's vocabulary; here is what consumers may rely on:

| Guard | Sources verified? | Condition | `Ready` | Route | Clears when |
|---|---|---|---|---|---|
| present | — | absent | unaffected | unaffected | — |
| absent or skewed | all match | `True`, reason `GuardAbsent` | **unaffected** | unaffected; **no new revisions** | guard restored *and* re-verified |
| absent or skewed | any diverges | `True` + `RevisionMaterialChanged` | `False` | **weight 0** for referencing revisions | divergence cannot clear — the revision is gone |
| restored, not yet re-verified | pending | `True`, reason `VerificationPending` | unaffected | unaffected; no new revisions | re-verification completes |
| restored and verified | all match | absent | unaffected | unaffected | — |

Abnormal-true, so it is **dropped** when it stops applying rather than set `False` — its absence is the signal (A13). `phase` is unchanged by it alone; only the divergence row moves phase, via `Degraded`. The CLI treats it as a warning and **not** terminal for `deploy`, because a healthy fleet with a missing guard is still serving; design 10 alerts on it as a ticket, and on `RevisionMaterialChanged` as a page.

**"The exposure is prospective" was false (A28).** The spike measured that removing the Binding makes `data` updates immediately admissible, and the finalizer stops a *delete*, not a write. So: Binding gone, an editor who is legitimately allowed to edit the ConfigMap changes a prompt, and a node drain or Pod deletion replaces an R1 Pod — all before the operator processes the source watch. The replacement Pod serves changed content under R1's gated hash, and the divergence check sets weight 0 **after requests have been served**. Detection is a controller reaction racing an admission gap, and a reaction cannot be fail-closed against one.

- **Planned guard changes are overlap-only**: establish and verify the replacement Policy and Binding **before** removing the old ones, so no window exists in which no guard is installed. That is the only case the table's first row covers.
- **Unplanned guard loss cannot be handled by reacting, and "fall back to snapshots" was not a fix (A34).** The sentence that stood here made A23's snapshot fallback the thing that closes this race. It cannot be, because it is *reactive*: at the moment of loss no snapshot exists, no PodSpec references one, and once the editor has won, the original bytes are gone. A fallback triggered afterwards can only copy the attacker's new content or fail for want of the old. A remedy that runs after the loss cannot restore a pre-loss invariant.

  **The race is closed by A35, and not by anything reactive.** The user chose **immutable revision-scoped copies created before publication** (§3.3): the revision's PodSpec references material the editor never had a reference to, so guard loss, an authorised edit and a Pod replacement leave what that revision serves unchanged. The alternative considered and not taken was a separately protected Pod admission control; it was rejected on two counts — a `ValidatingAdmissionPolicy` cannot read another object from CEL, so it needs a webhook on the Pod-creation path with a `failurePolicy: Fail` blast radius, and it very likely does not cover an **in-place container restart**, which re-resolves `envFrom` without creating a Pod object and so never reaches admission at all.

  What remains true is narrower and is not a bypass: while the guard is absent, an editor can change the **original** object freely. That mints a candidate and passes a gate, which is the designed path.
- **Not claimed until measured**: the seal is not described as fail-closed against unplanned guard loss until the Binding-removal + edit + Pod-replacement sequence runs with a kubelet. Envtest has none; `make conformance-cluster` is where it belongs.

**The residual, stated because it is the honest part.** Detection rides the source watch, so a change that is applied and reverted between watch events is not observed, and a running Pod that already read the changed value keeps it. The seal is what makes that window small; it is not zero, and no arrangement of conditions makes it zero while the guard is absent.

**Vocabulary.** `EnvSourceProtectionUnavailable` was named by A23 and never added to §3.1's closed list — caught here by the count, which is what that list is for; both it and `RevisionMaterialChanged` are abnormal-true. **No count is restated here (A34).** The number written in this sentence was 29 while the list above held 30, and a prose count that drifts from the list is worse than none: it reads as a check and is a second place to be wrong. §3.1's list is the count, and §11's closure test is what should enforce it — which, as the amendment on `schema_contract_test.go` records, it does not yet do.

Four conditions enter the list in this round: `RevisionRecordUnreadable` (design 03 A28 — a revision's persisted record fails its integrity check, so it is not recompiled and what is serving keeps serving), `PolicyInputDrifted` (A29 — a non-spec producer's tightening is withheld, naming the producer and the input), `CapabilityUnavailable` (A33 — this Agent requested a binding from a producer that is not installed) and `LLMFallbackUnavailable` (A34 — the pre-provisioned fallback Backend is not converged, so an activation did not happen). All four are abnormal-true.

**Measured** (k3d, ConfigMap finalizers):

| Check | Result |
|---|---|
| 20 concurrent **naive** appends | **1 of 20 survived** — the obvious implementation silently drops holds |
| 20 concurrent `resourceVersion` CAS adds with retry | **20 of 20** |
| 19 concurrent releases while one holder remains | the remaining holder survived; each writer removed only its own entry |
| `delete` while one holder remains | blocked — `deletionTimestamp` set, object retained |

So the refcount is sound *with* CAS and unsound without, which makes the retry loop a contract rather than an implementation detail. The lossy variant is the one an implementer reaches for first, so it is named here and belongs in the mutation battery.

**Still unmeasured**: orphan reclamation after an operator crash, and the divergence→weight-0 transition. Codex's condition stands, but its remedy does not: showing the lease race-free is necessary and **not sufficient**, because unplanned guard loss defeats the seal whether or not the refcount is correct (A34).

A42 correctly says no run-namespace object may carry a cross-namespace `ownerReference`, and A35's ownership row, A41's missing-copy check, A39's `AlreadyExists` invariant and A38's rollback test all read "owner UID". An implementer running them as written gets `RevisionMaterialUnavailable` on every revision and nothing ever serves; one who drops the unsatisfiable clause is left verifying kind + immutable + bytes, which is adoption-by-name — the exact hole A39 exists to close. Provenance moves to operator-stamped `plume.dev/agent-uid` and `plume.dev/revision-digest` labels covered by the record digest, and all four rules are rewritten against them. The same amendment adds what the move silently dropped: the run namespace is **created, never adopted** (a principal with cluster-scoped namespace `create` could otherwise pre-create it with a self-granting RoleBinding and wait for Secret copies), Pod Security labels are mirrored from the source namespace, ResourceQuota is named as an unsolved gap rather than omitted, the name is truncate-and-hashed because `plume-run-` plus a 63-character namespace is not a DNS label, the sweep is label-based and runs every reconcile so a crash between Create and publish leaves sweepable objects rather than orphaned credential material, and §3.7 gains the teardown step A42 claimed it already had.
- **A43 (2026-08-31) — the content-hashing design is unimplemented, said in the body rather than only in a code comment.** Codex r7 BLOCKER 4. `internal/revision` hashes referents and the operator creates workloads in the Agent's namespace, so A20, A35 and A42 are design-only while §3.3 reads as though they hold — and this is the identity the shipped operator uses, not future scaffolding. The bypass is live: change a referenced ConfigMap, replace a Pod, and the new content serves under the old revision's gate result. The code comment that still asserted the *withdrawn* "rotating a Secret must not re-gate" rule is corrected in the same change; a comment stating a superseded rule in the file that implements the identity is worse than no comment. The three amendments are **one** implementation — content resolution, immutable copies, and the run namespace — and partial delivery of any of them closes nothing.
- **A42 (2026-08-31, decided by the user) — revision workloads and their material move to an operator-owned namespace.** Codex r7 BLOCKER 5. A35 called a same-kind, same-namespace, name-resolved object an invariant while repeating the exact distinction that refuted A20: `immutable: true` forbids an update and permits delete-and-recreate, and `ownerReference` does not protect deletion. A namespace editor with ordinary `create`/`delete` on ConfigMaps could therefore replace `agent-H-env-0` and have a node drain serve the new bytes under H's gate result, with no Agent write. Kubernetes has no UID or resourceVersion field on a Pod env reference, so a naming scheme cannot supply the missing property.

  Two options were put to the user with their costs; the choice is the **operator-owned run namespace**, because a ConfigMap can only be used by Pods in its own namespace — so the material is out of the editor's reach only if the Pod is too. The rejected alternative inlined ConfigMap content into the PodSpec, which closes prompts and config without moving anything but leaves behaviour carried in a **Secret** exposed, and A23 had already noted that `envFrom.secretRef` carries a system prompt exactly as well as an API key.

  **Verified before writing, because this design has been wrong about a Kubernetes premise before** (A20's immutability argument): cross-namespace owner references are *disallowed* and the reference is **treated as absent**, with an `OwnerRefInvalidNamespace` Event — so GC must be finalizer-driven and setting the reference anyway would leak every workload silently. Sources: the OwnerReference API definition and the garbage-collection concept page.

  **This amendment owes work in three other designs** — 06 (SPIRE entries key on namespace and ServiceAccount; both move, and an SVID naming the wrong namespace is an authorization change), 26 (which side of the vCluster split owns the run namespace), and wherever a NetworkPolicy selects agent Pods by namespace. They are named rather than assumed, because propagation is the failure this review set has found in every round. User read access is also owed and is not hand-waved: deriving which subjects may read an Agent requires watching RoleBindings the operator does not watch today, so `plume logs` is the supported path until it is designed.
- **A41 (2026-08-31) — a copy is non-optional, and a missing one is weight 0.** Codex r7 BLOCKER 5, the half that holds whichever mechanism is chosen. A copy inheriting `optional: true` would let a *deletion* silently change the process environment — the variable simply absent on the next Pod — so copies are always rewritten non-optional, which turns the same act into a visible failure to start. A missing or UID/digest-mismatched copy sends the revision's route to weight 0 with `RevisionMaterialUnavailable`.
- **A40 (2026-08-31) — the retained set is defined once, and everything is sized from it.** Codex r7 BLOCKER 6. Three documents counted it differently: §3.3 says `revisionHistoryLimit: 2` means two retained *in addition to* active and candidate, while design 03 A28 capped records at three "active, candidate, rollback target" and A35 bounded copies at three live revisions. At the default the legal set is **four**, every member required by the documented rollback contract — so an implementer would have had to reject a lawful candidate, delete a promised rollback target, or retain material it could not record. The set is now written once as a union, `revisionHistoryLimit + 2 + holds`, and a design 20 hold **extends** it rather than occupying a history slot: a hold that displaced a history entry would shorten the rollback window during the incident the hold exists for.
- **A39 (2026-08-31) — one read, one buffer, one publish.** Codex r7 MAJOR 1. A35's copy rules are implementable only if a single GET produces the buffer used for **both** the hash and the Create; the natural two-read implementation races an editor between reads, so the first GET computes H over safe bytes and the copy is created from malicious ones — faithfully immutable and faithfully wrong. The acquisition order is now fixed and `AlreadyExists` is explicitly **not** an adoption: a copy this operator did not just create must satisfy kind, owner UID, immutability and bytes, or it is `RevisionMaterialCollision` and nothing publishes. Separately, `RevisionRecord` gains `schemaVersion` (design 03 A39) and this design's vocabulary gains `RevisionRecordUnsupported`.
- **A38 (2026-08-31) — rollback tests the COPY, not the original's drift.** Codex r7 MAJOR 4. The failure table still refused a rollback when the user's env content had changed since the revision was gated — pre-A35 semantics sitting in the authoritative body beside A35 itself. Under A35 that refusal declines a recovery that is perfectly available, extending an incident for no safety gain, because the revision does not read the original. The reproducibility test is now the retained copy's existence, owner UID and digest. The docs gate gains `referent-drift-refusal` so the old rule cannot return unnoticed; mutation-checked both ways.
- **A37 (2026-08-31) — the revision name is 40 bits and was being used as a security identity.** Codex r7 BLOCKER 1, reproduced here in **1.2 seconds**: two specs differing in their image both hashing to one ten-character revision. The old rationale counted coexisting revisions, which is an accidental-collision argument about an **attacker-controlled** input. The full digest is now the identity and is persisted in status; the short form is a name. A workload whose recorded digest disagrees with the desired one is a terminal `RevisionHashCollision` rather than a revision to converge — converging it is the bypass. Two further omissions in the same projection, both reproduced and both fixed here: **`llm.egressAllowlist` was classified behaviour and projected nowhere** (r7 BLOCKER 2), so widening a HIPAA agent's egress hashed identically and reached the compiler ungated; and **every named env arm dropped leaves** (r7 BLOCKER 3) — `Optional` on all four selectors, `FieldRef.APIVersion`, `ResourceFieldRef.Divisor` — so flipping `optional: false → true` on a referenced prompt minted no revision, and a replacement Pod would start *without* the prompt instead of failing. Named arms are replaced by a canonical marshal of the complete upstream selector, which covers leaves a dependency bump adds on the day they appear rather than the day someone remembers them. Twenty leaf-level differential tests, generated from the upstream type rather than a hand list.
- **A36 (2026-08-31) — the condition vocabulary is enforced by NAME, and thirteen conditions get constants.** The closure test asserted `len(designConditions()) == 21` and compared no names, so renaming `CondPricingStale` to `TotallyWrongName` survived it — a defect this design already recorded and which stayed open. The count was checked against the wrong number too: §3.1 declared 34 while the Go list declared 21, and **thirteen conditions had no constant at all** — nine of them raised by designs 03 and 20 and drifting in unnoticed, four added by A28–A34. A condition the code cannot name is one no controller can set, so NFR-8's promise that a degraded path is never silent did not hold for any of them. The test now parses §3.1's list from this document and compares both directions: a constant with no design entry fails, and a design entry with no constant fails. Parsing a document from a unit test is deliberate — the design decides this list, so a second copy in Go is a second place to be wrong, which is precisely how 21 and 34 coexisted. A missing or unparseable design is a **failure**, never a skip. Six mutations checked, all killed, including the exact rename that survived before. `CondEnvSourceProtectionUnavailable` is declared even though A35 supersedes it, because the list must match §3.1 exactly; both are removed together in A35's owed sweep, not separately.
- **A35 (2026-08-31, decided by the user) — a revision reads its own immutable copy; A23's seal is superseded.** Closes Codex r6 BLOCKER 1. A34 established that the race needed a **pre-loss** invariant and that no reactive remedy could supply one. Two candidates were put to the user with their costs; the choice is **immutable revision-scoped copies created before publication**, with the revision's PodSpec referencing the copy. The editor never had a reference to what the revision reads, so guard loss plus an authorised edit plus a Pod replacement changes nothing that revision serves — an invariant rather than a control, and a control is exactly what removal defeats. The rejected alternative was a separately protected Pod admission control: a `ValidatingAdmissionPolicy` cannot read another object from CEL so it needs a webhook on the Pod-creation path with a `failurePolicy: Fail` blast radius, and it very likely misses an **in-place container restart**, which re-resolves `envFrom` without creating a Pod object and never reaches admission.

  This **reverses A23**, whose whole point was "no bytes are copied", and the costs A23 named are accepted with bounds rather than argued away: copies are `immutable: true`, kind-preserving (a `Secret` never becomes a `ConfigMap`), owner-referenced to the Agent, named from the revision hash so re-reconcile converges, deleted with their revision, and bounded at three revisions' worth. The operator gains `create` on `Secrets` in agent namespaces — a real escalation surface, stated in §3.3 rather than buried. A rollback re-runs the material its revision was gated with and can therefore resurrect a rotated credential; the mitigation is the typed credential binding A23 already records as owed, and until it exists the behaviour is documented rather than hidden.

  **OWED, and not done in this change:** the retirement sweep. The seal's finalizer, its `ValidatingAdmissionPolicy`, the lease refcount built by A26/A29/A32 and the `EnvSourceProtectionUnavailable` condition are superseded but still appear in this document's history, in §3.1's condition list and in the chart. They are marked, not yet removed — removing them touches the chart, the condition vocabulary and three amendments' worth of machinery, and doing it in the same pass as the reversal is how a hasty excision breaks something else. Until that sweep lands, **§3.3 is the operative mechanism and nothing else is.**
- **A34 (2026-08-29) — the snapshot fallback is deleted, and the guard-loss race is recorded as OPEN.** Codex r6 BLOCKER 1. A28 correctly proved that Binding removal plus an authorised source edit plus Pod replacement serves changed material before any watch reaction, and then named A23's snapshot fallback as the closure. It cannot be: the fallback is **reactive**, and at the moment of loss no snapshot exists, no PodSpec references one, and the original bytes are already gone — so anything triggered afterwards copies the attacker's content or fails for want of the old. A remedy that runs after the loss cannot restore a pre-loss invariant, and calling it the closure made a bypass look handled. Every sentence naming snapshots as the fallback is corrected. The two candidate pre-loss invariants — immutable revision-scoped material created before publication, or a separately protected Pod admission control — are tabled with their costs; **neither is chosen, and the design no longer claims the seal is fail-closed against unplanned guard loss.** The guard-loss condition table also gains the two limits on its own predicate: a match is point-in-time and races an edit plus a kubelet restart, and under a retired key it is not false but unknowable.
