01

The lightweight doctrine

Every design decision in this document passes six rules. They are the product: competitors ship platforms; graphene ships a control plane. The recipe is bind, don't build — the platform never implements what an open standard already provides, and its own code is confined to thin operators, a data-plane policy compiler, and a CLI.

RULE 1

Bind, don't build

CRDs + operators + a CLI. Zero proprietary protocols, zero bundled agent framework, zero bundled UI.

RULE 2

Two stateful deps, ever

Postgres + NATS. Durability, eval results, audit, KV, object store, queues — all in those two. No Kafka, no Redis, no Temporal cluster.

RULE 3

Library over server

If a capability can run as a library inside an existing pod (DBOS, DeepEval, OTel SDK), it never becomes a service.

RULE 4

The reconcile loop is the product

Versioning = CR generations + GitOps. Self-healing = conditions + controllers. graphene adds semantic health to machinery Kubernetes already has.

RULE 5

Weight budget is a spec

Core control plane ≤ 8 pods. One helm install on any conformant cluster — minikube, k3d, kind, k3s included. Local distros are a CI target, not a courtesy. Every added pod needs a written justification.

RULE 6

Tiered install

core (agents + KG + security + traces) → plus (evals, drift, modelhub). Each tier independently removable.

02

System overview

Three planes. The control plane is GitOps-driven: custom resources reconciled by three small core operators, plus the enterprise tenant-operator. The data plane is a single gateway every agent hop crosses — which is where security, budgets, and receipts are enforced, so guarantees hold for black-box agents regardless of SDK. The substrate is the two stateful dependencies.

In every diagram in this document, ultramarine marks what graphene builds; grey marks adopted open components. Notice how little is ultramarine — that is the thesis.

BYO-SDK, precisely: an agent is any container that serves A2A and exposes an Agent Card. LangGraph, CrewAI, Google ADK, Pydantic AI, the Claude Agent SDK, or a bash script — the platform doesn't know or care. Registration = the operator reads the card, publishes it to the OASF directory (JetStream KV — not another database), issues identity, wires gateway routes.

The App CR — whole products, not just plumbing

An App is not a bundle of agent infrastructure — it is a shippable product: a frontend, its API, and the agents, workflows, and graphs behind them, versioned and released as one unit. The anatomy exploits everything already built, which is why it stays thin:

  • The backend mostly disappears. Workflows and agents exposed over HTTP are the API: a workflow becomes POST /api/<name>, an agent's A2A task stream becomes the chat endpoint over SSE. A custom backend-for-frontend shrinks to nothing unless the product genuinely needs one.
  • Human auth with zero custom code. Users log in via the platform IdP (OIDC); the gateway exchanges the user's token into on-behalf-of agent credentials — so every agent action carries the human's identity in its receipt, and budgets can be per-user. Login, roles, audit chain: configuration, not code.
  • Released as a unit. The App pins member versions — agent v1.4.2, graph v12, frontend v2.1.0. Rolling the app forward is one change; the agents inside still pass their eval gates individually (§08). Rollback restores the whole coherent set.
  • Scaffolded. graphene init app generates a frontend template plus a typed client derived from the exposed workflow/agent schemas (Agent Cards, MCP tool schemas → TypeScript), with auth wired.
kind: App
metadata: {name: prior-auth-desk}
spec:
  frontend: {image: ghcr.io/acme/pa-desk-ui:2.1.0, route: pa.acme.dev}
  api:
    - workflowRef: prior-auth-check     # → POST /api/prior-auth-check
    - agentRef: pa-reviewer             # → SSE /api/chat (A2A task stream projected)
  members:                              # the release: pinned, coherent, roll-back-able
    agents:  [{name: pa-reviewer, version: "1.4.2"}]
    graphs:  [{name: payer-policies, version: "v12"}]
  auth: {oidc: platform-idp, roles: [reviewer, admin]}

kro composes the resources; graphene's own additions are only the HTTP projection of workflows/agents, typed-client generation, and release pinning — the App layer adds product capability without adding platform machinery.

04

The KnowledgeGraph contract — the differentiator

The claim that separates graphene from kagent, Rossoctl, and Dapr Agents: the domain is data, not code. Standing the platform up in a new vertical means dropping in a new KnowledgeGraph CR and reusing every other part of the platform.

Every serious graph engine already exposes MCP, so graphene doesn't pick a winner — it defines the socket. A provider is anything behind an MCP query surface; the contract adds what providers don't have: a versioned ontology, semantic readiness, and derivation of the correctness machinery.

Three properties nobody else has:

  • Versioned like a deployment. Agents pin knowledge[].version. Rolling a graph forward is a rollout; rolling back is repointing. The ontology diff is code review.
  • Semantic readiness. A graph isn't Ready because its pod is up — it's Ready because the known-answer probe set passes. Agents bound to a non-Ready graph receive no traffic. A readiness probe for meaning.
  • The ontology is the eval scaffold. Golden sets, probes, and drift baselines derive from one reviewed artifact — no second source of truth to drift from the first.

Exposure — everything that runs here is also a server

The symmetry rule: graphene consumes open standards and publishes over the same ones. Any Agent, Workflow, or KnowledgeGraph can be exposed beyond the cluster with a declarative expose block — no code, no separate API layer. The policy compiler turns the block into gateway listeners, so external consumers get the identical treatment internal traffic gets: OAuth clients minted in the IdP, per-consumer rate/token budgets, receipts on every call.

Strategically this is the distribution story: every graphene installation is a node that offers agents and tools to the wider ecosystem over the same protocols it consumes — interoperability in both directions, versus the walled platforms' one-way doors.

Service mesh — deliberately optional, by architecture

Core needs no mesh, and this is a consequence of the design, not an omission: all agent traffic already crosses one gateway, which provides the L7 policy, mTLS (via SPIRE), and observability a mesh would — a mesh would duplicate it for the traffic that matters. Two 2026 facts refine the position: Istio's ambient (sidecar-less) mode is GA and cheap (ztunnel, ~90% less memory than sidecars), and Istio announced experimental agentgateway support at KubeCon EU 2026 — the ecosystems are converging, not competing. So: an ambient profile adds ztunnel-only L4 mTLS for the residual non-agent traffic (Postgres, NATS connections) in enterprises that want encryption-everywhere attestation; waypoints stay off (agentgateway is the L7). Core stays meshless.

Note how much tenancy is inherited from components already chosen: NATS accounts, RLS, Zitadel orgs — the platform's own tenancy code is mostly the fan-out controller.

Compliance profiles — HIPAA as configuration, not a project

Most of HIPAA's technical safeguards are emergent from the architecture: unique user identification and per-action attribution (on-behalf-of receipts), complete audit of every query/output/PHI access (the receipt stream — 2026 guidance: tamper-evident, 6-year retention), access controls (ReBAC at the gateway), encryption in transit (SPIRE mTLS / ambient profile). A compliance: hipaa profile — shipped as a pack — configures the rest:

  • Receipt hardening: hash-chained (tamper-evident) receipt stream, 6-year retention policy to object storage, scheduled access-review reports.
  • Model egress allowlist: the gateway restricts PHI-touching agents to LLM endpoints under your BAA (Bedrock / Azure OpenAI / self-hosted via §10) with Zero-Data-Retention flags asserted — enforced at the chokepoint, not by trusting agent code.
  • PHI minimization: redaction filters at the gateway and at the ingestion normalize stage (§13) — already designed; the profile turns them mandatory.
  • Session controls: automatic logoff, break-glass emergency access role with its own audit trail, encryption-at-rest storage classes for Postgres/NATS/graph stores.

Same pattern extends to SOC 2 and GDPR profiles. The pitch line is real: because every hop crosses one audited gateway, compliance is a profile you enable, not an integration you build.

07

Harness & observability

The harness is a proven pattern promoted to platform level and made SDK-agnostic — because it lives in the data plane, not in the agent:

  • Sessions & receipts. Every A2A task through the gateway is recorded to a JetStream stream: full request/response, tool calls, model calls, cost, identity chain. Every agent action is replayable. One stream is simultaneously the audit log, the debugging substrate, and the eval-data collector (§08).
  • Traces. OpenTelemetry GenAI semantic conventions — adopted now, pinned to a commit SHA — the conventions moved to an unreleased repo, so there is no version number to pin — since they remain pre-stable in mid-2026 (shape settled, names may churn). The gateway emits spans for every agent/tool/LLM hop, so even uninstrumented agents get traces; instrumented agents (OpenLLMetry SDKs) add interior reasoning spans.
  • Backend. OpenObserve — metrics, logs, and traces in a single binary on object storage. The Prometheus + Grafana + Tempo + Loki equivalent is 6+ pods; this is one. Arize Phoenix is an optional plus pod for LLM-native trace views and embedding-drift visuals.
  • Golden signals for agents, exported as real metrics with alert rules shipped in the Helm chart: task success rate, tool-error rate, tokens/task, cost/task, latency per hop, loop depth, handoff count.
08

Evals — semantic admission

Kubernetes gates rollouts on health checks; graphene gates them on semantic checks. Agents and models earn traffic. This is the headline feature — nobody in the kagent / Rossoctl / Dapr set does eval-as-admission.

kind: EvalSuite
spec:
  runner: deepeval            # or inspect-ai; runs as a Job — 0 standing pods
  dataset:
    goldenSetRef: pa-golden-v3          # derived from KG ontology + curated cases
    fromSessions: {sample: 200, since: 7d}   # replay real recorded sessions
  metrics: [task_completion, tool_correctness, faithfulness_to_kg, cost_regression]
  gate: {minScore: 0.85, blocking: true}

As designed (ADR-0024): the gate runs once, pre-canary — canary progression is SLO-judged, not re-evaluated. Datasets and reports are content-addressed artifacts binding (dataset, judge, revision) digests, which makes rerun-shopping structurally impossible. Everything fails closed: empty dataset, judge down, or budget exhausted means no pass. EvalRunner is a shipped provider slot; models reuse the flow with their own metric family (never per-task — models have no tasks).

Nightly full-suite runs are CronJobs; results land as CR status and metrics, so "eval score over time" is just another OpenObserve panel. Models pass through the same gate (§10) — one promotion mechanic for the whole platform.

ModelHub plus tier

The Model CR is a thin envelope over four adopted components — train → package → eval-gate → serve — and models pass through the same EvalSuite admission gate as agents: one promotion mechanic for the whole platform.

StageBindingNotes
Versioning / packagingKitOps ModelKits (CNCF ModelPack)Models, datasets, prompts, configs as OCI artifacts in the registry you already run; kit:// URIs; cosign-signed like everything else
Serving (classic / predictive)KServe InferenceService fronting Triton/vLLM; Kueue for GPU queueing
Serving (generative)KServe LLMInferenceService — built on llm-d (CNCF Sandbox): KV-cache-aware routing, disaggregated prefill/decode, tiered KV offload, scale-to-zero
TrainingKubeflow Trainer v2 TrainJobSFT / DPO / GRPO built in; Unsloth is landing as a BuiltinTrainer — ride it, don't wrap it
ExperimentsMLflowTracking only; runs launched from the CLI

As designed (ADR-0026 + design 25 A1): KServe split its API at v0.17, and the generative path — LLMInferenceService — is built on llm-d. The honest statement is therefore that assayd binds llm-d transitively through KServe for generative serving (the classic InferenceService path does not involve it), not "only for one giant model" as v0.1 had it. Generative pools bind at the gateway as a GAIE InferencePool (verified OSS in agentgateway), so KV-cache-aware routing and prefill/decode disaggregation arrive by binding a contract rather than building anything — while budgets, receipts, authz and egress allowlists stay exactly where they always are. Because llm-d is Sandbox-stage and moving fast, assayd pins the two contracts and never llm-d internals.

KServe runs in RawDeployment mode — a stated constraint, not a default. It is what lets KServe run without Knative or Istio, which is the only reason binding it respects the pod budget (rule 5) and the meshless core (ADR-0012); Serverless mode is forbidden and CI asserts no Knative CRDs are required. Kits are the only serving source (signed, digest-pinned), resolved by a chart-shipped ClusterStorageContainer. The shadow InferenceService gets a candidate-only route admitting just the eval run principal; general registration happens only on pass. The operator writes internal/<model> pricing rows so agent policy compilation can never fail on an unpriced in-cluster model. Models gate through design 16's flow with their own metric family (§08).

Developer experience — the golden path

The platform contract is deliberately tiny — a container that serves A2A plus an Agent Card — which is why creating an agent can be this easy: your SDK, your code; the CLI generates the thin wrapper and drives all the machinery. Target: empty directory to an agent answering from a knowledge graph on a local cluster in under 15 minutes.

Three ways in, ordered by effort:

  • Scaffolded. graphene init runs an interview — what the agent does, which graph, which tools (listed from the directory), which SDK (recommended with reasoning, never silently chosen) — and generates a complete working agent (~100 lines) that the user owns. No bundled runtime; doctrine holds.
  • BYO. An existing LangGraph / CrewAI / ADK / Pydantic AI / Claude-SDK agent gets an A2A wrapper, card, Dockerfile, and agent.yaml from a per-SDK template — typically a few dozen generated lines.
  • External. An agent already running elsewhere: graphene agent register --endpoint — the operator reads its card and wires identity, routes, and directory entry.
$ graphene init

? Knowledge graph:             payer-policies (v12)   — 3 others available

✓ scaffolded pa-reviewer/ — agent.py (74 lines), agent.yaml, Dockerfile, card.json

Workflows — two authoring levels, one runtime

  • Declarative for compositions: a Workflow CR lists triggers (JetStream event, cron, A2A task) and steps (call agent A, then agent B, human-approval step, notify). The operator compiles it to a DBOS program — no code written.
  • Code-first for real logic: graphene init workflow --code scaffolds a DBOS project — plain decorated functions with crash-resume and retries, no orchestrator to learn. Local run with fake event injection: graphene workflow test --event fixtures/claim.json.
  • Apps: graphene init app scaffolds a frontend with a typed TS client generated from the exposed workflow/agent schemas, IdP login wired — the product layer with no hand-written backend (§03).

The wizard's rule everywhere: the platform asks, you choose — every generated choice shows its reasoning and is editable; a blank field the user can't understand is treated as a product failure.

Graph engineering

The KnowledgeGraph contract (§04) says what a graph promises; this section is how one is built and kept true. Graph engineering is a pipeline discipline with the same rigor as the agent pipeline — extraction is itself eval-gated, every edge carries provenance, and no snapshot goes Ready without passing its probes.

The ontology document

One reviewed YAML artifact per domain — entities, relations, invariants, and probes. Everything downstream derives from it (Fig 2):

ontology: payer-policies
version: v12
entities:
  - name: Policy
    keys: [policy_id]
    attrs: {effective_from: date, state: enum[draft,active,retired]}
  - name: Procedure
    keys: [cpt_code]
relations:
  - Policy COVERS Procedure        # with conditions: prior_auth, age_range
  - Policy SUPERSEDES Policy
invariants:                        # checked on every write — violations block the snapshot
  - an active Policy has ≥1 COVERS edge
  - SUPERSEDES has no cycles
probes:                            # known-answer set — semantic readiness (§04, §09)
  - q: "Does policy P-1042 cover CPT 97110 without prior auth?"
    expect: {answer: no, cites: [P-1042 §4.2]}

Creating a graph — three starting points, zero infrastructure

The promise: you bring documents and review an ontology; Kubernetes runs everything else. The user never provisions a graph database, an embedder, or a pipeline worker — kg init makes the operator materialize the provider, the Connector ingestion facet, and the pipeline workflow from the chart, and kubectl get knowledgegraphs shows build progress as conditions: Ingesting → Validating → ProbesPassing → Ready.

  • From a knowledge pattern — graphene kg init --pattern sop-decision-tree --from connector/sharepoint-sops. The pattern pack supplies the ontology template, extractors, probe generators, and bundle recipes; the wizard customizes names and thresholds.
  • From scratch, with a proposed ontology — point at 20–50 sample documents; the platform proposes an ontology (entities, relations, invariants, inferred with stated reasoning), the human edits and locks v1, the pipeline runs. An ontology is never silently generated — proposal → review → lock, always.
  • Bring your own graph — an existing Neo4j/Graphiti/anything wraps in a provider adapter and gains probes and versioning; the platform manages only the query surface and lifecycle.

Knowledge patterns — different documents, different graph shapes

A pile of SOPs and a product catalog should not produce the same kind of graph. Knowledge patterns are packs (§15, socket 4 + 1): each bundles an ontology template, extraction prompts/parsers, auto-derived probes, and the context-bundle recipes agents use. This entire capability is fast-plane content — the engine does not grow, which is the pattern charter's first load-bearing test.

The provider adapter interface

Every provider (Graphiti, cognee, Neo4j, BYO) must expose six MCP tools — this is the whole pluggability contract: search · neighbors (typed traversal) · get_context_bundle (a pre-composed retrieval recipe, so agents don't hand-roll traversals) · cite (provenance for any fact) · schema (the ontology, machine-readable) · probe (execute the readiness set). Anything beyond the six is provider-specific bonus, invisible to portable agents.

Operations

  • Versioning mechanics: a snapshot per ontology or corpus change (namespace-per-version on the provider); graphene kg diff v11 v12 renders entity/edge/probe deltas for PR review.
  • Re-embedding on embedding-model change is a version bump, never an in-place mutation — agents on the old pin are untouched.
  • PII is redacted at the normalize stage, before anything persists; provenance keeps a pointer to the source system rather than a copy of sensitive payloads.
  • Scoping: per-agent subgraph access is enforced at the gateway (tool-call filters on the KG's MCP surface), not trusted to the provider.

Loop engineering

Two loops get engineered, deliberately separated. The inner loop — how an agent thinks — is scaffolded, user-owned code (doctrine: no bundled framework). The governance ring — what an agent may never exceed — is platform-enforced at the data plane, so it holds even for black-box agents. The outer improvement loops are §08 (evals) and §09 (drift).

The reference inner loop (scaffolded, ~100 lines, yours)

assemble → act → observe → stop-check. Assemble builds the turn's context from the Agent Card, the KG context bundle, and skills — versioned, governed instruction assets loaded per task by a router, so context stays small and behavior is reviewable data rather than a frozen mega-prompt. (Prior A/B evidence from a production harness: skills-first routing beats static toolsets.) Every iteration emits a receipt; every termination carries a named reason: goal_met · budget · max_depth · timeout · interrupted.

Governance mechanics

  • Budgets (tokens, $, wall-clock) compile from the Agent CR to gateway policy; exceeding one terminates the task with reason budget — never a silent truncation.
  • Hop limit & cycle detection: the gateway stamps each A2A handoff with a task-lineage header; depth > N or a repeated agent-pair in the lineage kills the chain. Multi-agent runaway is a data-plane problem, solved once.
  • Approval interrupts: tools marked requiresApproval in the Agent CR pause the task as a durable Workflow step; a human resumes or rejects from the CLI. The agent just sees a slow tool.
  • Loop observability: loop-depth, retries-per-tool, and termination-reason are first-class metrics; "termination reason ≠ goal_met rising" is a shipped alert rule and a drift signal (§09).

Extension model — absorbing tomorrow's patterns

A new agent-engineering pattern arrives every few weeks; the platform must outlive all of them. Graph engineering and loop engineering are merely today's examples — tomorrow it will be something with no name yet. The systems that absorb this churn share a structure: Kubernetes did it with CRDs, CSI drivers, and admission hooks; Claude Code does it most visibly — skills, hooks, subagents, plugins, output styles arrive every few weeks because the engine is a tiny frozen loop and every "feature" is really data plus convention. graphene adopts that structure deliberately, as seven named design patterns and one governing split.

The governing split: two planes, hard boundary

The slow plane is the engine — three operators, the gateway binding, Postgres + NATS. It ships rarely and gets more boring over time. The fast plane is the technique plane — ontologies, skills, policies, eval suites, gateway filters, driver implementations, scaffold templates. Everything in it is a versioned data artifact, so a new technique ships as an artifact publish, never a platform release. The platform's velocity lives entirely in the fast plane; its stability lives entirely in the slow one.

The seven meta-patterns

The mechanics: four sockets, one triage rule

The seven patterns materialize as four concrete sockets in the Kubernetes machinery. Graph engineering (§13) and loop engineering (§14) are not special cases — they are the first occupants of sockets 1 and 4, the existence proof that the mechanism works.

The four sockets, precisely

  • 1 · Provider slots — the CSI/CNI move. An agent-facing capability gets a named, versioned driver contract with a conformance suite. Shipping first: KnowledgeGraphProvider (the 6-tool MCP surface, §13), IdentityProvider, AuthzProvider. Reserved next: MemoryProvider, EvalRunner, DriftDetector, SandboxProfile. When the next Graphiti or the next DeepEval appears, it's a new driver — the platform supports contract version N and N−1, and swapping drivers never touches agents.
  • 2 · Gateway filters — a cross-cutting traffic concern drops in at the one place every hop already crosses: new guardrail techniques, semantic caching, context compaction, PII scrubbing. Zero agent changes, zero SDK coupling; black-box agents get the new pattern the moment the filter lands.
  • 3 · New CRD + controller — a pattern with its own lifecycle gets its own resource and a separate operator binary. This is already how Model, Workflow, and EvalSuite exist; the core Agent/KG machinery never grows to accommodate them.
  • 4 · Templates + skills — an engineering practice (loop recipes, context engineering, prompt patterns) ships as versioned scaffold templates and skills through the CLI. Practice can update weekly without a platform release — the knowledge is data, not code.

The governing claim: graphene's core is small enough to freeze because everything opinionated lives in a socket. The day a "graph engineering"-sized pattern emerges, the response is a driver contract, a filter, a CRD, or a template — shipped in weeks, breaking nothing, and every existing installation adopts it with a pack install.

Packs — how a new technique actually ships

The pack is the delivery vehicle for the fast plane — the equivalent of a Claude Code plugin: one signed OCI artifact bundling any mix of driver implementations, gateway filters, skills, scaffold templates, eval metrics, and CRs, with a manifest declaring which socket contracts (and versions) it targets. Installation is discovery-by-convention: push to the registry, graphene pack install, the operators pick it up.

# pack.yaml — a hypothetical technique that doesn't exist yet
name: context-compaction
version: 0.3.0
requires: {sockets: [gateway-filter/v1, template/v1]}
provides:
  filters:   [compact-context.wasm]       # socket 2 — every agent covered on install
  skills:    [when-to-summarize.md]        # socket 4 — loaded by loop routers
  templates: [loop-with-compaction/]       # socket 4 — graphene init picks it up
  metrics:   [context_efficiency]          # EvalSuites can gate on it immediately

$ graphene pack install context-compaction
✓ signature verified · contracts compatible (gateway-filter/v1)
✓ filter live on 12 agents · 1 new template · 1 skill indexed
  no platform release · no agent redeploys · rollback: pack uninstall

The enforcement mechanism is procedural, not aspirational: every feature proposal must name the pattern and socket it lands in. A proposal that needs an engine change is presumed wrong until an RFC proves the five primitives genuinely cannot express it — the rarity of such RFCs is the ongoing test that the core was drawn correctly.

Open source and enterprise — the split

License: Apache 2.0 for the core. It keeps the CNCF path open, avoids the AGPL-fear tax at adoption time, and sidesteps the community damage of the 2024–26 relicensing wave (HashiCorp BSL, Redis). The realistic protection against cloud strip-mining at this stage is velocity plus the enterprise layer, not a restrictive license. Enterprise features ship as separate proprietary modules — open-core split by component, never by crippling the core.

The split line is the classic one that works: a single team gets everything, free; organizational scale is paid.

Runs anywhere — local distros are a CI target

The same chart must install unmodified on minikube, k3d, kind, and k3s as on any managed cluster — CI runs the full e2e suite against k3d and kind on every merge, so "works on a laptop" is enforced, not aspirational. Three design consequences:

  • No cloud assumptions in core. No LoadBalancer requirement (Gateway API via the distro's default class or NodePort), no cloud storage classes (Postgres and NATS run on local-path), no managed-identity dependencies — SPIRE and the platform IdP are the identity story everywhere.
  • Sandbox degrades gracefully. gVisor/Kata aren't available on most local distros; the agent-sandbox profile falls back to a hardened runtime class + seccomp with a visible condition (SandboxDowngraded), never a silent skip.
  • Single-node honest mode. On one node the chart collapses replicas and skips anti-affinity — the profile is named (--profile local) so the gap between demo and production posture is explicit.

How these were produced

Each design ran draft → independent adversarial critique → revision → re-critique → approval; nothing reached approved status on a single pass. Roughly 150 findings were raised and fixed. Three were blockers that would otherwise have shipped as real defects: non-atomic policy apply (fail-open windows where a route could serve before its auth policy was accepted — the origin of ADR-0020's fail-closed ordering), a circular revision hash (a content hash depending on a value only knowable after the workload it identifies had already run) and non-deterministic receipt IDs (which silently defeated the deduplication that audit integrity rests on). Where one design amended an already-approved one, the delta is recorded as a numbered amendment in the amended design — design 02 carries eight.
