# ADR-0032: A tool allowlist is required, not optional — the mistake is rejected at apply time

- **Status**: accepted · 2026-09-10 · decided by the human on `research/secure-by-default-omitted-allowlist-2026-09.md`
- **Context**: Design 11 §11 and design 03 stated **opposite outcomes** for the same input, each recording that the other owed it the reverse statement. Omitting `spec.tool.toolAllowlist` either gives an agent **every tool the server offers** (design 11: "omitting it means no tool filter is emitted at all") or **no route at all** (design 03 `03:102`: "undeclared is a compile error, not a wider filter" — §3.4 makes `-toolfilter` mandatory and §3.3.1 turns a mandatory concern with an absent input into `PolicyCompileFailed` with the route withheld). Those are opposite failure modes — a silent over-grant against a loud outage — and design 11 §11 records that neither document may settle it unilaterally. Research found no standard anywhere endorsing "omitted allowlist ⇒ grant everything" (NIST SC-7(5), OWASP A01:2025, ASVS, CISA), so design 03 is right on that axis; but it also found that the convention is that a security allowlist **is not an optional field at all**. Measured, both halves are true of different layers: with no `AgentgatewayPolicy` attached, agentgateway lists and serves every tool the MCP server offers (design 07 A6.8), which is design 11's claim about the *gateway*; design 03's claim is about assayd's *compiler*, which would refuse to emit.
- **Decision**: **`toolAllowlist` is a required field with `minItems: 1`** on the Connector CRD's tool facet. Admission rejects an omitted or empty list at `kubectl apply`, so neither of the two outcomes above is reachable: there is no such thing as a tool binding without a declared allowlist. `+kubebuilder:validation:Required` alone does **not** achieve this — controller-tools accepts an empty slice, which would reintroduce an undefined third state — so `MinItems=1` is part of the decision and not an implementation detail. Design 03's `PolicyCompileFailed` behaviour is **kept** as the backstop for a CR that predates the constraint or arrives through a path admission did not cover; it stops being the ordinary case.
- **Consequences**: The error moves from a reconcile-time outage on a *different* object — an Agent that fails to serve because a Connector it references lacks a field — to a synchronous rejection in the author's own terminal, naming the field. Design 11 §11's sentence is **withdrawn**; design 03's `03:102` rule stands and its "owed to design 11" is discharged by this ADR rather than by an edit to either body. A tool server with genuinely many tools must enumerate them, which is the intended cost: an allowlist that can be omitted is not an allowlist. **The bound design 03 A51 owes design 11 — a `maxItems` on the same field — is not decided here** and is still owed; this ADR sets the floor, not the ceiling. Neither the Connector CRD nor the compiler exists in code today, so **this costs nothing to adopt now and would be a breaking API change after publish**, which is the reason to record it at v1alpha1 rather than when the CRD is written. Nothing is enforced until that CRD exists; until then this is a decision, not a control, and `test/envtest` owes the assertion that an empty list is actually rejected once it does.
