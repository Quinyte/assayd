- **Compliance (27)**: hash-chaining moves **downstream of the stream** — a single-writer chainer consumer chains over JetStream sequence numbers (parallel tap replicas cannot share a chain; 04 A3), which is also a stronger auditor statement. The `profile` facet **never mutates chart values**: declare → preflight emits a GitOps values delta → human applies → posture doc verifies (07 keeps sole ownership). Safeguard map de-overclaimed (ambient profile now mandated; "PHI minimization" not de-identification; audit proves access not post-redaction content; StorageClass mandated, CSI encryption is customer attestation) with the limits moved into the shipped §6. Compliance filters occupy the `compliance` priority band. **ADR-0015 held checkably**: OSS users can enable chaining and run `assayd compliance verify` without a license.

## Amendment 1 (2026-09-04) — three consequences of design 26 A1, from ADR-0029's run namespace

Design 02 A42 put every Agent's workload in an operator-owned namespace (ADR-0029), and design 26 A1 worked out what that means across the vCluster split. Three of its consequences touch what this ADR states; the other decisions stand, which is why this is an amendment and not a supersession.

1. **The compiler holds one tenant-side write.** "Tenant CR read only" stands for CRs. Hard-mode teardown must order host-side route revocation before the tenant-side workload deletion, and Kubernetes orders finalizers not at all; so the compiler writes a marker ConfigMap `assayd-routes-revoked-<agent-uid>` in the tenant agent-operator's namespace inside the vCluster — `create` on ConfigMaps in that one namespace, by a namespaced Role, and nothing else. Not a status write: design 02 A37 makes `status.activeRevisionDigest` the collision guard's authority *because* only the agent-operator writes it. The producer side (the deletion lifecycle) is owed in design 03 A45; hard mode is not implementable until it exists.
2. **Compute quotas are per-namespace ceilings** (decided by the user 2026-09-04). ADR-0029's mirroring gives the tenant namespace and its run namespace each the full `ResourceQuota`, so a tenant with `gpu: 1` can hold one in each. The Tenant API says so: `QuotasEnforced`'s message names both namespaces, and `tokensPerDay`/`usdPerDay` — enforced against the Agent's identity, not a namespace — remain single ceilings. An aggregate quota controller is a later mechanism, not foreclosed.
3. **Hard mode's gate is bypassable by the tenant's own admin**, who is cluster-admin inside the vCluster and can replace a gated revision's material there. Not cross-tenant, but a bypass of ADR-0006's gate for that tenant, surfaced as `GatesTenantAdminBypassable=True` on every hard-mode Tenant; design 27 A1 reports gate integrity on such a tenant as an attested exception, never as passing.

Also recorded from the same amendment: the per-tenant SPIRE inside a vCluster (this ADR's second new mechanism) is **unmeasured and in doubt** — spire-controller-manager selects on the virtual Pod UID while the host agent attests the host one (design 06 A3); nothing may be built on it until the spike design 26 A1 owes has run.
