# Gateway authz extension facts for designs 22/24 (2026-08)

- **agentgateway OSS in-proxy CEL**: policies carry CEL expressions compiled at config load, evaluated per-request with request attributes + JWT claims + ext-authz dynamic_metadata in context — stateless checks (lineage depth/cycle, design 22) run with no external call. https://deepwiki.com/agentgateway/agentgateway/4-policy-system
- **External authorization**: agentgateway is **API-compatible with Envoy's ext-authz gRPC** — sends CheckRequest (headers etc.), receives OK/Denied + optional dynamic_metadata (then visible to CEL as `extauthz`). OPA and Cerbos integrations demonstrated; the same seam carries the OpenFGA adapter (design 24). https://agentgateway.dev/docs/standalone/main/configuration/security/external-authz/ · https://www.cerbos.dev/blog/governing-ai-agents-at-the-gateway-with-agentgateway
- Enterprise-tier adjacents exist (CEL RBAC inside EnterpriseAgentgatewayPolicy; Solo OPA extauth docs) — OSS ext-authz + OSS CEL cover assayd's needs; no enterprise dependency (ADR-0020 D1 discipline). https://docs.solo.io/agentgateway/2.3.x/security/extauth/opa/about/
- OpenFGA: CNCF Zanzibar-style; batch-check API; store on Postgres (per ADR-0011 pod budget). Revocation latency = decision-cache TTL + token lifetime (design 24 states the number).
- **OpenFGA contextual tuples**: check requests may carry contextual (request-time) tuples — the mechanism for user↔role/group facts resolved from verified JWT claims per-check (design 24 r2 f1); no directory sync needed. https://openfga.dev/docs/interacting/contextual-tuples
